# Design

## Context

参见 [proposal.md](./proposal.md) 的变更动机和 [label-template-lifecycle 规范](./specs/label-template-lifecycle/spec.md) 的行为契约。

仓库已经存在一批尚未提交的标签能力在制代码：纯 Go 的 `internal/engine/label`、平台适配层 `internal/platform/label`、迁移 `000084`、前端 `@evolyn.do/label` 包、API 客户端和表单扩展页面。现有实现已体现完整草稿、乐观锁、真实记录预览门槛和不可变发布快照等方向，但测试覆盖和跨层一致性尚未形成交付证据。本设计以现有代码为起点进行审查、补齐与收敛，不重建第二套标签实现。

总体设计来源为 `docs/低代码平台/二维码标签/二维码打印引擎前后端功能开发设计.md`，本 change 仅落地其中模板生命周期相关子集。

## Goals / Non-Goals

**Goals:**

- 建立 `LabelSchema 1.0` 草稿的单一事实源和稳定的模板公开编码。
- 通过租户隔离、资源权限、记录权限和字段权限形成完整的发布前安全链路。
- 通过草稿乐观锁和发布行锁保证保存、预览与发布的并发一致性。
- 以不可变快照支持后续正式渲染对历史版本的稳定引用。
- 让后端 DTO、前端类型、错误码、迁移和审计保持同一契约。
- 对现有在制实现补齐单元测试、真库集成测试和跨端验证。

**Non-Goals:**

- 不实现 PNG/PDF、批量任务、对象存储、扫码 Token 或打印机语言输出。
- 不在本 change 扩展表达式运行时；包含未配置表达式的数据源必须明确拒绝发布。
- 不建设第二套表单、字段、数据权限或公式能力；标签域只通过窄端口消费既有能力。
- 不交付完整可视化设计器交互、撤销重做、图层或对齐系统；仅保证现有配置页能接入生命周期 API。
- 不提供发布版本回滚、历史版本列表或禁用/启用操作；这些能力另行立项。

## Decisions

### 1. 纯协议内核与平台适配层保持单向依赖

`internal/engine/label` 只承载 `LabelSchema 1.0`、协议校验和确定性渲染所需纯逻辑，不依赖 Gin、GORM、Redis、HTTP 或平台领域模型。模板持久化、权限、事务、审计和 HTTP 接口位于 `internal/platform/label`，依赖方向固定为平台适配层指向纯内核。

选择这一结构是为了让同一协议可以被服务端验证器、渲染器和跨端测试复用。备选方案是把协议校验直接写入 service，但会导致协议与 HTTP/数据库生命周期耦合，后续渲染和测试难以复用，因此不采用。

### 2. 模板持有可变草稿，发布版本采用追加写快照

模板记录保存元信息、当前完整 `draft_schema`、`draft_revision`、已预览修订号、已发布草稿修订号和当前发布版本指针。版本记录仅追加写，保存完整协议快照、模板内版本号、发布人和发布时间，不提供更新或删除接口。

每个有效表单仅允许一个有效模板，通过“租户 + 表单”的软删除条件唯一约束在数据库层兜底；模板公开编码同样按租户唯一。选择完整 JSONB 快照而非拆分元素表，是因为标签元素属于单文档设计协议，原子保存与版本冻结比单元素查询更重要。

备选方案是为每次编辑建立 draft version。该方案会把高频设计操作放大为大量版本记录，并增加发布选择歧义；当前阶段保留一个可变草稿，仅在发布时生成业务版本。

### 3. 草稿保存使用 Compare-And-Swap 乐观锁

客户端读取详情后必须在保存时回传 `draftRevision`。更新语句同时匹配模板主键和旧修订号，成功后原子递增修订号；匹配失败统一返回 `LABEL_REVISION_CONFLICT`。页面宽高、单位和 DPI 从通过校验的完整协议中投影更新，避免模板元信息与草稿页面设置分叉。

选择乐观锁是因为标签编辑以长时间客户端交互为主，不适合持有数据库锁。备选的最后写入胜出会静默覆盖他人设计，不能接受。

### 4. 真实数据预览是发布准入条件且绑定精确修订

真实数据预览读取当前草稿，通过表单域窄端口获取一条受数据权限裁剪的记录，并检查草稿引用的每个字段都出现在授权结果中。只有渲染成功后，才以“模板 ID + 当前修订号”条件写入 `previewed_draft_revision`；预览期间若草稿变化，条件更新失败并返回修订冲突。

发布要求 `previewed_draft_revision == draft_revision`。这样既能防止未验证的草稿发布，也能保证修改草稿后旧预览不会继续有效。Mock 预览只用于设计反馈，不能替代真实数据预览。

备选方案是仅在发布时校验 Schema。该方案无法提前发现记录权限、字段权限和真实值格式问题，因此不采用。

### 5. 发布在单事务内串行化并支持同修订幂等重试

发布事务按模板公开编码锁定当前租户的模板行，依次校验请求修订、真实预览标记、协议、已发布表单、字段引用和当前阶段不支持的数据源。不同草稿修订使用“当前最大版本号 + 1”生成新快照，再更新模板的发布指针和发布状态。

若当前草稿修订已经发布，直接返回现有版本号，不创建新快照。模板行锁将同模板并发发布串行化，版本唯一约束作为最终兜底。快照创建和发布指针更新必须处于同一事务，任一步失败整体回滚。

备选方案是仅依赖版本唯一约束后重试；这会把正常并发转化为数据库异常，并增加快照与指针部分成功的风险，因此采用显式行锁。

### 6. 租户隔离和权限在多层执行

- HTTP 路由进入现有认证、租户、租户状态和 RBAC 中间件链。
- service 校验当前成员属于 context 中的租户，并区分 `label-templates` 管理面和 `labels` 正式生成面资源。
- repository 继续使用既有租户 GORM callback 和 `ResolveDB`，调用方不能自行关闭租户条件。
- 表单、记录和字段访问均经表单域窄端口完成；标签域不直接读取表单 JSONB 或动态物理表。
- 跨租户或不可访问模板统一映射为模板不存在，避免存在性泄露。

管理能力随迁移补授给基线管理员角色，普通成员不自动获得模板设计权限。正式生成仍需独立 `labels:create` 权限，并再次执行记录与字段权限检查。

### 7. API、前端和稳定错误码使用同一生命周期模型

API 使用稳定模板编码而非数据库自增 ID，对外提供创建、游标列表、详情、草稿保存、真实数据预览、发布和删除。前端 API 类型镜像后端 DTO，配置页保存成功后立即采用服务端返回的新修订号；收到修订冲突时必须提示刷新，不得自动覆盖。

协议问题返回 `LABEL_SCHEMA_INVALID` 及安全、可定位的 issues；表单重复绑定、模板不存在、真实预览缺失和修订冲突使用独立稳定错误码，并同步登记前端错误码映射。文件流预览不使用统一 JSON data 信封，但失败响应仍遵循统一业务错误结构。

### 8. 成功生命周期变更接入既有审计域

创建、保存草稿、发布和删除在业务成功后记录模块、动作、模板编码、模板名称、应用和必要结果摘要。审计失败遵循既有 Recorder 的策略，不得伪造业务成功；被权限或校验拒绝的操作不写成功审计。

## Risks / Trade-offs

- **[在制代码与规划契约存在偏差]** → apply 阶段先做逐条场景审计，再决定保留、修改或补测，禁止因为代码已经存在就直接勾选任务。
- **[仅保存当前草稿，无法恢复未发布编辑历史]** → 发布版本仍永久可追溯；草稿历史与恢复能力作为独立 change 设计。
- **[真实数据预览门槛增加发布操作步骤]** → 前端明确显示当前修订的预览状态，并在保存新修订后立即使旧预览状态失效。
- **[表单字段在预览后、发布前发生变化]** → 发布事务重新读取已发布表单字段并校验，不能依赖预览时结果。
- **[删除模板后历史版本仍占用存储]** → 当前优先保证审计与追溯；物理清理需单独设计保留期和引用检查。
- **[只支持 SVG 真实预览限制当前交付]** → 生命周期 API 保留格式字段并明确拒绝不支持格式；PNG/PDF 在后续渲染 change 中扩展。
- **[迁移补授规则可能误判自定义管理员角色]** → 沿用仓库既有基线管理员识别口径，并通过迁移集成测试验证升级和回滚结果。

## Migration Plan

1. 先审查 `000084` 是否仍是当前迁移序号，并校验 up/down 对模板、版本、索引和权限规则完全对称。
2. 应用迁移，创建标签模板和版本存储、软删除条件唯一索引及管理员基线授权；开发态 AutoMigrate 仅维持与生产迁移一致，不替代迁移链。
3. 部署后端纯内核、平台适配层、表单窄端口和服务装配，再部署前端共享包、API 客户端与配置页接线。
4. 使用真库验证同表单唯一绑定、跨租户访问、草稿 CAS、并发发布和软删除后重新绑定。
5. 若尚未产生业务数据，可执行 down migration 回滚；一旦存在已发布快照，回滚前必须先确认没有渲染或审计引用，默认通过前向修复而非删除历史数据。

## Verification Strategy

- 纯内核单元测试：协议校验、元素引用、页面单位与 DPI 边界。
- service 单元测试：权限拒绝、修订冲突、真实预览门槛、同修订幂等发布和失效字段拒绝。
- PostgreSQL 集成测试：租户隔离、条件唯一索引、事务回滚、并发发布单快照及 down/up 迁移对称性。
- 前端单元测试：DTO/协议适配、保存后修订推进、冲突提示和发布按钮准入状态。
- 端到端检查：创建模板 → 保存草稿 → 真实记录预览 → 发布 V1 → 修改并重新预览 → 发布 V2 → 验证 V1 快照未变化 → 删除并重新绑定表单。
- 安全回归：跨租户编码探测、无资源权限操作、无记录权限预览、无字段权限预览均不泄露受限数据。
