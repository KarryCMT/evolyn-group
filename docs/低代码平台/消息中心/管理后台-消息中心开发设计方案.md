# 管理后台-消息中心开发设计方案

## 1. 背景、目标与边界

消息中心为租户成员提供站内消息收件箱，并为租户管理员提供通知策略、提醒对象和短信额度查询能力。前端现有抽屉已具备分类、未读筛选、单条/批量已读、通知方式开关和提醒对象管理交互，但目前全部使用内存样例数据。

一期目标：将站内消息、未读状态和租户级通知策略形成可靠的后端闭环；消息保留最近六个月。邮件、短信的真实供应商投递、计费扣减和重试可按本方案的模型在后续阶段接入。

### 1.1 非本域职责

- `audit_logs` 继续记录业务审计，不能代替消息中心。审计回答“谁做了什么”，消息中心回答“谁应被通知、是否已读、是否送达”。
- [消息推送](../消息推送/管理后台-消息推送开发设计方案.md) 是租户级外部 Webhook 配置，与成员个人收件箱、邮件和短信通道相互独立；后续两者可以共享可靠事件投递基础设施，但不能共用配置或权限。
- 现有租户套餐配额不包含云币。若云币是可消费余额，应进入独立账本，不应写入 `tenants.quotas`。

### 1.2 领域归属

新增 `apps/evolyn-core/internal/platform/notification/`，按 `controller → service → repository → model` 分层，并在 `internal/platform/server/server.go` 装配。该域属于租户路由，必须走 Authentication → Tenant → TenantStatus → Authorization 链；租户 ID 只从请求上下文取得。

## 2. 前端能力与后端语义

| 前端能力 | 后端语义 |
| --- | --- |
| 分类侧栏与未读红点 | 查询当前成员收件箱，并返回总未读数和按分类聚合的未读数。 |
| 消息列表与“只看未读” | 以当前成员为范围的游标分页查询；分类是展示分组，消息类型是策略和投递的最小单位。 |
| 打开消息 / 全部转为已读 | 写入个人收件箱项的 `read_at`；批量操作必须覆盖所有符合条件的记录，不能仅处理当前页。 |
| 通知设置 | 由租户管理员维护每种事件类型的站内信、邮件、短信开关与接收规则。 |
| 提醒对象管理 | 管理租户的外部联系人目录；联系人本身不等于某项策略的接收人，需经策略目标关联后才会收到外部通知。 |
| 云币余额和可发短信数 | 查询独立消费账本的汇总；一期若未接短信渠道，接口可返回能力未开通状态，不伪造余额。 |

前端“创建者”“系统管理员”等接收对象不能持久化为展示字符串。它们应分别表示 `event_creator`、`tenant_admin` 等规则，并在发送时解析为实际成员；历史收件箱项记录的是当时已展开的成员，避免成员关系变更改写历史。

## 3. 事件类型与分类

分类用于侧栏分组，事件类型用于策略、模板和投递。第一期固定枚举并由后端校验，前端只消费返回的目录与可配置能力。

| 分类 | 建议首批事件类型 |
| --- | --- |
| `app-log` 应用日志 | `application.created`、`data_push.failed`、`assistant.execution_failed`、`data_flow.execution_failed`、`output_table.sync_failed` |
| `usage-reminder` 用量提醒 | `usage.threshold_reached`、`usage.limit_reached` |
| `contacts-management` 通讯录管理 | `member.invitation_accepted`、`member.status_changed` |
| `open-platform` 开放平台 | `open_platform.callback_failed`、`open_platform.credential_expiring` |
| `system-management` 系统管理 | `system.configuration_changed`、`system.task_failed` |
| `operation-notice` 运营通知 | `operation.notice_published` |

`data-reminder` 与 `document-activity` 可先支持站内消息，标记为不可配置；待前端开放设置页后再启用邮件、短信和接收对象策略。

## 4. 数据模型

新增版本化迁移（编号在当前最新迁移之后递增）、对应 down 迁移，并同步 `scripts/db.sql` 快照。所有表、字段、约束、索引均按仓库约定写中文 SQL 注释。

### 4.1 通知事件与个人收件箱

| 表 | 关键字段 | 约束与说明 |
| --- | --- | --- |
| `notification_events` | `id`、`tenant_id`、`event_type_code`、`actor_member_id`、`title`、`content`、`payload JSONB`、`source_type`、`source_id`、`action_url`、`occurred_at`、`expire_at` | 一次业务事件的一份不可变快照。`tenant_id + event_type_code + dedupe_key` 建唯一约束，避免重试产生重复事件。 |
| `notification_inbox_items` | `id`、`tenant_id`、`event_id`、`recipient_member_id`、`read_at`、`created_at` | 每位成员一条收件箱项；唯一键 `(event_id, recipient_member_id)`。列表索引为 `(tenant_id, recipient_member_id, created_at DESC, id DESC)`，未读聚合建立 `read_at IS NULL` 部分索引。 |

`notification_events` 不做软删，过期后按保留策略物理清理；`notification_inbox_items` 同步清理。接口出网的时间统一使用 `internal/model.JSONTime`。

### 4.2 通知策略与接收对象

| 表 | 关键字段 | 约束与说明 |
| --- | --- | --- |
| `notification_policies` | `id`、`tenant_id`、`event_type_code`、`in_app_enabled`、`email_enabled`、`sms_enabled`、`revision` | 每租户、每事件类型一条有效记录；`revision > 0`，更新时乐观锁。系统消息默认开启且不可关闭。 |
| `notification_policy_targets` | `id`、`policy_id`、`target_type`、`target_id` | `target_type` 为 `event_creator`、`tenant_admin`、`member`、`external_recipient`；仅后两者需要 `target_id`。唯一约束防止重复接收者。 |
| `notification_external_recipients` | `id`、`tenant_id`、`name`、`mobile`、`email`、`status`、`created_by_member_id` | 姓名必填，手机或邮箱至少一个；手机号、邮箱分别建立租户内有效记录唯一约束。删除采用软删，仍被历史投递引用时保留脱敏快照。 |

### 4.3 为外部通道预留的可靠投递模型

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `notification_outbox` | `id`、`tenant_id`、`event_type_code`、`payload JSONB`、`dedupe_key`、`status`、`available_at`、`published_at` | 与业务写入同一事务落库，后台 worker 再展开策略与接收者。 |
| `notification_delivery_tasks` | `id`、`event_id`、`channel`、`target_snapshot`、`status`、`attempts`、`provider_message_id`、`last_error_code`、`sent_at` | 邮件、短信等异步投递任务；不保存敏感响应正文。 |
| `notification_credit_ledger` | `id`、`tenant_id`、`entry_type`、`amount`、`balance_after`、`source_type`、`source_id`、`created_at` | 云币充值、扣减、退款等不可变流水；余额由流水汇总或受事务保护的投影计算。 |

一期仅站内消息时可先实现前五张表；`outbox` 应与第一批产生消息的业务事件同时落地，避免后续补可靠性时遗漏历史写入路径。

## 5. API 契约

所有接口使用统一 `{ code, errCode, msg, data }` 响应包络；业务错误使用 `httpx.BizError`，Swagger 注释使用中文。

### 5.1 当前成员收件箱

| 方法与路径 | 权限 | 用途 |
| --- | --- | --- |
| `GET /api/v1/notifications/summary` | `notifications:get` | 返回总未读数、各分类未读数和保留期限。 |
| `GET /api/v1/notifications/inbox` | `notifications:list` | 参数：`category`、`unreadOnly`、`limit`、`cursor`；返回游标分页消息。 |
| `PATCH /api/v1/notifications/inbox/{id}/read` | `notifications:patch` | 标记当前成员的一条收件箱项为已读，重复调用幂等成功。 |
| `POST /api/v1/notifications/inbox/read` | `notifications:patch` | 批量已读；请求可带 `category`、`before`，空分类代表全部分类。 |

收件箱详情和已读接口都必须以 JWT 中的当前 `memberId` 过滤；禁止由前端提交目标成员 ID。

### 5.2 租户通知设置与提醒对象

| 方法与路径 | 权限 | 用途 |
| --- | --- | --- |
| `GET /api/v1/notification-policies` | `notification-policies:get` | 返回事件类型目录、通道开关、接收规则展示项与 `revision`。 |
| `PATCH /api/v1/notification-policies/{eventTypeCode}` | `notification-policies:patch` | 更新通道和接收目标，必须携带 `revision`；冲突返回 409。 |
| `GET /api/v1/notification-recipients` | `notification-recipients:list` | 游标分页读取外部联系人。 |
| `POST /api/v1/notification-recipients` | `notification-recipients:create` | 新增提醒对象。 |
| `DELETE /api/v1/notification-recipients/{id}` | `notification-recipients:delete` | 软删提醒对象。 |
| `GET /api/v1/notification-credits/summary` | `notification-credits:get` | 返回云币余额、短信单价和理论可发送数量；未启用时明确返回能力状态。 |

`notification-policies:*`、`notification-recipients:*` 与 `notification-credits:get` 仅授予租户管理员；`notifications:*` 授予已认证成员。前端设置入口应根据能力字段隐藏或禁用，不能让普通成员看到提交后才被拒绝的管理操作。

建议错误码：`NOTIFICATION_CURSOR_INVALID`、`NOTIFICATION_INBOX_NOT_FOUND`、`NOTIFICATION_POLICY_NOT_FOUND`、`NOTIFICATION_POLICY_CONFLICT`、`NOTIFICATION_RECIPIENT_INVALID`、`NOTIFICATION_RECIPIENT_DUPLICATE`、`NOTIFICATION_CHANNEL_UNAVAILABLE`、`NOTIFICATION_CREDIT_INSUFFICIENT`。

## 6. 事务、事件与投递

以“创建应用”为例，应用实例写入与 `notification_outbox` 写入必须同处一个 `TxManager.WithinTransaction` 事务：

```text
创建应用事务提交
  → notification_outbox
  → 通知 Worker 读取待处理事件
  → 加载租户策略并展开接收规则
  → 写 notification_events 与个人 notification_inbox_items
  → 按需创建邮件 / 短信 delivery task
```

不得从提交后的 `audit.Record` 反向生成通知；审计写入是 best-effort，既不具备事务原子性，也缺少通知模板和接收者语义。

Worker 处理应具备：`dedupe_key` 幂等、短暂失败指数退避、最终失败状态、可观测指标和受限批量处理。外部通道真正启用后，发送不应阻塞原业务 HTTP 请求。

## 7. 留存、安全与审计

- 默认保留六个月：创建事件时写入 `expire_at`；定时任务按批清理过期事件、收件箱项和投递任务。
- `payload` 只保存页面渲染、跳转所需的最小快照；不得写入密码、令牌、短信验证码、邮件正文或完整下游响应。
- 手机号、邮箱在列表响应中按权限脱敏；只有通知 Worker 在内存中取得真实联系方式。
- 策略、外部联系人、余额调整等写操作提交后以 best-effort 写入审计；审计记录动作、资源 ID 和脱敏摘要，不记录联系方式全文或消息敏感载荷。
- 修改策略必须先加载、核验当前租户和 `revision`，零行更新返回冲突，禁止跨租户更新零行仍返回成功。

## 8. 实施顺序与验收

1. 新建通知域、资源权限、迁移和默认事件类型/策略种子；补授已认证成员与租户管理员的基线权限。
2. 实现个人收件箱查询、未读汇总、单条已读和按分类批量已读；替换前端 `initialMessageRecords`。
3. 实现通知策略与外部联系人管理，替换前端 `initialMessagePreferences` 与本地联系人数组；补充“策略接收对象选择”交互。
4. 在应用创建等首批业务事务内写入 outbox，启动 Worker 生成站内消息。
5. 引入邮件/短信通道、投递任务、云币账本、失败重试和余额展示。

至少验证：成员不能访问其他成员的收件箱；租户之间消息、策略、联系人严格隔离；批量已读跨分页生效且幂等；重复 outbox 消费不产生重复收件箱项；事务回滚不产生通知；六个月到期记录不可再查询；策略并发更新只有一个请求成功。
