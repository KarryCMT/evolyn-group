# 消息中心现状分析与后端开发设计

> - 盘点基线：2026-08-28
> - 前端范围：`apps/evolyn-web/apps/web/src/components/dashboard/messageCenter/` 及两个顶栏入口
> - 后端状态：**P1（站内信最小闭环）+ P2（通知设置闭环）已于 2026-08-28 落地**——`internal/platform/notification/` 域（迁移 000039，七表 + 权限补授 + Outbox/保留清理 Worker）、application 域资产变更真实事件接入、前端 API 层与 Pinia 未读单一事实源及消息中心抽屉全量接入；P3（邮件/短信外部渠道与云币计费）、P4（近实时推送与运维指标）仍为后续阶段。实施偏差备注：P1.4 首发业务事件为 `application.asset.changed`（应用资产变更），首批事件目录为该事件 + 四个应用日志事件；领取到期判定带 1 秒宽限（容忍应用节点与数据库时钟毫秒级偏移）。

## 1. 结论摘要

当前消息中心已完成较完整的前端展示和本地交互：全屏抽屉、八个消息分类、分类未读数、只看未读、单条/全部已读、通知偏好和自定义提醒对象管理都有界面。但它仍是一个内存样例：没有 API、没有跨页单例状态、没有服务端分页和并发控制，提醒对象也没有真正关联到某个通知类型。

后端建议新建 `internal/platform/notification/` 领域，将以下三类数据分开：

1. 不可变的消息内容 `notification_messages`；
2. 成员在租户内的收件箱/已读状态 `notification_member_inboxes`；
3. 租户级通知偏好、动态接收规则和自定义外部联系人。

业务域不应在 HTTP 请求中直接发邮件/短信，也不应把审计日志当作消息源。同库业务通过事务 Outbox 发布结构化事件，消息 Worker 负责模板渲染、接收人解析、站内信扇出和外部渠道投递。

### 2.2 已有交互

- 入口：`TopNavigation.vue` 和 `ApplicationWorkspaceHeader.vue` 均能打开消息中心，未读总数驱动顶栏红点。
- 收件箱：默认进入「应用日志」，可按八个分类切换，支持只看未读、单条已读和全部已读。
- 分类：`data-reminder`、`app-log`、`document-activity`、`usage-reminder`、`contacts-management`、`open-platform`、`system-management`、`operation-notice`。
- 设置：除数据提醒和文档动态外，其余分类出现在设置 Tab；当前只有应用日志下 4 个事件样例。
- 渠道：站内信为必选禁用态，邮件和短信可在内存中切换；短信显示会消耗云币的提示。
- 接收对象：偏好样例中有「创建者」「系统管理员」动态对象；页面另有自定义姓名/手机/邮箱联系人池。

### 2.3 已确认的功能缺口

| 缺口 | 直接影响 | 设计处理 |
| --- | --- | --- |
| 消息、偏好、提醒对象全在组件内存 | 刷新或重建抽屉即恢复样例 | 替换为服务端收件箱与租户设置数据 |
| 两个顶栏各自创建抽屉与状态 | 同一会话可出现两份未读数 | 未读摘要收敛到 Pinia 的会话级单一事实源 |
| `markAllAsRead()` 实际修改所有分类 | 用户在某分类点击却清空全局未读 | API 默认只标记当前分类，不影响其他分类 |
| 「全部」下拉只有一项 | 无法筛选具体事件 | 由服务端事件目录下发选项；未接前先隐藏空筛选 |
| 点击消息只会已读 | 不能跳到应用、表单、管理页等目标 | 消息返回受控 `action`，前端按白名单路由名执行 |
| 自定义提醒对象可以只填姓名 | 没有手机/邮箱时无法投递 | 后端强制手机或邮箱至少一项，前端同步校验 |
| `openRecipientManagement(preferenceId)` 忽略了事件 ID | 自定义联系人从未与某条偏好关联 | 顶部按钮管理联系人池；每行「修改」单独全量替换该事件的接收规则 |
| 云币余额与可发短信数写死 | 会向用户展示虚假资产信息 | 未有账户/计费事实源前不返回数值，前端隐藏该摘要 |
| 列表没有分页、加载和失败状态 | 真实数据增长后无法使用 | 服务端游标分页，列表内 `el-scrollbar` 增量加载 |
| 偏好表和提醒对象列表使用原生 `overflow: auto` | 与项目统一列表滚动规范不一致 | 接入数据时一并改为仅内容区承担的 `el-scrollbar` |

## 3. 产品语义与范围

### 3.1 一期目标

- 当前租户成员查看自己的站内消息，按分类/事件/已读状态过滤。
- 顶栏展示服务端未读摘要，单条和当前分类全部已读幂等持久化。
- 租户管理员读写事件级通知渠道和接收规则，管理自定义提醒对象。
- 先完成站内信可靠闭环；邮件/短信在专用 Provider、费用与投递 Worker 落地后按能力开启。
- 同库业务域能在自身事务中可靠发布消息事件，重试不产生重复消息。

### 3.2 明确边界

- 消息中心是「租户 × 成员」的收件箱；不将跨租户的账号安全消息混入本模型。账号级消息后续需要独立 `account_notification_inboxes`。
- 「管理后台-消息推送」是租户配置外部 Webhook 的能力，与本域的站内信/邮件/短信不同，不共用配置表。
- `audit_logs` 是业务操作审计事实，`login_logs` 是会话建立流水；两者不作为消息中心的读模型或已读表。
- 一期不提供租户自定义消息模板、消息编辑器、群发编排、浏览器 Push 或移动端 Push。
- 「运营通知」一期只负责接收和展示可信平台事件，不新增运营人员发布后台。

## 4. 分类与事件目录

### 4.1 稳定分类码

| 分类码 | 展示名 | 分组 | 事件来源与语义 |
| --- | --- | --- | --- |
| `data-reminder` | 数据提醒 | 灵衍云 | 数据规则命中、表单数值阈值等，依赖后续低代码规则引擎 |
| `app-log` | 应用日志 | 灵衍云 | 应用资产变更、数据推送/助手/数据流/同步任务结果 |
| `document-activity` | 文档动态 | 灵衍云 | 评论、@我、协作权限变更，依赖后续文档协作域 |
| `usage-reminder` | 用量提醒 | 企业消息 | 套餐资源阈值、试用/订阅将到期与降级结果 |
| `contacts-management` | 通讯录管理 | 企业消息 | 成员邀请、加入/离职、组织与角色重要变更 |
| `open-platform` | 开放平台 | 企业消息 | API 凭据、开放接口额度、集成运行结果 |
| `system-management` | 系统管理 | 企业消息 | 安全、租户生命周期、关键系统配置变更 |
| `operation-notice` | 运营通知 | 企业消息 | 平台维护、版本更新、服务公告 |

分类码是历史数据与前端路由的稳定契约，只增不改。展示名和分组由服务端目录下发，前端不再把 `messageCenter.constants.ts` 作为业务事实源。

### 4.2 事件注册表

参照 `audit/service/events.go` 的做法，在 `notification/service/catalog.go` 维护代码注册表。每个事件定义：

- 稳定 `eventCode` 和所属 `categoryId`；
- 中文展示名、参数 Schema 和纯文本模板；
- 支持的渠道、默认渠道、不可关闭的渠道；
- 默认接收规则（事件发起人、事件指定受众、系统管理员）；
- 严重等级、可选跳转动作与保留期。

首批可以从当前页面的四个应用日志事件开始：

| 事件码 | 展示名 | 默认接收规则 |
| --- | --- | --- |
| `application.data_push.notice` | 数据推送提醒 | 事件发起人、系统管理员 |
| `application.assistant.run_failed` | 智能助手执行失败 | 事件发起人、系统管理员 |
| `application.data_flow.run_failed` | 数据流执行失败 | 事件发起人、系统管理员 |
| `application.output_sync.failed` | 输出表同步失败 | 事件发起人、系统管理员 |

事件码只增不改。模板修改不回写历史消息，消息创建时必须固化展示文本。不得用未经约束的 `map[string]any` 直接拼接 HTML。

## 5. 领域与代码结构

新建后端域：

```text
internal/platform/notification/
  errors.go
  controller/
    notification.go          # 成员收件箱和已读 API
    setting.go               # 租户通知偏好/联系人 API
  model/
    message.go               # 消息、收件箱、列表 DTO
    setting.go               # 偏好、接收规则、联系人 DTO
    outbox.go                # 事件 Outbox（可靠发布批次）
  repository/
    interface.go
    message.go
    setting.go
    outbox.go
  service/
    interface.go
    catalog.go               # 分类/事件注册表唯一事实源
    inbox.go
    setting.go
    publisher.go             # 业务域使用的窄发布端口
    dispatcher.go            # Outbox 领取、接收人解析、扇出
    worker.go
```

保持 controller → service → repository 小三层；由 `internal/platform/server/server.go` 组装事务管理器、IAM 窄端口、邮件/短信 Provider 和 Worker。领域内不得反向导入具体 IAM Service，使用以下窄端口：

- `MemberDirectory`：校验成员租户归属、激活状态和投递联系方式；
- `AdminRecipientResolver`：按现行系统管理员事实源解析成员，不依赖可改名的角色名；
- `ChannelCapabilityReader`：读取邮件/短信 Provider 和计费可用性；
- `NotificationBudgetReader/Consumer`：二期与云币/短信费用事实源对接，本域不自建余额。

## 6. 权限与数据范围

| 资源 | 授权对象 | 操作 | 语义 |
| --- | --- | --- | --- |
| `notifications` | 当前租户的全体有效成员 | `view` + `update` | 只能查看自己的收件箱，只能更新自己的已读状态 |
| `notification-settings` | 租户管理员基线角色 | `*` | 读写全租户事件偏好、接收规则和自定义联系人 |

两类路由都挂租户域链：Authentication → Tenant → TenantStatus → Authorization。租户 ID、账号 ID 和成员 ID 仅从 JWT/Gin 上下文解析，不接受客户端传入的替代值。

只授予 `notifications:view` 不能查看他人消息；Repository 查询必须同时显式约束 `tenant_id + member_id`。`notification-settings` 不经管理组范围回落放行，因为当前模型是全租户配置且包含外部联系人隐私数据。

迁移补授建议：

- 按现有「已认证用户」基线角色口径追加 `notifications:view` 和精确 `notifications:update`；
- 按 `members:* + roles:* + departments:*` 规则签名识别租户管理员，补授 `notification-settings:*`，不按可改名的角色名匹配。

## 7. 数据模型

实施时以版本化 SQL Migration 为唯一 Schema 事实源，同步 `scripts/db.sql`。当前最新迁移为 `000038`；若紧接实施可使用 `000039_notification_center`，若期间已有新迁移则必须顺延，禁止复用版本号。所有新表、字段、约束和索引按仓库规则添加中文注释。

### 7.1 `notification_messages`

一条不可变的逻辑消息，多成员共享内容，不重复存储大段文本。

| 字段 | 类型 | 约束 / 语义 |
| --- | --- | --- |
| `id` | `BIGSERIAL` | 主键 |
| `tenant_id` | `BIGINT` | 归属租户，非空 |
| `event_id` | `varchar(128)` | 生产者事件唯一 ID，与租户组合唯一，承担幂等 |
| `category_code` | `varchar(64)` | 稳定分类码 |
| `event_code` | `varchar(128)` | 稳定事件码 |
| `severity` | `varchar(16)` | `info/success/warning/error` |
| `title` | `varchar(200)` | 可选短标题，纯文本 |
| `content` | `varchar(2000)` | 模板渲染后的展示快照，纯文本 |
| `action` | `JSONB` | 受控跳转动作；仅稳定动作码和白名单参数，默认 `{}` |
| `source_ref` | `JSONB` | 应用/表单/任务等可选追溯引用，不直接出网 |
| `occurred_at` | `timestamptz` | 业务事件发生时间 |
| `expires_at` | `timestamptz` | 读取与未读统计的有效期上界 |
| `created_at` | `timestamptz` | 消息物化时间 |

约束与索引：

- 唯一索引 `(tenant_id, event_id)`，Worker 重试使用 `ON CONFLICT DO NOTHING` 防重。
- `(tenant_id, category_code, occurred_at DESC, id DESC)` 支撑租户内排查；常规成员查询仍从收件箱表进入。
- `severity` 和 `action` 增加 CHECK；`content` 不允许空文本。
- 该表不使用软删除；按保留策略成批硬删，它不是合规审计表。
- 收件箱到消息、偏好/接收规则到设置聚合根使用明确外键；Service 层仍在写关联前复核冗余 `tenant_id` 一致，不用裸 ID 跨租户绑定。

### 7.2 `notification_member_inboxes`

消息向租户成员的站内信扇出与已读状态。

| 字段 | 类型 | 约束 / 语义 |
| --- | --- | --- |
| `id` | `BIGSERIAL` | 主键，也作游标后备值 |
| `tenant_id` | `BIGINT` | 冗余租户条件，所有查询必填 |
| `message_id` | `BIGINT` | 逻辑消息 ID |
| `member_id` | `BIGINT` | 接收成员 ID |
| `category_code` | `varchar(64)` | 不可变分类冗余，用于未读分类索引 |
| `occurred_at` | `timestamptz` | 不可变事件时间冗余，用于稳定排序 |
| `read_at` | `timestamptz NULL` | `NULL` 表示未读；重复标记已读不改写首次时间 |
| `created_at` | `timestamptz` | 扇出时间 |

约束与索引：

- 唯一约束 `(tenant_id, message_id, member_id)`；
- 列表索引 `(tenant_id, member_id, category_code, occurred_at DESC, id DESC)`；
- 未读部分索引 `(tenant_id, member_id, category_code, occurred_at DESC, id DESC) WHERE read_at IS NULL`；
- 更新必须以 `tenant_id + member_id + id` 定位，零行影响按不可见处理，不泄露消息是否属于其他成员。

### 7.3 `tenant_notification_settings`

每租户一行的通知设置聚合根。

| 字段 | 类型 | 约束 / 语义 |
| --- | --- | --- |
| `id` | `BIGSERIAL` | 主键 |
| `tenant_id` | `BIGINT` | 有效记录唯一 |
| `revision` | `BIGINT` | 整个偏好/联系人聚合的乐观锁，初始 1 |
| `created_at/updated_at/deleted_at` | `timestamptz` | 对齐 `TenantBaseModel` |

租户开通事务通过 `NotificationSettingSeeder` 创建聚合根；读取侧仍提供幂等补齐，兼容存量租户。任何偏好、接收规则或自定义联系人变更都使 `revision + 1`。

### 7.4 `tenant_notification_preferences`

只保存租户对事件注册表默认值的覆盖。

| 字段 | 类型 | 约束 / 语义 |
| --- | --- | --- |
| `id` | `BIGSERIAL` | 主键 |
| `setting_id` / `tenant_id` | `BIGINT` | 聚合根与租户冗余条件 |
| `event_code` | `varchar(128)` | 当前租户内唯一 |
| `system_enabled` | `BOOLEAN` | 站内信开关；受注册表必选规则限制 |
| `email_enabled` | `BOOLEAN` | 邮件开关 |
| `sms_enabled` | `BOOLEAN` | 短信开关 |
| `recipients_overridden` | `BOOLEAN` | 区分「使用注册表默认对象」与「显式配置为空」 |
| `created_at/updated_at` | `timestamptz` | 创建/更新时间 |

新事件加入代码注册表后，不需要为所有租户立即插入数据；无覆盖行时投影注册表默认值。

### 7.5 `tenant_notification_preference_recipients`

事件偏好的接收规则关联。

| 字段 | 类型 | 约束 / 语义 |
| --- | --- | --- |
| `id` | `BIGSERIAL` | 主键 |
| `tenant_id` / `preference_id` | `BIGINT` | 租户隔离和偏好归属 |
| `target_kind` | `varchar(32)` | `event_actor/event_audience/tenant_admin/custom_recipient` |
| `custom_recipient_id` | `BIGINT NULL` | 仅 `custom_recipient` 时必填 |
| `created_at` | `timestamptz` | 创建时间 |

CHECK 强制 `target_kind` 与 `custom_recipient_id` 组合合法。同一偏好内动态规则只能出现一次，自定义联系人不能重复关联。

`custom_recipient` 只能用于邮件/短信，因为它没有租户成员身份，不能生成站内收件箱记录。

### 7.6 `tenant_notification_custom_recipients`

租户级自定义外部提醒对象池。

| 字段 | 类型 | 约束 / 语义 |
| --- | --- | --- |
| `id` | `BIGSERIAL` | 主键 |
| `tenant_id` | `BIGINT` | 租户隔离 |
| `name` | `varchar(80)` | trim 后 1–80 字符 |
| `mobile` | `varchar(32)` | 规范化手机号，可空 |
| `email` | `varchar(254)` | 小写规范化邮箱，可空 |
| `revision` | `BIGINT` | 联系人自身修改口令，一期新增/删除也预留 |
| `created_at/updated_at/deleted_at` | `timestamptz` | 软删除保留关联历史 |

手机和邮箱至少一项必填；单租户一期默认最多 200 个有效自定义对象，上限由服务端配置，不信任前端。读取完整联系方式只对 `notification-settings` 管理员开放；日志、审计和错误信息只记录脱敏值。

### 7.7 `notification_outbox_events`

业务事务与消息物化之间的可靠边界。

| 字段 | 类型 | 约束 / 语义 |
| --- | --- | --- |
| `id` | `BIGSERIAL` | Worker 领取顺序 |
| `event_id` | `varchar(128)` | 全局幂等 ID，唯一 |
| `tenant_id` / `event_code` | `BIGINT` / `varchar(128)` | 租户与事件目录键 |
| `actor_member_id` | `BIGINT` | 可选事件发起人，0 表示系统 |
| `audience_member_ids` | `JSONB` | 事件显式成员受众，Worker 再做同租户校验 |
| `parameters` | `JSONB` | 受注册表 Schema 限制的模板参数 |
| `occurred_at` | `timestamptz` | 业务时间 |
| `status` | `varchar(16)` | `pending/processing/done/failed` |
| `attempt_count/next_attempt_at` | `INTEGER/timestamptz` | 有界指数退避 |
| `last_error_code` | `varchar(100)` | 稳定内部错误码，不存原始敏感错误 |
| `created_at/processed_at` | `timestamptz` | 创建/完成时间 |

Worker 使用 `FOR UPDATE SKIP LOCKED` 小批领取。消息与成员收件箱在同一个事务中插入；重试依靠 `event_id` 和收件箱唯一约束幂等。

邮件/短信真实投递落地时再增加 `notification_deliveries` 和可选的 `notification_delivery_attempts`，不把 Provider 重试字段塞进站内收件箱表。

## 8. API 契约

所有 JSON 接口使用统一 `{code,msg,data}` 包络，时间使用 `model.JSONTime` 以东八区秒级 `yyyy-MM-dd HH:mm:ss` 出网。Swagger `@Tags`、`@Summary`、`@Description` 和错误码说明全部使用中文。

### 8.1 接口清单

| 方法与路径 | 权限 | 用途 |
| --- | --- | --- |
| `GET /api/v1/notifications/unread-summary` | `notifications:view` | 顶栏未读总数和分类未读数 |
| `GET /api/v1/notifications` | `notifications:view` | 当前成员消息游标分页 |
| `PUT /api/v1/notifications/:id/read` | `notifications:update` | 幂等标记单条已读 |
| `PUT /api/v1/notifications/read-all` | `notifications:update` | 标记当前分类/可选事件的已有消息为已读 |
| `GET /api/v1/notification-settings` | `notification-settings:view` | 分类与事件目录、租户有效偏好、渠道能力和 revision |
| `PATCH /api/v1/notification-settings/preferences/:eventCode` | `notification-settings:patch` | 部分更新渠道或全量替换该事件接收规则 |
| `GET /api/v1/notification-settings/recipients` | `notification-settings:view` | 自定义提醒对象列表 |
| `POST /api/v1/notification-settings/recipients` | `notification-settings:create` | 新增提醒对象 |
| `DELETE /api/v1/notification-settings/recipients/:id?revision=...` | `notification-settings:delete` | 删除未被偏好引用的提醒对象 |

### 8.2 未读摘要

```json
{
  "unreadTotal": 3,
  "categories": [
    { "categoryId": "app-log", "unreadCount": 2 },
    { "categoryId": "system-management", "unreadCount": 1 }
  ],
  "generatedAt": "2026-08-28 10:30:00"
}
```

只返回未读数大于 0 的分类。统计排除 `expires_at <= now()` 的消息，即使清理 Worker 尚未物理删除也不得继续计数。

### 8.3 消息列表

查询参数：

- `categoryId`：必填，八个稳定分类之一；
- `eventCode`：可选，必须属于当前分类；
- `unreadOnly`：可选布尔，默认 `false`；
- `cursor`：不透明游标，固化 `(occurred_at,id)`；
- `limit`：默认 20，上限 100。

```json
{
  "items": [
    {
      "id": 1024,
      "categoryId": "app-log",
      "eventCode": "application.data_flow.run_failed",
      "eventLabel": "数据流执行失败",
      "severity": "error",
      "title": "",
      "content": "数据流「客户汇总」执行失败",
      "createdAt": "2026-08-28 10:20:31",
      "read": false,
      "readAt": "",
      "action": {
        "type": "open_application_data_flow",
        "params": { "appCode": "app_xxx", "flowId": "42" }
      }
    }
  ],
  "nextCursor": "opaque-cursor",
  "hasMore": true,
  "retentionMonths": 6,
  "serverTime": "2026-08-28 10:30:00"
}
```

`action` 不存在时返回空对象。外部 URL 默认不允许；确有需求时必须使用服务端域名白名单和前端二次校验。

### 8.4 单条与批量已读

`PUT /notifications/:id/read` 无请求体，重复调用成功且不改写首次 `readAt`。响应同时返回新摘要，避免前端立即多发一次请求。

`PUT /notifications/read-all` 请求：

```json
{
  "categoryId": "app-log",
  "eventCode": "",
  "through": "2026-08-28 10:30:00"
}
```

`through` 由前端使用本次列表响应的服务端时间，服务端只标记 `occurred_at <= through` 的旧消息，不误伤操作同时新到达的消息。`categoryId` 必填，与当前工具栏语义一致。

### 8.5 通知设置聚合

`GET /notification-settings` 的核心结构：

```json
{
  "revision": 7,
  "categories": [
    {
      "id": "app-log",
      "label": "应用日志",
      "group": "product",
      "configurable": true,
      "events": [
        {
          "code": "application.data_flow.run_failed",
          "label": "数据流执行失败",
          "supportedChannels": ["system", "email", "sms"],
          "lockedChannels": ["system"],
          "channels": { "system": true, "email": false, "sms": false },
          "recipients": [
            { "kind": "event_actor", "label": "创建者" },
            { "kind": "tenant_admin", "label": "系统管理员" }
          ]
        }
      ]
    }
  ],
  "channelCapabilities": {
    "system": { "available": true, "reason": "" },
    "email": { "available": false, "reason": "通用邮件通道尚未配置" },
    "sms": { "available": false, "reason": "短信计费通道尚未配置" }
  },
  "smsBudget": null
}
```

数据提醒/文档动态若尚无事件注册，仍在收件箱分类目录中返回，但 `configurable=false`且 `events=[]`；前端不用硬编码排除。

云币或短信额度服务未接入时 `smsBudget=null`，前端隐藏数值摘要，不使用样例数值兜底。

### 8.6 更新事件偏好

```json
{
  "revision": 7,
  "channels": { "email": true },
  "recipients": [
    { "kind": "event_actor" },
    { "kind": "tenant_admin" },
    { "kind": "custom_recipient", "recipientId": 19 }
  ]
}
```

- `channels` 是部分更新；缺省键保持不变。
- `recipients` 一旦出现即全量替换；缺省表示不修改。
- 不支持的渠道、必选渠道关闭、异租户/已删除联系人都由服务端拒绝。
- 成功返回该事件的有效偏好和新 `revision`；旧 revision 返回 HTTP 409。

### 8.7 提醒对象

新增请求同时携带聚合 revision：

```json
{
  "revision": 7,
  "name": "运维值班",
  "mobile": "13800000000",
  "email": "ops@lingyanyun.example"
}
```

删除被偏好引用的对象返回 `NOTIFICATION_RECIPIENT_IN_USE` 和脱敏的 `data.usedByEventCodes`，不默认级联改变投递范围。前端应先从相关事件接收规则中移除，再删除联系人。

## 9. 业务流程与事务

### 9.1 事件发布与站内信扇出

```text
业务 Service 在自身事务中完成业务写入
  → NotificationEventPublisher.PublishInTx 写 Outbox
  → 业务事务提交
  → Worker 领取 pending 事件
  → 校验事件目录与参数 Schema
  → 读租户有效偏好、解析动态成员与外部对象
  → 渲染纯文本快照
  → 同事务写 notification_messages + member_inboxes
  → 标记 Outbox done
  → 后续产生 email/sms delivery 任务
```

`PublishInTx` 必须经 `infrastructure.ResolveDB(ctx, db)` 加入调用方事务。不允许业务主记录已提交却因进程退出而永久丢失消息事件。

事件受众解析规则：

- `event_actor`：事件发起成员，必须仍属于当前租户；
- `event_audience`：生产者明确给出的成员 ID，Worker 批量复核同租户与有效状态；
- `tenant_admin`：通过系统管理员窄端口实时解析，并对合并结果去重；
- `custom_recipient`：仅进入邮件/短信投递任务，不产生成员收件箱。

### 9.2 已读操作

- 单条已读：`UPDATE ... SET read_at = now() WHERE tenant_id=? AND member_id=? AND id=? AND read_at IS NULL`；已读行或首次更新均返回成功。
- 批量已读：在一个事务内按成员、分类、可选事件和 `through` 更新，然后重新统计该成员摘要。
- 已读状态是用户收件箱交互，不记入业务操作审计，避免高频噪声。

### 9.3 偏好与提醒对象写入

- Service 通过 `TxManager.WithinTransaction` 加载并锁定当前租户聚合根。
- 先比对 `revision`，再校验事件、渠道、接收规则和联系人归属。
- 接收规则全量替换在同一事务内先删关联、再批量插入，最后以旧 revision 为条件原子递增。
- 聚合根更新零行影响返回 409，禁止伪成功。
- 事务提交后 best-effort 写业务审计：偏好修改、提醒对象新增/删除；摘要只记录事件码、渠道开关和脱敏联系方式。

## 10. 邮件、短信与云币

### 10.1 能力开关

认证域的验证码邮件/短信 Provider 有强安全场景和固定模板，不直接复用为通用通知通道。消息域定义独立 `EmailChannel` / `SMSChannel` 窄端口，装配层可共享底层 SMTP/供应商客户端，但模板、限流、计费和错误映射必须独立。

当通用 Provider 或费用事实源不可用时：

- 设置读取仍返回该渠道，但 `available=false` 和可展示原因；
- 前端禁用勾选；
- 后端拒绝新开启请求，不保存「已开启但永远无法发送」的虚假状态；
- 已有偏好在能力临时故障时保留，投递任务可重试，不自动改写用户配置。

### 10.2 投递任务

`notification_deliveries` 建议至少固化：租户、消息、渠道、目标类型/脱敏提示、幂等键、状态、尝试次数、下次重试时间、Provider 稳定错误码和发送时间。投递目标完整值必须使用可轮换的应用层密钥加密或在领取任务时按受控引用读取，不以明文写普通日志。

状态机：`pending → sending → sent`；可重试错误返回 `pending + next_attempt_at`，超过上限或明确不可重试进入 `failed`。Provider 调用必须有超时、并发上限和租户级限流。

### 10.3 费用口径

- 云币余额、短信单价和可发条数必须来自账户/计费域，消息域只读取和消费授权，不新建另一份余额。
- 任务入队前可做预检，真正扣减必须与 Provider 投递幂等键绑定，避免重试重复扣费。
- 余额不足时站内信仍正常产生，短信任务记录为不可投递，不让业务主流程失败。

## 11. 安全、隐私与审计

- 所有收件箱查询/更新同时使用 `tenant_id + member_id`，还需要真库 `SEC-NOTIFICATION-*` 集成测试防止横向越权。
- 消息 `content` 只存纯文本；前端用插值展示，禁止对事件参数使用未清洗 `v-html`。
- 跳转动作仅允许登记稳定动作码与受控参数，由前端 action registry 映射到实际路由；到达目标页时仍执行目标资源的正常鉴权，消息本身不是访问凭证。
- 模板参数不得包含密码、验证码、JWT、OAuth 凭据、私钥、完整生产连接串或未受控 SQL 错误。
- 外部联系人手机/邮箱不进入消息内容、错误 msg 或审计摘要；审计中仅保留如 `138****0000` / `o***@lingyanyun.example` 的脱敏快照。
- 不向普通成员出网自定义联系人目录和租户偏好；前端依赖登录聚合信息中的 capability 隐藏「通知设置」入口，后端权限仍是最终边界。
- 用户查看消息不记审计；租户级偏好与外部联系人变更记审计。

## 12. 保留、清理与性能

- 页面已明示「保存最近六个月」，一期将其定义为 PostgreSQL `occurred_at < now() - interval '6 months'`，而不是模糊的 180 天。
- 所有列表和未读统计在 SQL 中排除已过期消息，不依赖清理任务准时性。
- `NotificationRetentionWorker` 每日分批先删收件箱行，再删无收件箱引用的过期消息；每批数量受控，避免长事务和大量表膨胀。
- 列表使用 `(occurred_at,id)` 游标，不使用深页 `OFFSET`；排序固定为事件时间倒序、ID 倒序。
- 一期未读数以 PostgreSQL 为事实源。当单租户扇出量达到性能阈值后，可加 Redis 未读缓存，但缓存只是可重建投影，失效时必须回源数据库。
- 大租户扇出使用分批插入和唯一约束去重；不在业务 HTTP 事务内对成千上万成员循环插入。

## 13. 前端接入设计

### 13.1 状态与数据流

保留现有视图组件边界，将 `useMessageCenter.ts` 从样例数据容器收敛为功能组装 composable：

```text
stores/notification.ts
  会话级未读摘要唯一事实源
  切换租户/退出时清空，登录初始化时加载

api/notifications.ts
  收件箱、未读摘要、单条/批量已读 DTO

api/notificationSettings.ts
  事件目录、偏好和提醒对象 DTO

components/dashboard/messageCenter/useMessageCenter.ts
  抽屉局部分类/筛选/分页/加载状态
  调用 API，已读成功后同步 notification store
```

- `records`、`preferences`、`recipients` 改为异步服务端数据；派生的当前分类、标签和可见项仍使用纯 `computed`。
- watcher 只处理「分类/筛选改变后取消旧请求并加载」等副作用，使用 `AbortController` 或请求序号防止旧响应覆盖新状态。
- 对外暴露 readonly 状态和显式 action，视图组件不直接改写共享列表。
- 两个顶栏都只读取同一 Pinia 未读摘要，不再依靠各自抽屉的 `unreadChange` 作为初始数据源。

### 13.2 界面行为调整

- 打开抽屉时加载默认/上次分类首页；切换分类重置游标和事件筛选。
- 消息列表只有内容区滚动，使用 `el-scrollbar`；标题、侧栏和工具栏固定。
- 工具栏事件下拉由当前分类的服务端目录产生；无事件选项时不显示占位下拉。
- 单击消息先执行幂等已读，成功后再按 `action` 导航；已读请求失败时不伪造持久成功。
- 普通成员隐藏「通知设置」；有权管理员进入设置时再加载设置聚合。
- 设置行开关采用等待服务端成功后提交的保守更新，409 时重载最新配置并提示已被其他管理员修改。
- 每行「修改」打开该 `eventCode` 的接收对象选择器；顶部「提醒对象管理」只管理可复用联系人池。
- 新增提醒对象前端校验「手机/邮箱至少一项」，但不替代后端校验。
- 消息量少时可在抽屉打开时刷新摘要；一期若需近实时红点，仅在页面可见时以 60 秒间隔轻量轮询摘要，后续再接 SSE/WebSocket。

## 14. 业务错误码

错误全部通过 `httpx.BizError` 出网，原始 SQL/Provider 错误仅作 wrap cause 入服务端日志。前端 `packages/utils/src/request/errorCodes.ts` 同步维护稳定码，禁止匹配 message 文本。

| errCode | HTTP | 语义 |
| --- | --- | --- |
| `NOTIFICATION_CATEGORY_UNKNOWN` | 400 | 分类码未登记 |
| `NOTIFICATION_EVENT_UNKNOWN` | 400 | 事件码未登记或不属于当前分类 |
| `NOTIFICATION_CURSOR_INVALID` | 400 | 游标无法解析或签名无效 |
| `NOTIFICATION_NOT_FOUND` | 404 | 当前成员收件箱中不存在该消息 |
| `NOTIFICATION_SETTINGS_CONFLICT` | 409 | 租户通知设置 revision 冲突 |
| `NOTIFICATION_CHANNEL_NOT_SUPPORTED` | 400 | 事件不支持请求渠道 |
| `NOTIFICATION_CHANNEL_REQUIRED` | 400 | 尝试关闭必选渠道 |
| `NOTIFICATION_CHANNEL_UNAVAILABLE` | 409 | Provider/计费能力尚不可用，不允许新开启 |
| `NOTIFICATION_RECIPIENT_INVALID` | 400 | 姓名/手机/邮箱或接收规则不合法 |
| `NOTIFICATION_RECIPIENT_NOT_FOUND` | 404 | 联系人不存在、已删除或不属于当前租户 |
| `NOTIFICATION_RECIPIENT_IN_USE` | 409 | 联系人仍被事件偏好引用 |
| `NOTIFICATION_RECIPIENT_LIMIT_EXCEEDED` | 403 | 自定义提醒对象达到租户上限 |

## 15. 实施分期

### P0：契约冻结

1. 冻结八个分类码、首批事件码、模板参数 Schema 和默认接收规则。
2. 核对应用、版本/配额、IAM 等事件生产者，不承诺仍无数据源的类别。
3. 冻结 API DTO、权限资源、保留口径和错误码。

### P1：站内信最小闭环

1. 迁移落消息、收件箱、设置聚合、偏好/接收规则、联系人和 Outbox，同步 `scripts/db.sql`。
2. 完成 Repository/Service/Controller 、服务器装配、权限补授和租户开通 Seeder。
3. 实现未读摘要、游标列表、单条/分类已读和六个月清理。
4. 选一个已落地业务事件完成真实 Outbox 端到端，不使用手工插表作为验收。
5. 前端引入 API 层和 Pinia 单一未读事实源，删除运行时样例数据依赖。

### P2：通知设置闭环

1. 完成管理员偏好、接收规则和自定义联系人 API。
2. 前端区分「联系人池管理」与「事件接收对象选择」，接入 revision 冲突处理。
3. 将无权成员的设置入口隐藏，后端完成越权拒绝。

### P3：外部渠道与费用

1. 新增通用邮件/短信 Provider 窄端口、投递任务、重试/死信与监控指标。
2. 对接云币/短信计费事实源，确保幂等扣费。
3. 通过能力下发启用邮件/短信勾选与真实余额摘要。

### P4：近实时与运维

1. 根据负载决定 SSE/WebSocket 或 Redis 可重建未读投影，不以前端高频轮询代替。
2. 增加 Outbox 积压、扇出延迟、渠道成功率、重试/死信和清理滞后指标。

## 16. 测试与验收矩阵

### 16.1 Service / Repository

- 事件目录：未知事件、参数缺失、默认渠道/接收人投影、模板纯文本输出。
- 幂等：同 `event_id` 重放不新增逻辑消息，重复解析同一成员不新增收件箱行。
- 已读：首次时间不被重写，批量已读仅影响指定分类/事件和 `through` 之前的数据。
- 分页：同时间多条消息不重复/不漏项，非法游标稳定报错。
- 偏好：缺省值投影、部分渠道 PATCH、接收规则全量替换、必选渠道、不支持/不可用渠道拒绝。
- 并发：两个相同 revision 的管理员写入只有一个成功，另一个返回 409。
- 联系人：同租户归属、手机/邮箱至少一项、上限、被引用删除冲突。

### 16.2 真库安全集成测试

- `SEC-NOTIFICATION-LIST`：租户 A/成员 A 不能读租户 B 或同租户成员 B 的消息。
- `SEC-NOTIFICATION-READ`：猜测他人收件箱 ID 不能标记已读，也不泄露存在性。
- `SEC-NOTIFICATION-SETTINGS`：普通成员不能读取/修改租户偏好和联系人。
- `SEC-NOTIFICATION-RECIPIENT`：偏好不能关联其他租户联系人。
- `NOTIFICATION-OUTBOX-INT`：业务事务回滚时 Outbox 同步回滚；提交后 Worker 可物化且重放幂等。
- `NOTIFICATION-MIGRATE-INT`：up/down/up 链与 `scripts/db.sql` 终态结构一致，索引和 CHECK 全部生效。

### 16.3 前端

- 抽屉加载/空/错误/增量分页、分类切换和快速切换请求竞态。
- 两个顶栏共享未读摘要，单条/批量已读后同步且刷新后不回滚。
- 「全部已读」不影响其他分类或操作后新到达消息。
- 无权设置入口、渠道不可用、revision 409、联系人被引用等状态都有明确反馈。
- 消息内容始终按纯文本渲染，非白名单 action 不导航。
- 在 `apps/evolyn-web` 执行 `pnpm run lint:format`、`pnpm -F @evolyn.do/web typecheck` 和 `pnpm -F @evolyn.do/web build`；按项目约定不要求浏览器 E2E 走查。

### 16.4 后端验证

- `gofmt -s` / `make fmt`；
- `go test ./...`；
- 需要真库时按固定 `TEST_PG_DSN` 约定执行集成测试；
- 接口实现后执行 `make swagger` 本地核对，生成物不入库。

## 17. 验收标准

1. 页面刷新、切换页面或使用另一个顶栏入口后，未读数和已读状态一致。
2. 成员只能读写「当前租户 × 当前成员」的收件箱；任何猜 ID 都不能越权。
3. 当前分类全部已读不改变其他分类，也不改变 `through` 之后新到达的消息。
4. 业务事件与 Outbox 同事务；Worker 重放不产生重复消息或重复收件箱。
5. 两个管理员并发修改同一租户通知设置时，只有一个旧 revision 写入成功。
6. 普通成员不可读取联系人隐私数据；日志、审计和错误响应不包含完整手机/邮箱。
7. 通用邮件/短信与计费能力未就绪时，页面不显示虚假余额，后端不接受开启不可用渠道。
8. 过期消息即使尚未物理清理，也不出现在列表和未读摘要中。
