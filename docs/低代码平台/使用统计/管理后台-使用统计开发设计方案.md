# 管理后台-使用统计开发设计方案

## 1. 背景与目标

管理后台“使用统计”（`/tenant/usage`）面向**当前租户**的管理员，提供资源存量、管理员活跃、成员活跃、系统效益和登录情况五类统计。页面可按应用或成员、日期区间及日/周/月粒度筛选，并支持明细分页与异步导出。

本方案的目标是建立可扩展、可重算且租户隔离的统计读模型。前端只消费统计结果，不能在请求时跨业务表、审计表或登录流水临时做大范围聚合。

## 2. 范围与非目标

### 2.1 首期范围

- 资源用量：应用数、数据记录数、文件存储量，以及已落地资产的数量快照。
- 成员与管理员活跃：访问、创建、修改、删除、导出等人数与次数的趋势、明细。
- 登录数据：通讯录人数、本月登录人数、登录比例、登录趋势与成员明细。
- 系统效益：基于租户启用的、可版本化的节省时间与成本规则计算。
- 租户内的查询、导出、权限控制、数据截止时间展示和错误码定义。

### 2.2 非目标

- 不把 HTTP 请求数、接口耗时或 Prometheus 指标当作业务使用量。
- 不复用 `audit_logs` 作为高频统计主数据源；审计与统计分别承担可追责和可分析职责。
- 不在首期引入跨租户运营报表；平台运营统计另行建设。
- 未上线的表单、流程、仪表盘、集成等资产不伪造数据；接口应返回 `unavailable` 或明确的零值口径。

## 3. 统计口径

所有日期按租户配置时区计算；首期默认 `Asia/Shanghai`。日期区间为闭区间，服务端转换为 `[start, end + 1 day)` 查询。所有响应返回 `timezone`、`dataAsOf` 与 `isPartial`，使前端可明确展示“数据截至”。

| 指标 | 口径 |
| --- | --- |
| 活跃人数 | 统计周期内至少产生一次对应事件的去重有效成员数 |
| 活跃次数 | 对应事件的总次数；同一成员多次操作分别计数 |
| 访问人数/次数 | `application.visit` 事件的成员去重数/事件数 |
| 创建、修改、删除、导出 | 对应 `data.*` 事件的成员去重数/事件数 |
| 通讯录人数 | 查询时租户内状态为有效的成员数，不包含待接受邀请、已禁用或已离职成员 |
| 本月登录人数 | 自然月内成功登录的去重有效成员数 |
| 登录系统比例 | 本月登录人数 ÷ 通讯录有效成员数；分母为 0 时返回 `null` |
| 资源用量 | 每日快照中的期末存量；不是区间内的新增量 |
| 节省时间/成本 | 按生效统计规则，将事件次数折算为时间和成本；未配置规则时不可计算 |

管理员活跃数据是成员活跃数据的受控子集：成员在统计日拥有管理员身份或由身份快照标记为管理员，避免角色变更导致历史数据被重写。

## 4. 总体架构

```text
领域服务成功提交业务事务
        │
        ├─ 同事务写 usage_outbox_events（可重试、可追溯）
        │
        └─ 使用统计 Worker 领取并幂等消费
                 ├─ usage_events（原始事件，短期留存）
                 ├─ tenant_usage_activity_daily（活跃日事实）
                 ├─ tenant_usage_login_daily（登录日事实）
                 └─ tenant_usage_resource_daily（资源日快照）
                                      │
                                 Usage Service
                                      │
                         查询 API / 异步导出任务
```

新增后端域位于 `apps/evolyn-core/internal/platform/usage/`，遵循 controller → service → repository 分层，并由 `internal/platform/server/server.go` 装配。统计事件写入必须跟随业务事务；事件消费、聚合和导出均可异步，但不得因异步任务重试造成重复计数。

## 5. 数据模型

### 5.1 出站事件与原始事件

`usage_outbox_events` 用于事务性投递，Worker 成功处理后标记完成；`usage_events` 是可重放的分析事件，建议保留 180 天。二者均以 `event_id` 唯一约束防重。

```text
event_id             UUID           业务侧生成的幂等键
tenant_id            BIGINT         所属租户，禁止为 0
application_id       BIGINT NULL    所属应用；租户级操作为空
account_id           BIGINT NULL    操作者账号快照
member_id            BIGINT NULL    操作者成员快照
actor_role_snapshot  VARCHAR(32)    member / administrator / system
event_type           VARCHAR(64)    稳定事件名
resource_type        VARCHAR(64)    资源类别
resource_id          VARCHAR(128)   资源标识，不存业务内容
occurred_at          TIMESTAMPTZ    实际发生时间
occurred_date        DATE           按租户时区归属的统计日
request_id           VARCHAR(64)
properties           JSONB          小型、非敏感的扩展属性
```

首批稳定事件名：`application.visit`、`data.create`、`data.update`、`data.delete`、`data.export`、`workflow.start`、`workflow.complete`、`form.submit`、`dashboard.view`、`file.upload`、`integration.invoke`、`login.success`。

`properties` 不得写入表单字段值、手机号、邮箱、完整 IP、文件内容或其他个人敏感信息。统计域只保留分析所需的最小化元数据。

### 5.2 活跃日事实表

`tenant_usage_activity_daily` 的粒度是“统计日 × 租户 × 应用 × 成员”。

```text
stat_date, tenant_id, application_id, member_id
visit_count, create_count, update_count, delete_count, export_count
workflow_start_count, workflow_complete_count
form_submit_count, dashboard_view_count, integration_invoke_count
is_administrator_snapshot
first_active_at, last_active_at, updated_at
```

唯一键为 `(stat_date, tenant_id, application_id, member_id)`；至少建立以下索引：

- `(tenant_id, stat_date)`：租户趋势。
- `(tenant_id, application_id, stat_date)`：按应用筛选和资源关联。
- `(tenant_id, member_id, stat_date)`：按成员筛选、管理员活跃与明细。

查询“人数”时以 `count(distinct member_id)` 计算；不能将多个应用行的“人数”简单相加。

### 5.3 登录日事实表

`tenant_usage_login_daily` 的粒度是“统计日 × 租户 × 成员”。

```text
stat_date, tenant_id, member_id
login_count, first_login_at, last_login_at, updated_at
```

现有 `login_logs` 已保存 `tenant_id`、`member_id`、`created_at`，可作为历史回填来源，但其账号级设计不可改变。迁移补充 `(tenant_id, created_at, member_id)` 索引；聚合后由本域读事实表提供租户统计查询。

### 5.4 资源日快照表

`tenant_usage_resource_daily` 用于保存期末存量，粒度为“统计日 × 租户 × 应用 × 指标”。

```text
stat_date, tenant_id, application_id, creator_member_id
metric_key, metric_value, metric_unit, captured_at
```

唯一键为 `(stat_date, tenant_id, application_id, metric_key)`。`metric_key` 首批包含 `application_count`、`data_record_count`、`file_storage_bytes`，其余资产随模块上线扩展。资源快照由每日任务生成；最新概览读取最近一次成功快照。

### 5.5 效益规则与日事实

系统效益不能从事件次数直接推测。使用可版本化的规则定义：

```text
tenant_efficiency_rules
tenant_id, event_type, saved_seconds_per_event, labor_cost_per_hour
effective_from, effective_to, revision, enabled
```

聚合时写入 `tenant_usage_efficiency_daily`，固化规则版本和计算结果。公式为：

```text
saved_seconds = Σ(event_count × saved_seconds_per_event)
saved_cost    = saved_seconds / 3600 × labor_cost_per_hour
```

规则缺失时，接口返回不可计算状态及原因，不展示推测数值。

## 6. 事件生产与聚合

### 6.1 生产原则

- 领域服务在其业务写事务内写入出站事件；不得在事务提交后以 best-effort 方式补写。
- 事件 ID 由生产端生成；消费者按 `event_id` 幂等。
- 删除、成员禁用、权限变动等事件保留操作发生时的成员、应用及管理员身份快照。
- 只有成功完成的业务动作产生统计事件；失败、重试中的动作不计入。

### 6.2 Worker 与补数

Worker 使用批量领取和行锁机制处理出站事件。聚合使用数据库 UPSERT 递增计数；对同一 `event_id` 的重复消费必须无副作用。每日快照任务和事件聚合任务都记录运行状态、水位和错误摘要。

提供受限的重算能力：按租户、日期范围删除对应日事实后，从原始事件重放。仅允许平台运维或受控后台任务调用，并记录审计。原始事件过期后不可无依据重算。

## 7. API 设计

所有接口均从租户中间件上下文取得 `tenantId`，请求参数不得允许指定其他租户。

| 接口 | 权限 | 用途 |
| --- | --- | --- |
| `GET /usage/filter-options` | `usage-statistics:view` | 可选择的应用、成员与数据截止时间 |
| `GET /usage/resources/overview` | view | 资源概览与最新快照时间 |
| `GET /usage/resources/details` | view | 应用/成员维度资源明细分页 |
| `GET /usage/activity/overview` | view | 管理员或成员活跃概览 |
| `GET /usage/activity/trends` | view | 访问、创建、修改、删除、导出趋势 |
| `GET /usage/activity/details` | view | 活跃明细分页 |
| `GET /usage/logins/overview` | view | 通讯录人数、登录人数和比例 |
| `GET /usage/logins/trends` | view | 登录人数和次数趋势 |
| `GET /usage/logins/details` | view | 登录明细分页 |
| `GET /usage/efficiency` | view | 节省时间、成本及规则状态 |
| `POST /usage/exports` | `usage-statistics:export` | 创建异步导出任务 |
| `GET /usage/exports/:id` | export | 查询本人导出任务状态及下载地址 |

活动相关接口统一支持：`dimension=application|member`、`applicationIds[]`、`memberIds[]`、`granularity=day|week|month`、`startDate`、`endDate`。导出任务须持久化提交时的筛选条件、操作者、生成时间、数据截止时间、文件引用与过期时间。

## 8. 权限、隔离与留存

- 新增 `usage-statistics:view`、`usage-statistics:export` 两项租户权限，默认仅授予租户管理员。
- Repository 必须经租户上下文和 `infrastructure.ResolveDB` 获取连接；所有事实表查询强制带 `tenant_id`。
- 成员或应用删除后，历史统计继续保留，通过快照名称或“已删除成员/应用”展示，不因关联变化丢失历史。
- 原始事件建议保留 180 天；日事实与导出审计按平台数据治理策略长期保留。导出文件设置可配置过期时间。
- `usage_events`、聚合任务、导出和重算的写操作都需记录业务审计；但审计日志不能反向充当统计来源。

## 9. 分期实施

1. **统计底座**：迁移、域骨架、权限、出站事件、Worker、事件幂等和任务监控。
2. **资源与登录**：资源日快照、`login_logs` 回填与登录日事实，先满足资源用量和登录数据页。
3. **成员活跃**：应用访问及数据创建/修改/删除/导出事件，完成成员与管理员活跃趋势、明细与筛选。
4. **业务资产扩展**：表单、流程、仪表盘、集成等模块上线时各自发出稳定统计事件，严禁由前端补记。
5. **效益与导出**：效益规则配置、日事实、异步导出、数据重算与运营监控。

## 10. 与当前实现的关系

当前仓库已具备应用、成员、文件配额、审计和登录日志能力；其中 `login_logs` 含本次会话的租户与成员快照，可用于登录统计回填，租户套餐配额可提供成员、应用、存储等部分资源数据。当前尚未存在活跃事件、统计事实表、聚合 Worker、使用统计 API 或导出任务模型，因此“使用统计”前端接入真实数据前必须先建设本方案中的后端读模型。
