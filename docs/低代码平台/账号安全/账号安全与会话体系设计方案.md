# 账号安全与会话体系设计方案（ADR-009）

> 来源：2026-08-25 账号安全能力评审。目标：为前端 `AccountSecurityPanel.vue`
> 的「登录二次验证」「禁止同时登录」两个开关提供可落地的后端能力。
> 状态：已落地；集成测试收口项见任务清单第 6 步。

## 结论

这两个开关不能只在 `accounts` 增加两个布尔字段。现有后端能「全账号失效旧
JWT」（`session_version`，密码变更场景）和「登出吊销单枚 JWT」（`jti` 黑名
单），但没有「某次设备登录」的服务端会话实体，所以无法可靠做到新登录立即
挤掉旧登录。

## 现状要点

- 页面开关目前是禁用占位：`apps/evolyn-web/apps/web/src/components/dashboard/account/AccountSecurityPanel.vue`。
- JWT 固定有效期 7 天，仅含账号、成员、租户、`sessionVersion` 与 `jti`
  （`apps/evolyn-core/internal/platform/auth/jwt.go`）。
- `session_version` 适合密码变更后让该账号所有令牌失效，但不能区分「当前
  设备」和「其他设备」（迁移 `000015_account_session_version`）。
- 登录日志只记录成功登录，不是可校验、可撤销的会话（迁移 `000013_login_log`）。
- 前端把 Bearer JWT 存在 `localStorage/sessionStorage`，这是本次安全能力
  上线前应一并处理的风险项；OWASP 明确不建议把 JWT 放在 Web Storage。
  参考 [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)。

## 产品定义

- 「登录二次验证」一期采用 **密码 + TOTP 验证器**（Google/Microsoft
  Authenticator 等），不要把「短信验证码登录后再发一次短信」称为 MFA；
  相同类别的验证证据不构成真正的多因素认证。
- 已启用二次验证的账号，密码、OAuth、短信等所有登录入口都必须经过第二步，
  避免 OAuth/SMS 成为绕过路径。
- 短信登录与真正 MFA 有冲突：若用户开启 MFA，应要求先设置密码，再使用
  「密码 + TOTP」；否则它仍是无密码登录，而非严格 MFA。
- 「禁止同时登录」定义为：开启后，新登录成功立即撤销该账号其他活跃会话；
  租户切换只是同一次会话内换发令牌，不算新的登录。
- 修改密码、换绑手机、启用/停用 MFA、使用恢复码等高风险操作，均要求近期
  重新验证；其中密码、手机号和 MFA 变更应撤销其他会话。OWASP 也建议 MFA
  因子变更必须重新验证现有因子，而不能只信任当前登录态。
  参考 [OWASP MFA](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html)。

## 数据模型（全部平台级，归属 account_id，不放租户成员 users）

| 表 | 核心字段 | 用途 |
|---|---|---|
| `account_security_settings` | `account_id PK`、`mfa_enabled`、`single_session_enabled`、`updated_at` | 两个开关的账号级配置 |
| `account_mfa_factors` | `id`、`account_id`、`type=totp`、`secret_ciphertext`、`key_version`、`verified_at`、`last_used_counter`、`disabled_at` | 已验证的 TOTP 因子；密钥仅加密保存，绝不明文或出网 |
| `account_mfa_recovery_codes` | `id`、`account_id`、`code_digest`、`used_at` | 一次性恢复码，只保存摘要，明文只在创建时展示一次 |
| `account_sessions` | `id/session_id`、`account_id`、`token_version`、`auth_method`、`mfa_method`、`created_at`、`last_seen_at`、`expires_at`、`revoked_at`、`revoke_reason`、`ip`、`location`、`user_agent` | 可查询、可撤销、可判断并发登录的逻辑会话 |
| `account_security_events`（建议） | `account_id`、`event_type`、`session_id`、`request_id`、`ip`、`metadata`、`created_at` | MFA 开关、恢复码、会话挤出等安全流水；不污染现有成功登录日志语义 |

并发控制不能只靠「先查再写」。登录创建会话时应在数据库事务内锁住账号行：
读取账号安全设置 → 若禁止并发则撤销其余活跃会话 → 创建新会话 → 提交。
这样两个并发登录最终只会留下后提交的一次会话。

## 后端流程

1. 登录第一步验证密码/OAuth/短信身份，但不立刻签发 JWT。
2. 若未启用 MFA：创建 `account_sessions` 记录后签发 JWT。
3. 若启用 MFA：返回 5 分钟、单次使用、限次数的 `mfaChallenge`；挑战状态放
   Redis，不落长期数据库。
4. `POST /auth/mfa/verify` 校验 TOTP 或恢复码，原子消费挑战和验证码，再创建
   会话、签发 JWT。
5. JWT 新增 `sid` 与 `sessionTokenVersion`；认证中间件除校验签名、账号
   `session_version` 外，还必须校验 `account_sessions` 是否未撤销且版本一致。
6. 退出登录撤销当前 `sid`；禁止同时登录导致的旧会话在下一个请求返回稳定码
   `AUTH_SESSION_REPLACED`。
7. 租户切换复用同一个 `sid`，只递增该会话的 `token_version` 后重签，避免被
   误判为第二台设备。

## 接口

- `GET /accounts/me/security`：读取开关、TOTP 状态、恢复码余量、当前会话摘要。
- `POST /accounts/me/security/reauth`：密码或已绑定因子的近期重新验证，返回
  短期 `reauthToken`。
- `POST /accounts/me/security/mfa/totp/enroll`：创建待确认的 TOTP 二维码。
- `POST /accounts/me/security/mfa/totp/confirm`：验证首个 TOTP，落库并一次性
  返回恢复码。
- `DELETE /accounts/me/security/mfa/totp`：重新验证后关闭。
- `PUT /accounts/me/security/single-session`：重新验证后开关「禁止同时登录」；
  开启时立即撤销其他会话。
- `GET /accounts/me/sessions`、`DELETE /accounts/me/sessions/:id`：同期提供，
  便于用户查看并踢出异常设备。

## 落地顺序

1. 新增 `000019_account_security_and_sessions` 迁移、对应 GORM 模型与仓储；
   同步 `scripts/db.sql`。
2. 在认证域新建 `security` 子域（controller → service → repository），并通过
   窄接口接入现有账号控制器；不把认证逻辑塞进 IAM 账号服务。
3. 改造 JWT 与认证中间件，增加 `sid`、会话版本校验；登录、注册、OAuth、
   短信、租户切换统一走会话签发器。
4. 实现 TOTP 注册、挑战校验、恢复码、重新验证及错误码；TOTP 密钥的加密
   主密钥必须由生产环境配置注入并支持轮换。
5. 实现单会话事务锁与会话撤销；保留现有 `session_version` 用于密码重置等
   「全账号失效」。
6. 前端解除两个禁用开关，补 MFA 安装/确认、恢复码确认页和「被新登录挤出」
   的统一跳转。
7. 将 Bearer JWT 从 Web Storage 迁到短期访问令牌 + `HttpOnly; Secure;
   SameSite` 刷新 Cookie，或采用 BFF；**与 MFA 解耦为独立批次**（评审补充：
   工程量大，不捆绑上线）。
8. 补齐登录并发、TOTP 重放、挑战过期、OAuth/SMS 绕过、切换租户、密码/手机
   号变更撤销会话等集成测试。

## 评审补充（2026-08-25）

- `account_sessions` 随登录增长，需配清理策略（过期/撤销会话的定期归档删除）。
- TOTP 适合作为一期兼容方案；后续可增加 WebAuthn/Passkey 作为更抗钓鱼的
  因子。NIST 指出手工输入 OTP 不具备抗钓鱼性，而 WebAuthn 可通过站点绑定
  提供该能力。参考 [NIST SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html)。
