流程引擎阶段开发功能设计文档

> 项目：evolyn-group
> 后端：`apps/evolyn-core`
> 技术定位：面向企业级低代码表单与审批场景的 Go 原生流程引擎
> 架构原则：模块化单体优先、领域隔离、未来可拆独立服务
> 文档版本：v1.0
> 日期：2026-08-29

---

## 1. 建设目标

在 `apps/evolyn-core` 内建设 `Evolyn Workflow Engine`，为低代码平台提供流程定义、流程运行、人工任务、审批路由、表单联动、条件表达式、超时任务、操作历史和事件扩展能力。

本项目不以实现完整 BPMN/Flowable 替代品为目标，而是建设一套：

- Go 原生；
- 与 Evolyn 租户、组织、IAM、表单、数据引擎深度集成；
- 适合审批流、业务流、低代码自动化；
- 可持续演进到并行、子流程、服务任务等复杂能力；
- 未来可以从 `evolyn-core` 平滑拆分为独立 Workflow Service；

的轻量企业级工作流引擎。

## 2. 总体技术栈

| 能力              | 技术选型                           |
| ----------------- | ---------------------------------- |
| 后端语言          | Go 1.25+                           |
| Web Framework     | Gin                                |
| 数据库            | PostgreSQL                         |
| PostgreSQL Driver | pgx                                |
| 动态节点配置      | PostgreSQL JSONB                   |
| 流程 Runtime      | Go 自研                            |
| Task Engine       | Go 自研                            |
| 流程定义          | Evolyn Workflow DSL / JSON         |
| 前端流程设计器    | LogicFlow                          |
| 表达式引擎        | Expr                               |
| 缓存              | Redis                              |
| 延时/异步任务     | Asynq                              |
| 数据事务          | pgx Transaction                    |
| 并发控制          | PostgreSQL `SELECT ... FOR UPDATE` |
| 事件可靠投递      | Transactional Outbox               |
| API               | REST + OpenAPI                     |
| 日志              | Go slog / 项目现有日志体系         |
| 可观测性          | Prometheus / OpenTelemetry（后续） |

### 2.1 核心原则

1. PostgreSQL 是 Workflow 状态的唯一可信数据源。
2. Redis/Asynq 只负责异步、延时、提醒和重试，不保存核心流程状态。
3. Workflow Runtime 与 Task Engine 分离。
4. 流程引擎不直接操作具体低代码业务表，通过 Provider 接口访问表单数据、组织、IAM、通知和插件。
5. 流程定义发布后必须版本冻结，运行实例固定绑定 Definition Version。
6. Runtime 模型参考 Flowable 的 Definition / Instance / Execution / Task 思想，但不复制 Flowable `ACT_*` 表结构。
7. 第一阶段不追求完整 BPMN 兼容。

## 5. 核心领域模型

### 5.1 模型关系

```text
wf_definition
      │
      ▼
wf_definition_version
      │
      ├──────────────┐
      ▼              ▼
   wf_node         wf_edge

wf_instance
      │
      ├──────────────┐
      ▼              ▼
wf_execution    wf_node_instance
                       │
                       ▼
                    wf_task
                       │
                       ▼
                 wf_task_actor

wf_instance
      ├── wf_variable
      ├── wf_operation
      └── wf_job
```

### 5.2 核心概念

- **Definition**：逻辑流程，例如“报销审批”。
- **Definition Version**：某次发布后的不可变执行版本。
- **Node**：设计时节点。
- **Edge**：设计时连线及条件。
- **Instance**：某条业务数据发起的一次流程。
- **Execution**：流程运行路径，为并行、分支、子流程演进提供基础。
- **NodeInstance**：某个 Node 在某次流程中的一次实际运行。
- **Task**：具体用户待办。
- **TaskActor**：任务审批人、候选人、会签参与人。
- **Variable**：流程变量。
- **Operation**：不可变操作记录。
- **Job**：超时、提醒、异步任务等持久化任务描述。

必须坚持：

```text
Node != NodeInstance != Task
```

例如一个三人会签审批节点，应为：1 个 NodeInstance + 3 个 Task。

# 6. 分阶段开发规划

## Phase 0：基础设计与骨架

### 目标

完成 Workflow Engine 的技术基线，暂不实现完整审批业务。

### 功能

- 建立 `internal/workflow` 模块；
- 定义核心 Domain Model；
- Repository 接口；
- Provider 接口；
- Workflow DSL v1；
- NodeExecutor SPI；
- Runtime Context；
- 统一 Workflow Error Code；
- PostgreSQL Migration；
- 多租户字段规范；
- Workflow API 路由骨架；
- 单元测试基础设施。

### 首批数据库表

```text
wf_definition
wf_definition_version
wf_node
wf_edge
wf_instance
wf_execution
wf_node_instance
wf_task
wf_task_actor
wf_variable
wf_operation
wf_job
```

### Definition Version 规则

- 草稿允许修改；
- 发布生成新版本；
- 发布版本不可直接修改；
- Instance 必须保存 `definition_version_id`；
- 修改流程不会影响已经运行的实例。

### 验收标准

- migration 可重复执行；
- Workflow 模块不反向依赖 HTTP Handler；
- Domain 层不依赖 Gin/pgx/Redis；
- 可以创建、保存、发布一个空流程定义；
- 可以查询流程版本。

## Phase 1：最小可运行 Workflow Runtime

### 目标

实现最简单的：

```text
开始 → 人工审批 → 结束
```

### 节点

- StartNode
- ApprovalNode
- EndNode

### Runtime 能力

```text
StartWorkflow
    ↓
Create Instance
    ↓
Create Root Execution
    ↓
Create Start NodeInstance
    ↓
StartExecutor
    ↓
Navigator
    ↓
ApprovalExecutor
    ↓
Create Task
    ↓
WAIT
```

审批后：

```text
ApproveTask
    ↓
Complete Task
    ↓
Complete NodeInstance
    ↓
Resume Execution
    ↓
EndExecutor
    ↓
Complete Instance
```

### Task 状态

建议至少：

```text
PENDING
APPROVED
REJECTED
CANCELLED
```

### Instance 状态

```text
RUNNING
COMPLETED
REJECTED
CANCELLED
TERMINATED
```

### 并发控制

审批必须使用 PostgreSQL Transaction + `SELECT ... FOR UPDATE`。

### API

```text
POST /api/workflows/definitions
POST /api/workflows/definitions/{id}/publish
POST /api/workflows/{definitionId}/start
GET  /api/workflows/instances/{id}
GET  /api/workflows/tasks/todo
GET  /api/workflows/tasks/done
GET  /api/workflows/tasks/{id}
POST /api/workflows/tasks/{id}/approve
```

### 验收标准

可以完成：

```text
用户发起 → A审批 → 流程结束
```

并保证重复点击审批不会导致流程推进两次。

## Phase 2：低代码表单深度集成

### 目标

让 Workflow Engine 正式成为 Form Engine 的流程能力。

### BusinessDataProvider

```go
type BusinessDataProvider interface {
    GetData(ctx context.Context, ref BusinessRef) (map[string]any, error)
    UpdateData(ctx context.Context, ref BusinessRef, values map[string]any) error
}
```

### Workflow Instance 业务引用

Instance 保存：

```text
business_type
app_id
form_id
data_id
```

流程引擎不关心表单底层采用物理表、JSONB 还是其他存储模型。

### WorkflowContext

```text
tenant
starter
form
variables
```

表达式能够访问：

```text
form.amount
form.department_id
form.project_manager
starter.id
starter.department_id
variables.xxx
```

### 审批页面数据聚合

增加：

```text
GET /api/workflows/tasks/{taskId}/context
```

统一返回：

```text
Task
Instance
FormSchema
FormData
FieldPermission
AvailableActions
WorkflowHistory
```

### 字段权限

审批节点支持：

```text
EDITABLE
READONLY
HIDDEN
REQUIRED
```

字段权限属于 Node Config，而不是直接写死在 Form Schema。

### 审批并保存表单

```text
POST /api/workflows/tasks/{taskId}/approve
```

允许同时提交：

```json
{
  "comment": "同意",
  "formData": {
    "cost_center": "CC001"
  }
}
```

在同一数据库部署阶段，尽量使用同一 PostgreSQL Transaction 完成表单更新和流程推进。

### 验收标准

完成：

```text
填写低代码表单
       ↓
提交并发起流程
       ↓
审批人打开待办
       ↓
按节点权限查看/修改字段
       ↓
审批
       ↓
保存表单数据
       ↓
推进流程
```

## Phase 3：条件路由与动态审批人

### 目标

支持真正可配置的企业审批流程。

### Expr 表达式引擎

增加 `expression.Engine`：

```text
Compile
Validate
EvalBool
EvalAny
```

发布流程时应提前 Compile/Validate 表达式，而不是运行时才发现语法错误。

### ConditionNode

例如：

```text
form.amount <= 5000
form.amount > 5000 && form.amount <= 50000
form.amount > 50000
```

支持：

```text
条件边
默认边
优先级
```

### Assignment Engine

定义统一：

```text
AssigneeResolver
```

第一批 Resolver：

- 指定用户；
- 指定角色；
- 部门负责人；
- 发起人直属主管；
- 表单成员字段；
- Expr 动态表达式。

### Provider

Workflow 不直接查询组织表，而通过：

```text
OrganizationProvider
IdentityProvider
```

### 验收场景

```text
金额 <= 5000
    ↓
部门主管

金额 5000~50000
    ↓
部门主管 → 财务

金额 > 50000
    ↓
部门主管 → 财务 → 总经理
```

## Phase 4：完整人工审批 Task Engine

### 目标

建立可用于企业审批中心的 Task Engine。

### 审批模式

支持：

```text
SINGLE       单人审批
OR_SIGN      或签
COUNTERSIGN  会签

```

### 会签规则

支持：

- 全部通过；
- 指定人数通过；
- 指定比例通过。

例如：

```text
5人会签
通过比例 80%

4人通过后：
NodeInstance → COMPLETED
剩余 Pending Task → CANCELLED
```

### Task Action

```text
APPROVE
REJECT
TRANSFER
DELEGATE
WITHDRAW
CANCEL
```

### 驳回策略

第一版控制范围：

```text
退回发起人
退回上一审批节点
指定可退回节点（后续）
```

### Operation History

`wf_operation` 至少记录：

```text
START
CREATE_TASK
APPROVE
REJECT
TRANSFER
DELEGATE
WITHDRAW
CANCEL_TASK
COMPLETE_NODE
COMPLETE_PROCESS
```

### 验收标准

完成企业常用的：

```text
单审
或签

转办
委派
驳回
撤回
审批意见

```

## Phase 5：抄送、通知、超时与 Asynq

### 目标

补齐流程运行外围能力，同时保证核心 Runtime 不依赖异步队列才能正确运行。

### CCNode

支持：

- 指定用户；
- 角色；
- 部门负责人；
- 表单成员字段；
- 动态 Resolver。

### Asynq 任务类型

建议：

```text
wf:task:timeout
wf:task:reminder
wf:service:execute
wf:webhook:retry
wf:timer:fire
```

### 审批超时

节点可配置：

```text
超时提醒
重复提醒
超时自动通过
超时自动拒绝
超时转交管理员
```

自动审批/拒绝必须仍然通过 Task Engine 正常执行，不能由 Worker 直接改数据库状态。

### NotificationProvider

Workflow 只产生通知意图：

```text
TASK_CREATED
TASK_APPROVED
TASK_REJECTED
PROCESS_COMPLETED
PROCESS_REJECTED
```

具体站内信、邮件、企业微信等由通知领域处理。

### 验收标准

Redis/Asynq 临时不可用时，不破坏已经提交成功的流程状态；恢复后可以重建/重试相关异步任务。

## Phase 6：Domain Event + Transactional Outbox

### 目标

为通知、插件、Webhook、审计和未来微服务化建立可靠事件边界。

### Outbox

增加通用或 Workflow 专用 Outbox：

```text
domain_outbox
```

事务：

```text
BEGIN

更新 wf_task
更新 wf_node_instance
推进 wf_execution
写 wf_operation
写 domain_outbox

COMMIT
```

### 事件

建议：

```text
workflow.process.started
workflow.task.created
workflow.task.approved
workflow.task.rejected
workflow.node.completed
workflow.process.completed
workflow.process.rejected
```

### 消费方

```text
Notification
Audit
Plugin
Webhook
Statistics
```

### 原则

通知失败、Webhook 失败、插件失败不得回滚已经完成的人工审批事务。

### 目标

流程从“人工审批引擎”升级为“业务流程自动化引擎”。

### ServiceNode

第一批建议：

```text
HTTP Request
Update Form Data

```

### 执行模式

```text
同步 ServiceTask

```

```text

```

### 表单动作

例如：

```text

   ↓

   ↓

   ↓
```

### 安全要求

Service Task 必须限制：

- 内网地址访问；
- Secret 管理；
- Header 脱敏；
- 超时时间；
- 响应体大小；
- 重试次数。

## Phase 8：并行执行模型

### 目标

真正启用前期预留的 `wf_execution` 执行树模型。

### 支持

```text
Parallel Split
Parallel Join
```

例如：

```text
           ┌→ 财务审批 ─┐
开始 → 并行             ├→ 汇聚 → 结束
           └→ 法务审批 ─┘
```

### Execution Tree

```text
Root Execution
├── Execution A → 财务
└── Execution B → 法务
```

Join 节点等待符合条件的 Execution 全部到达后，仅允许推进一次。

### 并发重点

必须解决：

- 两个分支同时完成；
- Join 重复触发；
- Instance 被重复推进；
- 分支取消；
- 分支失败恢复。

这里继续以 PostgreSQL 行锁/事务作为核心并发机制。

## Phase 10：可观测性、治理与独立服务评估

### 目标

在流程规模真正增长后再判断是否拆服务。

### 指标

建议监控：

```text
运行流程实例数
每日新建实例数
Pending Task 数
平均审批时长
节点平均停留时长
Asynq Pending/Retry 数
ServiceTask 失败率
Workflow Runtime Error Rate
数据库锁等待
Outbox Lag
```

### 是否拆 Workflow Service 的判断条件

出现以下情况再评估：

- Workflow 发布周期明显独立；
- 流程 Worker 需要独立扩容；
- ServiceTask/Timer 数量巨大；
- 跨应用/跨系统流程成为主要场景；
- Workflow 数据量需要独立数据库；
- Runtime 资源占用影响 `evolyn-core` 其他 API；
- 团队已经可以承担分布式事务和服务治理成本。

### 未来形态

```text
API Gateway
     │
     ├── evolyn-core
     │
     └── evolyn-workflow
             │
             ├── workflow-api
             └── workflow-worker
```

由于第一阶段已经通过 Provider/Repository/Domain 隔离，拆分应主要改变基础设施适配层，而不是重写 Runtime。

# 9. 流程与低代码表单交互规范

## 9.1 职责边界

```text
Form Engine
├── Schema
├── Data
├── Validation
└── Base Permission

Workflow Engine
├── State
├── Routing
├── Task
├── Approval
└── Node Field Permission
```

两者通过：

```text
BusinessDataProvider
WorkflowContext
FieldPermission
WorkflowEvent
```

连接。

## 9.2 发起

```text
保存表单数据
      ↓
StartWorkflow
      ↓
绑定 app_id/form_id/data_id
      ↓
读取表单上下文
      ↓
Runtime
```

## 9.3 审批

```text
Task Context API
      ↓
Schema + Data + FieldPermission
      ↓
表单渲染器
      ↓
用户修改允许编辑字段
      ↓
Approve
      ↓
同一事务保存数据并推进流程
```

## 9.4 流程状态

业务数据可以冗余：

```text
process_instance_id
process_status
```

用于快速查询，但流程真实状态必须以：

```text
wf_instance
wf_node_instance
wf_task
```

为准。

# 11. 安全要求

- 所有 Workflow 表必须进行 Tenant Scope 校验；
- 不允许仅凭 Task ID 操作任务；
- 每次 Task Action 都重新校验 Actor；
- 表单修改必须校验节点 FieldPermission；
- Expr 环境仅暴露白名单数据/函数；
- 不允许表达式执行任意 Go 方法；
- Operation Log 不允许业务侧直接修改；
- ServiceTask Secret 不进入普通 JSON Config 明文；
- Webhook/HTTP 节点需要 SSRF 防护；
- 管理员流程干预必须进入审计日志。

# 13. V1 里程碑建议

### Milestone A：Workflow Core

对应 Phase 0 ~ Phase 1。

# 14. 最终架构定位

Evolyn Workflow Engine 不应被定义成：

> Go 版 Flowable

而应该定义为：

> **面向 Evolyn 企业级低代码平台的 Go 原生流程与审批引擎。**

其核心架构为：

```text
Workflow Engine
│
├── Definition Engine
├── Workflow Runtime
├── Task Engine
├── Assignment Engine
├── Expression Engine
│      └── Expr
├── Job Engine
│      └── Asynq
├── Event Engine
│      └── Transactional Outbox
└── Provider Layer
       ├── Form/Data
       ├── IAM
       ├── Organization
       ├── Notification
       └── Plugin
```

运行模型参考 Flowable 的成熟领域思想，但数据结构、流程 DSL、组织模型、表单交互和 API 全部围绕 Evolyn 自身低代码平台设计。

当前阶段采用：

```text
apps/evolyn-core
└── internal/workflow
```

模块化单体方式落地。

未来满足独立扩容条件后，再演进为：

```text
services/evolyn-workflow
```

这样可以在不过早引入微服务复杂度的情况下，为 Evolyn 后续流程自动化、跨应用流程、插件节点、并行流程和企业级审批能力保留长期演进空间。
