# 流程引擎阶段开发功能设计v1.1

> 项目：`evolyn-group`
> 后端：`apps/evolyn-core`
> 技术定位：面向企业级低代码表单与审批场景的 Go 原生流程引擎
> 架构模式：模块化单体 + 纯引擎内核 + 平台适配层，未来可独立拆分服务
> 文档版本：V1.1
> 日期：2026-08-29

---

## 1. 文档目的

本文档用于定版 Evolyn Workflow Engine 的 V1 技术架构、领域模型、DSL 协议、状态语义、事务边界、表单交互、组织解析、事件机制、API 规范、数据库迁移规范与阶段开发计划。

V1.1 在 V1.0 基础上完成以下关键修正：

- Workflow 核心从 `internal/workflow` 调整为 `internal/engine/workflow`；
- HTTP、GORM、租户、权限、通知等平台适配放入 `internal/platform/workflow`；
- 事务统一复用仓库现有 `TxManager / ResolveDB`，不新增 pgx Transaction 体系；
- Workflow Engine 内核禁止依赖 Gin、GORM；
- 不新增 `domain_outbox`，Workflow 事件接入既有 Outbox / EventPublisher；
- V1 不引入 Asynq，延时任务先采用 PostgreSQL `wf_job` + Worker 轮询；
- Expr 保留为 V1 表达式引擎；
- LogicFlow 独立排期，不阻塞 V1 Runtime；
- Workflow DSL v1、状态机、幂等、会签规则、Withdraw/Reject 语义提升到 Phase 0 冻结；
- Form 写回必须经过 Form Domain，不允许 Workflow 直接修改 `form_records`；
- Workflow Instance 固定绑定 Workflow Definition Version 与 Form Version / Snapshot；
- API 统一使用 `/api/v1`、现有 Tenant/Auth 中间件、`httpx.BizError` 与 Swagger 中文注解；
- 数据库 Migration 必须遵循仓库现有 up/down、中文注释、`scripts/db.sql` 同步约束。

V1.1 评审补充定版：

- **DSL 单文档存储**：废弃 `wf_node` / `wf_edge` 独立表，Node/Edge 内嵌于 `wf_definition.draft_content`（草稿）与 `wf_definition_version.dsl_snapshot`（发布快照）JSONB，唯一事实源，消除规范化表与快照的双写一致性负担（与表单域 `draft_content` 目标保存协议同构）；
- **草稿乐观锁**：草稿保存走 `draft_revision` 乐观锁（对齐表单域协议），发布生成递增 `version_no`；
- **流程稳定公开标识**：`wf_definition.code` 为路由/API/菜单 target 的稳定公开标识，内部自增 ID 不出网（对齐表单域 `form_code` 迁移 000045 先例）；
- **审批人快照语义**：审批人在任务创建时一次性解析并快照到 `wf_task_actor`，运行中不随组织变化重算；
- **超时自动动作边界**：超时自动通过/拒绝必须调用 Task Engine 正常执行路径（同事务校验），Worker 不得直接改数据库状态；
- **前端错误码对齐**：`wf` 域 errCode 在 `packages/utils/src/request/errorCodes.ts` 对齐维护，前端按 errCode 分支，禁止 message 文本匹配；
- **时间字段规范**：API 时间字段统一 `JSONTime`（秒级「2006-01-02 15:04:05」东八区，`model/JSONTime` 出网统一载体）；
- **落地前同步动作**：AGENTS.md 目录条目、架构文档 ADR 追加、docs README 映射等，见第 33 章。

## 2. 建设目标与非目标

### 2.1 建设目标

在 `apps/evolyn-core` 内建设 `Evolyn Workflow Engine`，支持：

- 流程定义与发布版本；
- 顺序审批流程运行；
- 人工任务 / 待办；
- 条件路由；
- 动态审批人；
- 单人审批、或签、会签；
- 驳回、退回发起人、撤回、转办、抄送；
- 与低代码 Form Domain 双向交互；
- 审批节点字段权限；
- 超时、提醒、延迟任务；
- Workflow Domain Event；
- 操作历史与审计；
- 后续演进到服务任务、并行、子流程的模型基础。

### 2.2 非目标

V1 不建设完整 BPMN/Flowable 替代品，不实现：

- BPMN XML 兼容；
- DMN；
- 任意节点跳转；
- 任意驳回；
- 运行中 Definition Version 迁移；
- Compensation；
- Signal / Message Event；
- Event Subprocess；
- 完整子流程；
- 完整并行网关；
- 分布式微服务事务；
- Redis 作为流程状态事实源。

核心定位：

> **Evolyn Workflow Engine = 面向低代码表单和企业审批场景的 Go 原生流程引擎，而不是 Go 版 Flowable。**

## 3. 总体技术决策

| 能力               | V1.1 定版方案                                                   |
| ------------------ | --------------------------------------------------------------- |
| 后端语言           | Go 1.25+，以仓库实际 `go.mod` 为准                              |
| HTTP               | Gin，限平台适配层使用                                           |
| ORM / 数据访问     | 沿用现有 GORM / Repository 体系                                 |
| 数据库             | PostgreSQL                                                      |
| 事务               | 现有 `TxManager / ResolveDB`                                    |
| 并发控制           | GORM `clause.Locking{Strength: "UPDATE"}` / PostgreSQL Row Lock |
| 批量 Worker 竞争   | `FOR UPDATE SKIP LOCKED`                                        |
| Runtime            | Go 自研                                                         |
| Task Engine        | Go 自研                                                         |
| Workflow DSL       | Evolyn Workflow DSL v1 / JSON                                   |
| 动态配置           | PostgreSQL JSONB                                                |
| 表达式             | `expr-lang/expr`                                                |
| 延时任务           | V1：`wf_job` + DB Worker                                        |
| Asynq              | V1 不引入，后续按吞吐需求评估                                   |
| Redis              | 可用于已有缓存能力，但不是流程状态源                            |
| Domain Event       | 接入既有 EventPublisher / Outbox                                |
| 新建 domain_outbox | 不允许                                                          |
| 前端流程设计器     | LogicFlow，独立里程碑                                           |
| 组织/IAM           | 复用现有 IAM / Department / Role / User                         |
| 表单交互           | Provider + Form Domain Adapter                                  |
| 错误模型           | `httpx.BizError`                                                |
| API                | `/api/v1/...` + 现有 Tenant/Auth 链                             |
| API 文档           | Swagger 中文注解                                                |

### 3.1 七条核心架构原则

1. PostgreSQL 是 Workflow Runtime 状态的唯一事实源。
2. Workflow Engine 内核不得依赖 Gin、GORM、HTTP、具体 IAM/Form Repository。
3. 所有事务必须通过仓库现有 TxManager 统一建立，禁止第二套事务边界。
4. Workflow 不直接更新低代码 Form 数据，必须经 Form Domain 完成校验与写回。
5. Workflow Definition 发布后版本冻结；运行实例必须绑定固定 Definition Version。
6. Form 数据在流程运行期间绑定固定 Form Version / Schema Snapshot。
7. 外部副作用通过既有 Outbox / EventPublisher 异步处理，人工审批事务不因通知失败回滚。

## 6. 核心领域模型

### 6.1 模型关系

```text
wf_definition（draft_content JSONB，草稿）
      │ 发布（DSL 整体冻结，version_no 递增）
      ▼
wf_definition_version（dsl_snapshot JSONB，不可变快照）

wf_instance
      │
      ├──────────────┐
      ▼              ▼
wf_execution    wf_node_instance
                       │
                       ▼
                    wf_task
                       │
                       ▼
                 wf_task_actor

wf_instance
      ├── wf_variable
      ├── wf_operation
      └── wf_job
```

> v1.1 补充定版：**不建 `wf_node` / `wf_edge` 独立表**。Node/Edge 是 DSL 文档内的结构，设计时整体存于 `draft_content`，发布时整体冻结进 `dsl_snapshot`；运行时 Navigator 按 node key 从快照读取 config。规范化拆表会引入「发布事务双写」一致性负担，而 V1 运行时没有跨实例按节点维度查询的需求，JSONB 单文档即可满足。

### 6.2 核心概念

- `Definition`：逻辑流程，例如“报销审批”。
- `DefinitionVersion`：一次发布后冻结的可执行版本。
- `Node`：设计态节点。
- `Edge`：设计态连线和路由条件。
- `Instance`：业务数据的一次流程执行。
- `Execution`：运行路径，为并行、子流程预留。
- `NodeInstance`：某个设计态 Node 在一次 Instance 中的一次实际运行。
- `Task`：面向用户的人工待办。
- `TaskActor`：审批人、候选人、会签参与人。
- `Variable`：流程上下文变量。
- `Operation`：不可变业务操作记录。
- `Job`：超时、提醒、延迟执行的持久化调度记录。

必须坚持：

```text
Node ≠ NodeInstance ≠ Task
```

例如三人会签：

```text
1 Approval Node
      ↓
1 NodeInstance
      ↓
├── Task A
├── Task B
└── Task C
```

## 7. Workflow DSL v1

DSL v1 是 Phase 0 必须冻结的核心协议，LogicFlow 只是其可视化编辑器，不是 Runtime 领域事实源。

### 7.1 顶层结构

```json
{
  "schemaVersion": "1.0",
  "nodes": [],
  "edges": [],
  "settings": {}
}
```

### 7.2 Node 基础结构

```json
{
  "key": "manager_approval",
  "type": "approval",
  "name": "部门负责人审批",
  "config": {}
}
```

V1 Node Type：

```text
start
approval
condition
cc
service
end
```

其中 `service` 节点的数据模型可先定义，执行能力延后到 Phase 7。

### 7.3 Edge

```json
{
  "key": "edge_001",
  "source": "condition_001",
  "target": "finance_approval",
  "condition": {
    "expression": "form.amount > 10000"
  }
}
```

普通 Edge 的 `condition` 允许为空；条件节点出边必须有明确条件或 default 分支。

### 7.4 Approval Config

```json
{
  "approvalMode": "single",
  "assignee": {
    "type": "department_manager"
  },
  "rejectStrategy": "terminate",
  "formPermissions": {
    "amount": "readonly",
    "finance_code": "editable",
    "remark": "editable"
  }
}
```

字段权限 V1：

```text
hidden
readonly
editable
required
```

### 7.5 DSL 严格校验

发布 Definition Version 前必须完成：

- schemaVersion 校验；
- Node key 唯一；
- Edge key 唯一；
- source / target 必须存在；
- 必须且只能存在一个 start；
- 至少存在一个 end；
- start 不允许入边；
- end 不允许出边；
- approval config 必填项校验；
- condition 出边表达式校验；
- Expr 预编译；
- Assignee Resolver 类型校验；
- 不允许 V1 不支持的 node type；
- 图可达性与死节点检查；
- 不允许直接形成未支持语义的环。

DSL 是前后端共同协议，字段命名必须逐字一致。

## 8. Definition 与 Form 双版本冻结

### 8.1 Workflow Definition Version

```text
wf_definition（含可编辑草稿 draft_content + draft_revision 乐观锁）
   ↓ 发布：DSL 严格校验 + Expr 预编译通过后整体冻结
wf_definition_version v1（version_no = 1）
wf_definition_version v2（version_no = 2）
wf_definition_version v3（version_no = 3）
```

- 草稿保存走 `draft_revision` 乐观锁（与表单域 `draft_revision` 协议一致），并发保存冲突返回稳定 BizError；
- `wf_definition.code` 为稳定公开标识，路由 / API / 菜单 target 一律用 `code`，内部自增 ID 不出网（对齐表单域 `form_code` 先例）；版本以 `version_no` 标识；
- 每次发布生成新 `DefinitionVersion`，`version_no` 在定义内递增。

发布后：

```text
DefinitionVersion = immutable
```

运行中 Instance 永远不自动升级。

流程删除为软删，仅允许删除无运行中实例的定义；运行态历史（operation / instance）不随设计态删除。

### 8.2 Form Snapshot

`wf_instance` 发起时至少记录：

```text
definition_version_id
business_type
business_id
app_id
form_id
form_version_id / form_snapshot_id
```

流程运行期间始终按照发起时绑定的 Form Version / Snapshot：

- 渲染审批详情；
- 校验审批节点可修改字段；
- 校验字段类型和约束；
- 计算条件表达式。

禁止运行中因管理员重新发布表单而自动切换 Schema。

## 9. 状态机语义

状态语义必须在 Phase 0 冻结，Runtime 代码不得自行解释。

### 9.1 Workflow Instance

```text
DRAFT
RUNNING
COMPLETED
REJECTED
CANCELLED
```

含义：

- `DRAFT`：定义保留，V1 Runtime 可不创建草稿 Instance；
- `RUNNING`：流程进行中，包括等待人工任务或退回发起人修改；
- `COMPLETED`：正常进入 End；
- `REJECTED`：执行终止型驳回；
- `CANCELLED`：发起人撤回或管理员终止。

### 9.2 NodeInstance

建议 V1：

```text
PENDING
RUNNING
WAITING
WAITING_RESUBMIT
COMPLETED
REJECTED
CANCELLED
```

### 9.3 Task

建议 V1：

```text
PENDING
APPROVED
REJECTED
TRANSFERRED
CANCELLED
EXPIRED
```

`TRANSFERRED` 表示原任务被转办后关闭，新任务另建，不直接修改原审批人。

## 10. 审批动作语义

### 10.1 Approve

- 任务必须 `PENDING`；
- 当前用户必须有执行权；
- 表单修改必须通过节点字段权限与 Form Domain 校验；
- 写 `wf_operation`；
- 根据 single / or-sign / countersign 判断 NodeInstance 是否完成；
- 完成后 Runtime 推进下一节点。

### 10.2 Reject

V1 仅支持：

```text
rejectStrategy = terminate
```

效果：

```text
Task -> REJECTED
NodeInstance -> REJECTED
Instance -> REJECTED
其它未完成 Task -> CANCELLED
```

V1 不支持“驳回到任意历史节点”。

### 10.3 ReturnToStarter

用于退回发起人修改，不等价于 `REJECTED`：

```text
Instance = RUNNING
当前 NodeInstance = COMPLETED / RETURNED（实现可由 operation 表达）
新建或激活发起人修改 NodeInstance = WAITING_RESUBMIT
```

发起人重新提交后继续流程。

### 10.4 Withdraw

V1 默认规则：

> 只有流程尚未存在任何“已完成的人工审批 Task”时，发起人才允许撤回。

允许：

```text
提交 → 第一审批节点待办 → Withdraw
```

不允许：

```text
提交 → 主管已同意 → 财务待办 → Withdraw
```

撤回结果：

```text
Instance -> CANCELLED
所有 PENDING Task -> CANCELLED
记录 WITHDRAW operation
```

管理员使用独立 `terminate` 权限，不等价于 Withdraw。

### 10.5 Transfer

- 原 Task 标记 `TRANSFERRED`；
- 创建新的 Task；
- 保留 transfer source / target；
- Task 历史链可追溯；
- NodeInstance 不因 Transfer 自动完成。

### 10.6 CC

CC 不是审批 Task，不参与节点完成判定；可独立保存 `wf_task_actor` 或 operation/event，最终实现以查询模型最简为准。

## 11. 会签 / 或签规则

### 11.1 Single

单任务完成即节点完成。

### 11.2 OR-Sign

任意一名参与人 `APPROVED` 即节点完成，其他 `PENDING` Task 自动 `CANCELLED`。

### 11.3 Countersign

配置：

```json
{
  "approvalMode": "countersign",
  "passRatio": 0.8
}
```

通过人数：

```text
requiredApprovals = ceil(totalActors * passRatio)
```

示例：

```text
4 × 0.5 = 2   → 需要 2 人
5 × 0.5 = 2.5 → ceil = 3 人
```

达到通过阈值后：

- NodeInstance -> COMPLETED；
- 剩余 `PENDING` Task -> CANCELLED；
- Runtime 仅允许推进一次。

V1 可先采用“任何一人 Reject 即整个会签终止”，若未来需要拒绝比例，则新增明确策略，不在 V1 隐式扩展。

## 12. Workflow Runtime

### 12.1 NodeExecutor

```go
type NodeExecutor interface {
    Type() NodeType
    Execute(ctx context.Context, input ExecuteInput) (ExecuteResult, error)
}
```

Executor 不依赖 Gin/GORM。

V1：

```text

EndExecutor
```


### 12.2 Runtime 推进原则

```text
StartWorkflow
   ↓
Create Instance
   ↓
Create Root Execution
   ↓
Create Start NodeInstance
   ↓
Execute Start
   ↓
Navigator.FindNext
   ↓

```

```text

   ↓
```

```text
   ↓
Runtime.Resume
   ↓
FindNext
```

## 13. 事务与并发控制

### 13.1 唯一事务事实源

Workflow 不新建 pgx transaction 抽象，所有 Application Transaction 统一由现有：

```text
TxManager
   ↓
transaction context
   ↓
ResolveDB(ctx)
   ↓
GORM Repository Adapter
```

Engine 内核仅通过 Repository Interface 感知原子操作，不感知 GORM。

### 13.2 Approve 事务模板

```text
BEGIN

1. SELECT wf_task FOR UPDATE
2. 校验 task = PENDING
3. 校验当前 actor
4. 校验 instance = RUNNING
5. 校验字段权限
6. 经 Form Domain 更新业务数据
7. 更新 wf_task
8. 写 wf_operation
9. 判断 NodeInstance 是否完成
10. 更新 NodeInstance / Execution
11. 创建下一 NodeInstance / Task
12. EventPublisher.PublishInTx(...)

COMMIT
```

GORM 实现：

```go
db.Clauses(clause.Locking{Strength: "UPDATE"})
```

### 13.3 禁止事项

禁止：

- GORM Transaction + pgx Transaction 两套并存；
- 用 Redis Lock 代替数据库行锁维护核心流程状态；
- Task 先更新、Runtime 后异步推进；
- 通知发送失败导致审批事务回滚。

## 14. StartWorkflow 幂等

需要两层幂等。

### 14.1 业务实例唯一性

同一：


同一时间最多一个 `RUNNING` Instance。

PostgreSQL 建议部分唯一索引：

```sql
CREATE UNIQUE INDEX ...
```


### 14.2 请求幂等

Start API 支持 `idempotency_key`，解决：

- 双击提交；
- HTTP Timeout 重试；
- 客户端重复发送。

业务唯一性与请求幂等不可互相替代。

## 17. Assignment Engine

### 17.1 Resolver Contract

```go
type AssigneeResolver interface {
    Type() string
    Resolve(ctx context.Context, input ResolveInput) ([]Actor, error)
}
```

### 17.2 V1 Capability Matrix

| Resolver       |          V1 | 前置能力                      |
| -------------- | ----------: | ----------------------------- |
| 指定用户       |          是 | IAM User                      |
| 指定角色       |          是 | IAM Role / Membership         |
| 表单用户字段   |          是 | Form user field               |
| 部门成员       |        可选 | Department membership         |
| 部门负责人     |    条件开放 | IAM 必须有明确 leader 语义    |
| 发起人直属主管 |    条件开放 | IAM 必须有 reporting relation |
| Expr 动态结果  | V1.1 可后置 | Expr + 用户结果校验           |

原则：

> IAM 不存在的组织语义，Workflow 不得自行猜测或私建第二套组织模型。

如 Department 尚无负责人字段，应先补 IAM 前置能力，再开放 `department_manager` Resolver。

补充语义（v1.1）：

- **审批人快照**：Resolver 在任务创建时一次性解析，结果快照写入 `wf_task_actor`；流程运行中不随组织变化重算，保证在途实例行为可预期；
- 人员离职 / 调岗导致的僵死任务，由管理员干预能力兜底（Phase 10 后评估，Phase 4 先提供 Transfer 手工转移通道）；
- Resolver 解析不到任何审批人时，返回稳定 BizError（`WORKFLOW_ASSIGNEE_NOT_FOUND`），并有明确兜底策略（默认转交租户管理员），禁止静默跳过节点。

### Runtime 流程

```text

→ 校验 published version
→ 校验不存在相同 running business instance
→ 创建 Instance
→ 创建 Execution
→ 执行 Start
→ 创建 Approval NodeInstance
→ 创建 Task
```

```text

→ lock Task
→ actor check
→ update Task
→ complete NodeInstance
→ execute End
→ Instance COMPLETED
→ PublishInTx workflow events
```

### DoD

- 双击 Approve 不会推进两次；
- 双击 Start 不会生成两个 Running Instance；
- 任意一步失败全部回滚；
- 通知发送不在人工审批事务中同步执行；
- 具备最小端到端集成测试。

## Phase 3：Form + Expr + Dynamic Assignment

### 目标

让 Workflow 真正成为低代码 Form 的审批引擎，而不只是固定用户状态机。

### 功能

#### Form

- BusinessDataProvider Adapter；
- 读取 Form Snapshot 数据；
- WorkflowContext `form.*`；
- 节点字段权限；
- Approve 时修改允许字段；
- 经 Form Domain 校验；
- Form 修改与 Workflow 推进同事务。

#### Expr

- Expr Engine；
- condition node；
- edge expression；
- default route；
- 发布期预编译；
- 运行期白名单 context。

#### Assignment

- 指定用户；
- 指定角色；
- 表单用户字段；
- 有 IAM 前置能力时加入部门负责人；
- 有 IAM 前置能力时加入发起人直属主管。

### 示例

```text
form.amount <= 10000
→ 部门经理
→ End

form.amount > 10000
→ 部门经理
→ 财务
→ End
```

### DoD

- Workflow 无任何 direct `form_records` SQL；
- Form 修改不符合 snapshot schema 时审批失败并整体回滚；
- Expr 无法调用非白名单能力；
- Resolver 找不到审批人时有稳定 BizError 与明确策略。

## 27. 安全设计

- tenant_id 每次查询必须遵循现有租户隔离体系；
- Engine 不接受客户端直接传入可信 tenant/user 上下文；
- Task 操作必须二次校验 TaskActor；
- Form 修改只能修改节点授权字段；
- Expr 只允许白名单上下文；
- Service Task 必须防 SSRF；
- workflow operation 不允许客户端覆盖系统字段；
- Definition publish 需要独立权限；
- terminate 与普通 withdraw 权限分离；
- 敏感字段不得落普通运行日志。

## 32. 最终架构结论

Evolyn Workflow Engine V1.1 定版为：

```text
Go 1.25+
Gin（Platform Only）
GORM（Repository Adapter Only）
PostgreSQL
Existing TxManager / ResolveDB
PostgreSQL Row Lock
Expr
Existing EventPublisher / Outbox
DB-backed wf_job Worker
LogicFlow（独立前端里程碑）
```

核心代码边界：

```text
internal/engine/workflow
        │
        │ pure Go workflow engine
        ▼
Repository / Provider Interfaces
        ▲
        │ adapters
internal/platform/workflow
        │
        ├── Gin
        ├── GORM
        ├── TxManager
        ├── IAM
        ├── Form Domain
        └── Existing Outbox
```

领域模型继续参考 Flowable 已验证的：

```text
Definition
Version
Instance
Execution
NodeInstance
Task
Variable
```

但物理模型、DSL、Identity、History、Job、API 都按 Evolyn 自身低代码平台需求设计，不复制 Flowable 实现。
