# 管理后台-企业日志开发设计方案

## 1. 目标与范围

企业日志是租户管理员查看本租户成员登录行为和关键操作审计的管理后台模块，入口为 `/tenant/enterprise-logs`。一期交付两个独立页签：

- **登录日志**：记录成员进入当前租户的会话建立事件，用于安全排查和访问追溯。
- **操作日志**：记录租户内的管理与业务变更，用于管理员审计和合规追溯。

日志是追加写、只读的历史流水。企业日志不承载运行时技术日志、链路追踪日志、监控指标，也不替代个人中心的“我的登录日志”。

## 2. 边界与权限

### 2.1 租户边界

所有企业日志接口从 JWT/请求上下文取得当前 `tenantId`，客户端不得传入或切换 `tenantId`。查询、导出、任务状态读取都必须再次校验任务所属租户，确保跨租户不可见。

个人登录日志与企业登录日志使用同一事实表但权限和查询维度不同：

| 场景 | 查询维度 | 权限 | 接口归属 |
| --- | --- | --- | --- |
| 个人中心登录日志 | `account_id` | 当前账号仅可查看自身 | 认证/账号域 |
| 企业登录日志 | `tenant_id`，可按 `member_id` 筛选 | 具备企业日志查看权限的当前租户成员 | 企业日志读取域 |

### 2.2 权限

新增资源权限：

- `enterprise-logs:view`：查看登录日志、操作日志及筛选项。
- `enterprise-logs:export`：创建和下载日志导出任务。

初始授予租户管理员角色。该资源不接受管理组的间接放行；如后续需要委派，应明确增加细粒度的数据范围设计，而不是默认复用管理组全量范围。

## 3. 事件源与数据模型

### 3.1 登录日志

继续使用现有 `login_logs` 表，不复制写入第二份企业登录事件。该表已有：

```text
id, account_id, tenant_id, member_id,
method, client, ip, location, user_agent, request_id, created_at
```

其中 `tenant_id`、`member_id` 是本次会话绑定的上下文快照；`tenant_id=0` 的平台或无租户场景不出现在企业日志中。

为保证成员改名、离职或删除后的历史展示一致，新增如下展示快照：

```text
actor_name_snapshot   varchar(128)  NOT NULL DEFAULT ''
```

前端登录日志展示字段为：登录人、登录时间、登录地、登录平台、IP。`client` 映射为“电脑网页版”“移动网页版”“未知”，而 `method`（密码、验证码、第三方登录等）保留作详情或后续筛选，不混作登录平台。

新增索引：

```sql
CREATE INDEX idx_login_logs_tenant_created
  ON login_logs (tenant_id, created_at DESC, id DESC);

CREATE INDEX idx_login_logs_tenant_member_created
  ON login_logs (tenant_id, member_id, created_at DESC, id DESC);
```

### 3.2 操作日志

继续以现有 `audit_logs` 为唯一业务操作事实源。该表保留 `module`、`action`、`resource_type`、`resource_id` 和 `before_data`/`after_data` 等技术审计字段；企业日志只读取经过受控投影后的展示数据，不将原始快照直接出网。

为支持稳定筛选、历史展示与安全详情，需要在 `audit_logs` 增加：

```text
event_code            varchar(100)  NOT NULL
category_code         varchar(64)   NOT NULL
actor_name_snapshot   varchar(128)  NOT NULL DEFAULT ''
target_name_snapshot  varchar(256)  NOT NULL DEFAULT ''
summary               varchar(1000) NOT NULL DEFAULT ''
```

字段职责：

| 字段 | 用途 |
| --- | --- |
| `event_code` | 稳定机器语义，如 `iam.member.field_visibility_updated`；用于前端按操作类型筛选。 |
| `category_code` | 稳定日志范围，如 `member_management`、`organization`、`role_permission`、`tenant_settings`、`application`。 |
| `actor_name_snapshot` | 操作发生时的成员显示名，避免成员资料变更影响历史。 |
| `target_name_snapshot` | 目标成员、部门、角色、应用等的当时名称。 |
| `summary` | 服务端生成且经过脱敏的“操作详情”，可直接展示与导出。 |

新增索引：

```sql
CREATE INDEX idx_audit_logs_tenant_created
  ON audit_logs (tenant_id, created_at DESC, id DESC);

CREATE INDEX idx_audit_logs_tenant_category_created
  ON audit_logs (tenant_id, category_code, created_at DESC, id DESC);

CREATE INDEX idx_audit_logs_tenant_member_created
  ON audit_logs (tenant_id, member_id, created_at DESC, id DESC);
```

### 3.3 写入与脱敏规则

业务服务提交成功后，仍通过现有 `audit.Recorder` best-effort 写审计；日志写入失败不得影响已成功提交的业务事务。写入侧在调用处提供事件码、分类、目标展示名和语义参数，由审计服务生成 `summary`。

禁止写入或出网密码、短信/邮箱验证码、访问令牌、私钥、完整手机号/邮箱、身份证明、连接串及原始敏感配置。`before_data`、`after_data` 仅作受控内部审计快照，序列化前执行字段白名单与脱敏处理。

## 4. 后端模块设计

新增 `internal/platform/enterpriselog/` 作为只读与导出编排域：

```text
enterpriselog/
  controller/   HTTP 参数解析、身份与权限检查、统一响应
  service/      查询规范化、租户隔离、导出任务编排
  repository/   login_logs 与 audit_logs 的只读查询
  model/        查询条件、受控出参、导出任务模型
```

该域不接管登录日志和审计日志的写入：登录事件仍在 `auth/loginlog`，业务审计仍在 `audit`。这样可避免页面模块反向耦合所有业务写路径。

仓储查询统一按 `(created_at DESC, id DESC)` 稳定排序。普通页面可使用 `page/pageSize`（最大 100）；在日志量或导出量较大时，仓储内部应优先使用时间加 ID 的 keyset/cursor 查询，避免深分页扫描。

## 5. API 契约

### 5.1 查询

```text
GET /api/v1/enterprise-logs/login
GET /api/v1/enterprise-logs/operations
GET /api/v1/enterprise-logs/operation-categories
```

登录日志查询参数：

```text
memberId       可选，当前租户成员 ID
startAt        可选，东八区开始时间
endAt          可选，东八区结束时间
page/pageSize  页码与页大小
```

操作日志在公共参数外支持：

```text
categoryCode   可选，日志范围
eventCode      可选，操作类型
```

开始时间晚于结束时间、成员不属于当前租户、未知事件码/分类均返回稳定 `httpx.BizError` 错误码。时间筛选采用东八区闭区间语义，服务端转换为数据库查询所需的半开区间。

操作日志出参只包括：操作人、发生时间、范围、操作类型、脱敏后的操作详情和 IP；不得输出请求 ID、用户代理、原始快照或内部资源 ID。

### 5.2 导出

```text
POST /api/v1/enterprise-logs/exports
GET  /api/v1/enterprise-logs/exports/:id
```

创建请求携带 `kind=login|operation` 及与列表完全相同的筛选条件。导出任务必须固化提交时的筛选条件、申请人、租户、数据量、状态、文件引用和过期时间。小数据量可同步生成；较大数据量走异步任务。下载时重新检查 `enterprise-logs:export` 与当前租户归属。

导出行为本身应记录为一条操作审计，包含日志类型、筛选时间范围和导出条数，但不记录导出文件中的敏感内容。

## 6. 前端交互对应

页面使用“登录日志 / 操作日志”两个页签，页签各自保存筛选条件、页码和列表状态：

- 登录日志：登录人、登录时间；列为登录人、登录时间、登录地、登录平台、IP。
- 操作日志：日志范围、操作类型、操作人、操作时间；列为操作人、操作时间、操作类型、操作详情、IP。
- 点击“查询”后从第一页重新拉取；切换页签不污染另一页签的条件。
- 表格内容区独立使用 `el-scrollbar` 滚动，筛选区、工具栏与分页保持固定。
- “导出”导出当前页签及当前筛选条件下的全部授权数据，而不是仅当前页。

## 7. 数据库迁移与实施顺序

1. 新建只增版本的 SQL migration：补齐 `login_logs` 与 `audit_logs` 展示字段、索引和中文注释；同步 `scripts/db.sql` 终态快照。
2. 扩展登录记录调用方，在签发绑定租户的会话时写入成员名称快照。
3. 扩展审计 `Entry` 与写入服务，为现有关键业务逐步补齐事件码、分类与安全摘要；未迁移历史记录允许以“历史操作记录”降级展示。
4. 实现 `enterpriselog` 域的 repository、service、controller，注册路由与权限种子；补充跨租户隔离、日期筛选、脱敏和导出授权测试。
5. 新增前端 API 契约与企业日志页面，替换 `/tenant/enterprise-logs` 的规划占位页。
6. 最后接入异步导出、留存策略与文件清理任务。

## 8. 留存策略

日志保留期、可查询的最大时间跨度、单次导出上限和导出文件有效期必须由平台/套餐策略决定，前端只展示服务端返回的限制与错误。清理任务按租户策略执行，清理过程须可审计；不得因为前端分页或筛选而改变原始日志留存。
