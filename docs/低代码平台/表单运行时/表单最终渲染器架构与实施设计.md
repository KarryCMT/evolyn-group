# 表单最终渲染器架构与实施设计

## 1. 文档目的与状态

本文定义灵衍云已发布表单的**最终渲染器**：用户在 Web、移动 Web 及后续原生容器中打开、填写、校验和提交表单时使用的运行时。本文是前端表单运行时的实施基线；实际接口、权限和存储模型落地前，需与后端契约一并评审。

目标优先级如下：

1. 移动端首屏填写体验与输入响应；
2. 一个 Schema、一套规则、一套提交数据，同时复用桌面与移动端；
3. 无 Element Plus、无设计器依赖的轻量运行时；
4. 字段能力可按需扩展，且不破坏已发布表单；
5. 值、规则、权限和服务端校验可审计、可验证。

## 2. 范围与边界

### 2.1 运行时负责的能力

- 读取已发布且已校验的表单 Schema、当前记录值、上下文权限与最小初始化数据；
- 根据 Schema 渲染字段、布局、提示、只读态、必填态和错误态；
- 管理填写值、默认值、显隐/禁用/必填联动、公式和本地校验；
- 通过宿主注入的能力完成成员选择、附件上传、定位、关联数据检索等交互；
- 校验后生成稳定的提交载荷，并通过事件交给页面或业务 API 提交；
- 支持草稿恢复、错误定位、提交中状态和提交结果回显。

### 2.2 明确不负责的能力

- 字段拖拽、素材面板、属性面板、设计草稿、撤销重做与版本编辑；
- 设计器代码编辑、脚本执行、Monaco、拖拽库和设计器接口；
- 直接请求业务 API、读取路由、访问登录 store 或持有租户上下文；
- 服务器端权限判定、最终提交校验、公式可信执行和审计写入；
- 桌面与移动端分别维护两份字段业务逻辑。

运行时只消费“已发布 Schema”。设计器写 Schema，后端校验、版本化并发布 Schema，运行时执行 Schema。

```text
表单设计器 ──写入草稿──► 后端发布服务 ──已发布 Schema──► 最终渲染器
                                      │                    │
                                      └──最终校验/权限───────┘
```

## 3. 总体架构

### 3.1 分层与依赖方向

```text
                 @evolyn.do/form-schema
             纯 TypeScript：类型、迁移、校验、规则 DSL
                     ▲                         ▲
                     │                         │
       @evolyn.do/form-designer       @evolyn.do/form-runtime
       仅设计态依赖 Schema             运行态依赖 Schema
                                              │
                    ┌─────────────────────────┼─────────────────────────┐
                    ▼                         ▼                         ▼
             RuntimeStore                RuleEngine               FieldRegistry
                    │                         │                         │
                    └─────────────────────────┴────────────► FormFieldHost
                                                                    │
                                                    基础字段 / 懒加载重型字段
```

强制依赖规则：

- `form-schema` 不依赖 Vue、组件库、网络或宿主应用；
- `form-runtime` 可以依赖 Vue，但不得依赖设计器包；
- `form-designer` 只依赖 `form-schema`，不得反向引用运行时内部状态；
- 字段组件不得导入具体业务 API；业务能力一律由 runtime adapter 注入；
- 已发布 Schema 中不得出现 Vue 组件、函数、DOM、脚本源码或循环引用。

### 3.2 包与入口规划

当前 `apps/evolyn-web/packages/form` 是共享表单包的基础。实施时应将其导出入口拆分，而不是让最终用户入口加载设计器相关模块：

```text
packages/form/src/
  schema/                 # @evolyn.do/form/schema
  runtime/                # @evolyn.do/form/runtime
    store/
    rules/
    validation/
    renderer/
    adapters/
    widgets/
      base/
      heavy/
  designer/               # @evolyn.do/form/designer，仅管理端按需使用
```

建议对外入口：

```text
@evolyn.do/form/schema
@evolyn.do/form/runtime
@evolyn.do/form/runtime/style.css
@evolyn.do/form/designer
```

`@evolyn.do/form/runtime` 的入口只能静态导入 Vue、Schema、运行时 store、规则引擎和基础字段。富文本、签名、地址地图、附件预览、成员/部门大选择器等必须是动态模块。设计器入口才允许导入拖拽、编辑器及设计态依赖。

## 4. Schema 与发布契约

### 4.1 单一事实来源

> **已被 ADR-010 取代**：本节所述 `FormDocument` 模型已由目标保存协议
> （`content.items[].widget` 两层结构）替换，见第 27 章 ADR-010 与
> `docs/低代码平台/表单设计器/目标协议字段字典.md`。本章其余结论（分层、发布不可变、
> Adapter 边界、性能预算）在目标协议上继续有效，涉及 `FormDocument`/`field.type`
> 的表述按目标协议对应概念（协议文档 / `widget.type`）理解。

当前 `FormDocument` 已定义 `version`、`kind`、`title`、`fields`、`settings`，并具备 JSON 可序列化、版本校验与克隆能力。后续运行时能力必须以这一模型为唯一事实来源，不再另建“画布字段模型”或“移动端字段模型”。

运行时扩展采用**新增版本**方式演进。不得修改既有版本字段语义；旧版本先迁移、校验，再执行。

```ts
interface PublishedFormDocument extends FormDocument {
  // 仅示意后续版本的扩展方向，具体字段需随 Schema 版本同步发布。
  layout?: FormLayout
  rules?: FormRule[]
  submit?: FormSubmitSettings
}
```

### 4.2 字段的稳定语义

`field.type` 表达业务能力，而非组件实现。例如 `single-line-text`、`member`、`attachment`、`sub-form` 是稳定类型；桌面弹出层、移动端底部抽屉、具体日期选择器均不得写入 Schema。

字段 `config` 按类型定义可校验的 JSON 子结构。公共配置包括占位文本、说明、只读、默认值、布局跨度和校验项；专属配置例如下拉选项、附件数量和关联对象范围。设计器、后端和运行时共享相同的类型校验器。

### 4.3 规则 DSL

规则必须是声明式 JSON，禁止将任意 JavaScript 字符串写入 Schema。首期规则类型：

| 规则 | 作用 | 示例结果 |
| --- | --- | --- |
| `visibility` | 控制字段或区块是否展示 | 合同类型为“长期”时展示合同期限 |
| `disabled` | 控制可编辑性 | 已审批记录不可修改金额 |
| `required` | 动态必填 | 选择“其他”时其他说明必填 |
| `default` | 首次初始化默认值 | 当前成员作为申请人 |
| `compute` | 受控计算 | 数量 × 单价得到金额 |
| `validate` | 跨字段约束 | 结束时间不得早于开始时间 |

规则只允许引用字段 `key` 和白名单上下文变量；表达式由受控 AST 或结构化条件树执行。服务端必须重复执行权限、关键计算与最终校验，浏览器规则只改善交互，不构成可信边界。

### 4.4 发布不可变性

- 草稿可修改，发布版本不可覆盖；记录必须绑定其填写时的 Schema 版本；
- 运行时 bootstrap 返回 `formId`、`publishedVersion` 和 `schemaRevision`；提交时原样回传；
- 服务端发现版本过期时返回稳定业务码，客户端提示刷新或按业务策略保留草稿；
- 不兼容变更通过 Schema migration 处理，不能以运行时猜测字段含义的方式兼容。

## 5. RuntimeStore 与数据流

### 5.1 唯一状态源

每个 `FormRenderer` 创建独立的 runtime session，不使用全局 Pinia 承载填写值。建议状态如下：

```ts
interface FormRuntimeState {
  values: Record<string, FormValue>
  fieldStates: Record<string, FieldRuntimeState>
  formState: 'initializing' | 'ready' | 'submitting' | 'submitted' | 'failed'
  dirtyKeys: Set<string>
  issues: FormIssue[]
}

interface FieldRuntimeState {
  visible: boolean
  disabled: boolean
  readonly: boolean
  touched: boolean
  validating: boolean
  errors: string[]
}
```

实现要求：

- Schema 使用 `shallowRef` 保存，替换版本时只替换根引用；
- 值表和字段状态按 key 进行细粒度响应式追踪；字段组件只订阅自身 key；
- `FormRenderer` 只遍历静态 render plan，不读取全部字段值；
- 所有修改经过 `setValue(key, value, source)`，由 Store 触发依赖规则、脏状态和定向校验；
- 对外暴露只读状态与显式 action，禁止子组件直接修改共享对象；
- 禁止对完整 values 使用 deep watch、每次输入 JSON 序列化比较或全表单循环校验。

### 5.2 组件数据流

```text
FormRenderer
  ├─ 创建 RuntimeStore，provide 只读状态和 action
  └─ FormSectionRenderer
       └─ FormFieldHost(field)
            └─ 字段组件
                 └─ emit update:modelValue
                      └─ Store.setValue(field.key, value)
```

字段不接收整张表单值对象。`FormFieldHost` 以依赖注入的 field key 获取自身 `modelValue` 和状态，从而让输入一个字段时仅重渲染该字段及其规则依赖项。

```ts
interface RuntimeFieldProps {
  field: FormField
  modelValue: FormValue
  disabled: boolean
  readonly: boolean
  errors: readonly string[]
}

interface RuntimeFieldEmits {
  'update:modelValue': [value: FormValue]
  blur: []
}
```

字段组件使用 `defineProps` 和 `defineEmits`（或语义明确的 `defineModel`）建立双向值契约，不得修改父级 prop。跨三层以上共享的 session 通过带 `Symbol` 的 `InjectionKey` 注入；状态只读，写操作由 Store action 集中执行。

### 5.3 值初始化与提交

初始化顺序：已保存值 → 记录上下文默认值 → Schema 静态默认值 → 空值。动态默认值只在字段第一次需要时执行，不覆盖用户已填写值。

提交顺序：刷新动态规则 → 校验所有可见且可提交字段 → 等待必要异步校验 → 组装提交载荷 → 触发 `submit` 事件。提交载荷使用字段 `key`，不使用页面索引或组件内部 ID。

```ts
interface FormSubmitPayload {
  formId: string
  publishedVersion: number
  schemaRevision: string
  values: Record<string, FormValue>
}
```

## 6. 规则、校验与计算

### 6.1 规则依赖图

加载 Schema 时一次性完成：Schema 校验、字段 key 索引、规则解析、循环依赖检测及依赖图编译。

```text
合同类型 ───► 合同期限.visible
数量 ───────► 金额.compute
单价 ───────► 金额.compute
开始时间 ───► 结束时间.validate
```

字段值改变后，仅沿依赖图执行下游规则。规则计算需有最大迭代次数和循环错误诊断，避免配置错误导致主线程长时间阻塞。

### 6.2 校验分层

| 层次 | 时机 | 内容 |
| --- | --- | --- |
| 字段即时校验 | 输入、失焦 | 类型、长度、格式、范围 |
| 定向规则校验 | 依赖字段改变 | 跨字段关系、动态必填 |
| 异步校验 | 失焦或停顿后 | 唯一性、远程资格、关联记录有效性 |
| 提交前校验 | 点击提交 | 全部可见且可提交字段 |
| 服务端最终校验 | 接收提交 | 权限、版本、规则、数据完整性 |

异步校验必须节流/防抖，并在输入继续变化、字段隐藏或组件销毁时用 `AbortController` 取消旧请求。不得在 `onUpdated` 中执行网络请求、全表单校验或状态变更。

### 6.3 计算字段

计算字段默认只读；计算结果带来源标记，防止用户输入与规则回写相互覆盖。对金额、审批条件、权限相关计算，服务端为最终事实来源；客户端仅用于即时预览。

## 7. 渲染与组件设计

### 7.1 核心组件图

| 组件 | 单一职责 | 是否进入首屏包 |
| --- | --- | --- |
| `FormRenderer` | 初始化 session、提供上下文、管理提交和整体状态 | 是 |
| `FormSectionRenderer` | 按 render plan 渲染区块与延迟区块 | 是 |
| `FormFieldHost` | 字段外壳、标签、说明、错误、字段组件懒加载 | 是 |
| `FormFieldError` | 无障碍关联的错误展示 | 是 |
| `FormSubmitBar` | 提交、保存草稿、错误摘要 | 是 |
| `TextField` 等基础字段 | 轻量原生控件 | 是 |
| `MemberField`、`AttachmentField` 等 | 重交互和远程数据字段 | 否，按需 |

`FormFieldHost` 是唯一了解“字段通用展示”的组件。字段本身不重复实现标签、必填星号、说明、错误列表、间距和只读文本样式。

### 7.2 基础字段与重型字段

基础字段使用原生 HTML 控件和最小 Vue 包装：单行/多行文本、数字、单选、复选、基础下拉、日期时间、分割线、只读文本。它们不得依赖 UI 组件库。

下列字段作为重型字段动态加载：富文本、签名、图片/附件上传、成员/部门搜索、地址/定位、关联表单、关联查询、数据选择器、文字识别、复杂子表单。字段模块仅在首屏实际出现或临近可视区/用户点击时导入。

```ts
registry.register('single-line-text', TextField)
registry.register('number', NumberField)
registry.register('member', () => import('./widgets/heavy/MemberField.vue'))
registry.register('attachment', () => import('./widgets/heavy/AttachmentField.vue'))
```

未知或当前套餐未启用的字段类型不可静默丢弃：`FormFieldHost` 渲染受控的“此字段暂不支持”状态，并将诊断回传给宿主；发布时服务端应尽量阻止这种情况。

### 7.3 子表单

子表单有独立的行级 Store，父字段仅保存行值数组。桌面可使用表格化编辑；移动端使用逐行卡片或抽屉编辑，但两端都遵循同一子字段 Schema、同一行 ID 和同一值协议。长子表单的记录行使用虚拟列表；普通表单字段本身不默认虚拟化，以避免焦点丢失和无障碍问题。

### 7.4 主题与可访问性

运行时样式自带最小、语义化的 CSS，并通过主题入口提供颜色、字号、间距、圆角、边框和状态色映射。运行时不依赖 Element Plus 的组件或样式；接入 Web 宿主时，主题值需与前端中性色变量规范保持一致。

所有字段必须具备：可关联的 `label`、`id`、`aria-describedby`、错误 `aria-live` 提示、键盘可达的焦点态、最少 44px 的移动端触控目标、禁用和只读的语义区分。错误定位时优先聚焦第一个错误字段；懒加载区块需先挂载再聚焦。

## 8. 桌面与移动端复用

### 8.1 一套业务组件协议

桌面和移动端共享 Schema、Store、规则、校验、Adapter、字段值类型和字段组件事件。大多数基础字段使用同一 Vue 组件，通过容器查询或媒体查询调整列数、标签位置、间距和操作栏。

```text
同一 Field type + 同一 FormValue 协议
           │
     ┌─────┴─────┐
     ▼           ▼
桌面呈现       移动呈现
Popover        Bottom Sheet
双列布局       单列布局
表格子表单     卡片子表单
```

只有交互形态确有差异的字段才允许按 presentation resolver 替换：日期时间、成员/部门、地址定位、文件预览、复杂子表单。不得基于 User-Agent 分叉业务逻辑，也不得在 Schema 中写具体组件名。

### 8.2 Layout 契约

Schema 可声明响应式布局意图，例如区块顺序、桌面列跨度和移动端单列，但字段配置不得复制两份。移动端默认策略是单列、标签上置、提交栏固定在安全区内、复杂选择器全屏/底部抽屉展示。

## 9. 移动端首屏性能设计

### 9.1 首屏关键路径

```text
路由进入
  └─ 单一 bootstrap 请求（Schema + 值 + 权限 + 首屏必要枚举）
       └─ 校验与编译 render plan / 规则依赖图
            └─ 同步加载基础字段并挂载首个可视区
                 └─ 空闲或临近可视区时加载后续区块与重型字段
```

bootstrap 必须避免瀑布请求。成员目录、关联记录、附件历史、地图库和富文本资源不得随页面初始化加载；它们由字段获得焦点、搜索或滚动接近可视区后再请求。

建议的接口形态：

```text
GET /applications/code/:appCode/forms/:formId/runtime
```

响应只含渲染必需信息：已发布 Schema、记录值、版本口令、当前操作权限、当前可见区块必要的静态选项。所有大集合均使用字段级分页检索接口。

### 9.2 代码与资源拆分

- runtime 核心与基础字段构成唯一首屏 JS；设计器、代码编辑、拖拽、地图和富文本必须从依赖图剔除；
- 字段注册表用 loader 函数动态导入重型字段，避免静态 export 把它们合并进主入口；
- 根据 bootstrap 中首屏字段类型选择性 `modulepreload`，不得预加载未出现的重型字段；
- 首屏只引入运行时关键 CSS；重型字段样式与模块同分片加载；
- 图片缩略图使用尺寸信息和延迟加载，避免布局抖动。

### 9.3 DOM 与响应式开销控制

- 以区块为单位延迟挂载非首屏内容；可见性预热由 `IntersectionObserver` 驱动；
- 非首屏静态区块可以使用 `content-visibility: auto`，但焦点、错误跳转和读屏场景必须先确保区块已挂载；
- 字段列表超过 50 至 100 个且单项复杂时，使用区块级渐进挂载；对子表单行、远程搜索结果使用虚拟列表；
- 大列表渲染避免多层纯样式包装组件；字段热路径只保留 `Section → Host → Widget` 的必要层级；
- 静态说明可使用 `v-once`；只读的大型列表可谨慎使用 `v-memo`；可编辑输入控件和依赖频繁变化的节点不得使用 `v-memo`；
- 不在模板中做过滤、排序、规则计算或 JSON 转换，派生状态由纯 `computed` 或预编译 render plan 提供；
- 不在 `onUpdated` 里执行计算、请求或变更状态。

### 9.4 性能验收指标

实施时以代表性中端 Android 设备、4G 网络和真实表单数据做持续测量。首期建议门槛：

| 指标 | 目标 |
| --- | --- |
| 首屏运行时附加 JavaScript | 构建产物 gzip 后不超过 40 KB，重型字段不计入 |
| 首次可填写字段出现 | bootstrap 成功后 1 秒内完成，实验室网络条件需记录 |
| 最大内容绘制 LCP | 小于 2.5 秒 |
| 输入交互 INP | 小于 200 ms |
| 单字段修改影响范围 | 仅自身与依赖字段，不触发全表单规则扫描 |
| 初始远程请求 | 1 个 bootstrap；无字段交互时不请求成员、地图、附件等资源 |

性能门槛需结合 CI 构建体积报告、移动真机性能追踪和线上真实用户监控共同验收，不能只以开发机体验判断。

## 10. Runtime Adapter 与服务端接口

### 10.1 注入边界

运行时不导入宿主 API。页面将业务能力作为 adapter 传入：

```ts
interface FormRuntimeAdapter {
  queryMembers(input: MemberQuery, signal: AbortSignal): Promise<Page<MemberValue>>
  queryDepartments(input: DepartmentQuery, signal: AbortSignal): Promise<Page<DepartmentValue>>
  uploadFile(input: UploadInput, signal: AbortSignal): Promise<FileValue>
  queryRelatedData(input: RelatedDataQuery, signal: AbortSignal): Promise<Page<RelatedValue>>
  submit(payload: FormSubmitPayload, signal: AbortSignal): Promise<FormSubmitResult>
  saveDraft?(payload: FormDraftPayload, signal: AbortSignal): Promise<void>
}
```

Adapter 是 Web、移动 Web、后续原生容器的替换点。运行时只处理加载、取消、错误和结果状态；认证头、租户上下文、接口地址、离线能力和宿主权限由 adapter 负责。

### 10.2 失败处理

- bootstrap 失败：展示可重试的全局错误，不创建半初始化 session；
- 字段数据源失败：字段内展示可重试状态，不阻塞无关字段填写；
- 上传失败：保留本地待上传条目和错误原因，禁止将不完整文件值提交；
- 提交失败：服务端字段错误按 key 回填，非字段错误显示在提交栏；
- 版本冲突：禁止静默覆盖，提示刷新、比较或另存草稿；
- 请求取消：不展示为业务错误，不覆盖较新请求结果。

## 11. 安全、权限与数据治理

- 客户端 Schema 必须经结构校验、字段能力白名单和版本校验后才渲染；
- 富文本显示需按信任边界进行净化，未受信任内容禁止 `v-html`；
- 前端显隐、禁用和字段只读不构成授权，服务端必须依据成员、角色、记录状态及发布版本复核；
- 客户端不得执行 Schema 内脚本、拼接接口地址或泄露租户/内部 ID 到提示文案；
- 附件、关联数据和成员搜索均需在服务端执行范围权限与审计；
- 草稿本地缓存必须使用账号、租户、表单和版本隔离的键，并定义过期与清理策略；敏感字段是否允许本地草稿由服务端配置决定。

## 12. 可观测性与测试

### 12.1 运行时指标

运行时以匿名、最小化事件记录：bootstrap 时长、字段模块加载时长、首屏可填写时间、规则执行耗时、校验失败类型、提交耗时和失败码。不得上报字段原始值、附件内容、成员名单或敏感配置。

### 12.2 测试层次

| 层次 | 验证重点 |
| --- | --- |
| Schema 单测 | 迁移、未知字段、重复 key、规则循环、JSON 安全性 |
| RuntimeStore 单测 | 默认值优先级、脏状态、字段隔离、提交载荷 |
| RuleEngine 单测 | 依赖图、显隐、动态必填、计算、取消与循环保护 |
| 字段组件单测 | 值协议、禁用/只读、错误展示、无障碍属性 |
| Adapter 契约测试 | 分页、取消、服务端字段错误回填、版本冲突 |
| 性能测试 | 首屏分包、长表单、长子表单、弱网与中端 Android |

新增字段类型必须同时提交：Schema 子配置校验、基础/重型加载归类、字段值编解码、校验规则、桌面/移动呈现、无障碍测试、服务端提交校验和性能影响说明。

## 13. 实施分期

### 阶段 R0：基础收敛

- 确认 `FormDocument` 为唯一 Schema，定义发布版本与 bootstrap 契约（Schema 模型已按 ADR-010 替换为目标保存协议，其余结论不变）；
- 从最终用户入口剥离设计器、拖拽、代码编辑等依赖；
- 补齐 Schema migration 与字段类型白名单；
- 建立 `form/schema`、`form/runtime`、`form/designer` 独立入口。

### 阶段 R1：轻量填写闭环

- 落地 RuntimeStore、`FormRenderer`、`FormFieldHost`、基础字段注册表；
- 支持文本、数字、日期时间、单选、多选、下拉、分割线和提交；
- 实现基础校验、服务端字段错误回填、移动单列布局；
- 接入单一 bootstrap 与表单提交接口，完成首屏性能基线。

### 阶段 R2：规则与业务字段

- 落地依赖图、显隐、动态必填、受控计算与异步校验；
- 接入成员、部门、附件、关联数据的 adapter；
- 完成草稿、版本冲突、权限回显与错误定位；
- 对成员搜索和子表单实施分页/虚拟列表。

### 阶段 R3：高级字段与跨端深化

- 按需引入签名、地址、定位、富文本、关联查询、文字识别等重型字段；
- 为确有交互差异的字段补充移动 presentation resolver；
- 完成可观测性、线上性能监控、无障碍审计及弱网降级。
