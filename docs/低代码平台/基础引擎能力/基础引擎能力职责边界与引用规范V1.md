# 基础引擎能力职责边界与引用规范V1

适用范围：apps/evolyn-web/packages

基于当前 packages/engines + form/dashboard/workflow 分层规划

版本：V1.0 日期：2026-09-04

# 1. 文档目的

本文档用于固定 Evolyn 前端低代码 Engine Layer
的长期架构约束，明确每个引擎"负责什么、不负责什么、允许依赖什么、禁止依赖什么"，避免随着
Form、Dashboard、Workflow、插件、远程组件等能力扩展后出现职责侵入、循环依赖、重复实现和领域层反向污染基础引擎的问题。

- Engine 是无具体业务页面、尽量无
  UI、可独立测试、可复用的低代码核心能力。

- Form / Dashboard / Workflow 属于领域层，负责组合 Engine，而不是被
  Engine 反向引用。

- 后端权威能力（数据权限、DDL 执行、SQL
  生成与执行等）不能因为前端存在同名 Engine 而转移到浏览器。

- 所有跨 Engine 协议应优先使用稳定类型、DTO、AST、Context、Result 和
  Diagnostic，而不是直接共享内部实现。

# 3. Engine 总体设计原则

1.  单一职责：一个 Engine
    只拥有一种稳定的核心语义，不因为某个页面需要而扩展成业务工具箱。

2.  依赖向下：领域层可以依赖 Engine；Engine 不得依赖领域层。

3.  禁止 UI 反向污染：基础 Engine 原则上不得依赖 Vue SFC、Element
    Plus、页面 Router、业务 Store。

4.  协议优先：跨包通过公开 API
    和类型契约协作，禁止深层路径引用其他包内部文件。

5.  确定性优先：Schema、Rule、Formula、Validator、Query
    等核心计算应尽可能做到相同输入产生相同输出。

6.  前后端语义一致：涉及规则、公式、校验、权限、查询协议时，应定义可镜像到
    Go 后端的协议与测试 Fixture。

7.  安全边界后置：浏览器 Permission Engine
    只负责权限投影与交互控制，后端才是最终授权边界。

8.  持久化权威后置：Physical Engine 前端只描述存储模型/迁移意图，DDL
    生成与执行必须由 Go + PostgreSQL 完成。

## 3.1 当前落地基线（2026-09-04）

- `pnpm-workspace.yaml` 已显式纳入 `packages/engines/*`；Engine Layer 不再是
  workspace 之外、无法建立 `workspace:*` 依赖图的目录。
- `@evolyn.do/formula` 已承接公式函数目录、AST、解析器与静态诊断；
  `@evolyn.do/form` 仅保留表单变量投影、CodeMirror 编辑器和函数库 UI。
- `@evolyn.do/rule` 已承接领域无关的规则依赖图编译、拓扑求值与增量重算闭包；
  Form 通过适配器保留自己的字段显隐 DSL 与条件比较语义。
- `@evolyn.do/permission` 已承接字段权限投影；Form Runtime 不再定义第二份
  `visible/editable` 协议。
- `@evolyn.do/field` 已承接无 UI 的字段定义/注册表；Form 的 27 种控件字典作为
  该契约的领域实例注册，控件面板和拖拽创建逻辑仍保留在 Form。
- `@evolyn.do/validator` 已承接不可变的结构化 Diagnostic/Result 契约；Form
  严格校验器通过适配器维持既有 `document` 返回字段和 Go 镜像语义。
- `@evolyn.do/schema` 已承接 JSON 安全 Schema 的通用深拷贝；Form 的迁移链和
  目标保存协议仍保持领域所有权。
- `@evolyn.do/runtime` 已承接框架无关的运行会话状态工厂；Form Runtime 仍是
  Vue 适配层，负责用 `reactive` 连接会话、渲染器和表单规则。
- `@evolyn.do/data` 已收敛为无 UI 的数据访问协议、资源上下文和查询归一化；
  `@evolyn.do/data-workspace` 承接 `DataWorkspace`、工具栏及 Vue 查询状态，
  通过公开协议组合引擎，禁止反向被 Data Engine 引用。
- `@evolyn.do/query` 已承接可序列化的 Query DSL v1（条件树、排序、分页、
  投影、分组与聚合）、字段操作符能力、归一化、组合和结构校验；Data Engine
  通过其公开 AST 透传筛选与列表查询，不生成 SQL 或注入页面权限。
- `@evolyn.do/physical` 已承接稳定字段 id 到物理列、存储类型、索引与迁移
  意图的纯 DTO/计划计算；字段移除只会产生 `deprecate` 审阅意图，前端绝不
  生成或执行 DDL，当前 JSONB 记录存储链路不受影响。
- Form 已把既有 `widgetName` 正式作为逻辑存储字段标识投影给 Physical Engine；
  它独立于可改的 `label`，布局/按钮控件不进入存储模型。当前协议无需另加会
  漂移的 `fieldId`，后端可由发布快照沿同一 `widgetName → JSONB 路径/物理列`
  映射解释不同存储模式。
- Schema 的表单目标保存协议、字段字典、发布校验以及 Vue Runtime/Designer
  仍属于 Form 领域层。它们必须继续由 Form 与 Go 后端镜像维护，不因基础能力
  下沉而泛化为跨领域协议。

# 4. 各 Engine 职责与边界

## Schema Engine

位置：packages/engines/schema

职责：

- 定义低代码 Schema 的基础协议、节点/字段标识、版本信息和公共结构。

- 负责 Schema decode/encode、normalize、clone、version/migration
  等纯模型能力。

- 为 Form、Dashboard、Workflow 及其他领域提供稳定的 Schema 基础契约。

边界 / 禁止事项：

- 不负责 Vue 渲染。

- 不负责表单设计器交互。

- 不执行数据 CRUD。

- 不直接执行规则、公式或 SQL。

- 不得引用 form/dashboard/workflow。

允许依赖：engine-core（如未来引入）或极少量纯 utils。

主要消费者：form、dashboard、workflow、field、validator、rule、formula
等可依赖公开 Schema 类型。

## Field Engine

位置：packages/engines/field

职责：

- 定义 FieldType、FieldDefinition、FieldCapability、FieldValue
  等字段领域基础类型。

- 维护字段类型
  Registry/Descriptor，描述字段支持的能力：输入、显示、查询、排序、公式、存储映射等。

- 提供字段值 normalize/serialize/deserialize 等与 UI 无关的能力。

边界 / 禁止事项：

- 不直接注册具体 Vue 页面。

- 不拥有 Form Designer Palette。

- 不负责 Element Plus 组件细节。

- 不负责物理 DDL 执行。

允许依赖：schema；必要时依赖极少量 core。

主要消费者：form runtime/designer、query、formula、validator、physical
可消费字段能力描述。

## Validator Engine

位置：packages/engines/validator

职责：

- 统一 Schema Validation、Value Validation、Rule Validation
  等校验协议。

- 输出结构化 ValidationResult / Diagnostic，而不是直接弹 Toast。

- 支持 required、range、regex、precision、cross-field、custom
  等可扩展规则。

边界 / 禁止事项：

- 不负责 UI 错误展示。

- 不直接修改表单值。

- 不负责权限判断。

- 不执行网络请求作为默认校验机制。

允许依赖：schema、field；如需表达式能力，应通过稳定接口接入
rule/formula，避免互相反向依赖。

主要消费者：form、workflow、dashboard 发布校验和 runtime 校验。

## Rule Engine

位置：packages/engines/rule

职责：

- 定义 Condition / Predicate / Action / Dependency 等规则模型。

- 编译字段依赖图、检测循环依赖、确定执行顺序。

- 执行显隐、必填、禁用、赋值等规则语义；输出结果，不直接操纵 DOM。

- 保证与 Go 后端规则语义可对齐。

边界 / 禁止事项：

- 不使用 Vue watch 作为规则核心实现。

- 不直接操作组件实例。

- 不拥有权限数据源。

- 不把公式计算全部塞入规则引擎。

允许依赖：schema、field；可通过接口调用 formula，而不是形成双向依赖。

主要消费者：form runtime、workflow、dashboard 条件能力。

## Formula Engine

位置：packages/engines/formula

职责：

- 定义 Expression/AST/Function Registry/Calculation Context。

- 负责公式解析、编译、字段引用分析、依赖关系和求值。

- 统一 Decimal/Money/Date/String/Boolean/Null 等计算语义。

- 支持 SUM、IF、ROUND 等平台函数扩展，并为前后端一致性提供 Fixture。

边界 / 禁止事项：

- 不直接读取 Vue Store。

- 不直接查询数据库。

- 不负责 UI 公式编辑器。

- 不得以 JavaScript eval/new Function 作为平台公式协议。

允许依赖：schema、field；NumericRuntime 如独立则作为更底层能力。

主要消费者：rule、form、dashboard、workflow 可调用公式求值 API。

## Data Engine

位置：packages/engines/data

职责：

- 提供领域无关的数据访问与数据状态抽象：load/create/update/delete/save/refresh/mutation。

- 定义
  DataContext、DataSource、DataRecord、Mutation、Repository/Adapter
  等协议。

- 负责协调 Query Engine 与远程 API Adapter，但不泄露具体页面逻辑。

边界 / 禁止事项：

- 不拥有 Query AST 定义。

- 不生成 SQL。

- 不负责物理表迁移。

- 不实现某个具体表单页面的 draft/submit UI。

- 不直接绑定 axios/fetch 为唯一实现。

允许依赖：query；必要时 permission 以策略/上下文方式接入，避免循环。

主要消费者：form、dashboard、workflow 通过 Data Engine 获取或变更数据。

## Query Engine

位置：packages/engines/query

职责：

- 定义统一 Query DSL /
  AST：filter、sort、paging、projection、group、aggregate。

- 负责 Query normalize、validate、compose、serialize。

- 提供字段操作符能力映射，支持表单列表、仪表盘、数据视图等复用。

边界 / 禁止事项：

- 前端不负责最终 SQL 生成和执行。

- 不负责 CRUD 生命周期。

- 不直接读取页面组件状态。

- 不把数据权限硬编码进 Query AST 内部实现。

允许依赖：schema、field；permission 通过明确的 Policy/Constraint
合成接口接入。

主要消费者：data、form list、dashboard、API query builder。

## Permission Engine

位置：packages/engines/permission

职责：

- 定义 Resource/Action/Subject/Field/Record 等权限模型。

- 负责前端权限投影：canView/canEdit/canCreate/canDelete/fieldVisible/fieldEditable。

- 把后端返回的授权结果转换成 Runtime 可消费的 PermissionContext。

- 可产生 QueryConstraint，但最终授权仍由后端执行。

边界 / 禁止事项：

- 不能作为安全边界。

- 不能只靠隐藏组件保护敏感数据。

- 不直接执行 SQL。

- 不在前端自行推导用户拥有后端未授予的权限。

允许依赖：schema/field 或 core 类型；避免直接依赖
form/dashboard/workflow。

主要消费者：form、dashboard、workflow、data/query 可消费权限上下文。

## Physical Engine

位置：packages/engines/physical

职责：

- 定义 Logical Field 到 Physical Storage 的映射协议。

- 描述
  PhysicalFieldDefinition、StorageType、IndexDefinition、MigrationPlan
  DTO 等前端可见模型。

- 支持设计器展示存储映射、索引配置和迁移预览。

边界 / 禁止事项：

- 严禁浏览器直接生成并执行 CREATE/ALTER/DROP TABLE。

- 不拥有 PostgreSQL 连接。

- 不负责 DDL Lock、事务、Migration Executor。

- 不成为后端 Physical Table Engine 的替代品。

允许依赖：schema、field。

主要消费者：form/admin designer 等可以读取物理模型；真正执行交给
evolyn-core。

# 6. 引用限制（强制规范）

## 6.1 包级引用规则

- 必须通过包公开入口引用，例如 @evolyn/schema-engine；禁止跨包引用
  src/internal、src/private 等内部路径。

- engines/\* 禁止 import
  packages/form、packages/dashboard、packages/workflow。

- engines/\* 原则上禁止依赖 @evolyn/ui、Element Plus、Router、页面级
  Pinia Store。

- 领域包之间默认禁止直接互相引用；确有协作需求时通过 Engine 协议、共享
  DTO 或上层 Orchestrator 组合。

- 禁止循环依赖。任何 A → B → A 或跨多个包形成的依赖环都必须在 CI
  阶段失败。

- 禁止同一协议在多个 Engine 重复定义。例如
  FieldId、SchemaId、QueryOperator 应有唯一权威来源。

- 禁止为了方便从其他 Engine 深层导入未公开实现；需要复用时应提升为公共
  API 或更底层 core 能力。

## 6.2 推荐依赖矩阵

说明：该矩阵作为 V1
推荐上限，不表示每个允许依赖都必须实际发生。优先保持依赖更少。Data ↔
Permission、Query ↔ Permission 等高风险关系应通过 Context/Constraint
接口进一步解耦，避免未来形成环。

## 6.3 Vue/UI 依赖限制

    engines/schema       -> 禁止 Vue UI
    engines/field        -> 核心禁止 Vue UI；具体 Renderer 放 form/dashboard
    engines/validator    -> 禁止 Toast / Dialog / FormItem 操作
    engines/rule         -> 禁止 DOM / component instance
    engines/formula      -> 禁止 Vue Store
    engines/query        -> 禁止页面组件状态
    engines/permission   -> 禁止通过 v-if 代替后端授权
    engines/physical     -> 禁止数据库连接 / DDL execution

# 7. Engine 公共 API 规范

- 每个 Engine 只从 src/index.ts（或 package exports
  明确声明的入口）暴露公共 API。

- 公开 API 优先包含：types、factory、compile/evaluate/validate
  等稳定函数；内部 helper 不导出。

- 返回错误优先使用结构化 Result/Diagnostic，不在 Engine 内直接
  message.error。

- 涉及运行上下文统一使用 Context 对象，避免函数参数无限增长。

- 可扩展点使用 Registry/Adapter/Provider/Resolver 等明确
  SPI，不允许领域层 monkey patch Engine 内部状态。

- 所有 AST/Schema/Rule/Formula 协议必须带版本或具备迁移策略。

# 9. 建议的依赖治理机制

- 在 ESLint 中增加 no-restricted-imports，禁止 engines 引用
  form/dashboard/workflow 和 UI 层。

- 引入 dependency-cruiser 或 madge，在 CI 检测循环依赖与非法跨层引用。

- 为每个 Engine 的 package.json exports
  设置公开边界，避免深层路径导入。

- 为 Rule / Formula / Validator / Query 建立独立 Fixture 测试，后续 Go
  侧使用同一批输入输出样例验证语义一致。

- 新增 CODEOWNERS 或架构 Review 规则：修改 Engine 公共协议、跨 Engine
  新依赖时必须进行架构评审。

- 为 packages/engines 建立依赖图文档，并在新增包或新增依赖时同步更新。

# 11. 新增 Engine / 新增依赖评审清单

1.  该能力是否真的跨 Form / Dashboard / Workflow
    可复用？如果只属于一个领域，应留在领域包。

2.  是否已经存在职责相近 Engine？避免通过新增包解决命名问题。

3.  是否需要依赖另一个 Engine？能否改成类型契约、Context、Adapter
    或回调注入？

4.  新增依赖是否会产生直接或间接循环？

5.  是否把 Vue、Element Plus、Router、业务 Store 带入基础 Engine？

6.  该能力是否属于后端权威职责，例如 SQL、DDL、安全授权、事务？

7.  公开类型是否具备稳定 ID、版本和迁移策略？

8.  是否需要 TS/Go 双端一致性 Fixture？

9.  是否补充单元测试、边界测试和 package exports？

10. 是否同步更新依赖矩阵和本规范？

# 12. V1 架构结论

Evolyn 前端应长期保持"领域层组合基础
Engine"的单向架构。Schema、Field、Validator、Rule、Formula、Data、Query、Permission、Physical
属于可复用基础能力；Form、Dashboard、Workflow 属于领域能力。Engine
的价值不在目录数量，而在稳定协议、确定性语义、严格依赖方向和前后端权威边界。

V1 核心红线：

- Engine 不反向依赖 Form / Dashboard / Workflow。

- Engine 不直接承担页面 UI。

- 禁止循环依赖和跨包深层引用。

- 前端 Permission 不是安全边界。

- 前端 Physical 不执行 DDL。

- Query DSL 不等于 SQL。

- Rule / Formula / Validation 的关键语义必须可与 Go 后端保持一致。
