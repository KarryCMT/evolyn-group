# 应用管理开发文档

## 1. 文档目的与范围

本文定义 evolyn 低代码平台的**应用管理（Application）**后端设计，作为 M2「应用实例与模板安装」实施前的开发契约。它覆盖：

- 成员在当前租户创建空白应用；
- 成员从模板中心安装应用模板；
- 应用实例的查询、修改、删除与生命周期；
- 应用模板、模板版本和安装记录的数据模型；
- 配额、RBAC、租户隔离、事务、审计、异步实例化的处理规则；
- Go 域模块、SQL Migration、HTTP API 与测试方案。

本文不实现表单、字段、页面、工作流、动态数据表等引擎。它们属于后续 Schema / DDL / Data Engine；但本文预留应用实例化协议，使这些引擎可以作为模板资产被安全复制。

## 2. 现状与设计结论

当前平台已具备：

- 平台账号 `accounts` 与租户成员 `users` 的拆分（ADR-006）；
- 租户上下文、GORM 租户 Callback、租户状态拦截；
- `apps` 配额键定义，但尚未具备用量统计和创建路径校验；
- 统一事务 `infrastructure.TxManager`、提交后 best-effort 审计、统一 `BizError`；
- 前端工作台中的“新建应用”入口、空白应用表单及模板选择弹窗。

因此本期结论如下：

1. **空白创建与模板安装是两个用户能力，但共享同一个应用实例化领域能力。**
2. `Application` 是租户内一级资源，必须嵌入 `model.TenantBaseModel`；所有业务读写均受租户 Callback 保护。
3. 应用所有者、创建者均引用租户成员 ID；租户开通者账号不直接替代应用所有者。
4. “当前成员能否编辑/删除/发布”的能力是运行时授权结果，不能存入 `applications` 表。
5. 模板必须以**已发布版本**安装，安装时记录不可变版本快照；禁止安装“模板最新草稿”。
6. 任何会创建应用的入口都必须在一个事务中完成配额占位、应用记录、来源记录和初始化任务记录；事务提交后才记审计或投递任务。

## 3. 领域术语

| 术语 | 含义 |
| --- | --- |
| 应用实例（Application） | 某租户实际使用、管理和授权的低代码应用。 |
| 空白应用 | 以系统最小蓝图创建的应用实例，来源为 `blank`。 |
| 应用模板（Application Template） | 可安装的业务蓝图元数据，不属于某个应用实例。官方模板为平台级资源；后续可扩展租户私有模板。 |
| 模板版本（Template Version） | 已发布且不可修改的模板快照；安装必须精确指向一个版本。 |
| 应用实例化（Provisioning） | 从空白蓝图或模板蓝图生成应用及其关联资产的统一过程。 |
| 安装记录（Installation） | 记录应用从哪个模板版本、哪个渠道创建，供升级、问题定位和审计使用。 |
| 应用所有者 | 在当前租户中对应用拥有最高管理语义的成员。 |

## 4. 领域边界与模块位置

依据 ADR-007，新域不预建引擎空包，应用管理的 HTTP 业务域落在：

```text
apps/evolyn-core/internal/platform/application/
├── controller/
│   └── application.go
├── model/
│   ├── application.go
│   ├── template.go
│   └── dto.go
├── repository/
│   ├── application.go
│   ├── template.go
│   └── interface.go
├── service/
│   ├── application.go
│   ├── provisioning.go
│   ├── template.go
│   └── interface.go
└── errors.go
```

职责边界：

| 层 | 责任 |
| --- | --- |
| Controller | 解析请求、获取当前成员、返回 `httpx` 统一信封、维护中文 Swagger 注释。 |
| Service | 权限前置校验、事务编排、配额占位、应用实例化、审计时机。 |
| Repository | 仅做持久化；必须经 `infrastructure.ResolveDB(ctx, db)` 获取连接。 |
| Template resolver | 校验模板状态/版本，返回不可变蓝图，不感知 HTTP 或 GORM。 |
| Provisioner | 将蓝图应用到新应用；后续由 Schema/DDL/Page/Workflow 引擎实现具体资产复制。 |

不得把业务应用模型放入 `internal/engine/`，也不得让模板复制逻辑依赖 Gin。后续引擎以 `ApplicationProvisioner` 接口接入即可。

## 5. 统一实例化模型

### 5.1 命令模型

空白创建和模板安装最终收敛到一个内部命令，避免在两个入口重复配额、编号、权限、审计和事务逻辑。

```go
type ProvisionSource string

const (
    ProvisionSourceBlank    ProvisionSource = "blank"
    ProvisionSourceTemplate ProvisionSource = "template"
)

type ProvisionApplicationCommand struct {
    TenantID        uint
    OwnerMemberID   uint
    CreatorMemberID uint
    Name            string
    Icon            string
    Color           string
    Source          ProvisionSource
    TemplateID      *uint
    TemplateVersion *uint
}
```

对外接口可保持不同的业务语义：

```text
POST /api/v1/applications
POST /api/v1/application-templates/:templateId/install
```

但二者均调用 `ApplicationService.Provision`。其中 `POST /applications` 固定使用 `blank` 来源；模板安装控制器在查询并锁定已发布版本后补齐 `TemplateID/TemplateVersion`。

### 5.2 实例化时序

```text
成员请求创建/安装
        │
        ▼
认证 + Tenant + TenantStatus + Authorization
        │
        ▼
ApplicationService.Provision
        │
        ├─ 校验名称、图标、颜色和来源参数
        ├─ 检查 applications:create 或 application-templates:create 权限
        ├─ 开启 TxManager.WithinTransaction
        │   ├─ 锁定租户并校验/占用 apps 配额
        │   ├─ 解析空白蓝图或已发布模板版本
        │   ├─ 创建 applications 记录（异步为 pending，同步为 ready）
        │   ├─ 创建 application_installations 记录
        │   ├─ 创建 application_provision_jobs 记录（如需要）
        │   └─ 同步最小蓝图可直接置为 ready
        ├─ 提交事务
        ├─ best-effort 记录 audit_logs
        └─ 投递实例化任务（如需要）
```

### 5.3 同步与异步边界

| 场景 | 首期策略 | 后续策略 |
| --- | --- | --- |
| 创建空白应用 | 同步：创建应用、默认首页壳与默认应用管理员绑定后直接 `ready`。 | 保持同步。 |
| 轻量模板安装 | 同步：仅复制少量元数据时可在同一事务完成。 | 保持同步。 |
| 含表单、页面、流程、文件、动态物理表的数据模板 | 建立 `pending` 任务，提交后由 worker 处理。 | 固定异步；可重试、可观测、可恢复。 |

首期不得使用进程内 goroutine 作为可靠任务队列。若任务跨越数据库事务或涉及 DDL，必须使用持久化任务/Outbox，并在后续 `cmd/worker` 处理。任务执行前后均应检查应用和租户状态。

### 5.4 现有 RBAC 适配决策（M2-A 定版）

现有 `RequestInfoFactory` 只从 URL 的第一个资源段和 HTTP 方法推导授权键：

```text
POST /api/v1/applications/:id/archive
→ resource = applications, subresource = archive, verb = create

POST /api/v1/application-templates/:id/install
→ resource = application-templates, subresource = install, verb = create
```

当前 `Authorizer` 只匹配 `resource + verb`，不会匹配 `subresource`。因此 M2-A/M2-B **不得**在规则中新增 `archive`、`install`、`manage`、`publish`、`copy` 等业务动词，也不得假定 `POST` 子资源能获得独立授权。

本期权限键固定复用既有动词与复数资源名：

```text
applications: get, list, create, update, patch, delete
application-templates: get, list, create
```

归档与恢复通过 `PATCH /applications/:id` 修改受白名单保护的 `status`；模板安装虽然保留 `POST /application-templates/:id/install` 的清晰业务路径，但在现有授权器下检查 `application-templates:create`。失败重试等需要独立业务动作的接口延后至 M2-C；届时必须先以 ADR 定义 `resource + subresource + operation` 的鉴权扩展和兼容迁移方案。

## 6. 数据模型

### 6.1 ER 关系

```text
tenants 1 ──── * applications
users   1 ──── * applications.owner_member_id
users   1 ──── * applications.creator_member_id

application_templates 1 ──── * application_template_versions
application_templates 1 ──── * application_installations
application_template_versions 1 ──── * application_installations
applications 1 ──── 0..1 application_installations
applications 1 ──── * application_provision_jobs
```

### 6.2 `applications`：应用实例主表

| 列 | 类型/约束 | 说明 |
| --- | --- | --- |
| `id` | `BIGSERIAL PK` | 内部稳定主键。 |
| `tenant_id` | `BIGINT NOT NULL` | 租户归属；GORM 通过 `TenantBaseModel` 管理。 |
| `code` | `VARCHAR(64) NOT NULL` | 服务端生成、租户内唯一、创建后不可修改；给 URL、外部引用和日志使用。 |
| `name` | `VARCHAR(128) NOT NULL` | 展示名称；允许同租户重名，避免将名称错误当作业务主键。 |
| `icon` | `VARCHAR(32) NOT NULL` | 稳定图标键，如 `bookmark`，不存前端组件名。 |
| `color` | `VARCHAR(32) NOT NULL` | 稳定颜色键，如 `primary`，不存 CSS 字面值。 |
| `owner_member_id` | `BIGINT NOT NULL` | 应用所有者；必须属于同一 `tenant_id`。 |
| `creator_member_id` | `BIGINT NOT NULL` | 创建者；删除后保留 ID 审计语义。 |
| `source_type` | `VARCHAR(16) NOT NULL` | `blank` / `template`；冗余于安装记录，便于列表查询。 |
| `status` | `VARCHAR(16) NOT NULL` | `active` / `archived`；仅表达可见业务状态。删除只使用 `deleted_at`。 |
| `provision_status` | `VARCHAR(16) NOT NULL` | `ready` / `pending` / `running` / `failed`；与 `status` 独立。 |
| `definition_version` | `INTEGER NOT NULL DEFAULT 1` | 应用定义版本；不是数据库乐观锁字段。 |
| `sort_order` | `BIGINT NOT NULL DEFAULT 0` | 预留应用列表排序。 |
| `config` | `JSONB NOT NULL DEFAULT '{}'` | 小型应用级配置；严禁混入表单/页面/流程大定义。 |
| `created_at`、`updated_at`、`deleted_at` | 时间/软删 | 继承 `TenantBaseModel`。 |

建议约束和索引：

```sql
CREATE UNIQUE INDEX uq_applications_tenant_code_active
    ON applications (tenant_id, code)
    WHERE deleted_at IS NULL;

CREATE INDEX idx_applications_tenant_status_sort
    ON applications (tenant_id, status, sort_order, id DESC)
    WHERE deleted_at IS NULL;

CREATE INDEX idx_applications_tenant_owner
    ON applications (tenant_id, owner_member_id)
    WHERE deleted_at IS NULL;

ALTER TABLE applications
    ADD CONSTRAINT chk_applications_source_type
    CHECK (source_type IN ('blank', 'template'));

ALTER TABLE applications
    ADD CONSTRAINT chk_applications_status
    CHECK (status IN ('active', 'archived'));

ALTER TABLE applications
    ADD CONSTRAINT chk_applications_provision_status
    CHECK (provision_status IN ('ready', 'pending', 'running', 'failed'));
```

`owner_member_id` 与 `creator_member_id` 的“同租户”约束无法仅靠普通外键表达；必须由 Service 层加载成员并验证其 `tenant_id`，禁止裸 ID 写入。若后续性能确有需要，再通过复合外键或触发器增强数据库保护。

### 6.3 `application_templates`：模板目录

官方模板是平台级资产，不能嵌入 `TenantBaseModel`，否则会被当前租户 Callback 过滤。首期只支持官方模板：

| 列 | 类型/约束 | 说明 |
| --- | --- | --- |
| `id` | `BIGSERIAL PK` | 模板主键。 |
| `code` | `VARCHAR(64) UNIQUE` | 稳定模板编码。 |
| `name`、`description` | `VARCHAR(128/512)` | 模板目录展示信息。 |
| `cover_url` | `VARCHAR(512)` | 封面资源地址；后续改为文件资源 ID。 |
| `icon`、`color` | `VARCHAR(32)` | 安装默认外观。 |
| `category` | `VARCHAR(64)` | 分类；首期单分类，复杂多分类另建关联表。 |
| `visibility` | `VARCHAR(16)` | `public` / `tenant` / `private`，首期仅 `public`。 |
| `status` | `VARCHAR(16)` | `draft` / `published` / `withdrawn`。 |
| `latest_published_version_id` | `BIGINT NULL` | 目录页默认安装的已发布版本。 |
| `created_at`、`updated_at`、`deleted_at` | 时间/软删 | 继承 `PlatformBaseModel`。 |

租户私有模板是后续能力。届时建议增加 `owner_tenant_id`（可空：空表示官方模板）并使用显式 repository 查询，不要把官方/私有模板简单混在租户 Callback 默认路径里。

### 6.4 `application_template_versions`：不可变发布快照

| 列 | 类型/约束 | 说明 |
| --- | --- | --- |
| `id` | `BIGSERIAL PK` | 版本主键。 |
| `template_id` | `BIGINT NOT NULL` | 所属模板。 |
| `version` | `INTEGER NOT NULL` | 模板内递增版本号，联合唯一。 |
| `status` | `VARCHAR(16)` | `draft` / `published` / `retired`。 |
| `blueprint` | `JSONB NOT NULL` | 已发布应用蓝图；不得保存任何源租户成员 ID、动态数据或敏感密钥。 |
| `checksum` | `CHAR(64) NOT NULL` | 对 canonical JSON 计算 SHA-256，防止发布后被篡改。 |
| `published_at` | `TIMESTAMPTZ NULL` | 发布时间。 |
| `created_by_account_id` | `BIGINT NOT NULL` | 平台模板维护者。 |
| `created_at`、`updated_at`、`deleted_at` | 时间/软删 | 继承 `PlatformBaseModel`。 |

约束：`UNIQUE(template_id, version)`；同一模板同一时间最多一个 `published` 版本由 Service 层保证，并同步更新 `latest_published_version_id`。

蓝图只允许逻辑标识，例如 `role:app_admin`、`form:customer`；安装时由 Provisioner 映射为新应用中的实际 ID。禁止把源应用的 ID、成员 ID、文件访问令牌或数据记录原样复制。

### 6.5 `application_installations`：来源与安装快照

| 列 | 类型/约束 | 说明 |
| --- | --- | --- |
| `id` | `BIGSERIAL PK` | 安装记录主键。 |
| `tenant_id` | `BIGINT NOT NULL` | 与应用相同的租户归属。 |
| `application_id` | `BIGINT NOT NULL UNIQUE` | 一个应用只有一个初始来源记录。 |
| `source_type` | `VARCHAR(16) NOT NULL` | `blank` / `template`。 |
| `template_id`、`template_version_id` | `BIGINT NULL` | 空白应用为 `NULL`；模板安装时必填。 |
| `channel` | `VARCHAR(32) NOT NULL` | `self` / `template_center` / `admin` / `api`。 |
| `blueprint_checksum` | `CHAR(64) NULL` | 安装时实际使用的蓝图校验值。 |
| `installed_by_member_id` | `BIGINT NOT NULL` | 当前租户发起安装的成员。 |
| `installed_at` | `TIMESTAMPTZ NOT NULL` | 安装记录时间。 |

这里承接简道云响应中的 `installChannel`、`isOfficial`、`forks` 等来源语义，但不把它们无差别堆入主表。复制/分叉应用将来可以新增 `source_application_id` 与来源类型 `fork`，不污染空白/模板主流程。

### 6.6 `application_provision_jobs`：持久化实例化任务

当模板包含跨引擎资产时使用此表；空白应用和轻量模板不必创建任务。

| 列 | 说明 |
| --- | --- |
| `id` | 任务主键。 |
| `tenant_id`、`application_id` | 租户和目标应用。 |
| `installation_id` | 对应安装记录。 |
| `status` | `pending` / `running` / `succeeded` / `failed` / `cancelled`。 |
| `attempts`、`max_attempts`、`next_run_at` | 重试控制。 |
| `payload` | 任务参数，只含版本 ID/校验和等可重建信息。 |
| `error_code` | 面向运维的稳定失败类别，不保存敏感原始错误。 |
| `error_detail` | 内部诊断文本；禁止出现在普通成员 API。 |
| `started_at`、`finished_at`、`created_at`、`updated_at` | 可观测性。 |

任务领取使用 PostgreSQL `FOR UPDATE SKIP LOCKED`，避免多个 worker 重复处理；每个 Provisioner 操作须幂等，以 `application_id + asset logical key` 防重复创建。

## 7. 状态机与删除规则

### 7.1 应用状态

```text
active  ──归档──> archived
  │                   │
  └────恢复───────────┘
  │                   │
  └──────DELETE───────┴──> deleted_at 写入（软删，进入保留期）
```

`provision_status` 独立变化：

```text
ready
pending ──worker领取──> running ──成功──> ready
                              └──失败──> failed ──重试──> pending
```

规则：

- `pending/running` 的应用不可进入设计器；列表可展示“正在初始化”。
- `failed` 应用可由拥有 `applications:delete` 的成员在 M2-A 删除；独立“重试”动作留待 M2-C 的子资源鉴权 ADR 后开放。
- `archived` 默认不可编辑和发布，但仍可读取；具体最终权限由 `capabilities` 派生。
- 执行 `DELETE` 时仅写入 `deleted_at`，立即从常规列表隐藏；保留期结束后由应用清理任务物理清理关联引擎资产和应用记录。`status` 不写入 `deleted`，避免与 GORM 软删双轨失真。

## 8. API 设计

所有接口处于租户业务域，统一经过：

```text
Authentication → Tenant → TenantStatus → Authorization
```

所有响应均为现有 `{ code, msg, data, errCode? }` 信封，时间字段使用 `model.JSONTime` 的统一出网格式。

### 8.1 创建空白应用

```text
POST /api/v1/applications
```

请求：

```json
{
  "name": "测试应用",
  "icon": "bookmark",
  "color": "primary"
}
```

约束：`name` 去首尾空格后长度 1–128；`icon`、`color` 必须来自服务端白名单；客户端不得传入 `tenantId`、`ownerMemberId`、`status`、`code` 等服务端字段。

成功返回 `201 Created`：

```json
{
  "code": 201,
  "msg": "创建成功",
  "data": {
    "id": 101,
    "code": "app_01j...",
    "name": "测试应用",
    "icon": "bookmark",
    "color": "primary",
    "source": { "type": "blank", "channel": "self" },
    "status": "active",
    "provisionStatus": "ready",
    "ownerMemberId": 8,
    "creatorMemberId": 8,
    "capabilities": {
      "view": true,
      "edit": true,
      "delete": true
    },
    "createdAt": "2026-08-22 15:32:23",
    "updatedAt": "2026-08-22 15:32:23"
  }
}
```

### 8.2 安装模板

```text
POST /api/v1/application-templates/:templateId/install
```

请求：

```json
{
  "version": 3,
  "name": "华东区 CRM",
  "icon": "contacts",
  "color": "primary"
}
```

`version` 省略时取模板当前已发布版本；若安装任务异步，返回 `202 Accepted` 与 `provisionStatus: pending`。前端通过 `GET /api/v1/applications/:id` 或列表轮询读取状态，不从任务内部错误文本推断失败原因。

异步安装响应：

```json
{
  "code": 202,
  "msg": "应用正在初始化",
  "data": {
    "id": 102,
    "code": "app_01j...",
    "name": "华东区 CRM",
    "source": { "type": "template", "templateId": 12, "version": 3, "channel": "template_center" },
    "status": "active",
    "provisionStatus": "pending"
  }
}
```

### 8.3 目录、详情与维护

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |

## 9. 权限、租户隔离与能力计算

### 9.1 权限资源

M2-A/M2-B 新增资源与既有动作：

```text
applications: get, list, create, update, patch, delete
application-templates: get, list, create
```

`applications:create` 与 `application-templates:create` 是租户级动作；应用详情后的 `patch/delete` 还必须叠加应用级范围校验。M2 未落地细粒度应用管理员范围时，可先由租户管理员授权，但 Service 接口必须预留 `ApplicationAccessEvaluator`，避免之后在 Controller 分散补判断。独立的 `archive/install/manage/publish/copy` 动词不属于本期规则集，详见 §5.4。

### 9.2 `capabilities` 的计算

`ApplicationResponse.capabilities` 在读取时计算：

```text
会员角色规则
  + 是否应用 owner
  + 应用 status / provision_status
  + 租户 status / 套餐能力
  = 当前请求成员 capabilities
```

因此不落库 `editable`、`deletable`、`isReadonly` 等瞬态布尔字段。这样既避免权限变更后的陈旧数据，也避免将简道云面向 UI 的派生字段误作实体状态。

`capabilities` 是前端展示契约，不是 RBAC 权限键；M2-A 仅输出已经实现的 `view`、`edit`、`delete`。发布、复制等能力在对应功能和鉴权模型落地后再增加，不能因响应字段存在而绕过 §5.4 的授权限制。

### 9.3 强制隔离规则

- Repository 不允许接收客户端提供的 `tenantID`；Service 从 `contextx.TenantIDFromContext` 获取。
- 读取/更新/删除均先按当前租户加载；禁止直接 `UPDATE ... WHERE id = ?` 后以“0 行也成功”返回。
- 绑定 owner/creator 时先查询成员并验证同租户；模板安装者同样必须是当前租户成员。
- 平台模板查询使用 `contextx.DetachTenant(ctx)` 或独立平台级 repository；不得借 tenant repository 绕过 Callback。
- 所有模板蓝图在入库、发布、安装三个阶段均校验禁止字段，尤其是 `tenant_id`、`account_id`、`member_id`、access token、文件临时 URL。

## 10. 配额与并发控制

现有 `QuotaApps = "apps"` 已定义，但 `QuotaService` 当前仅支持 `members`。实现应用域前必须先扩展：

```go
type applicationCounter interface {
    CountBillableByTenant(ctx context.Context, tenantID uint) (int64, error)
}
```

计数口径：`deleted_at IS NULL` 的全部应用均占用配额（包括 `active`、`archived`、`pending`、`running`、`failed`）。失败任务不立即释放名额，避免用户反复创建失败任务绕过限额；软删成功后才释放。

简单的“先 `QuotaService.Check` 再 INSERT”存在并发穿透。正确流程必须在同一事务中：

1. `SELECT id FROM tenants WHERE id = ? FOR UPDATE` 锁定当前租户；
2. 查询当前计费应用数；
3. 读取套餐与租户覆盖后的 `apps` 上限；
4. 未超限才插入应用及安装记录；
5. 提交事务后才投递任务。

可将此能力收敛为 `QuotaService.CheckAndReserve(ctx, tenantID, QuotaApps, fn)`，但不能在 Service 外绕过它。

## 11. 事务、审计与任务可靠性

### 11.1 事务边界

创建空白应用最小事务包含：

```text
配额并发校验
+ applications INSERT
+ application_installations INSERT
+ 默认应用级 RBAC/首页壳 INSERT（如本期落地）
+ application_provision_jobs INSERT（如异步）
```

任一步失败必须整体回滚。Service 通过 `TxManager.WithinTransaction` 开启事务，Repository 通过 `ResolveDB` 加入事务，禁止各 Repository 独立 `db.Transaction`。

### 11.2 审计

事务提交后调用现有 `audit.Recorder`，建议事件：

```go
audit.Entry{
    Module:       "application",
    Action:       "create", // template_install / update / archive / delete / retry
    ResourceType: "application",
    ResourceID:   strconv.FormatUint(uint64(app.ID), 10),
    After: map[string]any{
        "name": app.Name,
        "source": app.SourceType,
        "templateVersion": installation.TemplateVersionID,
    },
}
```

审计只记录必要快照，不记录模板 `blueprint` 全文、敏感配置或任务异常栈；写审计失败只告警，不能回滚已成功创建的应用。

### 11.3 任务投递

若启用异步实例化，推荐 Transactional Outbox：事务内同时创建 `application_provision_jobs` 与 outbox 事件；worker 轮询/消费 outbox 后执行。不得在事务尚未提交时向 Redis、消息队列或 goroutine 直接发送“安装完成”事件。

## 12. 模板蓝图规范

模板版本的 `blueprint` 是跨引擎契约，首期可先定义最小结构：

```json
{
  "schemaVersion": 1,
  "application": {
    "defaultName": "CRM",
    "icon": "contacts",
    "color": "primary"
  },
  "roles": [
    { "key": "app_admin", "name": "应用管理员" }
  ],
  "pages": [
    { "key": "home", "type": "home" }
  ],
  "forms": [],
  "workflows": []
}
```

规则：

- 所有资产以模板内稳定 `key` 引用；实际数据库 ID 在安装时分配。
- 蓝图 `schemaVersion` 用于演进和校验；不兼容变更只能新增版本，不得修改历史版本。
- 发布时 canonical JSON 后计算 `checksum`；安装记录保存该 checksum。
- 模板输入参数必须有白名单和类型定义，不能用任意 JSON 覆盖系统字段。
- 模板安装永远生成新应用，不会修改模板源应用，也不共享其业务数据。

## 13. Go 接口草案

```go
type ApplicationService interface {
    CreateBlank(ctx context.Context, req CreateBlankRequest) (*ApplicationDetail, error)
    InstallTemplate(ctx context.Context, templateID uint, req InstallTemplateRequest) (*ApplicationDetail, error)
    List(ctx context.Context, query ListApplicationsQuery) (*ApplicationPage, error)
    Get(ctx context.Context, id uint) (*ApplicationDetail, error)
    Update(ctx context.Context, id uint, req UpdateApplicationRequest) (*ApplicationDetail, error)
    Archive(ctx context.Context, id uint) error
    Restore(ctx context.Context, id uint) error
    Delete(ctx context.Context, id uint) error
    // RetryProvision 属于 M2-C；开放 HTTP 接口前必须完成 §5.4 所述的子资源鉴权 ADR。
    RetryProvision(ctx context.Context, id uint) (*ApplicationDetail, error)
}

type ApplicationProvisioner interface {
    // Validate 在写 application 前验证蓝图；不得产生副作用。
    Validate(ctx context.Context, blueprint Blueprint) error
    // Apply 为目标应用创建资产；必须幂等，并返回是否需要异步继续。
    Apply(ctx context.Context, appID uint, blueprint Blueprint) (ApplyResult, error)
}
```

`CreateBlank` 与 `InstallTemplate` 不在 Controller 中相互调用；两者由 Service 内部复用私有 `provision` 编排函数。Repository 接口按查询和写入拆分，不能向 Service 暴露 GORM `*DB`。

## 14. Migration 与模型落地顺序

生产 Schema 的唯一事实来源是 `migrations/`。实施时遵循：

1. 在当前最新迁移之后分配连续的新编号；当前工作区如已有未合并迁移，**不得假定编号**。
2. 新增 `applications`、`application_templates`、`application_template_versions`、`application_installations`；仅在异步安装实施时新增 `application_provision_jobs` 与 outbox 表。
3. 为每个 up 迁移提供对应 down 迁移，并同步 `scripts/db.sql` 终态快照。
4. GORM Model 与 SQL 迁移同步提交；AutoMigrate 仅辅助本地测试，不能作为生产建表手段。
5. 完成后运行 `make swagger` 生成本地 Swagger（生成目录不提交）。

初期可将官方模板作为 SQL 种子或受控管理命令导入；不要在普通 API 启动时无条件覆盖已发布模板版本。

## 15. 前端对接契约

当前前端存在两类入口：

| 前端动作 | 后端调用 | 成功后行为 |
| --- | --- | --- |
| 二级“创建空白应用”弹窗确定 | `POST /applications` | 关闭两层弹窗，刷新“我的应用”，跳转应用设计器。 |
| 热门模板卡片 | `POST /application-templates/:id/install` | 同步安装则跳转设计器；异步安装则展示初始化状态并轮询。 |
| 模板中心安装 | 同上 | 与热门模板完全复用安装调用。 |

M2-A 将图标键和颜色键定义为应用域服务端稳定枚举，并以请求校验白名单执行；不得把 Vue 组件名称、颜色 hex 值、临时图片 URL 当作 API 领域值。它们不加入匿名 `/app/conf`，以避免登录启动配置承担租户业务含义；未来需要动态下发时新增租户域 `GET /api/v1/applications/meta`。新增应用域 `errCode` 时必须同步维护 `apps/evolyn-web/packages/utils/src/request/errorCodes.ts`；前端按 `errCode` 处理 `QUOTA_EXCEEDED`、`TEMPLATE_VERSION_UNAVAILABLE` 等错误，禁止按 `msg` 文本判断。

## 16. 测试与验收

### 16.1 Service 单元测试

- 名称、图标、颜色的合法/非法输入；
- 当前成员无 `applications:create` 或 `application-templates:create` 权限；
- 所有者/创建者必须属于当前租户；
- 空白创建写入应用和安装记录，来源为 `blank/self`；
- 模板安装只接受 `published` 版本；
- 资产创建失败时，应用、安装记录、配额占位全部回滚；
- 审计仅在事务成功后记录；
- `failed` 状态重试的幂等性与状态机约束。

### 16.2 PostgreSQL 集成测试

- `SEC-APP-*`：租户 A 无法读取、修改、删除租户 B 的应用；
- `SEC-APP-*`：不能绑定其他租户成员为 owner/creator；
- `QUOTA-APP-*`：并发创建时不超过 `apps` 配额；
- `MIGRATE-INT-*`：空库迁移链与 `scripts/db.sql` 一致；
- `TEMPLATE-*`：模板安装记录锁定已发布版本，后续发布新版本不影响旧应用。

### 16.3 HTTP 验收

- 请求未认证返回 `UNAUTHORIZED`；
- 无租户上下文或租户冻结时被对应中间件拦截；
- 创建成功为 `201`，异步安装为 `202`；
- 错误响应仅含安全 `msg` 与稳定 `errCode`；
- Swagger 标签固定为“应用管理”“应用模板”，且摘要、描述均使用中文。

## 17. 分阶段实施计划

### M2-A：应用实例最小闭环

- `applications` + `application_installations` 迁移、模型、仓储、Service、Controller；
- 空白应用创建/列表/详情/更新/软删；
- `QuotaApps` 用量统计与事务内并发校验；
- 应用基础 RBAC 资源、审计、工作台接口接入；
- 前端空白应用弹窗接入真实 API。

### M2-B：官方模板中心

- 模板/模板版本迁移与受控种子；
- 模板目录、详情、安装接口；
- 最小 JSON Blueprint 校验与同步安装；
- 热门模板与模板中心复用同一安装 API。

### M2-C：跨引擎实例化

- Provisioner 注册机制；
- `application_provision_jobs` + Transactional Outbox + worker；
- 表单、页面、流程、权限资产的逻辑 ID 映射；
- 初始化进度、失败重试、清理与可观测性。

## 18. 非目标与后续决策

本设计刻意不在首期处理：

- 模板增量升级、三方模板市场、模板计费；
- 应用复制/分叉、跨租户迁移、导入导出；
- 应用级独立数据库、RLS 与动态数据表的物理建表；
- 应用协作者、应用管理员分组与细粒度资产授权；
- 多语言文案编辑、应用市场发布审核；
- 模板携带演示数据与敏感数据脱敏策略。

这些能力必须在 Schema/Permission/Data Engine 约束确定后通过新的 ADR 追加，不应通过向 `applications.config` 无约束塞入 JSON 规避设计。
