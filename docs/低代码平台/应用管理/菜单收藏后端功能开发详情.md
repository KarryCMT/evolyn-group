# 应用菜单收藏后端功能开发详情

## 1. 结论

截图中的“收藏”是成员在右键菜单中把一个**应用内可打开的菜单节点**加入个人快捷入口的动作。它不是：

- 对菜单的公共置顶，也不是管理员为全员配置的导航；
- 对表单、仪表盘等资产授予访问权；
- 应用菜单树的一部分，因此不应修改菜单结构或递增 `menu_revision`。

推荐将其建模为“`租户成员 × 应用菜单节点` 的个人关联”。收藏对象选择菜单节点而不是表单资产：同一个资产可能被放在不同应用、不同分组、不同导航位置；用户收藏的是截图中这一条入口及其打开语义。收藏始终服从实时菜单可见性和资产权限，不能成为绕过权限或隐藏规则的后门。

仓库已经具备第一版落库和增删接口：`tn_app_menu_favorites`、`POST /api/v1/menu-favorites`、`DELETE /api/v1/menu-favorites/:menuCode`，并在菜单快照中投影 `favorited`。本方案以此为基础明确完整契约，并列出尚需补齐的“可见性复核”和“我的收藏列表”能力。

## 2. 输入场景与产品边界

截图中，用户对“流程表单”菜单节点打开右键菜单并选择“收藏”。成功后，预期可在“我的收藏”工作台组件或收藏页快速打开该表单；再次操作应显示“取消收藏”。

| 维度 | 设计结论 |
| --- | --- |
| 归属 | 当前租户、当前成员私有；其他成员不可见、不可操作。 |
| 收藏目标 | 仅 `form`、`dashboard`、`page` 等可打开的资产节点；`group` 是树结构，不支持收藏。 |
| 权限 | 收藏不赋权。写入和读取都必须经过当前成员的菜单可见性判定。 |
| 隐藏 | 节点对成员隐藏、资产软删、失去表单入口权限时，收藏不展示也不能打开。隐藏/权限恢复后可重新展示。 |
| 删除 | 菜单节点或其资产被删除时，在同一事务硬删对应收藏，避免“幽灵收藏”。 |
| 排序 | 首期按 `created_at DESC, id DESC`（最近收藏优先）；未引入用户自定义排序。 |
| 并发 | 收藏/取消均幂等；不占用应用菜单的 `menu_revision`。 |

“最近使用”和“我的收藏”是两个不同概念：前者来自访问事件，后者只由用户显式收藏驱动，禁止共用一张表或相互覆盖。

## 3. 现状分析

### 3.1 已具备的基础

当前实现与上述模型的主要部分一致：

- 迁移 `000046_menu_hidden_and_favorites` 创建收藏表；表名前缀迁移 `000063` 后，实际表名为 `tn_app_menu_favorites`；
- `MenuFavorite` 位于应用管理域，包含 `tenant_id`、`member_id`、`app_id`、`menu_id` 和创建时间；
- `(member_id, menu_id)` 唯一约束配合 `ON CONFLICT DO NOTHING`，重复收藏返回成功；取消时按 `tenant_id + member_id + menuCode` 删除，重复取消同样成功；
- `GET /api/v1/apps/code/:code/menu` 会批量读取当前成员在该应用内的收藏集合，并在 `nodeMap[menuCode].favorited` 投影状态；
- 表单删除链路先删除其节点关联的收藏，再软删菜单节点；该顺序避免收藏指向已删除菜单；
- RBAC 将 `menu-favorites:create/delete` 授给 authenticated 系统分组，成员仍不能修改他人的收藏。

### 3.2 必须补齐的约束

现有 `AddFavorite` 能验证“节点属于请求中的应用”，但没有复用 `GetMenu` 的 `apps:get` 与最终可见性裁剪；同时当前 `capabilities.favorite` 随 `view` 直接投影，分组也可能显示收藏入口。这样会造成两类语义偏差：

1. 知道应用编码和节点编码的成员，理论上可尝试收藏无菜单读取权、隐藏或无资产访问权的节点；
2. 被隐藏或权限收回的收藏虽不会在正常菜单树出现，却可能留在后续“我的收藏”查询的候选集中。

因此后续开发必须将“节点可收藏”收敛为一个服务层策略，而不是只依赖路由权限或前端是否显示按钮：

```text
canFavorite(member, app, entry)
  = appCanRead(member, app)
  ∧ app.status = active
  ∧ entry.type ∈ {form, dashboard, page}
  ∧ entry is in member's effective menu snapshot
```

其中“effective menu snapshot”必须复用菜单读取时的完整规则：菜单 `hidden`、资产软删、表单权限组的 `view ∨ add` 判定，以及将来仪表盘/页面域的相应判定。服务端以此为唯一事实源；前端的 `capabilities.favorite` 只是其投影。

## 4. 领域模型与数据设计

### 4.1 关系模型

```text
tn_members (当前成员)
      1
      │
      │ 收藏（私有状态）
      n
tn_app_menu_favorites ── n:1 ── tn_app_menu_nodes
      │                                      │
      └──────────── n:1 ─────────────────────┴── tn_apps
```

收藏表冗余 `tenant_id` 与 `app_id` 是刻意的：它们是所有查询、删除和租户隔离的第一过滤条件，不需要通过节点表再反查。写入时必须由已校验的应用和节点回填，禁止相信客户端传入的数值 ID。

### 4.2 表定义

现有表结构可继续使用；新建环境的目标 DDL 如下（历史迁移中的原始表名由 `000063` 统一改为 `tn_` 前缀）：

```sql
CREATE TABLE tn_app_menu_favorites (
    id BIGSERIAL PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    member_id BIGINT NOT NULL,
    app_id BIGINT NOT NULL REFERENCES tn_apps(id),
    menu_id BIGINT NOT NULL REFERENCES tn_app_menu_nodes(id),
    created_at TIMESTAMPTZ,
    CONSTRAINT uk_tn_app_menu_favorites_member_menu
        UNIQUE (member_id, menu_id)
);

CREATE INDEX idx_tn_app_menu_favorites_member
    ON tn_app_menu_favorites (tenant_id, member_id, app_id);
```

`member_id` 与 `menu_id` 在本系统均为全局自增主键，故现有唯一约束可保证幂等。若未来成员 ID 改为“租户内编号”或收藏表被分片，唯一约束应升级为 `(tenant_id, member_id, menu_id)`，并同步调整冲突目标；在那之前不要新增重复索引。

不保存以下字段：

- `entry_name`、图标、表单名称：这些是菜单/资产的实时事实源，冗余会导致改名后不一致；
- `favorited` 布尔列：关联行是否存在即为状态；
- `menu_revision`：个人状态不属于共享树结构；
- 自定义排序：首期没有明确交互，避免过早引入排序重排和并发协议。

### 4.3 生命周期与一致性

| 事件 | 收藏表处理 |
| --- | --- |
| 收藏 | 对已通过 `canFavorite` 的节点执行幂等插入。 |
| 取消收藏 | 仅删除当前租户、当前成员对应行；不存在视为成功。 |
| 菜单节点/资产删除 | 与节点软删/资产删除在同一事务删除关联行。每一种新增资产类型都必须接入此维护口。 |
| 节点隐藏、资产权限撤销、应用归档 | 保留行但读侧过滤；以后恢复权限或显示状态时可自然恢复。 |
| 成员离开租户或应用被最终清理 | 由成员/应用清理事务显式删除关联行，不能仅等待外键，因为菜单节点是软删。 |

## 5. 接口契约

所有接口位于既有认证、租户、租户状态中间件链之后，统一返回 `{ code, msg, data }`。公开标识一律使用 `app_` 与 `menu_` 编码，绝不暴露数据库自增 ID。

### 5.1 收藏

```text
POST /api/v1/menu-favorites
```

```json
{
  "appCode": "app_3b355d3bfb73c444",
  "menuCode": "menu_flow_form"
}
```

成功（首次与重复请求均为 `200`）：

```json
{
  "code": 0,
  "msg": "成功",
  "data": { "menuId": "menu_flow_form", "favorited": true }
}
```

处理顺序：解析当前租户与成员 → 加载应用和菜单快照 → 计算有效可见节点集 → 校验目标属于该应用且可收藏 → 以 `(member_id, menu_id)` 幂等写入 → 返回最终状态。请求不携带 `baseMenuRevision`，因为它没有改变菜单树。

错误口径：应用不存在、跨租户或无读取权统一为 `APP_NOT_FOUND`；节点不属于该应用、分组节点或不可见节点返回 `APP_MENU_FAVORITE_INVALID`；无 `menu-favorites:create` 返回 `FORBIDDEN`。不得用错误信息泄露隐藏节点、资产或权限细节。

### 5.2 取消收藏

```text
DELETE /api/v1/menu-favorites/:menuCode
```

成功总是返回：

```json
{
  "code": 0,
  "msg": "成功",
  "data": { "menuId": "menu_flow_form", "favorited": false }
}
```

取消不要求目标仍可见，因为用户需要能够清除已被隐藏或已删除前留下的个人状态；SQL 必须限定当前 `tenant_id` 和 `member_id`。目标不存在或此前未收藏不报错，保证前端重试安全。

### 5.3 菜单快照中的状态投影

```text
GET /api/v1/apps/code/:code/menu
```

在既有 `nodeMap` 条目中返回：

```json
{
  "menuId": "menu_flow_form",
  "capabilities": {
    "view": true,
    "favorite": true,
    "actions": { "edit": true }
  },
  "favorited": true
}
```

`capabilities.favorite` 表示“当前可以执行收藏/取消”，而 `favorited` 仅表示当前成员是否已有记录。前端规则：`favorite=false` 时不渲染动作；`favorited=false` 显示“收藏”，为 true 显示“取消收藏”。不要根据本地数组猜测状态。

### 5.4 我的收藏列表（需新增）

仅有菜单快照的 `favorited` 无法支撑跨应用的“我的收藏”组件，因此建议新增：

```text
GET /api/v1/menu-favorites?cursor=<opaque>&limit=20
```

响应按 `created_at DESC, id DESC`，游标使用 `(created_at, id)`，不使用页码，以避免收藏/取消并发时重复或跳项：

```json
{
  "code": 0,
  "msg": "成功",
  "data": {
    "items": [
      {
        "app": { "code": "app_3b355d3bfb73c444", "name": "测试" },
        "entry": {
          "menuId": "menu_flow_form",
          "name": "流程表单",
          "type": "form",
          "icon": "file-list",
          "target": { "type": "form", "code": "form_xxx", "formType": "workflow" }
        },
        "favoritedAt": "2026-09-15 10:30:00"
      }
    ],
    "nextCursor": null
  }
}
```

列表查询先以 `tenant_id + member_id` 命中索引，再连接未软删应用和节点；随后必须复用资产可见性裁剪。权限失效或隐藏的记录只过滤、不在读取事务中删除，避免临时撤权后用户的显式收藏永久丢失。

## 6. 服务、仓储与权限职责

```text
MenuController
  └─ AppMenuService
       ├─ AppAccessEvaluator：应用读取权限
       ├─ Menu visibility builder：hidden、树与资产可见性
       ├─ FormPermissionDirectory：表单 view ∨ add
       └─ MenuRepository：限定 tenant/member 的幂等 DML
```

| 层次 | 应做的事 | 禁止做的事 |
| --- | --- | --- |
| Controller | 绑定编码、取当前成员、返回统一信封 | 根据前端参数判断节点归属或权限。 |
| Service | 复核 `apps:get`、计算 `canFavorite`、组织生命周期事务 | 将收藏视为资产授权，或信任中间件已完成全部对象级校验。 |
| Repository | 用当前租户/成员作为谓词，插入冲突忽略、精准删除 | 接收裸 `menu_id` 并缺少应用、租户约束。 |
| 菜单读取 | 批量加载收藏 ID 集合并投影，避免逐节点查询 | 在共享菜单快照缓存中写入某一成员的 `favorited`。 |

权限分两层：路由层使用 `menu-favorites:create/delete` 阻挡无资格调用；服务层再验证 `apps:get` 和节点的真实可见性。前者解决资源门禁，后者解决“当前成员能否对这个对象操作”。二者不可互相替代。

## 7. 并发、性能与安全

### 7.1 幂等与竞态

- 收藏：数据库唯一约束是最终幂等屏障，仓储使用 `INSERT ... ON CONFLICT DO NOTHING`；两个并发收藏只保留一行。
- 取消：`DELETE ... WHERE tenant_id=? AND member_id=? AND menu_id IN (...)`，受影响行数为零也是成功。
- 收藏与菜单删除并发：删除链路和收藏写入均需在验证后使用受租户约束的节点行；即使删除在收藏后完成，删除事务会清理关联行，读侧也会排除软删节点。
- 收藏与取消并发：最终状态以最后一次提交为准。界面在请求期间禁用同一节点动作，并以接口返回的 `favorited` 覆盖乐观状态。

### 7.2 查询与缓存

菜单读取只对一个应用批量查询一次收藏 ID 集合，复杂度为 `O(收藏数 + 节点数)`，禁止对每个菜单节点单独查询。跨应用收藏列表依赖成员索引并使用游标分页。若以后缓存公共菜单树，缓存内容只能是结构和资产投影；成员收藏集合必须单独读取或以 `tenantId:memberId` 为缓存维度，绝不能泄漏到其他成员。

### 7.3 审计与观测

收藏是频繁的个人偏好操作，不写入 `tn_audit_logs`，避免污染企业操作审计；保留结构化业务日志与指标：`menu_favorite_create_total`、`menu_favorite_remove_total`、`menu_favorite_list_total`、`menu_favorite_visibility_rejected_total`。日志只记录租户、成员和公开编码，不记录表单数据。

## 8. 开发拆分与验收

| 批次 | 内容 | 交付标准 |
| --- | --- | --- |
| P0（已落地） | 收藏表、幂等增删、菜单快照 `favorited` 投影、表单删除清理 | 重复收藏/取消安全，菜单结构修订号不变化。 |
| P1（应补齐） | `canFavorite` 统一策略；仅资产叶子节点可收藏；收藏写入复用有效可见性；`capabilities.favorite` 同源 | 无读取权、隐藏节点、无表单入口权限和分组都无法被收藏。 |
| P2 | `GET /menu-favorites` 跨应用列表、游标、工作台“我的收藏”接入 | 列表不会展示软删、隐藏或无权目标；权限恢复后收藏可恢复展示。 |
| P3 | 仪表盘/页面资产接入及其删除清理、性能指标与压测 | 新资产类型不会遗留孤儿收藏或绕过资产权限。 |

最低测试矩阵：

1. 同成员重复收藏只生成一条记录；重复取消返回 `favorited=false`；
2. 两名成员收藏同一菜单节点互不影响；跨租户、跨应用编码组合不可写入；
3. 无 `menu-favorites:create/delete` 时返回 `FORBIDDEN`；无 `apps:get` 时不泄露应用或节点；
4. 分组、隐藏节点、软删资产、无表单 `view ∨ add` 权限的节点不能收藏，也不出现在收藏列表；
5. 删除表单/菜单节点的事务同时清理收藏；恢复隐藏或权限后，未删除的收藏可再次展示；
6. 收藏、取消、节点删除并发执行后无重复行、无跨成员删除、列表无失效入口；
7. 菜单的 `menu_revision` 在收藏/取消前后不变，只有共享菜单结构变更才递增。
