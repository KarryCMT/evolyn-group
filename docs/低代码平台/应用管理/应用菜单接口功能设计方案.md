# 应用菜单接口功能设计方案

## 1. 结论

应用菜单应作为**应用内资产导航定义**独立建模，而不是复用现有 `iam.resources` 的 `menu` 类型，也不应塞进 `applications.config`。建议首期实现以只读菜单接口为交付边界：

```text
GET /api/v1/applications/code/:code/menu
```

接口使用当前应用编码定位应用，返回一个有序的、可按节点 ID 随机访问的菜单森林；组、表单、仪表盘和页面均是菜单节点。节点权限由当前成员、应用状态和后续资产权限在读取时派生，不持久化 `entryPerm` 一类布尔值。

在当前 M2-A 后端中，应用实例与租户边界、统一事务、配额、审计、应用编码及 `applications:get` 鉴权均已具备；表单、仪表盘、流程及其资产级权限尚未实现。`definition_version` 已明确用于应用发布演进、而非数据库乐观锁，本方案不改变该语义。因此本方案把“读取已可见菜单”与“创建资产时原子写入菜单”分阶段落地，避免以占位数据伪造低代码引擎能力。

## 2. 输入样本分析

用户提供的灵衍云菜单响应包含 22 个节点：7 个分组、11 个表单、4 个仪表盘；顶层顺序由 `entryList` 给出，完整节点由 `entryMap` 按 `entryId` 索引。其核心语义如下：

| 样本字段 | 语义 | evolyn 设计取舍 |
| --- | --- | --- |
| `entryList` | 根节点的展示顺序 | 保留为 `rootEntryIds`，顺序是接口契约。 |
| `entryMap` | 节点 ID 到节点详情的索引 | 保留为 `entryMap`，便于前端按 ID 查找、折叠和局部更新。 |
| `parent: "1"` | 虚拟根节点 | 改为 `parentEntryId: null`，不在数据库保存魔法值。 |
| `seq` | 同父节点排序值，样本以 1024 为间隔 | 使用 `sortOrder BIGINT`，首写 1024 间隔；服务端负责重排和压缩。 |
| `type: group/form/dash` | 分组或可打开的业务资产 | 使用稳定枚举 `group/form/dashboard/page`；不沿用歧义缩写 `dash`。 |
| `_id`、`entryId` | 资产 ID 与菜单节点 ID 两种身份 | 明确拆为 `entryId`（菜单节点）和 `target`（资产引用）。 |
| `hasCoop`、`hasFlow` | 表单能力摘要 | 由表单域投影为 `features`；当前没有表单域时不返回伪值。 |
| `entryPerm` | 当前会话可执行操作 | 改为服务端运行时派生的 `capabilities`，禁止落库。 |
| `hasFlowMenu` | 全局流程能力开关 | 改为顶层 `features.workflow`，由服务端能力注册表计算。 |
| `homeList` | 首页快捷入口 | 不属于应用资产树；首期不随菜单接口返回，后续由个人收藏/首页域单独提供。 |

样本中“根顺序”和“节点字典”是值得保留的传输结构；`_id`、魔法根 ID、重复的 `text`、前端图标数字以及会话权限则不应直接复制。

## 3. 现状与差距

### 3.1 已有后端基础

当前代码已经提供：

- `applications`：租户内应用实例，`code` 在活跃应用范围内租户唯一，支持 `active/archived`、软删及用于发布演进的 `definition_version`；
- `application_installations`：应用创建来源快照；
- `/api/v1/applications/code/:code`：按应用编码读取应用；
- `ApplicationAccessEvaluator`：对当前成员重新加载角色并派生 `applications:*` 权限；
- 统一租户中间件链、GORM 租户 Callback、`TxManager`、提交后审计和 `httpx.BizError`；
- 前端应用页已经以 `appCode` 为路由上下文，但工作区侧栏仍使用 `applicationWorkspacePreviewAssets` 的硬编码预览数据。

### 3.2 当前不能直接满足的部分

当前数据库没有菜单节点、表单或仪表盘表；`applications.config` 的注释也明确禁止存放表单、页面和流程等大定义。现有 `iam.resources.kind = menu` 是平台 RBAC 资源目录，用于“API/平台菜单”的授权元数据，不具备 `tenant_id`、`application_id`、父子关系、排序和资产引用，不能承载应用内菜单。

此外，现有 URL 鉴权只按“资源名 + HTTP 动词”匹配，不识别子资源动作。因此在没有新的鉴权 ADR 前，菜单管理接口只能复用 `applications:create`、`applications:patch`、`applications:delete`，不能假设 `applications:reorder`、`applications:menu-manage` 等新动词已经生效。

## 4. 目标与非目标

### 4.1 目标

1. 用应用编码在当前租户内读取完整、稳定排序的菜单树。
2. 支持分组以及后续表单、仪表盘、页面等资产在一个树中的导航。
3. 不向前端泄露跨租户数据、软删资产或无权资产；无可见子节点的分组须被裁剪。
4. 以菜单修订号（`menu_revision`）处理重排并发，菜单变化可被审计并驱动前端失效刷新。
5. 让表单/仪表盘创建、移动、删除以后都能在同一事务内维护菜单一致性。

### 4.2 非目标

- 不在本期实现表单、仪表盘、流程、动态数据表或其运行时；
- 不把个人“我的待办/我发起的/收藏”混入应用资产菜单；
- 不将单个成员的菜单权限或收藏状态写入公共菜单表；
- 不复刻灵衍云的 Mongo ID、数字图标编号或所有未使用字段。

## 5. 领域模型与数据表

建议新增迁移 `000016_application_menu`，并同步 `scripts/db.sql` 快照。菜单模型仍属于 `internal/platform/application/` 域，不应提前在 `internal/engine/` 新建空实现。

### 5.1 `application_menu_entries`

```sql
-- 菜单修订号独立于 definition_version；后者仍只用于应用发布演进。
ALTER TABLE applications
    ADD COLUMN menu_revision BIGINT NOT NULL DEFAULT 1;

CREATE TABLE application_menu_entries (
    id BIGSERIAL PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    application_id BIGINT NOT NULL REFERENCES applications(id),
    code VARCHAR(64) NOT NULL,
    parent_entry_id BIGINT NULL REFERENCES application_menu_entries(id),
    entry_type VARCHAR(16) NOT NULL,
    name VARCHAR(128) NOT NULL,
    icon VARCHAR(32) NULL,
    color VARCHAR(32) NULL,
    target_type VARCHAR(16) NULL,
    target_id BIGINT NULL,
    sort_order BIGINT NOT NULL DEFAULT 0,
    config JSONB NOT NULL DEFAULT '{}',
    created_at TIMESTAMPTZ,
    updated_at TIMESTAMPTZ,
    deleted_at TIMESTAMPTZ,
    CONSTRAINT chk_application_menu_entry_type
      CHECK (entry_type IN ('group', 'form', 'dashboard', 'page')),
    CONSTRAINT chk_application_menu_target
      CHECK (
        (entry_type = 'group' AND target_type IS NULL AND target_id IS NULL)
        OR
        (entry_type <> 'group' AND target_type = entry_type AND target_id IS NOT NULL)
      )
);

CREATE UNIQUE INDEX uk_application_menu_entries_tenant_code
    ON application_menu_entries (tenant_id, code)
    WHERE deleted_at IS NULL;

-- tiebreak 使用 code（与出网 entryId 同源），保证服务端输出序与前端复现序一致
CREATE INDEX idx_application_menu_entries_app_parent_sort
    ON application_menu_entries (tenant_id, application_id, parent_entry_id, sort_order, code)
    WHERE deleted_at IS NULL;

CREATE INDEX idx_application_menu_entries_app_target
    ON application_menu_entries (tenant_id, application_id, target_type, target_id)
    WHERE deleted_at IS NULL AND target_id IS NOT NULL;
```

字段约束与规则：

| 字段 | 规则 |
| --- | --- |
| `tenant_id`、`application_id` | 应用域服务在同一事务中从已加载的应用回填；查询始终受 Tenant Callback 限制。 |
| `code` | 服务端生成 `menu_` 前缀的随机稳定编码，供 API、前端 key 和审计引用；不使用前端提交的 ID。 |
| `parent_entry_id` | 根节点为 `NULL`；服务层必须验证父节点属于同一租户、同一应用且为 `group`。 |
| `entry_type` | `group` 没有目标；非分组节点必须恰好引用一种资产。资产表落地后，以服务层校验“目标资产属于同一应用”。 |
| `target_type`、`target_id` | `target_id` 保存资产域内部的数字主键；读取时由资产查询投影为稳定公开 `target.id`（资产 code）。在表单/仪表盘迁移落地前不建立指向尚不存在表的外键；相应资产服务在创建、移动、软删时与菜单同事务维护。 |
| `sort_order` | 仅在同父节点内有意义；新增使用 1024 间隔。重排由服务端写入连续间隔值，绝不相信客户端任意排序值。读取排序与索引 tiebreak 均为 `sort_order ASC, code ASC`，与 §6.2 的 `sortOrder ASC, entryId ASC` 契约同源。 |
| `config` | 只允许小型显示配置，例如页面打开方式；不存表单 Schema、流程定义、权限或前端组件名。 |
| 软删 | 继承应用域软删语义。删除资产时软删关联菜单节点；应用软删后的节点由应用清理任务处理，普通查询自动排除。 |

`parent_entry_id` 的同应用约束无法用普通单列外键表达，必须在 Service 层加载并核验。后续若确有数据库级强约束需求，可将 `(tenant_id, application_id, id)` 设计成可引用的唯一键并使用复合外键；首期不以触发器代替服务层校验。

### 5.2 版本与并发控制

新增 `applications.menu_revision BIGINT NOT NULL DEFAULT 1`，作为菜单专用的乐观并发口令；它与已定版的 `definition_version` 完全独立，后者继续只表达应用发布演进。菜单结构、菜单名称、资产绑定或重排成功时才增加 `menu_revision`；应用名称、图标、归档等非菜单更新不增加它。读取接口返回该值，管理写接口传入 `baseMenuRevision`，不匹配时返回 `APP_MENU_VERSION_CONFLICT`（409）。

版本占用必须在**任何菜单写入之前**以条件更新完成，不能先普通读取校验、最后无条件递增：

```sql
UPDATE applications
SET menu_revision = menu_revision + 1
WHERE id = :application_id
  AND tenant_id = :tenant_id
  AND menu_revision = :base_menu_revision
  AND deleted_at IS NULL
  AND status = 'active'
  AND provision_status NOT IN ('pending', 'running')
RETURNING menu_revision;
```

受影响行数为 0 时，服务层重新加载应用以区分 `APP_NOT_FOUND`、`APP_MENU_VERSION_CONFLICT` 与状态类错误，随后终止事务。条件更新成功即持有该应用行的写锁；后续锁定受影响的同父节点集合并写入节点/顺序均在同一 `TxManager.WithinTransaction` 内完成。后续任一步失败时整个事务回滚，包括刚刚占用的菜单修订号。

读取虽然不需要排它锁，但“菜单修订号与节点”必须是同一快照。`MenuRepository.GetSnapshot` 应以**单条 SQL（例如应用 CTE 联结节点）**返回应用和节点，或在一个只读 `REPEATABLE READ` 事务内先读应用、再读节点；禁止在默认 `Read Committed` 下用两个独立查询分别读取树和修订号。这样客户端不会取得“旧树 + 新 menuRevision”并在全量重排时漏检冲突。注意 `TxManager.WithinTransaction` 当前只开默认 `Read Committed` 读写事务，不支持指定隔离级别；**M2-菜单-1 首选单条 SQL 路径**（无基础设施依赖）。down 迁移需同时 `DROP TABLE application_menu_entries` 与 `DROP COLUMN applications.menu_revision`。

## 6. 读取接口

### 6.1 路由与授权

```text
GET /api/v1/applications/code/:code/menu
```

该路由位于既有租户业务域，经过：

```text
Authentication → Tenant → TenantStatus → Authorization → ApplicationMenuService
```

在当前授权器下，它使用 `applications:get`；Service 也必须用既有访问评估器复核，不能仅依赖中间件。应用不存在、已软删、跨租户或当前成员不能读取时，统一返回 `APP_NOT_FOUND`，避免泄露应用存在性。

### 6.2 成功响应

沿用后端统一信封 `{ code, msg, data }`。为与参考数据同样支持高效查找和严格排序，建议 `data` 如下：

```json
{
  "applicationCode": "app_6f391a21e65b4d8c",
  "menuRevision": 8,
  "rootEntryIds": ["menu_plan", "menu_progress", "menu_dashboard"],
  "entryMap": {
    "menu_plan": {
      "entryId": "menu_plan",
      "parentEntryId": null,
      "type": "group",
      "name": "计划管理",
      "icon": null,
      "color": null,
      "sortOrder": 1024,
      "target": null,
      "capabilities": {
        "view": true,
        "manage": true,
        "move": true,
        "delete": true,
        "favorite": false
      }
    },
    "menu_project_profile": {
      "entryId": "menu_project_profile",
      "parentEntryId": "menu_plan",
      "type": "form",
      "name": "项目档案",
      "icon": "file-list",
      "color": "primary",
      "sortOrder": 1024,
      "target": {
        "type": "form",
        "id": "form_customer"
      },
      "features": {
        "workflow": false,
        "collaboration": false
      },
      "capabilities": {
        "view": true,
        "manage": true,
        "move": true,
        "delete": true,
        "favorite": true
      }
    }
  },
  "features": {
    "workflow": false
  }
}
```

约定：

- `entryMap` 只包含当前成员可见的节点；按 `rootEntryIds` 开始并以 `parentEntryId` 建树。根节点与同父节点均按 `sortOrder ASC, entryId ASC` 排序；`entryId` 是公开且稳定的节点编码，前端可用它复现同值 `sortOrder` 时的服务端顺序。
- 表内 `target_id` 是资产域内部数字主键；`target.id` 是读取时经资产域映射的稳定公开编码。表单/仪表盘域落地时应各自提供 code；资产域落地前 target 暂不投影（出网为 `null`），菜单节点按库内真实菜单行出网（名称/类型/排序/图标来自菜单行本身，不返回硬编码的预览资产），供前端联调与 M2-菜单-2 树形渲染验证。
- `features` 只表达已经注册的后端能力。流程引擎未接入时固定为 `false`，不以菜单中是否“看起来像流程表单”猜测。
- `capabilities` 是本次请求的瞬态结果。首期由应用级权限和状态派生；资产级授权落地后再叠加表单/仪表盘访问结果。
- 返回空菜单是合法的 `200`，用于触发空应用引导；不是 `404`。

### 6.3 读取查询与权限裁剪

查询应先按 `tenant_id + application_id + deleted_at IS NULL` 读取所有节点，再由服务层合并资产可见性。资产域落地前没有资产级权限判定来源，资产节点按菜单行出网（`target` 为 `null`），接入资产查询与资产级授权后，资产不可见或已软删时排除其菜单节点；随后自底向上裁剪没有可见后代的分组（空分组始终裁剪）。发现孤儿节点、父节点不是分组或存在循环，记录告警并以 `APP_MENU_INVALID` 返回 5xx；这是服务端数据完整性故障，不是客户端可通过刷新解决的 409 冲突，也不能将损坏树作为正常数据悄然交给前端。

首期只有分组可手工创建，故空应用的正常响应为 `rootEntryIds: []`、`entryMap: {}`。表单、仪表盘未实现之前不应暴露用于演示的 `project-profile` 等硬编码条目。

## 7. 后续管理接口与写入规则

读取接口可独立先行。资产域落地后，按下列接口逐步开放；所有写接口使用应用编码，避免前端在路由上下文和 API 上混用数字 ID。

| 接口 | 当前授权映射 | 主要规则 |
| --- | --- | --- |
| `POST /applications/code/:code/menu/groups` | `applications:create` | 创建分组；验证父组、深度和 `baseMenuRevision`。 |
| `PATCH /applications/code/:code/menu/entries/:entryCode` | `applications:patch` | 仅更新分组名称/小型显示配置，或在同应用内移动节点。 |
| `PATCH /applications/code/:code/menu/orders` | `applications:patch` | 请求携带同一父节点的完整有序 `entryIds`；服务端验证集合完全一致后重新编号。使用 PATCH，避免 PUT 被当前 URL 鉴权器解析为 `applications:update`。 |
| `DELETE /applications/code/:code/menu/entries/:entryCode` | `applications:delete` | 仅能删除空分组；有子节点返回冲突，资产节点由资产删除流程处理。 |

表单、仪表盘和页面的创建服务不得由上述“通用菜单创建”接口直接生成空壳。正确流程是“创建资产 + 创建对应菜单节点 + 条件递增 `menu_revision`”处于同一个 `TxManager.WithinTransaction` 中。资产移动、改名或删除同理，避免出现可打开的资产没有导航入口，或菜单指向已经软删资产的短暂不一致。

首期可限制“分组最多嵌套两层、叶子节点总深度最多三层”；超出后返回 `APP_MENU_DEPTH_EXCEEDED`。这已覆盖参考数据的“分组 → 资产”结构，且能避免过深树对侧栏、拖拽和权限裁剪造成复杂度膨胀。需要无限级目录时应另行评审递归查询、性能和前端交互。

## 8. 权限、状态与审计

### 8.1 权限原则

- 读取应用菜单要求 `applications:get`；若后续列表入口直接消费菜单摘要，则仍以应用读取权限为前提。
- 菜单“管理”不是数据库角色字段。当前阶段使用 `applications:patch`、`applications:create`、`applications:delete` 映射；新增细粒度菜单动作前必须先扩展 Authorizer 的 `resource + subresource + operation` 模型并记录 ADR。
- 资产节点的 `view` 还必须通过资产域自己的授权判断。应用可读不等于任意表单可读。
- `owner_member_id` 不能绕过 RBAC 自动获得菜单编辑权，这与现有 `ApplicationAccessEvaluator` 的“owner 不放大权限”原则保持一致。

### 8.2 状态规则

| 应用状态 | 菜单读取 | 菜单管理 |
| --- | --- | --- |
| `active + ready` | 允许 | 按权限允许 |
| `active + failed` | 允许并可展示失败资产的可诊断状态 | 按权限允许菜单管理；资产重试仍由后续任务接口处理 |
| `active + pending/running` | 可返回初始化状态或空菜单 | 禁止写入，返回 `APP_PROVISIONING` |
| `archived` | 允许只读（若应用读取权限允许） | 禁止写入，返回 `APP_STATUS_INVALID` |
| soft deleted / 跨租户 | 不返回 | 不返回 |

### 8.3 审计

在事务提交成功后，以 best-effort 记录 `audit_logs`。沿用应用域短动作命名：`Module: "application"`，`Action: "create" | "move" | "reorder" | "delete"`，并以 `ResourceType: "application_menu_entry"` 区分资源；不新造 `menu_group_create` 一类长动作名。审计载荷仅包含应用编码、节点编码、节点类型、父节点变更和排序摘要；不得放入完整表单 Schema、成员权限详情或内部异常文本。

## 9. 错误码

在 `internal/platform/application/errors.go` 增加以下稳定错误，并同步前端 `@evolyn.do/utils` 的错误码定义：

| errCode | HTTP | 出网文案 |
| --- | --- | --- |
| `APP_MENU_NOT_FOUND` | 404 | 菜单节点不存在或无权访问 |
| `APP_MENU_PARENT_INVALID` | 400 | 菜单父节点无效 |
| `APP_MENU_TARGET_INVALID` | 400 | 菜单关联的应用资产无效 |
| `APP_MENU_DEPTH_EXCEEDED` | 400 | 菜单层级超过当前限制 |
| `APP_MENU_ORDER_INVALID` | 400 | 菜单排序请求无效 |
| `APP_MENU_VERSION_CONFLICT` | 409 | 应用菜单已更新，请刷新后重试 |
| `APP_MENU_INVALID` | 500 | 应用菜单数据异常，请联系管理员 |

数据库错误、目标资产内部错误和具体 ID 仅包装进日志，不放入 `msg`。

## 10. 代码落点与实施顺序

建议在既有应用域内扩展，不跨域创建空包：

```text
internal/platform/application/
├── controller/menu.go          # GET 菜单及后续写接口，中文 Swagger
├── model/menu.go               # MenuEntry、DTO、枚举
├── repository/menu.go          # ResolveDB(ctx, db) 查询与写入
├── repository/interface.go     # 菜单仓储接口
├── service/menu.go             # 校验、裁剪、版本/事务、能力派生
├── service/interface.go        # ApplicationMenuService 接口
└── errors.go                   # APP_MENU_* 稳定错误码
```

实施分批：

1. **M2-菜单-1：只读骨架。** 编写 `000016` up/down、同步 `scripts/db.sql`、新增模型/仓储/服务/控制器；空应用返回空树。此阶段不改现有应用创建接口的对外响应。
2. **M2-菜单-2：前端接线。** 在 `useApplicationHome` 成功读取应用后请求菜单接口，替换 `applicationWorkspacePreviewAssets`；用 `rootEntryIds + entryMap` 生成侧栏树，保留空状态和加载/重试状态。
3. **M2-资产-1：表单与仪表盘。** 每个资产创建、改名、移动、软删都通过应用菜单服务在同一事务维护节点；补资产可见性投影。
4. **M2-菜单-3：分组与重排。** 开放管理接口，接入 `baseMenuRevision`、完整同级排序校验和审计。
5. **M2-权限-后续：细粒度授权。** 先以 ADR 演进 URL Authorizer，再开放独立的菜单管理、收藏、复制、跨应用等动作；不能仅在 Controller 中新增自定义字符串权限。

每批至少覆盖：租户 A 不能读取/写租户 B 的菜单；软删应用/资产不出现；非分组父节点不可挂子节点；循环与跨应用父节点被拒；重排并发产生 409；空菜单返回 200；应用归档和初始化中写入被拒。后端验证执行 `cd apps/evolyn-core && go test ./...`，涉及新接口时执行 `make swagger`；前端接线后执行 `cd apps/evolyn-web && pnpm -F @evolyn.do/web typecheck && pnpm -F @evolyn.do/web build`。

## 11. 对现有前端的直接影响

当前应用主页仅通过 `getApplicationByCode(appCode)` 获取应用元信息，工作区侧栏把 `applicationWorkspacePreviewAssets` 作为临时数据源。菜单接口落地后应新增 `getApplicationMenuByCode(appCode)`，并将 UI 数据适配限制在一个 composable 中：

```text
后端 rootEntryIds + entryMap
        ↓
useApplicationMenu(appCode)（加载、错误处理、建树、按 capabilities 过滤）
        ↓
ApplicationWorkspaceSidebar（纯展示/选择事件）
```

不要让侧栏组件理解后端错误码、解析 `entryMap`、硬编码图标组件或发起 API。稳定图标键仍由前端的受控映射表转换为 Remix Fill 图标；未知键使用安全默认图标并记录前端可观测事件。

## 12. 验收口径

- `GET /api/v1/applications/code/:code/menu` 可在当前租户返回空树或真实有序菜单，不依赖硬编码预览资产。
- 响应使用 `null` 根父节点、稳定 `entryId`、明确 `target`，不包含灵衍云的 `_id`、`parent: "1"`、数字图标编号或持久化权限字段。
- 任何返回节点均属于当前应用和当前租户；不可见资产不会留下可见孤儿节点，空分组会被裁剪。
- 菜单写入和资产写入均符合当前 `TxManager`、`ResolveDB`、软删和提交后审计约束。
- 当前 RBAC 模型下的授权映射与 HTTP 中间件一致；细粒度菜单权限不以未被 Authorizer 识别的自定义动词“假实现”。
