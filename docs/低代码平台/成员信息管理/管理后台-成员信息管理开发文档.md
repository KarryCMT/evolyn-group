# 管理后台：成员信息管理开发文档

## 1. 文档目的与范围

本文定义租户管理后台“成员信息管理”的开发方案，覆盖当前界面的两个页签：

- **字段设置**：管理成员在“个人设置”页中的可见与可编辑权限；
- **卡片展示**：管理成员资料卡中展示的字段。

本期以当前界面已有的预置字段为范围，不提供管理员创建、删除或修改字段类型的能力。管理员在界面中勾选后应即时保存并在同一租户内生效；不设置额外的“保存”按钮。

## 2. 现状与目标

### 2.1 当前实现现状

前端已具备菜单、路由和两个页面，但字段集合、权限开关、卡片勾选与预览数据均为本地常量和内存状态。刷新页面或切换路由后配置会恢复默认值。

后端当前的 `users` 仅承载租户成员关系、昵称、状态、部门、分组和角色；手机号、邮箱、头像属于平台账号 `accounts`。工号、职务等资料仅存在于待接受成员邀请的 `member_invitations.profile` JSONB 草稿中，尚未进入正式成员档案。

### 2.2 建设目标

1. 为每个租户持久化预置字段的可见、可编辑和卡片展示配置。
2. 建立正式成员扩展档案，使工号、职务、入职日期等资料可长期保存和读取。
3. 让配置真实约束个人设置页的返回字段和更新字段，而非只影响视觉展示。
4. 让成员卡片和成员详情按同一配置读取数据。
5. 成员邀请被接受时，在同一事务中迁移邀请档案和部门归属。

## 3. 业务规则

### 3.1 预置字段目录

字段元数据由服务端固定维护，是接口响应的一部分，客户端不能提交或修改字段名称、类型及锁定规则。

| key | 名称 | 类型 | 实际数据归属 |
| --- | --- | --- | --- |
| `name` | 姓名 | 单行文本 | `users.nickname`，为空时回退账号昵称 |
| `code` | 编号 | 单行文本 | `member_profiles.identifier` |
| `mobile` | 手机 | 单行文本 | `accounts.phone` |
| `email` | 邮箱 | 单行文本 | `accounts.email` |
| `department` | 部门 | 部门多选 | `department_users` |
| `role` | 角色 | 角色多选 | `user_roles` |
| `alias` | 别名 | 单行文本 | `member_profiles.attributes` |
| `employeeId` | 工号 | 单行文本 | `member_profiles.attributes` |
| `gender` | 性别 | 单行文本 | `member_profiles.attributes` |
| `position` | 职务 | 单行文本 | `member_profiles.attributes` |
| `employment` | 聘用形式 | 单行文本 | `member_profiles.attributes` |
| `hireDate` | 入职日期 | 日期时间 | `member_profiles.attributes` |
| `workplace` | 工作地点 | 单行文本 | `member_profiles.attributes` |
| `birthday` | 出生日期 | 日期时间 | `member_profiles.attributes` |
| `education` | 学历 | 单行文本 | `member_profiles.attributes` |

`code`、`employeeId`、`position`、`employment`、`hireDate`、`workplace` 与既有邀请字段的 `identifier`、`employeeNo`、`title`、`employmentType`、`hiredAt`、`workLocation` 分别对应；前后端对外只使用本表中的统一 key。

### 3.2 锁定与约束

- 锁定规则由服务端字段注册表决定，禁止通过请求绕过。
- 当字段 `personalVisible=false` 时，服务端必须同时将 `personalEditable=false`。
- 当字段 `personalEditable=true` 时，必须同时满足该字段可编辑且 `personalVisible=true`。
- 手机、邮箱的值仍由账号安全绑定流程变更；即使它们在个人设置中展示，也不能经通用成员资料接口直接修改。
- 部门、角色通过现有关系管理接口维护，不接受通用成员资料接口写入。
- 姓名、编号等不可变字段的默认锁定策略以服务端字段注册表为准。

## 4. 数据设计

### 4.1 `tenant_member_field_settings`

用于保存租户级显示策略，每个租户、每个字段一行。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint | 主键 |
| `tenant_id` | bigint | 租户 ID |
| `field_key` | varchar(64) | 预置字段 key |
| `personal_visible` | boolean | 成员在个人设置可见 |
| `personal_editable` | boolean | 成员在个人设置可编辑 |
| `card_visible` | boolean | 成员卡片可展示 |
| `revision` | bigint | 乐观锁版本号 |
| `created_at` / `updated_at` / `deleted_at` | timestamp | 审计与软删除字段 |

约束与索引：

- `(tenant_id, field_key)` 建立有效记录唯一索引；
- `(tenant_id, updated_at)` 建索引，便于读取租户配置快照；
- `field_key` 的合法性由 Service 校验，不依赖数据库枚举，便于后续增加预置字段。

租户首次读取时，应由 Service 按服务端默认配置补齐 15 个字段；推荐在租户开通事务中预置，读取侧再做幂等兜底，确保旧租户也能得到完整配置。

### 4.2 `member_profiles`

用于保存正式成员的租户内扩展资料。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint | 主键 |
| `tenant_id` | bigint | 租户 ID |
| `member_id` | bigint | 对应 `users.id` |
| `identifier` | varchar(50) | 企业内编号 |
| `attributes` | jsonb | 别名、工号、性别、职务、日期等固定扩展值 |
| `created_at` / `updated_at` / `deleted_at` | timestamp | 审计与软删除字段 |

约束：

- `(tenant_id, member_id)` 建立有效记录唯一索引；
- 若产品确认“编号”须租户内唯一，则对 `(tenant_id, identifier)` 建有效记录唯一索引；
- `attributes` 只允许字段注册表中定义的扩展 key，日期统一校验为 `YYYY-MM-DD`，文本长度最多 50 个字符。

`member_profiles` 不重复存储手机号、邮箱、部门和角色，避免绕开既有账号安全与成员关系模型。

### 4.3 迁移要求

新增迁移文件时必须同步：

1. `migrations/NNNNNN_member_field_settings.up.sql` 与对应 down 文件；
2. `scripts/db.sql` 终态快照；
3. 每张新表和每个新增列的中文 `COMMENT`；
4. GORM Model、Repository 与必要的集成测试。

生产环境只以版本化 SQL Migration 建表，不依赖 GORM AutoMigrate。

## 5. 接口设计

所有接口属于租户域，使用现有认证、Tenant、TenantStatus、Authorization 中间件链。

### 5.1 管理端字段配置

#### 获取配置

```http
GET /api/v1/member-field-settings
```

响应：

```json
{
  "revision": 12,
  "fields": [
    {
      "key": "mobile",
      "label": "手机",
      "type": "单行文本",
      "personalVisible": true,
      "personalEditable": true,
      "cardVisible": true,
      "visibilityLocked": true,
      "editableLocked": true,
      "cardLocked": false
    }
  ]
}
```

#### 即时更新一个字段

```http
PATCH /api/v1/member-field-settings/:fieldKey
```

请求只允许提交本次变更的配置值和页面读取到的版本号：

```json
{
  "personalVisible": false,
  "personalEditable": false,
  "revision": 12
}
```

响应返回更新后的完整配置快照，前端以响应覆盖本地状态。字段设置页和卡片展示页均使用此接口；每次勾选立即请求，失败后回滚控件状态并提示错误。

不采用“整页保存”接口，以匹配当前界面没有保存按钮的交互。

### 5.2 成员资料读取与更新

```http
GET /api/v1/accounts/me/member-profile
PUT /api/v1/accounts/me/member-profile
GET /api/v1/members/:id/profile
PUT /api/v1/members/:id/profile
```

具体权限如下：

- `accounts/me/member-profile`：本人读取和更新；读取时按 `personalVisible` 裁剪，更新时仅允许 `personalEditable=true` 的扩展字段。
- `members/:id/profile`：管理员读取和维护成员扩展资料；权限由成员管理资源控制，不能替代手机号、邮箱、部门和角色的既有专用接口。
- 卡片使用资料接口的 `card` 视图，或在成员详情响应中新增按 `cardVisible` 裁剪后的 `cardProfile`；不得让前端自行读取隐藏字段再隐藏 DOM。

### 5.3 成员邀请接受

新增或完善受邀请注册/加入流程，使私有邀请 token 能被消费。接受时必须在一个事务中完成：

1. 校验邀请 token、状态、租户和受邀手机号/邮箱；
2. 创建或关联账号与正式成员；
3. 写入 `member_profiles`；
4. 建立部门关系；
5. 将 `member_invitations.status` 更新为 `accepted`；
6. 提交事务后追加审计日志。

公开邀请链接不携带成员档案，仍可沿用现有加入流程；不能将公开链接 token 与单人邀请 token 混用。

## 6. 后端实现结构

新增或扩展 `internal/platform/iam/` 中的模型、Repository、Service 与 Controller：

```text
iam/
  model/
    member_field_setting.go
    member_profile.go
  repository/
    member_field_setting.go
    member_profile.go
  service/
    member_field.go
    member_profile.go
  controller/
    member_field.go
    member_profile.go
```

职责要求：

- Service 维护唯一字段注册表及默认配置；
- Repository 一律经 `infrastructure.ResolveDB` 获取连接，加入上下文事务；
- 读取配置和更新配置均按当前租户过滤；
- 多步写入（邀请接受、成员资料及部门绑定）使用 `TxManager.WithinTransaction`；
- 审计日志在事务提交后以 best-effort 写入；
- 在 `server.go` 装配 Controller，并同步 Swagger 中文注释。

## 7. 权限、错误码与审计

建议新增资源与操作：

| 资源 | 操作 | 使用位置 |
| --- | --- | --- |
| `member_field_settings` | `get`、`update` | 管理后台字段设置、卡片展示 |
| `member_profile` | `get`、`update` | 成员扩展资料管理 |

建议新增稳定业务错误码：

| 错误码 | 场景 |
| --- | --- |
| `MEMBER_FIELD_NOT_FOUND` | 不存在的预置字段 key |
| `MEMBER_FIELD_LOCKED` | 修改受锁定的配置 |
| `MEMBER_FIELD_CONFIG_INVALID` | 可编辑与可见规则冲突或值非法 |
| `MEMBER_FIELD_CONFIG_CONFLICT` | revision 过期，配置被其他管理员修改 |
| `MEMBER_PROFILE_INVALID` | 扩展资料字段或日期格式不合法 |
| `MEMBER_INVITATION_ACCEPT_INVALID` | 邀请 token、状态或身份校验失败 |

配置与资料更新应记录操作人、租户、字段 key、变更前后值；手机号和邮箱不记录明文敏感值。

## 8. 前端对接改动

### 8.1 API 层

在 `apps/evolyn-web/apps/web/src/api/member.ts` 或独立 `memberField.ts` 中补充字段配置、成员档案读取与更新 API，前端字段 DTO 以服务端返回为准。

### 8.2 字段设置页

- 首屏调用 `GET /member-field-settings`；
- 勾选“可见”时，若关闭，前端先同步关闭“可编辑”，再发送一次 PATCH；
- 勾选“可编辑”或卡片展示时发送 PATCH；
- 请求期间禁用对应控件；失败后以服务端最近快照回滚并展示错误；
- 不再维护独立硬编码的可变配置。

### 8.3 卡片展示页

- 使用同一配置 store，切换页签不重复维护配置副本；
- 用服务端 `cardVisible` 初始化勾选；
- 预览可以保留样例成员，但生产成员卡片必须从按配置裁剪的服务端数据渲染；
- 适配暗黑模式，避免局部硬编码白色与品牌色；表格实现遵守项目 VTable 约束。

## 9. 实施顺序与验收

### 第一阶段：配置闭环

1. 新增字段配置迁移、Model、Repository、Service、Controller；
2. 在新租户和存量租户上补齐默认配置；
3. 接入管理端字段设置和卡片展示即时保存；
4. 覆盖租户隔离、锁定字段、联动校验、乐观锁冲突和权限不足测试。

### 第二阶段：成员档案闭环

1. 新增正式成员档案表与读写接口；
2. 对齐当前个人设置和成员详情的字段读取、编辑规则；
3. 补齐邀请接受时的档案和部门迁移；
4. 覆盖邀请码重复消费、事务回滚、跨租户访问、日期与字段长度校验。

### 验收标准

- 管理员修改字段/卡片开关后刷新页面仍保持配置；
- 不同租户的配置互不影响；
- 普通成员不能读取个人设置中被隐藏的字段，也不能提交不可编辑字段；
- 成员卡片不下发被关闭的字段值；
- 成员邀请接受后，正式成员资料与部门关系完整且邀请状态为 `accepted`；
- 后端执行 `go test ./...`，前端执行 `pnpm -F @evolyn.do/web typecheck` 与 `build`。

## 10. 非目标

本期不包含：

- 自定义字段的创建、删除、排序和字段类型变更；
- 成员卡片视觉模板编排；
- 跨租户共享成员档案；
- 手机号、邮箱安全绑定流程重构。
