# 数据库表命名空间前缀调整方案

## 1. 背景与目标

当前数据库业务表同时包含平台级、租户级、系统级及流程引擎数据，但多数表名没有表达其数据归属。随着平台、租户隔离、后台任务和流程引擎持续扩展，仅从表名难以判断数据访问边界，也不利于后续分库分表、审计和运维治理。

本方案统一以**数据所有权与隔离边界**作为表名前缀的判定依据：

| 数据边界 | 前缀 | 说明 |
| --- | --- | --- |
| 平台 | `pf_` | 平台拥有的全局业务实体，不属于某个具体租户。 |
| 租户 | `tn_` | 记录明确归属于某个租户，租户是其主要数据隔离边界。 |
| 系统 | `sys_` | 系统运行或全局定义数据，不是平台业务实体，也不属于某个租户。 |
| 流程引擎 | `wf_` | 流程引擎内部数据，维持现有独立命名空间。 |

本次仅调整物理表命名与对应数据访问代码，不改变 API 契约、前端接口字段或业务权限模型。

## 2. 归类原则

### 2.1 不以操作者决定归属

平台运营人员可以维护租户套餐、产品配置或成员资料，但这些记录的主体仍是租户，因此应使用 `tn_`，而不是 `pf_`。

### 2.2 不以是否存在 `tenant_id` 作为唯一依据

`pf_login_logs` 会记录登录时的租户上下文快照，但其主实体是平台账号；`pf_tenants` 本身没有“所属租户”的语义。相反，租户订阅即使由平台授予，也属于某个租户。

### 2.3 前缀后保留完整业务名

前缀只表达边界，后缀表达业务含义。原名已经以 `tenant_` 开头时，去除冗余的 `tenant_`，例如 `tenant_product_configs` 调整为 `tn_product_configs`，而不是 `tn_tenant_product_configs`。

### 2.4 `wf_` 是独立边界

流程引擎表已统一使用 `wf_` 前缀。本次不改动 `wf_definition`、`wf_instance`、`wf_task` 等 11 张流程引擎表；但流程引擎适配层中若直接读取其他领域表，应同步更新引用。

## 4. 审计日志的目标模型

当前 `audit_logs` 同时承载租户业务操作和 `tenant_id = 0` 的平台操作。该设计使表的物理归属不完全明确。

短期可以将其重命名为 `tn_audit_logs`，保持现有行为不变；但长期最佳方案是单独拆分：

| 目标表 | 内容 | 访问边界 |
| --- | --- | --- |
| `tn_audit_logs` | 租户业务操作审计，必须关联有效租户。 | 租户管理后台、租户导出。 |
| `pf_audit_logs` | 平台运营操作审计，不承担租户隔离。 | 平台运营后台。 |

审计拆分涉及历史数据归档、查询分流、导出与权限语义，属于领域模型调整，不应与机械表改名绑定在同一个交付批次。

## 5. 实施范围与分期

### 第一阶段：表名前缀标准化

1. 新增 `000060_table_prefixes.up.sql` 与对应 down 迁移，使用 `ALTER TABLE ... RENAME TO ...` 完成 52 张表的改名。
2. 同步更新 GORM `TableName()`、多对多关联表声明、原生 SQL、迁移集成测试和测试夹具。
3. 同步更新 `apps/evolyn-core/scripts/db.sql` 终态快照。
4. 按需重命名表相关索引、约束与序列，使数据库元数据也遵循新命名；表改名本身会保留这些对象的功能和关联关系。
5. 保持历史 `000001` 至 `000059` 迁移文件不变，以避免破坏 `schema_migrations` checksum 校验。

### 第二阶段：审计模型拆分

1. 设计平台审计与租户审计的独立模型、保留策略和访问接口。
2. 新增数据迁移，将既有数据按 `tenant_id` 分流。
3. 调整审计写入入口、企业日志查询和导出实现。
4. 在确认无存量依赖后，移除兼容读取逻辑。

## 6. 影响面

本次改名不改变 HTTP API，因此前端无直接表名依赖。影响主要集中在后端：

- 约 24 个 GORM 模型的表名映射；
- 约 18 个原生 SQL 使用点；
- 约 157 个 Go 文件需要筛查直接或间接的表名引用；
- 约 39 个测试文件需要验证；
- 流程引擎表不改名，但其表单、成员、组织适配器可能需要更新查询的目标表名。

## 7. 验收标准

1. 新库从 `000001` 完整执行至最新迁移后，表结构与 `scripts/db.sql` 快照一致。
2. 已有数据库升级后，原有数据、外键、索引和约束仍可正确使用。
3. 平台路由、租户路由、账号登录、成员与 RBAC、应用、表单、通知、版本与产品中心的单元测试及集成测试通过。
4. 流程引擎全部 `wf_` 表名称保持不变，流程定义、发起、任务流转及表单适配测试通过。
5. `schema_migrations` 仍能正确记录迁移版本与 checksum，历史迁移文件未发生修改。

## 8. 非目标

- 不调整 API 路由、请求字段或响应字段。
- 不调整前端页面、权限资源编码或业务领域名称。
- 不修改流程引擎 `wf_` 表。
- 不在本次变更中重命名 `schema_migrations`。
- 不在第一阶段实施审计日志的物理拆表。
