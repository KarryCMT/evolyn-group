# 企业级低代码平台技术架构设计

## 1. 架构定位

本平台采用：

> **Vue3 低代码设计器 + Go/Gin 平台核心 + PostgreSQL 统一数据底座 +
> Java/Flowable 流程引擎 + Eino AI 能力**

数据层同时支持：

-   PostgreSQL JSONB 动态数据模型
-   PostgreSQL Physical Table 物理表模型
-   后续可扩展 Hybrid 混合模型

核心目标是将平台能力沉淀为：

``` text
Schema → Engine → DSL → Planner → Compiler → Runtime
```

## 6. PostgreSQL 数据模型

平台不引入 MongoDB，统一使用 PostgreSQL。

### 6.1 JSONB 动态模式

适用于：

-   OA
-   审批
-   问卷
-   简单 CRM
-   行政
-   人事
-   轻量业务

示例：

``` sql
CREATE TABLE form_record (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    app_id UUID NOT NULL,
    form_id UUID NOT NULL,
    data JSONB NOT NULL,
    creator_id UUID,
    owner_id UUID,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

动态字段：

``` json
{
  "field_a81": "客户A",
  "field_b92": 120000,
  "field_c82": "华东"
}
```

优点：

-   字段新增无需频繁 ALTER TABLE
-   适合快速变化的 Schema
-   支持 GIN / 表达式索引
-   与 PostgreSQL 事务体系统一

### 6.2 Physical Table 物理表模式

适用于：

-   MES
-   ERP
-   WMS
-   采购
-   库存
-   订单
-   生产
-   设备
-   BOM

例如：

``` sql
CREATE TABLE app_x82_order (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    f_a812 VARCHAR(200),
    f_b923 NUMERIC(18,2),
    f_c723 VARCHAR(32),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

优势：

-   JOIN 更直接
-   B-tree Index
-   GROUP BY
-   ORDER BY
-   聚合查询
-   大数据量分页
-   外部系统 SQL 集成

### 6.3 Hybrid 模式

后续可支持：

``` text
高频核心字段 → Physical Column
低频扩展字段 → JSONB
```

兼顾查询性能与动态扩展能力。

## 7. Schema Engine

Schema Engine 是低代码平台最核心的基础能力之一。

负责描述：

``` text
Application
Form
Field
Page
Component
Data Model
Relation
Permission
Formula
```

字段示例：

``` json
{
  "id": "field_01J82",
  "name": "合同金额",
  "type": "decimal",
  "storage": {
    "column": "f_01j82",
    "type": "NUMERIC(18,2)"
  },
  "required": true
}
```

必须遵守：

``` text
field_id         永久稳定
field_name       可以修改
physical_column  永久稳定
```

例如：

``` text
合同金额
   ↓
订单金额
   ↓
含税金额

数据库字段始终：
f_01j82
```

## 8. Query Engine

Query Engine 是整个 Data Engine 的核心。

前端不能直接提交 SQL，而是提交统一 Query DSL：

``` json
{
  "filter": {
    "logic": "and",
    "conditions": [
      {
        "field": "field_amount",
        "operator": "gt",
        "value": 10000
      }
    ]
  },
  "sort": [
    {
      "field": "created_at",
      "direction": "desc"
    }
  ]
}
```

处理流程：

``` text
Query DSL
    ↓
Parser
    ↓
AST
    ↓
Schema Validation
    ↓
Permission Injection
    ↓
Relation Planner
    ↓
Query Planner
    ↓
Storage Resolver
    ↓
SQL Compiler
    ↓
pgx
    ↓
PostgreSQL
```

JSONB 模式可能编译为：

``` sql
(data->>'field_amount')::numeric > $1
```

物理表模式可能编译为：

``` sql
f_0182 > $1
```

上层完全屏蔽存储差异。

## 9. DDL / Schema Migration Engine

Physical Table 模式必须建设独立 Migration Engine。

不要：

``` text

   ↓
直接 ALTER TABLE
```

推荐：

``` text

   ↓
Save Draft
   ↓
Schema Version
   ↓
Schema Diff
   ↓
Migration Plan
   ↓
DDL Task
   ↓
DDL Executor
   ↓
PostgreSQL
   ↓
Publish
```

Schema Diff 示例：

``` text
Schema V10
   ↓
Schema V11

ALTER field_002
DELETE field_003
```

转换为：

``` text
ADD_COLUMN
ALTER_COLUMN
CREATE_INDEX
UPDATE_METADATA
SOFT_DELETE_COLUMN
```

## 21. 最终架构定版

> **Vue3 + Element Plus 构建设计态和运行态；Go + Gin 做平台主体；GORM
> 管理平台固定模型，pgx 承担低代码动态 DDL/DML 与 Query
> Engine；PostgreSQL 同时承载 JSONB 动态数据和 Physical Table
> 重业务数据；Redis + MinIO 提供缓存与文件基础设施；Java + Flowable
> 独立承担 BPM；Eino 作为 AI Agent 层。**

最终形成：

``` text
Vue3 + Element Plus
          ↓
       Go + Gin
          ↓
┌─────────┼──────────┐
│         │          │
Schema   Query    Permission
Engine   Engine     Engine
│         │          │
├──── Relation Engine
├──── Formula Engine
├──── Dashboard Engine
└──── DDL/Migration Engine
          ↓
     GORM + pgx
          ↓
      PostgreSQL
    JSONB + Physical
          │
     Redis + MinIO
          │
  Java + Flowable
          │
        Eino AI
```

平台建设重点应放在
**Schema、Query、Permission、Relation、Migration、Formula、Dashboard**
七大核心引擎，而不是重复建设基础 Web 框架能力。

# 二、顶层设计（2026-08 定版）

以下章节为平台顶层设计定版，是对上文的工程化落地；其中第 22 章细化并取代第 4 章的工程结构草案。关键决策见第 30 章 ADR。

## 22. 顶层工程拓扑（Monorepo 定版）

整平台在 `evolyn-group` 单仓内演进：

``` text
evolyn-group/
├── apps/
│   ├── evolyn-core/                 # Go 平台主体（沿用现有目录名，不改名）
│   │   ├── cmd/
│   │   │   ├── api/                 # HTTP API 入口
│   │   │   └── worker/              # 异步任务：DDL 执行、Automation、导入导出、Outbox 投递
│   │   ├── internal/
│   │   │   ├── platform/            # 固定模型业务（走 GORM）
│   │   │   │   ├── tenant/          # 租户管理
│   │   │   │   ├── iam/             # 用户/部门/角色，Casbin RBAC
│   │   │   │   ├── application/     # 应用管理与发布
│   │   │   │   ├── template/        # 应用模板（内置/自建/从模板创建）
│   │   │   │   ├── file/            # 附件元数据
│   │   │   │   └── audit/           # 审计日志
│   │   │   ├── engine/              # ★ 七大引擎，禁止依赖 gin/gorm/platform
│   │   │   │   ├── schema/  query/  permission/  relation/
│   │   │   │   ├── formula/  dashboard/  ddl/  automation/
│   │   │   └── infrastructure/      # 适配器层，实现 engine 定义的端口
│   │   │       ├── database/        # 共享 *pgxpool + GORM + 统一 TxManager
│   │   │       ├── cache/           # Redis（含 Stream 封装）
│   │   │       ├── storage/         # MinIO
│   │   │       └── workflow/        # Flowable HTTP 客户端
│   │   └── pkg/                     # 可复用非业务库：authentication、common、utils
│   └── evolyn-web/                  # Vue3 + TypeScript（沿用现有目录名，不改名）
├── services/
│   └── workflow/                    # Java + Spring Boot + Flowable
├── packages/
│   └── openapi/                     # ★ 全平台 API 契约唯一事实源
├── deploy/
│   ├── docker-compose.yaml          # 本地一键起 PostgreSQL/Redis/MinIO/workflow
│   └── docker-compose.prod.yaml
└── docs/                            # 设计文档（本文档所在位置）
```

要点：

- `internal/engine/` 与 `internal/platform/` 物理隔离：platform 是用 GORM 的固定模型业务，engine 是只认接口与 pgx 的核心资产；
- `packages/openapi/` 是 Go、Java、前端三方共同的契约源，任何客户端代码由它生成，禁止手写；
- `apps/evolyn-core` 与 `apps/evolyn-web` **沿用现有目录名不做更名**，随里程碑逐步演进为上述结构。

## 23. 模块依赖规则（CI 强制）

``` text
cmd/{api,worker}
     ↓
internal/platform  ←——  internal/infrastructure
     ↓                       ↑（实现端口）
internal/engine（仅接口 + pgx）
```

- engine 包**禁止** import gin、gorm 及 internal/platform 的任何类型；引擎需要的读 Schema、租户上下文等能力以端口接口（Ports）由 infrastructure 注入；
- GORM 的 postgres driver 底层即 pgx，全服务**共享一个 `*pgxpool`**，事务边界由统一 TxManager 管理：动态 DDL/DML 与固定模型操作落在同一连接池、同一事务体系，禁止出现第二套连接池；
- 以上规则用 golangci-lint `depguard` + CI 中的 `go list -deps` 检查强制执行。

## 24. 设计态 / 运行态生命周期与版本策略

**定版：只有表单与流程具备不可变版本；页面、仪表盘、权限配置保存即生效。**

| 资产           | 草稿 Draft | 不可变版本         | 运行态绑定                        |
| -------------- | ---------- | ------------------ | --------------------------------- |
| 表单 Form      | 有         | form_version       | form_record 记录创建时的版本      |
| 流程 Workflow  | 有         | flow_version       | 在途实例按发起时版本执行完毕      |
| 页面 Page      | 有（草稿即内容） | 无            | 始终最新                          |
| 仪表盘 Dashboard | 有（草稿即内容） | 无          | 始终最新                          |
| 权限配置       | 无         | 无                 | 始终最新                          |

流转规则：

``` text
表单：Draft（可任意改）→ Publish → form_version（不可变）→ 运行态使用
流程：Draft（可任意改）→ Publish → flow_version（不可变）→ 新发起实例使用
```

配套约束：

- **记录绑定版本**：`form_record` 保存 `form_version_id`，字段改名/删除不破坏历史数据；`field_id`、`physical_column` 永久稳定（衔接第 7 章）；
- **在途流程不受新版影响**：流程发布新版本后，仅新发起的实例使用新版，在途实例按发起时的 `flow_version` 走完全程；
- **发布时依赖校验**：表单字段删除/改名时，校验是否被流程节点、仪表盘指标、关联字段、公式引用，命中则拒绝发布——这是"无应用级整包版本"下防止跨资产引用断裂的唯一防线，必须建设；
- **DDL 延迟到发布时**：设计态保存只写草稿，Physical Table 的 ALTER 由 worker 异步执行（对应第 9 章 DDL Task），HTTP 请求内不跑 DDL；
- 后续若需要整应用回滚能力，可在不改本模型的前提下叠加"应用快照"（记录某时刻各资产版本组合），本期不建设。

## 25. 多租户体系（一级能力定版）

多租户是平台一级能力，而非仅做数据隔离。角色模型：

``` text
平台运营方（Super Admin，运营后台）
   └── 租户 Tenant（企业/组织）
         └── 租户管理员
               └── 部门 / 成员 / 角色（iam 模型，租户内封闭）
```

租户生命周期：

``` text
开通（租户编码/子域名、初始管理员）
   → 配置（品牌、套餐、配额）
   → 使用
   → 冻结（停用/只读）
   → 注销（软删除 + 数据保留期）
```

关键定版：

- **隔离机制**：单库共享表 + `tenant_id` 列 + PostgreSQL RLS 兜底。租户上下文由 JWT 中间件写入 `context.Context`，两条数据路径强制注入：GORM 走全局 Scope/插件，pgx 在 SQL Compiler 阶段注入；RLS 作为第二道防线防引擎缺陷导致跨租户读写，DDL Engine 为动态物理表建表时必须同步创建 RLS 策略；
- **租户识别**：登录以"租户编码 + 账号"或独立子域名识别租户，JWT 携带 tenantId，所有请求经租户中间件；
- **用户归属**：首期用户租户内封闭（一个用户属于单一租户、账号租户内唯一）；同一邮箱跨租户身份映射预留不做；
- **Flowable**：使用其原生 `tenantId`，由 workflow-service 从 Go 侧透传，Flowable 不自建用户体系；
- **配额与套餐**：应用数、表单数、成员数、存储容量、月度流程发起量；配额检查挂在应用/表单创建与附件上传路径，为商业化预留；
- **租户级配置**：logo、名称、首页、水印、语言等，存租户配置表并 Redis 缓存；
- **后台分离**：平台运营后台（管租户：开通/冻结/配额/用量统计）与租户业务后台（第 2 章的 Client Layer）为两套路由域；
- Redis Key 规范沿用第 15 章，所有 Key 必须含 `{tenant}` 段；
- 独立 schema / 独立库方案保留给后续"物理隔离大客户"档位，本期不封死。

## 26. Go ↔ Workflow 服务契约（HTTP + OpenAPI 定版）

``` text
Go platform ──HTTP + 内部服务令牌──→ workflow-service（Flowable）
     ▲                                      │
     └── 任务回调（HTTP，幂等，服务令牌）────┘
```

契约规则：

- 接口协议为**内网 HTTP + OpenAPI**，契约定义在 `packages/openapi`，双方生成客户端与服务端 stub；
- 认证使用**内部签发的服务间令牌**（service token），不透传用户 JWT 里的完整权限；
- 用户与部门以 `userId` 为准**单向同步**到 workflow-service，Flowable 只存映射不存档案；
- 发起审批时 Go 侧传递 `form_version + record_id` 快照引用，表单后续改版不影响在途流程取数；
- 跨服务一致性用**本地消息表（Outbox）**：Go 本地事务写 outbox，worker 异步投递到 workflow 与事件流，不用分布式事务；
- 所有回调接口以 `eventId` 做幂等键，at-least-once 语义。

## 27. 事件与消息底座（Redis Stream 定版）

``` text
本地事务 → Outbox 表 → worker 投递 → Redis Stream → Consumer Group → 订阅方
```

- 首期所有异步消息（Outbox 投递、Automation 触发、流程任务通知）统一走 **Redis Stream**，复用现有 Redis，不新增中间件；
- 每类事件一条 Stream（如 `stream:form-events`、`stream:flow-tasks`、`stream:automation`），消费侧使用 Consumer Group，处理成功后 XACK；
- 失败进死信 Stream（`stream:*:dlq`），Pending 超时由 worker 用 XACLAIM 回收重试；
- 语义为 **at-least-once**，所有消费方必须按 `eventId` 幂等；
- 代码层面以 `EventPublisher` 接口隔离，未来流量需要时平滑替换 Kafka，业务代码零改动。

## 28. 前端 TypeScript 定版

- M0 起前端全量 TypeScript：`vue-tsc` 进 CI，新代码一律 TS，存量 JS 通过 `allowJs` 渐进迁移；
- 表单/页面/流程/仪表盘设计器与渲染器**从第一行就是 TS**，Schema 类型定义与后端 DTO 对齐，后续可由 `packages/openapi` 生成；
- 存量 K8s 相关页面（Pod 终端等）随平台转型直接删除，不做迁移。

## 30. 架构决策记录（ADR）

### ADR-001 服务间协议：HTTP + OpenAPI

- 决策：Go ↔ Java 使用内网 HTTP，契约统一在 `packages/openapi`。
- 理由：实现与调试成本低，可复用网关、中间件与监控；当前调用频度不构成 gRPC 的必要性。
- 后果：性能上限低于 gRPC；个别高频接口未来可单独升级，不影响整体。

### ADR-002 事件底座：Redis Stream

- 决策：Outbox 投递、Automation 触发、流程通知统一走 Redis Stream，at-least-once + 幂等消费。
- 理由：复用现有 Redis，零新增运维成本，满足首期吞吐。
- 后果：超大流量或长期归档场景需迁移 Kafka；已用 `EventPublisher` 接口预留迁移路径。

### ADR-003 前端 TypeScript

- 决策：M0 起全量 TS，设计器新写、存量渐进迁移，vue-tsc 进 CI。
- 理由：设计器是重逻辑模块，Schema 类型安全是长期收益；越晚迁移成本越高。
- 后果：短期迁移工作量集中在 M0；与后端 DTO 的类型对齐收益在 M2 后显现。

### ADR-004 版本粒度：仅表单与流程

- 决策：只有 Form 与 Workflow Definition 具备不可变版本；页面/仪表盘/权限保存即生效。
- 理由：模型简单、用户心智负担低；数据兼容性风险恰恰集中在表单与流程两类资产上。
- 后果：跨资产引用破坏依赖发布时校验拦截（见第 24 章）；页面/权限误改需人工恢复；如需整应用回滚，后续叠加"应用快照"，不破坏本模型。

### ADR-005 多租户一级能力

- 决策：多租户为平台一级能力：租户开通/冻结/注销生命周期、套餐配额、租户级配置、运营后台与租户后台分离；隔离沿用共享表 + tenant_id + RLS（第 25 章）。
- 理由：企业级 SaaS 交付与私有化多组织场景共同需要，后补成本远高于先建。
- 后果：所有表、缓存 Key、Flowable 数据必须携带租户维度；运营后台带来额外开发量（计入 M1）。

### ADR-006 数据表格：VTable 生态

- 决策：数据表格统一采用 VisActor VTable 生态（vtable + vtable-editors + vtable-vue），取代第 2、3、19 章中的 vxe-table（见第 31 章）。
- 理由：Canvas 渲染满足大数据量浏览；内置透视表是仪表盘刚需；TS 原生与 ADR-003 契合。
- 后果：表格交互定制需按 VTable API 体系学习；图表层维持 ECharts，两套视觉规范需样式对齐，后续可评估 VChart 统一。

### ADR-007 应用模板

- 决策：支持官方内置模板与租户自建模板（应用另存为模板、从模板创建）；模板导入只产生草稿，field_id 冲突时整体重映射（见第 32 章）。
- 理由：降低从零搭建成本，沉淀行业最佳实践，是低代码平台获客与交付效率的关键能力。
- 后果：导出/导入与引用重映射引擎需在 M2 以 JSON 包形态先行，完整模板库在 M6 交付。

## 31. 前端数据表格定版：VTable 生态

本节定版并取代第 2、3、19 章选型中的 vxe-table。

选型：

``` text
@visactor/vtable             Canvas 渲染表格内核（虚拟滚动、大数据量）
@visactor/vtable-editors     单元格编辑器（输入/下拉/日期等）
@visactor/vtable-vue         Vue3 组件封装
```

承载场景：

``` text
运行态数据视图（列定义由表单 Schema 生成）
表单子表 SubForm 行内编辑
仪表盘明细表 / 透视表（Pivot Table）
批量导入预览 / 导出确认
```

设计要点：

- 列定义由 Schema Engine 输出的字段视图模型生成，渲染层不做业务判断，延续"设计态产生 Schema、运行态解释 Schema"原则；
- 性能：Canvas 渲染 + 虚拟滚动支撑大数据量浏览；取数仍走 Query DSL 分页/滚动加载，表格侧不得绕过 Query Engine 直接拉全量；
- 单元格编辑器与表单字段类型注册表一一对应，新增字段类型时两端同步注册；
- 图表层维持 ECharts（第 3 章既定）；若后续需要表内图表或统一 VisActor 视觉，可评估 VChart，本期不替换。

## 32. 应用模板体系

模板是**应用定义的可分发快照**，用于降低从零搭建成本、沉淀最佳实践。

模板构成：

``` text
应用模板 = 应用元信息
         + 表单 Schema（含字段定义）
         + 页面 / 仪表盘定义
         + 流程定义（草稿快照）
         + 权限预设（角色-资源映射）
         + 可选示例数据（默认关闭）
```

来源与可见范围：

``` text
官方内置模板：平台级，随版本发布，全租户可用
租户自建模板："应用另存为模板"生成，租户内共享或私有
模板市场：后期评估（M7 之后）
```

生命周期：

``` text
应用（已发布资产）→ 另存为模板 → 模板 vN → 从模板创建 → 新应用（全草稿）→ 走第 24 章正常发布
```

关键规则：

- **导入只产生草稿**：从模板创建的应用所有资产均为 Draft，发布期动作（依赖校验、DDL）不变；
- **field_id 重映射**：模板跨租户/跨应用导入时，若 `field_id` 或 `physical_column` 与目标冲突，整体重映射并同步修正公式、关联字段、流程表达式中的引用；无冲突则保留原 ID，保证模板可迭代；
- **模板与应用解耦**：已创建应用不随模板升级自动更新；模板升级 = 重新导出生成新版本；
- **示例数据**导入走 Data Engine 批量通道，受租户配额约束；
- **模板包格式**：首期 JSON 单文件；后续附件类资源引用 MinIO 对象并打包 zip。

与 AI 衔接：Eino Agent 的 `create_app` Tool 优先匹配官方模板，未命中再走字段级生成（第 17 章）。
