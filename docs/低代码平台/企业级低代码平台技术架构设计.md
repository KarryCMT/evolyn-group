# 企业级低代码平台技术架构设计

> 当前架构版本：**不包含 AI / Eino**\
> 核心技术路线：**Vue3 + Element Plus + VisActor + LogicFlow + Go/Gin +
> PostgreSQL + Redis + RustFS + Java/Flowable**

------------------------------------------------------------------------

## 1. 架构定位

平台定位为企业级低代码开发平台，核心覆盖：

-   应用设计
-   动态表单
-   页面设计
-   数据管理
-   工作流审批
-   仪表盘与数据分析
-   数据权限
-   公式计算
-   关联数据
-   自动化
-   JSONB 动态数据
-   PostgreSQL 物理表
-   开放 API

整体采用：

``` text
前端设计态 / 运行态
        ↓
Vue3 + TypeScript + Element Plus
        ↓
Go + Gin 平台核心
        ↓
Schema / Query / Permission / Relation / Formula / Dashboard
        ↓
GORM + pgx
        ↓
PostgreSQL
        ↓
Redis + RustFS

流程体系独立：
Java + Spring Boot + Flowable
        ↓
PostgreSQL Workflow DB
```

核心设计思想：

> **Schema → Engine → DSL → AST → Planner → Compiler → Runtime**

避免把业务能力硬编码在页面、Controller 或具体数据库结构中。

## 8. JSONB 动态数据模式

适合：

-   OA
-   审批
-   问卷
-   行政
-   人事
-   轻量 CRM
-   快速变化的业务表单

示例：

``` sql
CREATE TABLE form_record (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    app_id UUID NOT NULL,
    form_id UUID NOT NULL,
    data JSONB NOT NULL,
    creator_id UUID,
    owner_id UUID,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

业务数据：

``` json
{
  "field_a81": "客户A",
  "field_b92": 120000,
  "field_c82": "华东"
}
```

特点：

``` text
新增字段
   ↓
更新 Schema
   ↓
通常无需 ALTER TABLE
```

高频字段可以通过：

-   GIN Index
-   Expression Index
-   Partial Index

进行优化。

## 9. Physical Table 物理表模式

适合：

-   MES
-   ERP
-   WMS
-   BOM
-   采购
-   库存
-   订单
-   生产
-   设备
-   大数据量核心业务

例如：

``` sql
CREATE TABLE app_x82_order (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    f_a812 VARCHAR(200),
    f_b923 NUMERIC(18,2),
    f_c723 VARCHAR(32),
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

优势：

``` text
标准 SQL
JOIN
INDEX
GROUP BY
ORDER BY
复杂聚合
大数据量分页
外部系统集成
```

用户字段名称与数据库列名必须解耦：

``` text
field_id         = field_01J82
field_name       = 合同金额
physical_column  = f_01j82
```

即使：

``` text
合同金额
 ↓
订单金额
 ↓
含税订单金额
```

数据库列仍保持：

``` text
f_01j82
```


## 11. Query Engine

Query Engine 是 Data Engine 的核心。

前端禁止直接传递 SQL。

统一使用 Query DSL：

``` json
{
  "filter": {
    "logic": "and",
    "conditions": [
      {
        "field": "field_amount",
        "operator": "gt",
        "value": 10000
      }
    ]
  },
  "sort": [
    {
      "field": "created_at",
      "direction": "desc"
    }
  ]
}
```

执行链：

``` text
Query DSL
    ↓
Parser
    ↓
AST
    ↓
Schema Validation
    ↓
Permission Injection
    ↓
Relation Planner
    ↓
Query Planner
    ↓
Storage Resolver
    ↓
PostgreSQL Compiler
    ↓
pgx
    ↓
PostgreSQL
```

JSONB：

``` sql
(data->>'field_amount')::numeric > $1
```

Physical：

``` sql
f_0182 > $1
```

前端及上层业务无需感知底层存储方式。

## 12. DDL / Schema Migration Engine

物理表模式必须拥有独立的 Schema Migration Engine。

禁止：

``` text
HTTP Request
   ↓
Controller
   ↓
直接 ALTER TABLE
```

推荐：

``` text
Designer
   ↓
Save Draft
   ↓
Schema Version
   ↓
Schema Diff
   ↓
Migration Plan
   ↓
DDL Task
   ↓
DDL Executor
   ↓
PostgreSQL
   ↓
Publish Schema
```

支持：

``` text
ADD_COLUMN
ALTER_COLUMN
CREATE_INDEX
DROP_INDEX
SOFT_DELETE_COLUMN
UPDATE_METADATA
```

字段删除默认采用软删除：

``` text
用户删除字段
   ↓
Schema 标记 Deleted
   ↓
新版本不再展示
   ↓
物理列暂时保留
   ↓
延迟清理 / 人工确认
   ↓
DROP COLUMN
```

后续应支持：

-   Schema Version
-   发布
-   回滚
-   DDL 审计
-   异步执行
-   失败重试
-   大表变更
-   Migration 状态管理

## 23. 核心架构原则

### 23.1 前端不感知底层存储

``` text
Vue3
 ↓
Query DSL
 ↓
Query Engine
 ↓
Storage Resolver
 ├── JSONB
 └── Physical Table
```

### 23.2 Schema 是平台核心协议

``` text
Designer
   ↓
Schema
   ↓
Engine
   ↓
Runtime
```

### 23.3 动态 SQL 必须经过 Query Engine

``` text
DSL
 ↓
AST
 ↓
Validation
 ↓
Permission
 ↓
Planner
 ↓
Compiler
 ↓
pgx
```

禁止前端提交任意 SQL。

### 23.4 DDL 必须经过 Migration Engine

``` text
Schema Diff
 ↓
Migration Plan
 ↓
DDL Task
 ↓
Executor
```

不能把 DDL 散落在业务 Service 中。

### 23.5 设计态与运行态分离

``` text
Designer Component
≠
Runtime Component
```

### 23.6 先模块化单体，再按压力拆服务

第一阶段优先保证：

``` text
研发效率
事务简单
调试方便
部署简单
模块边界清晰
```

而不是追求微服务数量。

## 26. 多租户体系（一级能力定版）

> 本章恢复 2026-08 顶层定版中的多租户结论（原第 25 章 / ADR-005），并补充
> 契约级与落地层设计。多租户是平台一级能力，而非仅做数据隔离。

### 26.1 角色模型

``` text
平台运营方（Super Admin，运营后台）
   └── 租户 Tenant（企业/组织）
         └── 租户管理员
               └── 部门 / 成员 / 角色（iam 模型，租户内封闭）
```

### 26.2 租户生命周期

``` text
开通（租户编码/子域名、初始管理员）
   → 配置（品牌、套餐、配额）
   → 使用
   → 冻结（停用/只读）
   → 注销（软删除 + 数据保留期）
```

### 26.3 隔离机制（定版）

- **单库共享表 + `tenant_id` 列 + PostgreSQL RLS 兜底**，不采用
  schema-per-tenant / 库-per-tenant 作为主路径；独立 schema / 独立库方案
  保留给后续"物理隔离大客户"档位，本期不封死。
- 租户上下文由中间件写入 `context.Context`，两条数据路径强制注入：
  - GORM 路径：全局 Scope / 插件统一收口，业务 Repository 禁手写租户条件；
  - pgx 路径：Query Engine 的 SQL Compiler 阶段注入，`tenant_id` 是
    Query DSL AST 的必填隐式维度，由服务端注入，**禁止前端提交**。
- RLS 作为第二道防线，防引擎缺陷导致跨租户读写：会话级
  `SET LOCAL app.current_tenant`，策略统一为
  `tenant_id = current_setting('app.current_tenant')::uuid`；
  DDL Engine 为动态物理表建表时必须同步创建 RLS 策略。
- 复合索引最左前缀统一为 `tenant_id`；Migration Engine 生成的所有 DDL
  默认携带 `tenant_id NOT NULL`。

### 26.4 租户上下文契约

``` text
登录（租户编码 + 账号，或独立子域名识别租户）
   → JWT Claims：{ userId, tenantId, ... }
   → TenantContext Middleware（Authentication 之后、Authorization 之前）
   → gin.Context + context.Context 双写入
   → Service / Engine / Worker / 异步任务全链路携带
   → 审计日志、Trace、限流维度均含 tenantId
```

- 用户归属：首期用户租户内封闭（一个用户属于单一租户、账号租户内唯一）；
  同一邮箱跨租户身份映射预留不做。
- 缓存 Key 沿用第 18 章规范，所有 Key 必须含 `{tenant}` 段。

> **2026-08 修订（ADR-006，见第 27 章）**：上述「用户归属」表述与本节
> `{ userId, tenantId }` Claims 示意已被取代——平台账号与租户成员拆分后，
> Claims 定版为 `{ accountId, memberId, tenantId, name }`，同一账号可属
> 多个租户（登录后选择/切换）。本节其余契约（中间件顺序、上下文双写入、
> 全链路携带、缓存 Key 规范）不变，仍为现行结论。

### 26.5 数据模型（固定侧）

``` sql
sys_tenant (
    id UUID PRIMARY KEY,
    code VARCHAR(64) UNIQUE NOT NULL,   -- 登录识别用
    name VARCHAR(128) NOT NULL,
    plan VARCHAR(32) NOT NULL,          -- 套餐
    status VARCHAR(16) NOT NULL,        -- active / frozen / deleted
    config JSONB NOT NULL DEFAULT '{}', -- 品牌/水印/语言等租户级配置
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
)
```

- GORM 固定模型（User/Department/Role/Application/Form Definition 等，
  见 6.1）全部挂 `TenantID`，公共字段收敛进 BaseModel。
- 租户级配置（logo、名称、首页、水印、语言）存租户配置表并 Redis 缓存
  （Tenant Config Cache）。
- 动态侧 `form_record` 与物理表的 `tenant_id` 要求见第 8、9 章示例。
- 主键口径：平台固定侧（含 `sys_tenant`）沿用既有模型的 uint 自增主键与
  `TenantID`，避免对存量表的全量主键迁移；动态侧（JSONB 记录/物理表）保持
  UUID。两侧 ID 在 P2 由 ID 映射层统一。

**补充定版（2026-08，ADR-006/M1 已落地）**——固定侧在上述骨架之上补齐
账号、部门与租户扩展字段（模型落点 `internal/platform/{iam,tenant}/model`）：

``` text
accounts（平台账号：平台级、无 TenantID，时间三件套独立为 AccountBase）
    id uint PK / name 登录名全局唯一 / nickname / phone 全局唯一可空
    / email / password / avatar / auth_infos（第三方凭证挂账号）

users（租户成员：沿用表名，登录字段迁出至 accounts）
    account_id 归属账号 / nickname 租户内展示名
    / departments·groups·roles 多对多（BaseModel 含 TenantID）

departments（部门树：邻接表，ParentId=0 为根）
    parent_id / name / order 同级排序 / status（active/disabled）
    ；成员多部门挂载经 department_users 多对多

tenants 扩展列（owner_account_id / config / quotas）
    owner_account_id 开通者账号（is_owner 语义锚点，0 表示未设置）
    config JSONB：watermark{enabled,color,density}、theme{appNaviColor}、
        timezone（IANA）、locale；空值回落服务端默认
    quotas JSONB：键值配额覆盖，-1 不限 / 0 禁用 / 正数上限，
        缺键回落套餐默认值

套餐与配额（plan 常量与默认配额）
    plan ∈ { free, trial, pro }；配额首批五键：apps / forms / members /
    storage_gb / workflow_runs_monthly（free 3/10/5/1/100、trial
    10/50/30/5/10000、pro 全部 -1 不限；键值可扩展对齐灵衍云 pack 形态）
```

- `auth_infos` 归属由 user 改挂账号（`account_id`），存量列由启动幂等回填。
- 表名口径：GORM 实际表名为复数下划线（`accounts`/`users`/`departments`/
  `tenants`），本文 `sys_tenant` 为早期示意名，以实现为准。

### 26.6 权限、配额与套餐

- 租户内 RBAC：M1 起 Casbin 以租户为 domain（`p = {sub, dom, obj, act}`），
  与自研数据权限引擎叠加（见第 13 章）。
- 配额：应用数、表单数、成员数、存储容量、月度流程发起量；配额检查挂
  应用/表单创建与附件上传路径，为商业化预留。
- 后台分离：平台运营后台（管租户：开通/冻结/配额/用量统计）与租户业务
  后台（第 2 章 Client Layer）为两套路由域。

### 26.7 跨服务与存储

- Workflow：使用 Flowable 原生 `tenantId`，由 workflow-service 从 Go 侧
  透传，Flowable 不自建用户体系。
- RustFS：对象按租户隔离（bucket 或对象前缀），`sys_file` 元数据带
  `tenant_id`（见第 19 章）。

### ADR-006 平台账号与租户成员拆分（2026-08）

- **状态**：已定版，随 M1 后端全链路落地（模型、迁移回填、认证链路、
  API、种子）。
- **背景**：对标灵衍云登录形态的差距分析（`get_login_user` /
  `owned_tenant_list`）发现：灵衍云为「平台账号 × 多企业成员」——一个
  手机号可属多家企业，登录后选企业；而原模型 `users` 同时承载登录身份与
  租户身份、账号租户内唯一，无法表达一人多企业。
- **决策**：
  1. 拆分 `Account`（平台账号，`accounts` 表，平台级、无 TenantID；
     登录名/手机号全局唯一，密码与第三方 OAuth 凭证挂账号）与 `User`
     （租户成员，沿用 `users` 表，BaseModel 含 TenantID；仅承载租户内
     昵称与部门/分组/角色关联）。
  2. JWT Claims 定版 `{ accountId, memberId, tenantId, name }`：账号是
     登录身份，成员关系是会话绑定的租户上下文；切换租户即重签 token。
  3. 登录链路：账号名/手机号 + 密码 → 全局查账号 → 取成员关系（可用
     `tenantCode` 指定，缺省取第一个）→ 签发；注册与 OAuth 首登同时创建
     账号与默认租户成员。
  4. 租户选择与切换：`GET /auth/tenants`（账号的成员关系列表，含
     `is_owner`，对齐灵衍云 owned_tenant_list）与
     `POST /auth/token/switch`（切换租户重签）。
  5. 前端启动引导聚合接口：`GET /auth/userinfo`（账号资料 + 当前租户
     config/套餐配额 + 成员身份 is_admin/is_owner/部门）与
     `GET /auth/permissions`（按 Role.Rules 推导 resource → verb 权限
     布尔集）。
  6. 租户增加 `owner_account_id`（开通者账号，is_owner 语义锚点）与
     `config`/`quotas` JSONB（字段定版见 26.5 补充定版）。
- **取代关系**：26.4 中「用户归属：首期用户租户内封闭……同一邮箱跨租户
  身份映射预留不做」及该节 `{ userId, tenantId }` Claims 示意由本 ADR
  取代；26.4 其余契约（中间件顺序、上下文双写入、全链路携带）不变，
  仍为现行结论。
- **影响**：认证中间件按 claims 的 memberId+tenantId 加载成员；成员/
  部门/账号自助 API（`/api/v1/members`、`/api/v1/departments`、
  `/api/v1/accounts/me`）替代旧 `/users` 路由；存量库由启动幂等回填对齐
  （按 users 同 ID 复制 accounts → 回填 `users.account_id` →
  `auth_infos.account_id` → 默认租户 owner 指向 admin 账号）。

### ADR-007 后端工程结构定版：域模块化 + 解散 pkg（2026-08）

- **状态**：已定版，随 M1 与模型改造同批一次迁移到位。
- **背景**：第 5 章「建议工程结构」按业务域给目录，但存量实现是全局技术
  三层（controller/service/repository 跨域共享、巨型聚合接口）；顶层
  `pkg/` 与 `internal/` 并存且 pkg 反向依赖 internal/model，单模块私有
  仓库亦无可复用层需求。
- **决策**：
  1. **域模块化单体**：技术三层拆进各业务域，域内保留 controller →
     service → repository 小三层与域内 model；HTTP 服务器装配与路由
     注册集中在 `internal/platform/server`。
  2. **定版结构**：`internal/platform/{server, controller, middleware,
     auth, iam, tenant, ginctx, httpx}` + `internal/infrastructure`
     （postgres/redis/pgx 客户端、租户 Callback、生命周期）；跨域共享
     内核收 `internal/model`（BaseModel）与
     `internal/{config, contextx, metrics, utils, version}`。
  3. **解散顶层 `pkg/`**：`pkg/authentication` → `internal/platform/auth`
     （JWT 与 OAuth）；`pkg/common` 按职责拆为 `platform/ginctx`
     （gin 上下文助手）与 `platform/httpx`（统一响应）；`pkg/utils` →
     `internal/utils`；`pkg/version` → `internal/version`（Makefile
     ldflags 注入路径同步）。全量消除 pkg → internal 反向依赖，后续不再
     新建顶层 `pkg/`。
  4. **拆除 authorization 全局单例**：包级 store 改为显式依赖注入
     （`internal/platform/iam/authorization`），为 Casbin 接入铺路。
  5. **引擎域落位**：第 5 章清单中的引擎目录（schema/query/permission
     等）随 M2 起按里程碑逐个落 `internal/engine/`，不预建空包；引擎
     代码禁止 import gin/gorm。
  6. 第 5 章「建议工程结构」的顶层域目录（tenant/iam/application/...）
     由本 ADR 修订为 `internal/platform/` 前缀形态；该章「Gin 只承担
     API/Web 层、Engine 不与 Gin 耦合」的结论不变。
- **影响**：全量 import 路径变更与 Makefile ldflags 注入路径同步；
  repository 巨型聚合接口按域拆分；运营域（`/api/v1/platform`，无租户
  上下文）与租户业务域路由分离。



### ADR-008 统一业务错误码体系（2026-08）

- **状态**：已定版，批 1 已落地（错误类型、自动映射、既有哨兵改造、
  前端 errCode 消费）；裸错误全量 BizError 化随接口迭代渐进（批 2）。
- **背景**：统一响应 `{code, msg, data}` 的 `code` 直接复用 HTTP 状态码，
  双义无业务码空间；6 个稳定哨兵码仅 2 个有判定点；103 处错误响应的
  状态码映射不一致（同错不同码：重复创建散落 400/500，记录不存在散落
  400/403）；`err.Error()` 原文直出客户端（GORM 错误含 SQL 片段、租户
  ID 等内部数据）；前端 `ApiError.code` 带而不用，只能靠
  `msg.includes('cooldown')` 文本匹配分支。整改文档 FIX-002/003/006/011
  早已要求「稳定错误码」，本 ADR 收口为体系。
- **决策**：
  1. **信封渐进扩展**：`code` 保持 HTTP 状态码（兼容），新增 `errCode`
     string 字段承载稳定业务码（成功省略）。前端 `ApiError` 增加
     `errCode`，按码分支，禁止 message 文本匹配。
  2. **BizError 错误模型**（`internal/platform/httpx/errors.go`）：
     `{Code, Msg, HTTP, err}`——稳定码 + 对外安全文案 + 建议状态码 +
     仅入日志的原始错误；`errors.Is` 按 Code 判定（兼容 `%w` 包装链与
     既有哨兵调用方）。
  3. **ResponseFailed 自动映射**：BizError → 其 HTTP/Code/Msg；
     `gorm.ErrRecordNotFound`/`redis.Nil` → 404/`NOT_FOUND`；未知 5xx →
     500/`INTERNAL_SERVER` + 脱敏通用文案（原文只进日志）；未分类 4xx →
     保留调用方判定与文案，errCode 按状态给通用码。调用点签名不变，
     既有 if-ladder 可删。
  4. **状态码语义修正**：重复冲突 409、记录不存在 404、跨租户拒绝 403、
     配额超限 403、频控 429；前端当前无 409/404 消费点，无破坏。
  5. **码表治理**：通用码（`httpx`）+ 域码（iam/tenant/auth 各域包顶部
     定义，注释即文档）；新接口错误必须走 BizError（禁裸 `errors.New`
     出网），swagger `@Failure` 注明 errCode。
- **影响**：`DUPLICATE_NAME/DUPLICATE_MEMBER` 400→409、`QUOTA_EXCEEDED`
  数值细节不再外泄、`sms.ErrCooldown` 等英文句子文案废弃改稳定码中文
  文案；前端 `errorCodes.ts` 与后端码表对齐维护。

### ADR-009 账号会话体系与 TOTP MFA（2026-08）

- **状态**：方案定版，分批实施中（任务清单见
  `docs/低代码平台/账号安全/`）。
- **背景**：账号安全面板的「登录二次验证」「禁止同时登录」两个开关，
  现有能力不足以支撑——`session_version` 只能全账号失效（无法区分设备）、
  `jti` 黑名单只能吊销单枚令牌（无会话实体，无法「新登录挤掉旧登录」）；
  登录日志是流水而非可校验可撤销的会话。
- **决策**：
  1. 引入平台级 `account_sessions` 会话实体（sid/token_version/auth_method/
     revoked_at/...），JWT 增加 `sid` 与 `sessionTokenVersion`，认证中间件
     校验会话有效性；租户切换复用 sid（不算新设备）。
  2. MFA 一期为「密码 + TOTP 验证器」：挑战式两步登录（Redis mfaChallenge，
     5 分钟/单次/限次），OAuth/短信入口同样过第二步；恢复码只存摘要。
     短信码不作为第二因子（同证据类别不构成 MFA）。
  3. 「禁止同时登录」以登录事务内锁账号行实现：撤销其他活跃会话后建新
     会话；被挤出请求返回稳定码 `AUTH_SESSION_REPLACED`。
  4. 保留 `session_version` 承担密码变更的全账号失效；两机制职责分置。
  5. TOTP 密钥仅密文存储（`key_version` 支持主密钥轮换，主密钥生产配置
     注入）。
- **关联**：完整数据模型/流程/接口/落地顺序见
  `docs/低代码平台/账号安全/账号安全与会话体系设计方案.md`。
  Web Storage 令牌迁移（HttpOnly 刷新 Cookie/BFF）为独立批次，不与 MFA
  捆绑。


### ADR-010 表单保存协议定版：目标保存协议替换 FormDocument（2026-08）

- **状态**：已定版，P1+P2 基础字段纵向切片实施中（分期见
  `docs/低代码平台/表单设计器/目标保存协议重构与分期实施方案.md`）。
- **背景**：表单域开工在即，现有 `packages/form` 持久化模型
  `FormDocument {version,kind,title,fields,settings}`（字段 `FormField {id,key,type,
  label,required,config}`）与用户确认的目标保存协议两层结构不一致；设计器画布仅
  7 类控件、运行时仅 9 类基础组件、后端表单资产域空白，按「改字段名」处理会造成
  协议分叉与双事实来源。
- **决策**：
  1. 表单保存给后端的唯一事实结构固定为目标保存协议：
     `{content:{type:"form",items:[{widget:{type,widgetName,enable,visible,
     allowBlank, ...专属属性}, label, description, labelHidden, lineWidth}]}}`；
     设计器、后端草稿、发布版本与最终渲染器均直接读写该结构，禁止在中间持久化
     另一份等价 Schema（含旧 `FormDocument` 兼容层/双写）。
  2. `widget.type` 为判别键（27 种，字段字典逐项冻结：
     `docs/低代码平台/表单设计器/目标协议字段字典.md`）；`widget.widgetName` 是
     记录值、规则与错误回填的稳定字段键；未知字段不可静默删除，保存/发布返回
     JSON Path 级错误。
  3. 字段类型分批交付、协议不可分叉：未完成运行能力的控件由服务端发布白名单
     拦截（P2 仅开放 9 类基础字段），不得发布后在用户侧静默「暂不支持」。
  4. 结构与执行分离：`enable/visible/labelHidden/lineWidth/allowBlank` 等静态
     属性按保存值执行；依赖其他字段的动态规则以声明式 JSON 另行定义，Schema
     不执行任意 JavaScript。
  5. 发布不可变：草稿（forms.draft_content + draft_revision 乐观锁）与发布快照
     （form_versions，version_no + schema_revision 修订口令）分表存储；记录提交
     必须带 `publishedVersion + schemaRevision`，服务端按对应快照终审。
  6. 后端新增表单域 `internal/platform/form`（ADR-007 结构）与 `forms` /
     `form-records` 权限资源、`forms` 配额键；数据模型与 API 契约见
     `docs/低代码平台/表单设计器/表单资产域后端契约.md`。
- **取代关系**：取代《表单最终渲染器架构与实施设计》§4.1「FormDocument 为唯一
  Schema 事实来源」的结论（该文档已就地标注）；其 RuntimeStore/渲染器分层、Adapter
  注入边界、性能预算等结论在目标协议上继续有效。
- **影响**：`packages/form` schema/designer/runtime 三入口按协议重写并删除旧插件
  设计器遗留簇（开发环境无存量数据，不做数据迁移，清单见
  `docs/低代码平台/表单设计器/迁移清单与验收矩阵.md`）；前端 `packages/utils` 错误码
  表随表单域码同步；后端迁移 000037/000038 落表单资产/版本/记录。

### ADR-011 菜单按钮动作授权：注册表 + form-actions 资源扩展 RBAC（2026-08）

- **状态**：已实施（迁移 000046/000047，设计见
  `docs/低代码平台/应用管理/菜单按钮权限与节点状态设计方案.md`）。
- **背景**：应用菜单节点的右键按钮（编辑/改名/切换类型/复制/移动/隐藏/删除等，
  按表单类型呈现不同集合）需要按钮粒度授权；既有两层授权（URL 级
  `resource:verb` 中间件门 + 菜单读取时应用级派生的粗粒度 capabilities）
  均无按钮粒度，且一半按钮（切换类型/复制/隐藏/收藏）连后端端点都不存在。
- **决策**：
  1. 按钮动作建「动作注册表」（`iam/authorization/menuactions.go`，代码常量
     唯一事实源）：节点类型 → 动作授权表，每动作声明授权键（AND 语义，连同
     对应 URL 门权限键一起声明，保证投影按钮不被中间件 403）与 Landed
     （端点未落地不投影，与 MenuFeatures「只表达真实能力」同口径）。
  2. 动作授权存储扩展既有 `roles.rules` JSONB：新增 `form-actions` 资源，
     动作键 `switch-type/copy-in-app/copy-cross-app/hide`。该资源刻意不对应
     任何 URL 首段——中间件 URL 门永不命中，动作键只由各域 Service 按权限集
     复核，因此动作授权不可能越权放大 URL 访问；`PermissionsOf` 的键透传使
     派生零改动。否决自定义动词（会以 URL Authorizer 不识别的动词假实现）与
     独立授权表（与 roles.rules 形成双事实源）。
  3. 「对成员隐藏」拆两层：管理动作（`form-actions:hide` 控制按钮）+
     节点属性（`application_menu_entries.hidden` 列，普通成员读侧裁剪）；
     仅导航隐藏，不拦截 runtime 直连（资产级访问控制属后续批次）。
  4. 「收藏」是个人状态动作不是授权对象：新表 `application_menu_favorites`
     （member×entry 唯一幂等，硬删），`menu-favorites` 资源授全体成员
     （create/delete），与菜单管理权限彻底分离（口径同 form-records 与
     forms 的关系）。
  5. `form_type` 不可变语义放宽（取代 000044 注释「创建后不可变」）：
     standard↔workflow 可经 `form-actions:switch-type` 切换，流程表单切标准
     后原流程数据保留，仅不可再发起流程；草稿与发布快照不受影响。
  6. 资产节点展示属性（名称/图标/颜色）以资产域为事实源：「修改名称和图标」
     走单一权限点 forms:patch，经 MenuMaintenance 窄端口同事务同步菜单行；
     菜单接口拒绝旁路改名资产节点。
- **影响**：迁移 000046（hidden 列 + 收藏表）、000047（管理员规则签名补授
  `form-actions:*`、authenticated 分组补授 menu-favorites）；菜单快照
  capabilities 携带 actions 按钮图与 Favorited 状态（读时派生不落库）；
  新增 switch-type/copy/references/menu entries PATCH/favorites 端点；
  自定义角色可在权限中心按动作键单独授予/回收按钮能力。

### ADR-012 流程引擎定版：纯内核 + 平台适配层 + DSL v1（2026-08）

- **状态**：Phase 0~6 已实施（架构/协议/语义冻结 → Definition → 最小
  Runtime → Form/Expr/动态审批人 → 完整人工 Task Engine → wf_job 延时
  任务 → workflow.* 事件接入既有 Outbox；设计基线见
  `docs/低代码平台/流程引擎/流程引擎阶段开发功能设计v1.1.md`）。
- **背景**：平台需要原生审批流能力（顺序审批、条件路由、动态审批人、
  或签/会签、驳回/退回/撤回/转办/抄送、表单联动），作为 V1 不引入
  Flowable/BPMN，也不做 Go 版 Flowable；Workflow 核心从
  `internal/workflow` 调整为 `internal/engine/workflow`（V1.1 修正）。
- **决策**：
  1. 分层定版：`internal/engine/workflow` 为纯 Go 引擎内核（禁依赖
     gin/gorm/redis/http 与任何 platform 具体实现，平台能力经
     provider/ 窄端口注入）；`internal/platform/workflow` 为适配薄壳
     （Controller/Service/GORM Repository/Provider Adapter/Job Worker），
     依赖方向唯一（platform/workflow → engine/workflow）。未来拆
     `services/evolyn-workflow` 只替换 Adapter，不重写 Runtime。
  2. 事务唯一事实源：复用既有 `TxManager / ResolveDB`，禁止第二套
     事务边界；PostgreSQL 是 Workflow Runtime 状态唯一事实源，行锁
     （FOR UPDATE）与 `FOR UPDATE SKIP LOCKED` Worker 竞争由适配层承担。
  3. DSL v1 单文档存储：废弃 `wf_node`/`wf_edge` 独立表，Node/Edge/
     Config 内嵌于 `wf_definition.draft_content`（草稿 +
     draft_revision 乐观锁）与 `wf_definition_version.dsl_snapshot`
     （发布不可变快照）JSONB，消除发布事务双写一致性负担；运行时
     Navigator 按 node key 从快照读配置。`wf_definition.code` 为稳定
     公开标识（对齐表单域 `form_code` 迁移 000045 先例），内部自增
     ID 不出网，版本以 `version_no` 标识。
  4. 状态语义 Phase 0 冻结于 `task/state_machine.go` 迁移表（唯一
     事实源，代码不得自行解释）：Instance（DRAFT/RUNNING/COMPLETED/
     REJECTED/CANCELLED）、NodeInstance（PENDING/RUNNING/WAITING/
     WAITING_RESUBMIT/COMPLETED/REJECTED/CANCELLED）、Task（PENDING/
     APPROVED/REJECTED/TRANSFERRED/CANCELLED/EXPIRED）；V1 Reject 仅
     terminate、禁止任意跳转、撤回仅限无已完成人工任务窗口、会签阈值
     `ceil(total * passRatio)`；审批人任务创建时一次性快照。
  5. 表单交互铁律：Workflow 不直接写 `form_records`，读写一律经
     BusinessDataProvider 窄端口由 Form Domain 校验完成；实例发起时
     冻结绑定 Form Version/Snapshot，运行中不随表单重新发布切换。
  6. 事件与调度：接入既有 notification 域 `EventPublisher.PublishInTx`
     / Outbox（禁新建 domain_outbox），事件目录 `workflow.*` 冻结；
     V1 不引入 Asynq，延时任务用 `wf_job` + Worker 轮询，超时自动
     动作必须走 Task Engine 正常执行路径（Worker 不得直改状态）。
  7. 表达式引擎采用 `expr-lang/expr`：白名单环境（form/starter/
     variables）强类型编译 + AST 级函数调用拒绝，发布期预编译，
     长度上限 512。
  8. API/错误码/权限：`/api/v1` + 既有 Tenant→TenantStatus→
     Authorization 链；业务错误走 `httpx.BizError`，workflow 域
     errCode 段冻结 11 项（前端 `errorCodes.ts` 对齐维护）；权限资源
     `workflows:*` / `workflow-instances:*` / `workflow-tasks:*`。
- **影响**：Phase 0 已落地引擎内核骨架（model/definition/task/
  repository/provider/executor/assignment/expression/event 全部 SPI
  契约草案 + DSL 校验器/状态机/表达式沙箱单元测试）与
  `internal/platform/workflow` 分层 doc；不产生任何核心 `wf_*` 表
  写入逻辑，表结构随 Phase 1（Definition Engine，迁移编号自 000048
  顺延）落地。IAM 前置排期：部门负责人（leader）与发起人直属主管
  （reporting）字段随 Phase 3 开工前补齐，此前对应 Resolver 保持禁用。
