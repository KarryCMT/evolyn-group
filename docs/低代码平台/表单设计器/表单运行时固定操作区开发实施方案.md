# 表单运行时固定操作区开发实施方案

> 状态：前端阶段 1–4 已实施；2026-08-30 已完成运行时 Core / Web / Mobile 呈现层拆分。工作区完整类型检查仍受既有无关类型错误影响；阶段 5“最终用户填写草稿持久化”待独立后端契约确认
> 适用范围：表单设计预览抽屉、独立表单预览页、应用工作区表单填写页，以及后续移动 Web 宿主
> 关联基线：[表单最终渲染器架构与实施设计](../表单运行时/表单最终渲染器架构与实施设计.md)、[目标协议字段字典](./目标协议字段字典.md)

## 1. 背景与问题

当前 `FormRenderer` 同时承担字段渲染、运行时会话、表单校验、提交编排和底部提交按钮渲染。`FormSubmitBar` 又被放在 `FormRenderer` 内部，因此只要宿主在渲染器外层使用滚动容器，按钮就会随表单内容滚动，无法形成稳定的底部操作区。

该结构已经产生以下问题：

- 设计预览抽屉的 `el-scrollbar` 包裹整个 `FormRenderer`，提交按钮属于滚动内容，长表单下无法固定在可视区域底部。
- 应用工作区与独立预览页需要重复处理内容高度、滚动、底部边框、安全区和按钮排列。
- `FormSubmitBar` 只有一个硬编码提交按钮，无法自然扩展“保存草稿、提交、暂存、撤回、转交、退回、打印”等操作。
- 桌面端与移动端的动作密度、排列优先级不同，仅靠 `FormRenderer` 内部媒体查询无法识别“桌面浏览器中的移动端预览容器”。
- `FormRuntimeAdapter.saveDraft` 已存在，但运行时 Store 和 UI 均未消费该能力；同时它容易与设计器的“保存表单结构草稿”混淆。

本方案解决的是“运行时填写表单的固定操作区”。设计器保存的表单结构草稿仍使用 `PUT /forms/:code/draft`，两者不得复用接口、文案或状态。

## 2. 方案结论

采用“精简 `FormRenderer` + 二次封装运行时表面组件”的结构：

```text
设计预览抽屉 / 独立预览页 / 应用工作区
                    │
                    ▼
          FormRuntimeSurface
     ┌───────────────────────────┐
     │ el-scrollbar（唯一滚动区） │
     │   └─ FormRenderer         │
     ├───────────────────────────┤
     │ FormRuntimeActionBar      │  固定在当前容器底部
     └───────────────────────────┘
```

核心决策如下：

1. **操作区不放入 `FormRenderer`。** `FormRenderer` 是表单执行内核，只负责 Schema、字段、值、校验、载荷和运行时操作，不决定宿主显示哪些按钮。
2. **以 `FormRuntimeSurface` 作为 Web 端官方组合入口。** 它基于 `FormRenderer` 二次封装，统一提供 `el-scrollbar`、固定操作区、桌面/移动布局、错误摘要和安全区。
3. **动作采用描述符配置，不采用固定的两个插槽或两个布尔属性。** 内置行为只包含 `submit`、`save-draft`、`reset`；工作流及业务动作统一作为 `custom` 向宿主抛出。
4. **动作描述符不携带业务回调。** 操作栏只发出类型化事件，避免把 API、路由、权限和消息提示注入展示组件。
5. **移动布局由容器模式决定。** `layout="mobile"` 可强制移动预览；真实应用页使用 `layout="auto"` 并以容器查询降级，不能只依赖浏览器视口媒体查询。
6. **操作区固定在组件容器内，不使用页面级 `position: fixed`。** 通过纵向 Flex 布局让内容区滚动、操作区作为固定高度兄弟节点，避免遮挡表单和污染其他页面。

## 3. 组件与领域边界

### 3.1 `FormRenderer`：表单执行内核

保留职责：

- 校验并锁定目标保存协议 Schema。
- 创建独立运行时会话并提供字段上下文。
- 渲染字段、执行字段级校验和聚焦首个错误字段。
- 构造提交与填写草稿载荷。
- 调用 `FormRuntimeAdapter` 的内置运行时能力。
- 保留原生 `<form>` 语义和 Enter 提交行为。

移除职责：

- 不再导入或渲染 `FormSubmitBar`。
- 删除 `submitText` 属性；按钮文案属于宿主操作配置，不进入渲染器。
- 不负责底部吸附、按钮排列、移动安全区、更多菜单或宿主级提示。
- 不解释工作流按钮和其他业务动作。

### 3.2 `FormRuntimeSurface`：可滚动填写表面

该组件是 `@evolyn.do/form/runtime` 面向 Web 宿主的推荐入口，职责如下：

- 渲染并持有 `FormRenderer` 的类型化模板引用。
- 只让表单内容区进入 `ElScrollbar`，操作区永远是滚动区的兄弟节点。
- 将 `submit`、`save-draft`、`reset` 映射为渲染器公开方法。
- 把 `custom` 动作作为 `action` 事件交给页面处理。
- 将非字段错误、当前操作状态和禁用状态传给操作栏。
- 支持 `auto`、`desktop`、`mobile` 三种布局模式。
- 对外继续透传 `submit-success`、`submit-error`、`draft-success`、`draft-error`、`unsupported-field` 等运行时事件。

该组件属于表单运行时领域，不放入通用 `@evolyn.do/ui`。通用 UI 包不应反向依赖表单 Schema、Adapter 或运行时 Store。

### 3.3 `FormRuntimeActionBar`：无业务副作用的操作栏

职责如下：

- 根据动作描述符渲染任意数量操作。
- 处理主次样式、禁用、加载、桌面排列和移动端折叠。
- 展示非字段错误摘要，并使用 `aria-live="polite"` 通知辅助技术。
- 点击后只发出 `action` 事件，不直接调用接口、路由或全局消息。
- 自定义动作允许通过作用域插槽覆盖单个动作内容，但仍必须走统一触发入口。

## 4. 公共类型与接口契约

### 4.1 动作描述符

在 `packages/form/src/runtime/actions/types.ts` 新增以下公共契约：

```ts
export type FormRuntimeActionBehavior =
  | "submit"
  | "save-draft"
  | "reset"
  | "custom";
export type FormRuntimeActionIntent =
  | "primary"
  | "secondary"
  | "danger"
  | "plain";
export type FormRuntimeMobilePresentation = "button" | "compact" | "overflow";

export interface FormRuntimeActionDefinition {
  key: string;
  label: string;
  behavior: FormRuntimeActionBehavior;
  intent?: FormRuntimeActionIntent;
  order?: number;
  disabled?: boolean;
  loading?: boolean;
  visible?: boolean;
  mobilePresentation?: FormRuntimeMobilePresentation;
  confirmText?: string;
}
```

约束：

- `key` 在单个操作栏内唯一，是事件、加载态和测试定位的稳定标识。
- `behavior` 只决定执行通道；业务动作统一使用 `custom`，由宿主按 `key` 分派。
- `intent` 只表达视觉语义，不直接暴露 Element Plus 的 `type` 字符串。
- `confirmText` 只描述是否需要确认；确认弹窗由 `FormRuntimeSurface` 使用 Element Plus 实现，业务请求仍由宿主执行。
- 动作配置是运行时宿主配置，不写入 `content.items[].widget` 表单定义协议。
- 权限过滤应在宿主生成动作列表时完成；操作栏的 `visible` 只用于响应式切换，不是安全边界。

建议的标准表单默认动作：

```ts
const actions: FormRuntimeActionDefinition[] = [
  {
    key: "save-draft",
    label: "保存草稿",
    behavior: "save-draft",
    intent: "secondary",
    order: 10,
    mobilePresentation: "compact",
  },
  {
    key: "submit",
    label: "提交",
    behavior: "submit",
    intent: "primary",
    order: 100,
    mobilePresentation: "button",
  },
];
```

### 4.2 `FormRenderer` 公开能力

为模板引用新增显式类型 `FormRendererExpose`，并从运行时入口导出：

```ts
export interface FormRendererExpose {
  readonly runtime: Readonly<ShallowRef<FormRuntime | null>>;
  getRuntime(): FormRuntime | null;
  submit(): Promise<FormSubmitOutcome | undefined>;
  saveDraft(): Promise<FormDraftOutcome | undefined>;
  buildSubmitPayload(): FormSubmitPayload | null;
  buildDraftPayload(): FormDraftPayload | null;
  focusFirstError(): boolean;
  reset(): void;
}
```

`FormRenderer` 新增稳定的 `formDomId` 属性。操作栏的提交按钮通过 HTML `form` 属性关联该表单；键盘 Enter 仍触发同一个 `submit` 流程，避免出现“点击按钮”和“键盘提交”两套逻辑。

### 4.3 Store 操作状态

现有 `formState` 把生命周期和“正在提交”混在一起，接入保存草稿后会导致状态互斥含糊。实施时拆为：

```ts
export type FormRuntimeLifecycle = "initializing" | "ready" | "submitted";
export type FormRuntimeOperation = "submit" | "save-draft";

export interface FormRuntimeState {
  // 既有 values、fieldStates、dirtyKeys、issues 保持
  lifecycle: FormRuntimeLifecycle;
  activeOperation: FormRuntimeOperation | null;
}
```

规则：

- `activeOperation !== null` 时禁止再次触发内置持久化操作，防止重复请求和提交/保存竞态。
- 提交失败后回到 `ready`，错误通过 `issues` 表达，不再使用笼统的 `failed` 生命周期。
- 提交成功进入 `submitted`；由宿主决定跳转、关闭、重置或继续填写。
- 保存草稿成功不改变生命周期，清空 `dirtyKeys` 并发出 `draft-success`。
- 取消请求不展示业务错误，只清理 `activeOperation`。
- `custom` 动作的加载态由宿主通过动作描述符控制，不塞入运行时 Store。

### 4.4 填写草稿语义

新增 `buildDraftPayload()` 与 `saveDraft()` 时遵守以下规则：

- 保存草稿不执行必填校验，允许未完成数据暂存。
- 草稿收集全部数据字段当前值，包括暂时隐藏字段，保证恢复填写时不丢失用户输入。
- 提交仍只收集可见且可提交字段，并执行完整校验。
- `adapter.saveDraft` 缺失时返回 `unavailable`，宿主不得把未保存伪装为成功。
- 设计预览可提供无持久化的模拟 Adapter，并明确提示“预览模式不会保存草稿”。
- 应用运行页只有在真实填写草稿能力可用时才展示“保存草稿”。

`FormDraftPayload` 应补齐版本上下文，避免恢复旧发布版本的草稿时误套新 Schema：

```ts
export interface FormDraftPayload {
  formId: string;
  publishedVersion: number;
  schemaRevision: string;
  values: Record<string, FormValue>;
}
```

## 5. 布局与交互规格

### 5.1 固定方式

```scss
.evf-runtime-surface {
  display: flex;
  min-width: 0;
  min-height: 0;
  flex: 1;
  flex-direction: column;
}

.evf-runtime-surface__scrollbar {
  min-height: 0;
  flex: 1;
}

.evf-runtime-action-bar {
  flex: 0 0 auto;
}
```

禁止在该场景使用页面级 `position: fixed`。若未来表单被嵌入一个本身允许页面滚动的公开页，可由 `FormRuntimeSurface` 提供显式 `actionPosition="sticky"` 变体，但默认仍是容器内固定。

### 5.2 桌面端

- 操作栏占满宿主内容区域宽度，按钮组与表单画布内容宽度对齐。
- 次要动作在左，主要提交动作在右；产品若要求所有按钮左对齐，通过 Surface 布局属性统一配置，不由页面写深层样式。
- 三个以上低频动作进入“更多”菜单，高频动作按 `order` 保持稳定顺序。
- 非字段错误显示在按钮组上方或左侧错误区，不改变字段区域滚动位置。

### 5.3 移动端

- 主要动作占据剩余可用宽度；一个高频次要动作可使用紧凑按钮，其余进入“更多”。
- 操作栏增加 `env(safe-area-inset-bottom)` 安全区内边距。
- 操作栏高度变化后不遮挡最后一个字段，内容区由 Flex 自动获得正确剩余高度，不通过硬编码底部留白补偿。
- 点击目标不小于 40px，高频主按钮优先保留文字；纯图标操作必须提供 `aria-label` 和 Tooltip。

### 5.4 容器响应式

`FormRuntimeSurface` 接受：

```ts
type FormRuntimeLayout = "auto" | "desktop" | "mobile";
```

- 设计预览抽屉直接传入当前预览设备，保证桌面浏览器中的手机画布也使用移动操作栏。
- 应用工作区传 `auto`，通过组件容器查询决定折叠，不与整个浏览器宽度绑定。
- CSS 不硬编码颜色；文本、边框、背景、间距、圆角、阴影和字号统一使用 `--el-*` 变量，并以[前端中性色变量表](../前端中性色变量/变量表.md)为准。
- 暗色主题只消费 Element Plus 主题变量，不在组件内重定义品牌色。

## 6. 三类宿主的接入方式

### 6.1 表单设计预览抽屉

`FormDesignPreviewDrawer.vue` 保留抽屉 Header 插槽和设备切换，将当前的 `el-scrollbar + FormRenderer` 替换为 `FormRuntimeSurface`：

```vue
<FormRuntimeSurface
  :schema="schema"
  :form-id="formId"
  :adapter="previewAdapter"
  :actions="previewActions"
  :layout="viewport"
/>
```

抽屉 Header 固定在 Element Plus Drawer 的 Header 区，Surface 填满 Drawer Body。桌面端和移动端切换只改变 Surface 的容器布局，不重建表单会话，避免切换设备时丢失已填写值。

预览动作与真实产品保持相同排列；提交和保存均使用模拟 Adapter，不写入业务数据，并以消息提示这是预览行为。

### 6.2 独立表单预览页

`pages/form/preview.vue` 用 `FormRuntimeSurface` 替换页面内重复的 `el-scrollbar` 和画布滚动结构。页面 Header 保持固定；Surface 负责 Header 以下区域的滚动与操作栏。

- 已发布表单继续走真实提交 Adapter。
- 未发布表单继续读取 `sessionStorage` 回放。
- 没有真实填写草稿 Adapter 时，不展示保存草稿动作。

### 6.3 应用工作区表单页

新增 `ApplicationWorkspaceFormRuntime.vue` 作为应用资产与通用 Surface 之间的业务适配层：

- 根据 `appCode`、`activeAsset.targetCode` 加载运行时 bootstrap。
- 创建提交、填写草稿等 Adapter。
- 根据表单类型、当前模式、成员权限和服务端能力生成动作描述符。
- 处理 `custom` 动作、确认、成功消息、路由及重新加载。
- 切换菜单资产时取消上一表单的请求，防止旧响应污染当前表单。

`ApplicationWorkspaceShell.vue` 只负责根据资产类型选择内容组件；表单资产渲染 `ApplicationWorkspaceFormRuntime`，尚未实现的其他资产仍显示占位内容。

### 阶段 5：填写草稿持久化（独立业务子阶段）

现有后端只有“表单结构草稿”和“最终提交记录”，没有最终用户填写草稿。若产品确认应用页必须真实保存填写草稿，应先另行冻结以下后端契约，再启用 `save-draft` 动作：

- 在 `apps/evolyn-core/internal/platform/form/model/` 增加填写草稿模型和 DTO。
- 在 `repository/`、`service/`、`controller/` 各层增加同租户、同成员隔离的读取/保存/删除能力。
- 新增版本化 SQL migration，并同步 `apps/evolyn-core/scripts/db.sql`。
- 使用独立资源权限与稳定错误码，不复用 `forms:update`。
- 草稿必须记录 `publishedVersion + schemaRevision`；发布版本变化时由服务端返回明确冲突，不静默迁移值。
- 前端在 `apps/web/src/api/form.ts` 增加对应接口并实现 `adapter.saveDraft`。

该阶段不阻塞固定操作区、任意动作模型和提交功能落地，但阻塞应用页显示真实“保存草稿”按钮。

## 9. 验收标准

### 9.1 布局

- 表单内容超过可视高度时，只有字段内容区出现 `ElScrollbar`，Header 与操作区保持可见。
- 桌面抽屉、独立预览、应用工作区复用同一 Surface，不再各自维护固定底栏实现。
- 移动预览在桌面浏览器内也采用移动操作栏，不受浏览器总宽度误判。
- 最后一个字段、错误信息和弹出选择器不被操作区遮挡。
- iOS 安全区、暗色主题和 200% 文本缩放下仍可操作。

### 9.2 行为

- 提交执行完整校验，错误时滚动并聚焦第一个错误字段。
- 保存填写草稿不触发必填校验，成功后清除脏状态。
- 内置持久化操作进行中无法重复触发，按钮呈现准确加载态。
- 自定义动作不少于四个时仍有确定顺序、主次关系和移动端更多入口。
- 预览模式不产生真实记录或真实填写草稿。
- API 错误的字段错误回填到字段，非字段错误显示在操作区错误摘要。

### 9.3 可访问性与键盘

- Enter 提交、Tab 顺序和焦点可见性正常。
- 图标按钮具有 `aria-label`，动作组具有可识别名称。
- 错误摘要使用 `aria-live`，且不会在每次输入时重复播报无关消息。
- 更多菜单可用键盘打开、选择和关闭。

### 9.4 工程检查

在 `apps/evolyn-web` 执行：

pnpm run lint:format
pnpm -F @evolyn.do/form test
pnpm -F @evolyn.do/web typecheck

按仓库约定不执行前端生产 Build，浏览器联调由用户自行完成。

## 10. 非目标与防误用约束

- 本方案不把底部动作写入表单字段协议，也不修改 27 种 `widget.type` 字典。
- 表单内的 `button` 布局组件属于表单内容；底部操作区属于宿主，两者不是同一动作来源。
- 本方案不定义工作流审批、撤回、转交等后端业务语义，只提供 `custom` 扩展通道。
- 本方案不允许使用设计器结构草稿接口保存最终用户填写内容。
- 本方案不在各页面复制“固定底栏 + 媒体查询”，也不通过深层选择器修改运行时内部结构。
- 本方案不允许宿主直接改写 `runtime.state`；所有变更继续通过 Store action 或 Adapter 完成。
- 若未来动作配置需要由管理员配置，应设计独立的表单级运行配置及权限模型，不得临时塞入字段协议或依赖按钮文案识别行为。

## 11. 最终设计判断

`FormRenderer` 应保持为可嵌入、无具体操作栏的表单执行内核；固定底部区域应由基于它二次封装的 `FormRuntimeSurface` 统一实现。这样既能解决预览抽屉当前的滚动样式问题，也能让应用工作区和移动端共享同一套行为，同时为超过两个按钮的操作集合保留稳定扩展边界。

### 12.1 2026-08-30：终端呈现层拆分

原 `FormRuntimeSurface` 的“桌面 / 移动”仅是同一 Element Plus 外壳内的 CSS 布局模式，
不能满足 Web 与移动端使用不同字段组件库的要求。现调整为以下边界：

```text
Schema + Runtime Core（值、校验、提交、field_layout、lineWidth）
├─ runtime-web：Element Plus 字段注册表、Tabs、Scrollbar、操作栏
└─ runtime-mobile：原生字段注册表、移动页签、原生滚动区、安全区操作栏
```

- `@evolyn.do/form/runtime-core` 导出 Schema 无关的运行时契约、状态机和渲染器；标签页只保留无组件库回退实现。
- `@evolyn.do/form/runtime-web` 是 Web 官方入口，导出 `FormWebRuntimeSurface`；当前内部使用 Element Plus，但模块名不暴露组件库实现细节。
- `@evolyn.do/form/runtime-mobile` 导出 `FormMobileRuntimeSurface` 与 `createMobileFieldRegistry`；移动端使用原生字段和单列布局，未引入 Element Plus 的外壳组件。
- Web、移动端共享同一份发布 Schema 和 Runtime Store。字段值、校验、服务端错误回填和提交载荷必须保持一致；仅控件、标签页和操作栏呈现方式可不同。
- 设计预览、独立预览页及应用工作区已经切换至 `runtime-web`。移动宿主接入时只应选用 `runtime-mobile`，不得再通过 `layout="mobile"` 把 Web 外壳伪装成移动端。
