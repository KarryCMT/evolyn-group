# 表单前端事件后端功能设计

> 状态：待实施。设计器 UI 已按本契约完成交互闭环；服务端上线后，事件配置才随表单草稿持久化并允许在填写端执行。

## 1. 目标与边界

前端事件在填写人改变指定字段值时，按配置发起安全的 HTTP 请求，并把返回结果写入指定表单字段。它服务于“输入员工后补全信息”等填写辅助场景，不是工作流 Service 节点，也不是通用 Webhook。

- 配置属于表单 Schema：不新增独立事件表，也不改变已发布表单不可变快照的原则。
- 请求由后端代理执行，浏览器不得直接请求任意第三方地址。
- 第一阶段只支持字段变化触发、GET/POST、JSON/XML、Header/Body 键值对、字段回填和子表单 merge/replace。
- 不支持脚本、任意表达式、Cookie、`Authorization`、私网地址、重定向和前端明文密钥。

## 2. 协议升级

协议由 v9 升级为 v10，在 `content` 增加必填 `formEvents`；v9 及以下读取时补 `[]`。配置使用既有 `widgetName`，它是当前表单协议的字段引用键；字段展示名称不得写入配置。

```json
{
  "formEvents": [
    {
      "id": "evt_01j...",
      "enabled": true,
      "name": "补全联系信息",
      "description": "员工姓名变化后补全联系电话",
      "trigger": "_widget_employee",
      "trigger_type": "widget",
      "request_type": 0,
      "request": {
        "method": "get",
        "url": "https://api.lingyanyun.com/member?name=${_widget_employee}",
        "header": [],
        "body": [],
        "format": "json"
      },
      "request_rely": ["_widget_employee"],
      "action": [
        {
          "field": "_widget_phone",
          "value": "$response.data.phone"
        }
      ],
      "action_rely": [],
      "subform_fill_rule": "merge"
    }
  ]
}
```

### 2.1 字段语义

| 字段 | 约束 |
|---|---|
| `id` | 表单内唯一、`evt_` 前缀、长度 8–64。 |
| `name` / `description` | 名称 1–64、同表单唯一；说明 0–500。 |
| `trigger_type` | 第一阶段固定 `widget`。 |
| `request_type` | 第一阶段固定 `0`（自定义 HTTP 请求）。 |
| `request.method` | 仅 `get` / `post`。 |
| `request.url` | HTTPS URL，长度不超过 4,000，可含 `${widgetName}`。 |
| `header` / `body` | 最多各 20 条键值；空 key/value 不持久化。GET 的 body 不发送但可保留编辑草稿。 |
| `request_rely` / `action_rely` | 服务端从模板自动重建，客户端传值不得作为事实源。 |
| `action` | 最多 50 条；目标字段必须存在、可写且不等于触发字段。 |
| `subform_fill_rule` | `merge` 或 `replace`。仅 action 目标为子表单时生效。 |

### 2.2 模板与返回值表达式

- `${_widget_xxx}` 是请求或回填模板中的字段令牌，名称必须存在于当前表单。
- `$response` 是只读响应根；JSON 使用受限 JSONPath，例如 `$response.data.phone`，XML 使用受限 XPath，例如 `/response/data/phone`。
- 禁止 `eval`、函数调用、过滤器、递归查询与任意对象原型访问。
- 字段重命名必须同步替换 `trigger`、模板令牌、`action.field` 及依赖索引；删除、改为布局控件或静态隐藏前，如果被事件引用，服务端返回确定错误码并拒绝。

## 3. API

所有接口走 `/api/v1` 的认证、租户状态和 RBAC 链。

| 方法 | 路径 | 权限 | 用途 |
|---|---|---|---|
| `PUT` | `/forms/:code/draft` | `forms:update` | 沿用草稿保存；v10 校验并持久化 `formEvents`。 |
| `POST` | `/forms/:code/frontend-events/:eventId/debug` | `forms:update` | 对草稿事件执行一次调试，不写表单记录。 |
| `POST` | `/forms/:code/records/:recordId/frontend-events/:eventId/execute` | `form-data:update` | 编辑已有记录时执行已发布快照事件。 |
| `POST` | `/forms/:code/frontend-events/:eventId/execute` | `form-records:add` | 新建填写时执行已发布快照事件。 |

运行接口请求体：

```json
{
  "values": { "_widget_employee": "member-001" },
  "sequence": 12
}
```

响应不返回原始敏感 Header；返回 `sequence`、`writes`、脱敏 `requestSummary`、`responseSummary` 和可展示错误码。后端必须忽略客户端传入的事件定义，始终按当前已发布表单快照的 `eventId` 取配置。

## 4. 服务端实现

在 `internal/platform/form/` 下新增前端事件适配层，保持 Controller → Service → Repository 的既有边界：

```text
internal/platform/form/
  service/frontend_event.go          配置校验、执行编排、回填值校验
  service/frontend_event_template.go 令牌/受限路径解析与依赖重建
  service/frontend_event_policy.go   字段权限、循环与子表单规则
  controller/frontend_event.go       debug / runtime HTTP 入口
  repository/frontend_event.go       读取发布快照与可选审计查询
```

HTTP 出站能力抽为窄接口 `FrontendEventInvoker`。实现复用工作流 Service 节点的出站安全策略：DNS 解析后阻断回环、链路本地和 RFC1918 地址；仅允许 `workflow.allowedHosts` 白名单；禁重定向；1 MB 响应上限；请求超时 10 秒；日志脱敏。生产凭证不写入 `request.header`，后续凭证中心只允许用受控 `credentialRef` 注入。

## 5. 运行语义

1. 客户端只在用户真正修改 trigger 字段后调用；事件回填使用 `source=event`，不再次触发同类事件。
2. 服务端按事件 id 读取已发布快照，校验 trigger、权限和字段可见性。
3. 解析请求模板，调用安全代理，按 `format` 解析响应。
4. 依序求值 `action`，执行类型化转换与可写字段检查，再返回 `writes`；运行接口不直接提交记录。
5. 客户端只接受与最新 sequence 相同的结果，调用运行时 `setValue(field, value, 'event')` 写回并重算显隐规则。
6. 同一用户会话中，一个事件链不得重复触发同一 `eventId + trigger`；超过链深度 8 返回 `FORM_EVENT_CYCLE_DETECTED`。

子表单 `merge` 以当前行稳定主键匹配后局部覆盖；`replace` 整体替换目标子表单值。没有稳定行键或返回值类型不符时拒绝写回，不静默丢失数据。

## 6. 校验、错误码与审计

新增稳定错误码：

- `FORM_EVENT_NOT_FOUND`
- `FORM_EVENT_INVALID`
- `FORM_EVENT_DISABLED`
- `FORM_EVENT_TRIGGER_MISMATCH`
- `FORM_EVENT_TARGET_NOT_WRITABLE`
- `FORM_EVENT_TEMPLATE_INVALID`
- `FORM_EVENT_REQUEST_BLOCKED`
- `FORM_EVENT_REQUEST_FAILED`
- `FORM_EVENT_RESPONSE_INVALID`
- `FORM_EVENT_MAPPING_FAILED`
- `FORM_EVENT_CYCLE_DETECTED`

草稿更新、事件启停和事件删除随表单草稿保存写现有审计域。调试与运行只记录事件 id、耗时、状态码、目标字段键和错误码；不得记录字段原值、完整 URL query、Header、Body 或响应全文。

## 7. 开发顺序与验收

1. 协议 v10、TS/Go 校验镜像、v9→v10 迁移和表单草稿回归测试。
2. 发布快照读取与安全 `FrontendEventInvoker`，先完成 debug API。
3. 接入填写运行时执行 API、序列号竞态保护、字段/子表单回填。
4. 补齐审计、指标、限流、错误码和端到端测试。

验收至少覆盖：模板依赖自动重建、字段改名/删除保护、GET/POST、JSON/XML、禁私网/重定向/敏感 Header、超时和响应限长、禁用事件、竞态旧响应拦截、循环阻断、字段权限、merge/replace、草稿与已发布快照隔离。
