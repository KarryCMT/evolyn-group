# 表单物理表存储后端实施方案

## 1. 目的与结论

本文定义表单设计发布后以 PostgreSQL 物理表承载业务值的后端实施方案。新创建表单
的业务数据只有 physical 一种存储方式，不提供 JSONB 记录存储选项；它不替换表单资产、
不可变发布快照、权限终审或流程引擎。

首期结论如下：

1. 每个新建表单固定拥有一份 physical 存储绑定；首张物理值表在首次发布时创建，且不按
   租户、发布版本或流程实例拆表。
2. `tn_form_records` 继续作为所有表单记录的统一身份与系统元数据表；物理表只保存
   业务字段值及高频流程查询投影，绝不另造记录 ID。
3. 表单字段、权限、值校验、不可见字段赋值和流程写回仍归 Form Domain；物理表只是
   `RecordValueStore` 的一种持久化实现。
4. 物理建表与结构变更必须通过持久化 DDL Job 异步执行。HTTP Controller 不得直接
   执行 `CREATE/ALTER/DROP TABLE`。
5. 流程单号、流程状态和状态更新时间为高频筛选/导出字段，必须作为物理表的预置
   系统列，并在流程实例状态变更的同一数据库事务内更新。

表单草稿、发布快照、DDL 模型和计划仍使用 JSONB 保存**定义元数据**；本方案禁止把
任何新记录的**用户业务值**落在 JSONB。旧 JSONB 记录只作为历史兼容来源，迁移后不再
为新表单或新记录提供该路径。

本方案不包含旧 JSONB 记录到物理表的批量迁移、跨表关联、外部数据源、分区和跨库
隔离；这些能力应在本方案稳定后单独立项。子表单在 physical 模式下采用独立物理子表，
其行级 API、跨子表关联和子表汇总属于后续阶段。

## 2. 当前实现基线与差距

当前实现已具备表单草稿、不可变发布快照、字段映射、JSONB 记录提交、表单权限、
流程型表单原子发起以及流程单号绑定；但尚未具备物理表执行链路。

| 能力 | 当前状态 | 本方案目标 |
| --- | --- | --- |
| 表单字段值 | `tn_form_records.values` JSONB 唯一事实源 | 新记录仅由 physical RecordValueStore 承载 |
| 发布字段映射 | `tn_form_versions.field_mappings` 已冻结 JSONB 键和物理列意图 | 冻结可执行的物理模型快照、Diff 和 DDL Plan |
| 记录筛选 | 编译为 JSONB 谓词 | 新表单编译为物理列表达式；旧数据仅作兼容读取 |
| 流程单号 | `tn_form_records.workflow_instance_no` 独立列 | 同时预置到 physical 表作查询投影 |
| 流程状态 | 只在 `wf_instance.status` 中存在 | 写入记录/物理表的同事务查询投影 |
| 物理 DDL | 未实现 | Job Worker 异步、可重试、可观测执行 |
| RLS | 架构目标，尚未落地 | 动态物理表与动态 DML 首批同时落地 |

现有 `field_mappings` 中的 `physicalColumn` 仅是意图，不能被浏览器、Controller 或
Repository 当作已经存在的数据库列。任何动态表名、列名、类型、索引和 SQL 片段均
必须由服务端从不可变发布快照重新推导和校验。

## 3. 术语、所有权与事实源

| 术语 | 含义 | 唯一事实源 |
| --- | --- | --- |
| 表单业务存储 | 新表单固定为 `physical`，不对客户端暴露切换选项 | `tn_form_storages.backend` |
| 记录信封 | 记录 ID、租户、表单/版本、提交人、幂等键等通用元数据 | `tn_form_records` |
| 记录业务值 | 由字段 `widgetName` 定位的最终校验值 | 新记录为物理表行；`values` 仅承载旧历史记录 |
| 物理模型版本 | 某发布快照对应的完整列、类型、索引及弃用信息 | `tn_form_storage_schema_versions` |
| 流程实例状态 | 流程运行时状态机状态 | `wf_instance.status` |
| 流程查询投影 | 用于表单数据页筛选/导出的单号、状态和状态更新时间 | `tn_form_records` 与 physical 表；可由流程实例重建 |

物理表中的流程字段是投影，不得反向驱动 `wf_instance`，也不得允许客户端写入。

## 4. 固化前置契约

### 4.1 稳定字段标识

物理列必须由不可变字段标识推导，不能由可改的标签推导。现有 `widgetName` 已作为
记录键和公式/规则引用键使用，但前端 Physical Engine 的 `field_` 标识规则与当前
`_widget_` 规则并不一致，且 relation 被映射为 UUID，与后端现有 BIGINT 主键体系也
不一致。

实施前必须二选一并冻结：

1. 推荐：在表单协议中增加内部不可变 `fieldId`，发布后只允许改 `label`；
   `fieldId → physical_column` 永不变更。
2. 过渡：已发布字段的 `widgetName` 永久不可修改；字段改名仅修改 `label`。该方案
   必须在草稿校验、设计器、复制字段和引用迁移中强制执行。

不得继续让前端和后端各自转换名称。后端应以 `fieldId`（或冻结的 `widgetName`）
生成规范列名，示例为 `field_01j82 → f_01j82`。列名只允许小写字母、数字和下划线，
总长度不得超过 PostgreSQL 标识符上限；索引名超长时以稳定哈希后缀截断。

### 4.2 固定物理存储与发布规则

- `POST /forms` 不接收 `storageMode`；服务端为每个新表单创建固定的 physical 存储绑定。
- 新表单的首次发布和所有涉及结构变化的后续发布均创建待发布快照及 DDL Job，接口返回
  `202 Accepted`；只有 Job
  成功后才更新 `tn_forms.latest_version_id/published_version`，运行时才可使用新快照。
- 不涉及任何物理变更的发布可同步完成；是否同步由后端根据服务端生成的 Diff 决定。
- 历史 JSONB 表单在其离线迁移完成前保留兼容读取路径；该兼容状态不是新建表单的可选
  存储模式，也不向前端暴露。
- 同一表单任一时刻只能有一个待执行或执行中的物理模型 Job；新发布请求返回明确的
  `FORM_STORAGE_BUSY`。

### 4.3 支持字段范围

首期优先支持可无损转换且筛选语义明确的顶层标量字段：文本、长文本、数字、单选、
日期、日期时间以及确定为 BIGINT 的单成员/单部门引用。子表单启用时采用 §5.4 的
独立物理子表，不在父表保留 JSONB 副本。多选、附件、地址、定位、签名、关联查询和
数据联动在拥有明确的数组列、关系表或专用子表模型之前，必须被发布校验拒绝；禁止为了
兼容而将其用户业务值退回 JSONB。

以下约束必须成立：

- `required` 是发布快照的提交校验语义，不自动转为用户字段的 SQL `NOT NULL`。新增
  必填字段会遇到历史记录，SQL 非空约束会错误拒绝历史行。
- 发布后字段类型改变默认拒绝；应新建字段并弃用旧字段。高风险 `ALTER COLUMN TYPE`
  不在首期自动化范围内。
- 删除字段只写模型弃用标记，新版本不再展示/写入；物理列与历史值保留，后续经人工
  审批的维护任务才能清理。

## 5. 数据模型

### 5.1 统一记录信封

`tn_form_records` 继续保存以下通用列：

```text
id / tenant_id / form_id / form_version_id
data_op_id / entry_code
submitted_by_member_id / submitted_by_name / submitted_at / updated_at / created_at
workflow_instance_no / workflow_status / workflow_updated_at
values
```

其中：

- 旧历史记录：`values` 保持非空，供兼容读取和离线迁移使用。
- 所有新记录：`values` 为 `NULL`；业务值只能从对应物理父表与子表读取。
- 增加 `UNIQUE (tenant_id, id)`，供物理表使用复合外键防止跨租户错误绑定。
- `workflow_instance_no` 维持已有租户内唯一约束；`workflow_status` 和
  `workflow_updated_at` 是新建的通用查询投影，使新物理记录拥有统一的
  `sys.workflow*` API，并为历史记录兼容读取提供同一出网字段。

`values` 不能作为 physical 表的兼容双写副本。双写会产生无法裁决的两份业务事实源，
也会让流程写回和历史版本解释失去确定性。

### 5.2 表单存储元数据

```sql
CREATE TABLE tn_form_storages (
    id BIGSERIAL PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    form_id BIGINT NOT NULL,
    backend VARCHAR(16) NOT NULL,              -- PHYSICAL；LEGACY_JSONB 仅存量兼容
    table_name VARCHAR(63),                    -- 新建表单始终非 NULL
    state VARCHAR(16) NOT NULL,                -- READY / PUBLISHING / FAILED
    applied_schema_version_id BIGINT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT LOCALTIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT LOCALTIMESTAMP,
    CONSTRAINT uq_tn_form_storages_form UNIQUE (tenant_id, form_id),
    CONSTRAINT uq_tn_form_storages_table UNIQUE (table_name)
);

CREATE TABLE tn_form_storage_schema_versions (
    id BIGSERIAL PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    storage_id BIGINT NOT NULL REFERENCES tn_form_storages(id),
    form_version_id BIGINT NOT NULL REFERENCES tn_form_versions(id),
    model JSONB NOT NULL,
    plan JSONB NOT NULL,
    checksum VARCHAR(64) NOT NULL,
    state VARCHAR(16) NOT NULL,                -- PENDING / APPLIED / FAILED
    applied_at TIMESTAMPTZ,
    error_code VARCHAR(64),
    error_detail TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT LOCALTIMESTAMP,
    CONSTRAINT uq_tn_form_storage_schema_version UNIQUE (storage_id, form_version_id)
);

CREATE TABLE tn_form_ddl_jobs (
    id BIGSERIAL PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    storage_schema_version_id BIGINT NOT NULL
        REFERENCES tn_form_storage_schema_versions(id),
    status VARCHAR(16) NOT NULL,               -- PENDING / PROCESSING / SUCCEEDED / FAILED
    retry_count INTEGER NOT NULL DEFAULT 0,
    next_attempt_at TIMESTAMPTZ NOT NULL DEFAULT LOCALTIMESTAMP,
    last_error_code VARCHAR(64),
    last_error_detail TEXT,
    started_at TIMESTAMPTZ,
    finished_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT LOCALTIMESTAMP,
    CONSTRAINT uq_tn_form_ddl_jobs_schema UNIQUE (storage_schema_version_id)
);
```

实际迁移还需补全外键、状态 CHECK、索引与表注释。状态枚举由后端常量维护，数据库
CHECK 只保护已冻结且不会频繁演进的状态。

### 5.3 物理值表形态

每个 physical 表单创建一张表，表名由服务端分配。例如：

```sql
CREATE TABLE tn_fd_01ab_k7q2m8 (
    tenant_id BIGINT NOT NULL,
    record_id BIGINT NOT NULL,

    -- 所有 physical 表预置的流程查询投影
    workflow_instance_no VARCHAR(40),
    workflow_status VARCHAR(16) NOT NULL DEFAULT 'NONE',
    workflow_updated_at TIMESTAMPTZ,

    -- 当前模型的用户字段；字段名只由服务端模型生成
    f_01j82 NUMERIC,
    f_01j83 TEXT,
    f_01j84 DATE,

    PRIMARY KEY (record_id),
    CONSTRAINT fk_tn_fd_01ab_k7q2m8_record
      FOREIGN KEY (tenant_id, record_id)
      REFERENCES tn_form_records (tenant_id, id)
);

CREATE INDEX ix_tn_fd_01ab_k7q2m8_workflow_status
  ON tn_fd_01ab_k7q2m8
     (tenant_id, workflow_status, workflow_updated_at DESC, record_id DESC);

CREATE INDEX ix_tn_fd_01ab_k7q2m8_workflow_no
  ON tn_fd_01ab_k7q2m8 (tenant_id, workflow_instance_no)
  WHERE workflow_instance_no IS NOT NULL;
```

`workflow_instance_no` 的租户内全局唯一性仍由 `tn_form_records`/`wf_instance` 保证；
物理表上的索引用于同表单的数据页筛选与导出，不重复承担全局唯一约束。

### 5.4 子表单物理子表

子表单是父记录的一对多明细，不应作为父表的一列 JSONB，也不应把所有子表单混入一张
通用 EAV 表。每个已发布且启用 physical 存储的子表单字段拥有一张独立子表；它的名称
同样由服务端分配，例如 `tn_fc_01ab_p3n9v2`。

```sql
CREATE TABLE tn_fc_01ab_p3n9v2 (
    tenant_id BIGINT NOT NULL,
    row_id BIGSERIAL PRIMARY KEY,
    parent_record_id BIGINT NOT NULL,
    sort_order INTEGER NOT NULL,
    row_revision BIGINT NOT NULL DEFAULT 1,

    -- 子字段列；由子字段 fieldId 推导，不能与父表共享可变名称
    f_01l01 TEXT,
    f_01l02 NUMERIC,
    f_01l03 DATE,

    created_at TIMESTAMPTZ NOT NULL DEFAULT LOCALTIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT LOCALTIMESTAMP,
    CONSTRAINT fk_tn_fc_01ab_p3n9v2_parent
      FOREIGN KEY (tenant_id, parent_record_id)
      REFERENCES tn_form_records (tenant_id, id),
    CONSTRAINT uq_tn_fc_01ab_p3n9v2_sort
      UNIQUE (parent_record_id, sort_order)
);

CREATE INDEX ix_tn_fc_01ab_p3n9v2_parent
  ON tn_fc_01ab_p3n9v2 (tenant_id, parent_record_id, sort_order);
```

新增 `tn_form_storage_children` 保存 `storage_id + parent_field_id → table_name` 的永久映射，
并以 `table_name` 唯一约束防重。父表不为子表单建立 `f_*` 列；发布快照的字段映射应
显式标记该字段的 storage target 为 `child-table` 和子表存储 ID。

现有子表单值协议是“对象数组”，没有行级稳定 ID，前端也以数组下标作为渲染 key。首期
physical 子表单只能采用**集合替换**语义：父记录更新时，在同一事务内锁定父记录，删除
旧子行后按照客户端顺序批量写入新子行，并同步刷新父记录 `updated_at`。在这一阶段，
`row_id` 是数据库内部标识，不能由客户端提交、引用或作为权限对象。

未来若开放子表单的独立行编辑、行级审批、关联引用或行级权限，必须升级为新协议版本：
为每行引入保留的稳定 `rowId` 与 `rowRevision` 信封，新增行由服务端分配，更新/删除以
`rowId + rowRevision` 乐观锁执行。不得继续依靠数组下标识别行，也不得在现有行对象中
偷偷加入会与 `widgetName` 冲突的字段。该协议升级前，子表单字段不参与通用列表筛选、
排序、聚合和跨表关联；仅随父记录完整读写。

子表 RLS 策略与父物理表一致，均以 `tenant_id` 为条件。父记录创建、父字段写入、子行
替换、流程发起和流程投影更新必须使用同一个事务；任何子行校验失败均回滚整个父记录。

## 6. 字段演进与历史版本

表单设计更新先只修改草稿。只有发布时才根据“上一个已应用物理模型”与“新发布快照”
产生结构计划；草稿保存永不触发 DDL。每次成功发布都保留不可变 FormVersion 和物理模型
版本，因此流程实例和历史记录始终可以按其绑定版本解释。

| 设计变化 | 物理动作 | 发布方式 | 历史与提交语义 |
| --- | --- | --- | --- |
| 标签、帮助文案、布局、可见性、校验规则、选项 | 无 DDL | 同步发布 | 历史值不重写；新旧快照各自解释 |
| 新增父字段/子字段 | `ADD COLUMN`，用户列始终可空 | 异步 DDL Job | 旧记录为 NULL；旧版本仍可提交 |
| 新增索引 | `CREATE INDEX`；大表使用并发阶段 | 异步 DDL Job | 不改变记录值 |
| 提高 required、改变默认值 | 无 DDL | 同步发布 | 仅约束新快照提交，不回填旧记录 |
| 字段改标签 | 无 DDL | 同步发布 | 字段 ID/列名保持不变 |
| 删除字段 | 标记 deprecated，不删列 | 同步发布 | 新版本隐藏/禁止写入；旧版本仍可解释和提交 |
| 字段类型改变 | 默认拒绝 | 返回 `FORM_STORAGE_TYPE_CHANGE_UNSUPPORTED` | 新建字段、迁移数据、弃用旧字段 |
| 历史 JSONB 表单迁移 | 不属于普通发布 | 独立迁移项目 | 新表单不存在该选择；迁移完成后改用物理表 |

“旧版本仍可提交”沿用现有表单受理契约：每个记录使用提交请求中的
`publishedVersion + schemaRevision` 定位快照。物理表结构因此必须是历次已应用字段的
并集，不能随当前最新表单定义删除列。列表默认按最新快照投影字段；读取较早记录时，
新字段为 NULL，已弃用字段不向最新列表暴露。

字段物理清理是单独的维护计划：必须确认没有仍可受理/仍被流程实例绑定的版本、完成
备份并获得人工审批后，才允许对单一明确列或子表执行破坏性 DDL。普通发布和表单删除
都不触发该操作。

## 7. 表名分配与防重

表名固定格式：

```text
tn_fd_<app4>_<rand6>
tn_fc_<app4>_<rand6>
```

示例：父表 `tn_fd_01ab_k7q2m8`；子表单明细表 `tn_fc_01ab_p3n9v2`。

- `tn_fd_` 表示租户归属的动态表单父数据表；`tn_fc_` 表示子表单明细表。
- `app4` 是应用内部编号的 base36 末四位，仅供运维识别，绝不作为唯一性或归属判断。
- `rand6` 为服务端以密码学安全随机源生成的小写字母数字串，组合空间约 21.8 亿。
- 表名生成后永久不变；应用/表单改名、复制、归档均不改表名。
- `tn_form_storages.table_name` 的唯一约束才是防重边界。先尝试插入元数据，发生唯一
  冲突则重试生成，最多五次；不得先查 PostgreSQL catalog 再建表。
- 浏览器不得提交表名，任何 API 也不得通过表名定位表单。

## 8. 发布、DDL 与重试时序

```text
保存草稿
  → POST publish
  → 事务内：锁定 form/storage，校验草稿，创建不可变 FormVersion
  → 后端从快照生成 PhysicalModel，与已应用模型生成 Diff/Plan
  → 写 SchemaVersion + DDL Job，FormStorage=PUBLISHING
  → 返回 202 + jobId

DDL Worker
  → FOR UPDATE SKIP LOCKED 领取 Job
  → advisory lock(form_id) 防止同表并发 DDL
  → 校验模型 checksum 和当前已应用版本
  → 执行受控 DDL
  → 事务内：SchemaVersion=APPLIED、Storage=READY、推进 Form.latest_version
  → 返回新 publishedVersion/schemaRevision
```

首期允许的操作为：首次建父/子表、加父/子字段列、创建索引、弃用列/索引元数据。
禁止自动删列、自动删索引、自动窄化类型和自动执行不可逆的数据修复。

大表索引须使用独立阶段的 `CREATE INDEX CONCURRENTLY`；该命令不能在事务块内执行，
Job 必须显式记录阶段、处理失败后的无效索引并安全重试。普通表的首次建表/加列仍应
在单个事务中执行。

DDL Worker 使用独立的数据库迁移权限，不使用进程内 goroutine 充当可靠队列。所有
DDL、重试、失败、人工重试和最终完成均写审计日志与监控指标。

## 9. RecordValueStore 与原子事务

### 9.1 接口边界

Form Service 应只依赖面向业务值的窄接口：

```go
type RecordValueStore interface {
    Create(ctx context.Context, recordID uint, values map[string]any) error
    Read(ctx context.Context, recordID uint) (map[string]any, error)
    Replace(ctx context.Context, recordID uint, values map[string]any) error
    List(ctx context.Context, plan RecordListPlan) (Page, error)
}
```

新记录只由 `PhysicalRecordValueStore` 实现该接口。历史 JSONB 兼容读取可保留在单独的
`LegacyJSONBRecordValueReader` 中，但不得作为新记录写入实现。提交终审、字段权限、
值决议、审计和 WorkflowRecordStore 的语义不得在多个实现中复制。

### 9.2 原子性要求

当前流程型表单将记录创建、流程实例创建、任务创建和流程单号写回置于同一
`TxManager` 事务中。physical 模式必须保持这个原子边界：

```text
创建 tn_form_records 信封
→ 写入 physical 父表业务值与子表行
→ 创建 wf_instance / 分配 instance_no
→ 写入记录与 physical 表的流程投影
→ 任一步失败，全部回滚
```

首期动态 DML 应通过 `infrastructure.ResolveDB(ctx, db)` 获取当前 GORM transaction
并执行经过服务端编译、标识符白名单校验和参数绑定的原生 SQL。不得以独立 pgxpool
开启第二个事务，否则会破坏上述原子性。待基础设施提供统一事务会话后，可再将高吞吐
动态 DML 迁移到 pgx。

## 10. 流程系统字段与状态投影

### 10.1 当前与新增字段

当前可筛选的系统字段为：

```text
sys.submittedBy     → submitted_by_member_id
sys.submittedAt     → submitted_at
sys.updatedAt       → updated_at
```

流程单号已经独立保存且会出网，但尚未纳入后端系统字段筛选白名单；流程状态尚未投影
到表单记录。实施后统一支持：

```text
sys.workflowInstanceNo  → workflow_instance_no
sys.workflowStatus      → workflow_status
sys.workflowUpdatedAt   → workflow_updated_at
```

三者同时存在于记录信封；physical 表额外预置同名列，作为不依赖 JSONB 解包的高频
查询投影。系统字段不受用户字段矩阵裁剪，但仍必须通过行级 view 权限。

### 10.2 状态语义

`workflow_status` 直接复制流程实例状态枚举，不自行重定义业务状态。当前冻结的实例
状态是：`DRAFT`、`RUNNING`、`COMPLETED`、`REJECTED`、`CANCELLED`；普通表单或未
绑定流程的记录使用 `NONE`。退回发起人后的等待重提是节点状态，实例仍为 `RUNNING`，
不得将其错误投影成新的实例状态。

流程状态的唯一事实源始终是 `wf_instance.status`。Workflow 通过平台适配层调用
Form Domain 的 `UpdateWorkflowProjection` 窄端口；流程内核不得直接更新
`tn_form_records` 或任何 `tn_fd_*` 表。流程启动、同意、驳回、撤回、终止、退回后重提、
超时自动处理和服务节点续跑造成实例状态变化时，均必须在同一事务中更新投影。

必须提供管理员受控的校准 Job：以 `wf_instance` 为源按表单记录回填单号、状态和更新时间，
用于上线回填、故障修复和一致性巡检；它只能修复投影，不得反向修改流程实例。

## 11. 查询、权限与导出

Query DSL 继续只接收逻辑字段标识和 `sys.*` 字段，永不接受 JSONPath、物理列名、
表名或 SQL。

查询编译应先由不可变发布快照解析 `FieldRef`，再由物理存储解析器决定表达式：

```text
逻辑字段 field_01j82
  → physical：d.f_01j82
```

所有标识符来自服务器保存的模型，所有值一律使用绑定参数。记录列表仍以
`tn_form_records r` 为系统数据与权限锚点，再 `JOIN tn_fd_* d ON
d.record_id = r.id AND d.tenant_id = r.tenant_id`。权限数据范围、用户筛选、关键词
筛选、统计总数、分页和导出必须共享同一份编译计划，避免列表与导出结果不一致。

流程单号使用 `(tenant_id, workflow_instance_no)` 索引；流程状态导出使用
`(tenant_id, workflow_status, workflow_updated_at DESC, record_id DESC)` 索引做 keyset
分页。低基数状态列不能单独建立索引。子表单首期只按父记录完整读取；子字段筛选、
排序、分组与聚合必须在 Query DSL、权限数据范围和执行计划均具备明确语义后，以
`EXISTS`/受控 JOIN 方式单独开放。

## 12. 租户隔离与数据库安全

动态物理表必须包含 `tenant_id BIGINT NOT NULL`，尽管每张表绑定单一表单也是如此。
它用于复合外键、统一查询编译、RLS 和未来物理隔离迁移。

RLS 与动态 DML 同批实施：

```sql
ALTER TABLE tn_fd_01ab_k7q2m8 ENABLE ROW LEVEL SECURITY;
ALTER TABLE tn_fd_01ab_k7q2m8 FORCE ROW LEVEL SECURITY;

CREATE POLICY p_tn_fd_01ab_k7q2m8_tenant
  ON tn_fd_01ab_k7q2m8
  USING (tenant_id = current_setting('app.current_tenant', true)::BIGINT)
  WITH CHECK (tenant_id = current_setting('app.current_tenant', true)::BIGINT);
```

- 每个请求事务和按租户运行的 Worker 事务必须执行 `SET LOCAL app.current_tenant`。
- DDL Worker 使用受限的迁移角色；运行时应用角色不拥有任意 DDL 权限。
- `FORCE ROW LEVEL SECURITY` 与运行时/迁移角色分离是必要条件，避免表所有者绕过策略。
- 表名、列名、索引名必须经过服务端白名单与引用转义；值、日期和筛选条件一律参数化。

现有架构文档中的 UUID 租户 RLS 示例不适用于当前 BIGINT 租户主键，实现时应同步修订
为本方案口径。

## 13. 包结构与职责

```text
internal/engine/data/
  storage/             纯模型：StorageModel、Diff、Plan、字段类型映射、校验

internal/infrastructure/dynamicddl/
  executor.go          PostgreSQL DDL 执行、标识符引用、advisory lock、RLS 安装

internal/platform/form/
  model/               存储元数据、DTO、稳定错误码
  repository/          Storage/SchemaVersion/DDLJob/Record 信封持久化
  service/             发布编排、RecordValueStore、查询计划、流程投影端口
  worker/              DDL Job Worker、投影校准 Job
```

`internal/engine/data` 不得依赖 Gin、GORM、pgx、HTTP 或 Form/Workflow 的具体模型；
`internal/platform/form` 负责把表单发布快照适配为纯存储模型；`infrastructure` 才能执行
PostgreSQL 特定 DDL。

## 14. API、权限与错误码

建议新增或调整以下契约：

| 接口 | 语义 |
| --- | --- |
| `POST /forms` | 不接收存储模式；服务端固定创建 physical 存储绑定 |
| `POST /forms/:code/publish` | 结构变化返回 `202 + {jobId, publishedVersion, schemaRevision}` |
| `GET /forms/:code/storage-jobs/:jobId` | 查询 DDL 发布状态和受控失败信息 |
| `POST /forms/:code/storage-jobs/:jobId/retry` | 管理员重试失败 Job，不接受新模型 |
| `POST /forms/:code/records` | 继续使用 Query DSL，新增三项 `sys.workflow*` 字段 |

DDL Job 的查看/重试沿用表单管理权限，并在动作授权体系完善后拆出独立的
`form-actions:retry-storage-ddl`。记录查询仍使用数据面权限与表单权限组，不因使用
physical 表而扩大任何成员权限。

新增稳定错误码至少包括：

```text
FORM_STORAGE_BUSY
FORM_STORAGE_UNSUPPORTED_FIELD
FORM_STORAGE_MODEL_INVALID
FORM_STORAGE_DDL_FAILED
FORM_STORAGE_NOT_READY
FORM_STORAGE_TYPE_CHANGE_UNSUPPORTED
FORM_WORKFLOW_PROJECTION_INVALID
```

## 15. 分期实施计划

### Phase 0：契约冻结

1. 决定并实现不可变 `fieldId`，或冻结已发布字段的 `widgetName`。
2. 统一前后端物理类型映射，修复 `_widget_`、`field_` 与 relation UUID/BIGINT 的冲突。
3. 更新表单资产契约、字段字典、Query DSL 字段目录和架构文档的 RLS BIGINT 口径。

### Phase 1：元数据与历史兼容重构

1. 新增存储元数据、模型版本和 DDL Job 迁移。
2. 为 `tn_form_records` 增加流程状态和流程状态更新时间；保留 `values` 仅供历史 JSONB
   行兼容读取与离线迁移。
3. 抽取 `RecordValueStore`，新记录只接入 PhysicalRecordValueStore；历史 JSONB 读取与
   新记录写入严格隔离。
4. 增加 `sys.workflowInstanceNo`、`sys.workflowStatus`、`sys.workflowUpdatedAt` 的服务端
   Query DSL 编译、排序、前端数据源与导出字段定义。

### Phase 2：物理建表与标量 DML

1. 实现后端 StorageModel、Diff、计划校验和 DDL Worker。
2. 实现首次建表、标量字段加列、RLS、流程预置列和安全索引。
3. 实现 PhysicalRecordValueStore，并以同一事务覆盖创建、读取、更新和列表查询。
4. 新建普通表单固定使用 physical 存储；发布期拒绝尚未具备非 JSONB 物理模型的控件。

### Phase 3：物理子表单

1. 实现 `tn_form_storage_children`、子表模型 Diff 和父子表同 Job 的 DDL 执行。
2. 实现子表单集合替换写入、父记录锁定、顺序列和回滚测试。
3. 仅开放随父记录完整读写的子表单；不开放行级 CRUD、子字段筛选或聚合。

### Phase 4：流程型表单与导出

1. 在 Workflow 平台适配层接入 `UpdateWorkflowProjection`。
2. 覆盖所有实例终态/非终态迁移、超时 Job 和服务节点续跑的同事务投影写入。
3. 启用物理表的流程单号/状态高频筛选、排序、keyset 导出与投影校准 Job。
4. 对新建流程型表单开放 physical 模式。

### Phase 5：受控演进

1. 支持并发索引创建、索引弃用和大表限流。
2. 评估子表单行级协议、关系表、分区、历史 JSONB→physical 离线迁移与企业独立库。
3. 仅在备份、影响评估和人工审批具备后，设计列/索引物理清理能力。

## 16. 验收与测试

必须覆盖以下场景：

1. 同一表单并发发布只产生一个 DDL Job；多个 Worker 不会并发修改同一物理表。
2. DDL 失败时旧发布版本仍可运行，新版本不成为 `latest_version_id`；重试幂等。
3. 新 physical 记录对相同 Query DSL、字段权限、数据范围和分页产生稳定语义；历史
   JSONB 兼容读取不能影响新记录查询计划。
4. 物理表提交、审批写回、流程发起、流程单号分配和任意一步失败均整体回滚。
5. 流程同意、驳回、撤回、终止、重提、自动超时、服务节点续跑后，流程投影与
   `wf_instance` 同事务一致；校准 Job 可修复人为构造的不一致。
6. 租户 A 无法经 API、动态查询、手工构造 `record_id` 或 RLS 会话读取/写入租户 B 行。
7. 表名、列名、排序字段、过滤字段和索引配置无法造成 SQL 注入；所有用户值均为绑定参数。
8. 历史 JSONB 记录、已发布表单、流程单号与现有 API 响应保持兼容。
9. 高频流程状态/单号筛选和大批量导出使用目标索引，导出采用 keyset 分页，不允许
   `OFFSET` 扫描大量记录。
10. 子表单的父记录创建、更新、顺序调整、子行校验失败和流程写回均为原子操作；更新
    前后不能遗留孤儿子行，且不得用数组下标作为持久化行身份。
11. 新增、弃用、改标签、改校验、加索引和类型改变分别生成预期计划；禁止的类型改变
    和破坏性清理必须被稳定错误码拒绝。

## 17. 上线与运维

- 常规上线先执行版本化 SQL 迁移，禁止以 GORM AutoMigrate 建动态物理表。
- 首次只向内部测试租户开放 physical 模式，并限制单租户可创建的物理表数量、字段数、
  索引数和并发 DDL 数。
- 监控指标至少包含 DDL Job 队列长度、执行耗时、失败次数、重试次数、advisory lock
  等待、物理表数量、单表大小、索引大小和流程投影校准差异数。
- DDL 审计应记录操作者、表单/应用、模型 checksum、计划、Job、执行 SQL 的摘要、
  耗时和失败码；不得记录用户业务值或敏感配置。
- 删除表单默认只软删资产与停止运行时访问，不自动删除 `tn_fd_*` 表；物理删除需在
  数据保留期、备份确认和人工审批后以单表维护任务执行。

## 18. 不可违反的约束

1. 浏览器、Controller、Workflow 内核均不得直接执行或拼接动态 DDL/DML。
2. 物理表名、字段列名和存储模型只能由服务端不可变快照决定。
3. `wf_instance` 是流程状态唯一事实源；任何表单层字段仅为投影。
4. 一个 physical 记录只能有一份业务值事实源，不与 JSONB 双写。
5. 结构删除和破坏性类型变更不自动执行。
6. 子表单不能依靠数组下标作为跨请求的行身份；行级能力必须先升级协议。
7. 所有物理表强制租户列、RLS、参数绑定和同事务写入。
