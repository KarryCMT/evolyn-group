# 字段显隐规则设计方案

> 状态：设计提案；目标协议从 v4 升级至 v5 时实施。本文只定义“条件成立时显示字段”的规则，不把它扩展成字段权限、动态必填、联动赋值或公式计算。

## 1. 结论与范围

字段显隐应作为**表单级、声明式、可编译的规则集**存放在 `content.fieldShowRules`，而不是分散写入单个字段属性。规则以顶层字段稳定键 `widgetName` 引用条件字段和目标字段；一个目标字段只能属于一条规则，规则内可用“所有 / 任一”组合多个条件。

这样既能覆盖“选项为某值后追问”“数量达到阈值后补充配送信息”“成员为当前人员时显示专属项”等场景，也能使设计器、Web/移动运行时、服务端提交校验和历史记录详情使用同一事实源。

首期范围：

- 条件字段：顶层、具有值语义的基础字段和组织字段；条件不进入子表单行。
- 目标字段：顶层普通字段及整个子表单；不支持以子表单内部列、标签页容器或布局对象为目标。
- 运行场景：新建、预览、流程发起与历史详情；编辑记录复用同一引擎。
- 不在本期：子表单逐行显隐、动态可用/必填、条件赋值、跨表查询、脚本表达式。

子表单逐行规则必须使用“当前行”作用域和不同的值模型，后续另立 `subformFieldShowRules` 协议；禁止把其混入本规则，避免顶层字段值与行值混淆。

## 2. 对参考材料的分析

截图体现的交互路径可归纳为：在“表单设计 → 表单属性”提供入口；空状态解释“条件成立显示、否则隐藏”；编辑器先设定所有/任一和若干条件，再多选显示字段；保存后在列表中支持新增、编辑、复制、删除与拖拽整理。

条件编辑器有三个必须遵循的特征：

1. 条件字段可搜索，且字段类型决定可选比较关系和值输入控件；例如成员字段选择成员，日期字段选择日期，数值字段输入数值。
2. 规则把多个目标字段归为一组，用户看到的是“当……时，显示……”的完整自然语言摘要，而非多条难以维护的单字段规则。
3. 多级追问是常见情形。因此系统不能按画布顺序临时扫描；需要在保存/发布时编译依赖图、拒绝环，并在值变化时只重算下游字段。

所给 JSON 的核心结构是“条件树 + 目标字段数组”，与本方案一致：`filter.rel` 表示条件间关系，`filter.cond` 是条件，`fields` 是命中的显示目标。其成员条件中的 `type: "user"` 是字段类型指纹，`method: "eq"` 是比较操作，`value` 是成员稳定 ID 数组。`hasEmpty` 与 `hasCurrentUser` 这两个布尔开关语义重叠且难以组合：本方案改以明确的空值操作符和 `includeCurrentMember` 表达，避免“空值既是比较值又是额外开关”的歧义。

## 3. 协议设计

### 3.1 根结构与版本

目标协议 v5 在 `content` 增加必填数组 `fieldShowRules`；v4 文档升级时补 `[]`。因此必须同步修改协议版本常量、前后端严格校验器、迁移器、草稿/发布白名单和字段字典。`content` 的合法键变为：

```json
{
  "content": {
    "type": "form",
    "layout": "normal",
    "items": [],
    "layout_fields": [],
    "field_layout": [],
    "fieldShowRules": []
  }
}
```

`fieldShowRules` 是唯一事实源；禁止向 `widget` 增加 `showRule`、`condition` 等等价私有属性，也禁止保存 JavaScript 或任意字符串表达式。

### 3.2 完整示例

```json
{
  "content": {
    "type": "form",
    "layout": "normal",
    "items": [],
    "layout_fields": [],
    "field_layout": [],
    "fieldShowRules": [
      {
        "id": "_field_show_rule_01JH7M5K0A",
        "filter": {
          "rel": "and",
          "cond": [
            {
              "field": "_widget_applicant",
              "type": "user",
              "method": "eq",
              "value": ["member_6a85d0c477c234fe82a85d0d"],
              "includeCurrentMember": false
            }
          ]
        },
        "fields": ["_widget_total_hours", "_widget_daily_details"]
      }
    ]
  }
}
```

| 路径 | 类型 / 约束 | 语义 |
| --- | --- | --- |
| `fieldShowRules` | 数组，0–200 项 | 表单规则集合；数组顺序仅用于设计器展示，不是优先级。 |
| `[].id` | 非空稳定字符串，表单内唯一 | 设计器列表键、错误定位和审计差异定位；新建时生成，不随标签修改。 |
| `[].filter.rel` | `and` / `or` | 所有条件成立 / 任一条件成立。 |
| `[].filter.cond` | 数组，1–20 项 | 条件数组；不得为空。 |
| `[].filter.cond[].field` | 顶层 `widgetName` | 条件源字段。 |
| `[].filter.cond[].type` | 当前字段 `widget.type` | 类型指纹；必须与 `field` 解析出的控件类型一致，防止字段变更后误解释值。 |
| `[].filter.cond[].method` | 类型受限枚举 | 比较方法，见 3.3。 |
| `[].filter.cond[].value` | JSON 数组；按方法要求存在 | 比较常量；均以稳定值而非选项标签保存。 |
| `[].filter.cond[].includeCurrentMember` | 仅 `user` / `usergroup` 可选布尔值 | `true` 时将当前登录成员加入比较集合；匿名填写场景不加入任何值。 |
| `[].fields` | 顶层 `widgetName` 数组，1–100 项 | 条件成立后显示的目标字段，组内不得重复。 |

### 3.3 比较方法

`value` 只存实际业务值；“为空”使用专门方法，不能把 `null`、空字符串或空数组塞入 `value`。方法与控件值协议严格绑定：

| 条件字段 | 可用方法 | `value` 形态 |
| --- | --- | --- |
| text / textarea | `eq`、`ne`、`contains`、`notContains`、`isEmpty`、`notEmpty` | 前四项为单个字符串数组；空值方法不带 `value`。 |
| number / datetime | `eq`、`ne`、`gt`、`gte`、`lt`、`lte`、`between`、`isEmpty`、`notEmpty` | 单值数组；`between` 恰两项且下界不大于上界。 |
| radiogroup / combo / user / dept | `eq`、`ne`、`in`、`notIn`、`isEmpty`、`notEmpty` | `eq`/`ne` 恰一项；`in`/`notIn` 为 1–200 项。 |
| checkboxgroup / combocheck / usergroup / deptgroup | `containsAny`、`containsAll`、`containsNone`、`isEmpty`、`notEmpty` | 非空、去重的值数组。 |

发布版本未开放运行能力的字段不能作为条件源。后续新增控件时，必须在字段字典同时登记值形态、可用方法、比较器和服务端测试；不得以字符串强转方式“临时支持”。

### 3.4 参考 JSON 的映射

参考结构可按以下规则迁入 v5：

| 参考属性 | v5 属性 | 处理 |
| --- | --- | --- |
| `filter.rel` | `filter.rel` | `and` / `or` 原样保留。 |
| `filter.cond[].field` | `filter.cond[].field` | 保留稳定字段键。 |
| `filter.cond[].type` | `filter.cond[].type` | 保留，并在保存/发布时与 Schema 交叉校验。 |
| `filter.cond[].method` | `filter.cond[].method` | 原样迁入已支持的方法；否则报 JSON Path 错误。 |
| `filter.cond[].value` | `filter.cond[].value` | 保留稳定 ID/选项值数组。 |
| `hasCurrentUser` | `includeCurrentMember` | 仅成员类字段迁入；名称明确为“当前登录成员”。 |
| `hasEmpty` | 不迁入 | 改为 `isEmpty` / `notEmpty` 方法，避免双重语义。 |
| `fields` | `fields` | 保留，另生成规则 `id`。 |

## 4. 设计期校验与依赖图

### 4.1 结构校验

保存草稿与发布均执行下列校验；发布再执行运行能力白名单校验：

- `id`、条件字段、目标字段均存在于顶层 `content.items`，且不引用 `separator`、`button`、标签页或子表单内部字段；子表单只能作为整个目标字段。
- 条件源字段和目标字段不能是 `widget.visible=false` 的静态隐藏字段；这类配置没有可达语义，应直接报错。
- 条件的 `type`、`method`、`value` 与字段字典和值协议一致；选项值必须命中当前选项，成员/部门 ID 只校验形状，不在保存草稿时查询目录。
- 同一目标字段只能出现在一条规则的 `fields` 中。需要“满足 A 或 B 时显示 X”时，应把 A、B 放进同一规则并将 `rel` 设为 `or`。
- 一个规则不能以自身目标作为条件源；任意规则组合不得形成环。保存失败应返回参与环的规则 ID 与字段路径，例如 `content.fieldShowRules[2].fields[0]`。
- 规则数最多 200；限制与规则本身无关的表单字段总上限仍为 500。

规则图的边方向是“条件源 → 目标字段”。保存或发布时一次性构图并拓扑排序：

```text
是否外出 ──► 外出城市 ──► 住宿说明
     └──────────────────► 联系方式
```

允许多级规则，但不允许闭环；运行时只从发生变化的字段沿出边计算，不全表扫描。规则的拖拽顺序不参与计算，避免同一份配置因排序不同产生不同结果。

### 4.2 可见性优先级与数据保留

对字段 `F`，最终可见性为：

```text
effectiveVisible(F)
  = widget.visible(F)
  ∧ fieldPermission.visible(F)
  ∧ (F 无显隐规则目标 ? true : matches(ownerRule(F)))
```

字段权限永远高于显隐规则。若条件源因权限或上游显隐而不可见，条件引擎将该条件视为“不满足”，而不是读取其隐藏值；这样不会通过下游字段反推出无权字段的值。多级关系因此自然收敛：上游隐藏时其全部下游也隐藏。

字段隐藏后保留会话内值和填写草稿，清除该字段的前端错误，但不把值放入正式提交载荷；再次显示时恢复原值。不要在隐藏时清值，否则用户切换选项后会无故丢失已填内容。正式记录只保存提交时有效可见字段的值。

## 5. 产品与交互设计

### 5.1 入口和列表

在表单设计右侧“表单属性”面板新增“字段显隐规则”区块：空状态提供“添加显隐规则”，已配置时显示规则数和“管理规则”。点击后打开全屏或大尺寸抽屉，列表以两行自然语言摘要展示：

```text
当［填报人］等于［成员甲］时
显示［总工时］、［日报明细］
```

每项提供编辑、复制、删除和拖拽把手；删除需二次确认。复制生成新 `id`，其余内容复制。列表重排只改善阅读和审计 diff，不改变运行结果。

### 5.2 编辑器

编辑器固定为“条件”和“显示以下字段”两段：

1. 顶部选择“满足所有条件”或“满足任一条件”。
2. 条件行依次选择字段、方法和值；字段选择器支持搜索并带控件图标。切换字段后立即重置不兼容的方法和值，防止静默保留旧条件。
3. 值控件按字段类型渲染：选项多选、成员/部门搜索、日期时间选择器、数值输入等。空值方法隐藏值控件。
4. 目标字段采用可搜索的多选列表，仅展示符合范围的顶层字段；已被其他规则占用的字段置灰并解释占用规则。
5. 底部显示实时摘要和校验结果；保存前若发现环、被删除引用或类型不匹配，定位到具体条件行。

画布中的目标字段应在选中规则时高亮，条件源显示连线提示。预览提供“规则调试”开关：展示每条条件的布尔结果和最终可见性，但不得在普通填写界面暴露该信息。

字段改名不影响规则，因为引用的是 `widgetName`；删除字段、将字段移入子表单、改为不兼容类型或设为静态隐藏时，先提示依赖并阻止保存，直至规则被修改或删除。

## 6. 运行时、服务端与历史数据

### 6.1 客户端运行时

在 `@evolyn.do/form` 增加纯 TypeScript 的 `schema/rules`：负责协议校验、规则编译、拓扑排序和条件求值；`runtime/store/createFormRuntime.ts` 只消费编译结果并维护 `FieldRuntimeState.visible`。桌面与移动运行时共用该模块。

字段值变化后执行顺序为：规范化新值 → 仅重算变更字段的下游规则 → 更新受影响字段的 `visible` 和错误态 → 重新布局/焦点处理。当前焦点字段被隐藏时，焦点移至画布顺序中的下一可见可编辑字段，否则移到规则来源字段。渲染计划仍是静态结构，字段宿主依据自身 `visible` 决定是否渲染，避免对完整 `values` 建立深度监听。

运行时 bootstrap 继续返回发布快照和 `permissions`。填写模式以 `addFields` 合成字段权限；查看/历史模式以 `viewFields` 合成。规则引擎不得把权限矩阵或隐藏字段原始值暴露给字段组件。

### 6.2 服务端终审

浏览器可见性只是交互，不能作为信任边界。服务端在表单域内实现无 Gin/GORM 依赖的纯规则编译器与求值器，并与 TypeScript 使用同一组 JSON fixture：

1. 保存草稿和发布时校验/编译规则，拒绝未知键、环和不支持的方法。
2. 提交时先按发布快照、已解析的 `addFields` 权限和提交中可用的条件值计算最终可见性。
3. 每个非布局字段的包装 `visible` 必须与服务端结果相同；期望隐藏却携带 `data`、期望可见却伪造隐藏，均返回 `FORM_RECORD_INVALID` 和字段级错误。
4. 只对最终可见字段执行必填、类型、范围与选项校验并落库；隐藏字段不得落入正式记录值。

现有 `SubmitFieldValue { data, visible }` 载荷无需新增接口字段，只需把“与发布快照静态 `visible` 一致”的校验改为“与服务端动态求值结果一致”。错误码继续使用 `FORM_SCHEMA_INVALID`、`FORM_PUBLISH_UNSUPPORTED_FIELD`、`FORM_RECORD_INVALID`，并在 `data.issues` / `data.fieldErrors` 中给出 JSON Path 或 `widgetName`。

历史详情按该记录绑定的不可变发布快照和已保存值重算可见性，再渲染字段；绝不能拿当前草稿规则解释旧记录。流程审批中的表单快照同样遵循此口径，显隐规则不替代审批字段权限。

## 8. 验收与分期

### 8.1 验收用例

- 单条件、AND、OR、空值、数值区间、单选/多选/成员/日期等比较器均有前后端一致的 fixture。
- 多级 A→B→C 变化时仅重算 B、C；A/B/C 成环时草稿保存失败且能定位路径。
- 目标字段在规则中唯一；“A 或 B 显示 X”只能由一条 OR 规则表达。
- 字段被规则隐藏后不校验、不提交 `data`，重新显示仍保留会话值；服务端拒绝伪造 `visible` 或隐藏字段 `data`。
- 条件源无字段权限或被上游隐藏时，下游不显示，且界面和接口不泄露源值。
- 发布版本、历史详情、流程发起和桌面/移动端得到相同可见性结果。
- 500 字段、200 规则、每规则 20 条件的边界表单在单字段修改时不进行全量规则扫描。

### 8.2 实施顺序

1. 确认本文协议并登记 ADR，升级为 v5，完成 TS/Go 结构校验、迁移器和共享 fixture。
2. 完成规则编译器、前后端求值器和提交终审，先以接口/单元测试锁定安全语义。
3. 接入设计器属性面板、列表和预览调试，再接入桌面、移动与流程发起运行时。
4. 完成历史详情、权限组合、性能基准和端到端回归后开放发布白名单；子表单逐行规则作为独立后续需求评审。
