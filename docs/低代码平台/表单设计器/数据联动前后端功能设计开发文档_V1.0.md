# Evolyn 数据联动（Data Linkage）前后端功能设计与开发文档 V1.0

> 项目：Evolyn Group / 灵衍云低代码平台\
> 仓库：`KarryCMT/evolyn-group`\
> 技术基线：前端 Vue 3 + TypeScript + Element Plus；后端 Go + Gin +
> pgx + PostgreSQL\
> 目标：实现类似简道云"数据联动"的跨表查询、条件匹配、字段回填、动态选项/范围以及后续子表整体联动能力。\
> 文档日期：2026-09-21

------------------------------------------------------------------------

## 1. 背景与目标

数据联动用于在当前表单字段发生变化时，根据配置的条件查询另一数据源，并将查询结果自动写入当前表单字段，或动态生成字段选项/可选范围。

典型场景：

``` text
当前表单：订单明细
产品名称 = "A100"

联动数据源：产品管理
WHERE 产品管理.产品名称 = 当前表单.产品名称

返回：
产品管理.型号规格 -> 当前表单.型号规格
产品管理.单位     -> 当前表单.单位
产品管理.产品定价 -> 当前表单.单价
```

数据联动不是简单的"默认值"，而是：

``` text
Source
  -> Filter/Condition
  -> Query
  -> Result Strategy
  -> Mapping
  -> Form Runtime SetValue
```

V1 设计必须与 Evolyn 已规划的 Form Schema Engine、Field Engine、Form
Designer Engine、Form Runtime、Rule Engine、Query Engine、Data
Engine、Physical Table Engine、Form Permission Engine
配合，避免形成独立且重复的数据查询体系。

## 2. V1 功能范围

### 2.1 V1 必须实现

1.  字段属性中的"默认值 -\> 数据联动"入口。
2.  选择联动数据源。
3.  V1 首先支持普通表单数据源。
4.  支持多个过滤条件。
5.  条件关系支持 `ALL/ANY`。
6.  根据字段类型动态提供操作符。
7.  条件值支持：
    -   当前表单字段；
    -   自定义常量。
8.  支持一个联动规则映射一个或多个目标字段。
9.  当前表单依赖字段变化后自动重新联动。
10. 表单初始化时执行需要初始化的联动。
11. 无结果时支持清空/保持原值。
12. 多结果时提供确定性结果策略。
13. 数据权限、租户隔离必须在后端执行。
14. 联动查询必须通过 Query Engine / Data Engine，不允许前端拼 SQL。
15. 支持联动配置保存、发布、运行时读取。
16. 支持循环依赖检测。
17. 支持请求竞态取消/结果版本校验。
18. 支持基本审计与运行错误记录。

### 2.2 V1.1/V2 预留

-   聚合表；
-   数据流输出表；
-   动态选项联动；
-   可选范围联动；
-   子表整体联动；
-   跨应用数据联动；
-   公式作为条件值；
-   当前用户/部门/组织/时间作为上下文值；
-   聚合函数；
-   多行结果映射；
-   API/远程数据源。

### 3.1 关键原则

**前端负责配置和触发，后端负责可信查询。**

前端可以知道：

-   sourceId；
-   fieldId；
-   operator；
-   mapping；
-   当前字段值。

但不能决定：

-   真实物理表名；
-   真实数据库列名；
-   tenant SQL；
-   permission SQL；
-   任意 SQL 表达式。

## 4. 引擎职责边界

### Form Designer Engine

负责数据联动配置 UI、字段选择、操作符选择、类型兼容提示、配置校验和
Schema 写入。

不得负责实际业务数据查询。

### Form Schema Engine

负责 `DataLinkageDefinition` Schema
定义、序列化、反序列化、版本升级和发布冻结。

### Field Engine

负责字段元数据、字段能力、字段类型兼容、可用操作符、值标准化与 Codec。

例如：

``` ts
fieldEngine.getOperators('text')
fieldEngine.isCompatible(sourceField, targetField, 'linkage_mapping')
```

### Form Runtime

负责监听字段变化、Dependency Graph、调度 DataLinkageRuntime、字段写入和
UI 更新。

### Rule Engine

负责条件逻辑语义，如 AND/OR、表达式判断；不直接访问 PostgreSQL。

### Query Engine

负责统一查询 AST、Filter、Projection、Sort、Limit、Permission、Tenant
Scope 以及 PostgreSQL 查询编译。

### Data Engine

负责表单业务数据读取，不理解"这个查询来自数据联动还是列表页"。

### Physical Table Engine

负责逻辑字段到物理表/列映射。

### Form Permission Engine

负责为 Query Engine 注入当前用户允许读取的数据范围和字段权限。

## 5.4 前端 Schema

``` ts
export interface DataLinkageDefinition {
  id: string
  version: number
  enabled: boolean

  source: LinkageDataSource

  filter: FilterGroup

  mappings: LinkageMapping[]

  result: LinkageResultStrategy

  runtime: LinkageRuntimeOptions
}

export interface LinkageDataSource {
  type: 'form'
  appId: string
  sourceId: string
}

export interface FilterGroup {
  logic: 'and' | 'or'
  conditions: FilterCondition[]
}

export interface FilterCondition {
  id: string
  sourceFieldId: string
  operator: string
  value: LinkageValueSource
}

export type LinkageValueSource =
  | {
      type: 'field'
      fieldId: string
    }
  | {
      type: 'constant'
      value: unknown
      valueType?: string
    }

export interface LinkageMapping {
  sourceFieldId: string
  targetFieldId: string
}

export interface LinkageResultStrategy {
  mode: 'first'
  orderBy?: {
    fieldId: string
    direction: 'asc' | 'desc'
  }[]
}

export interface LinkageRuntimeOptions {
  trigger: 'dependency_change'
  runOnInit: boolean
  debounceMs: number
  emptyStrategy: 'clear' | 'keep'
  errorStrategy: 'keep' | 'clear'
}
```

## 5.5 字段类型与操作符

操作符不能写死在 Dialog 中。

``` ts
export interface FieldOperatorDefinition {
  code: string
  label: string
  fieldTypes: string[]
  requireValue: boolean
}
```

建议 V1：

  类型            操作符
  --------------- ---------------------------------------------------
  text            eq, neq, contains, not_contains, empty, not_empty
  number          eq, neq, gt, gte, lt, lte, empty, not_empty
  date/datetime   eq, neq, gt, gte, lt, lte, empty, not_empty
  select/radio    eq, neq, in, not_in, empty, not_empty
  member/dept     eq, neq, contains, empty, not_empty

`empty/not_empty` 不显示右侧 ValueSource。

------------------------------------------------------------------------

## 5.6 类型兼容规则

条件：

``` text
sourceField.type -> operator -> value.type
```

映射：

``` text
sourceField.type -> targetField.type
```

V1 默认采用严格兼容，不做隐式类型转换：

``` text
text    -> text
number  -> number
date    -> date
member  -> member
dept    -> dept
```

后续再由 Field Engine 提供显式转换能力。

## 5.7 Dependency Graph

保存 Schema 后构建：

``` text
field_product_name
      │
      └── linkage_product
              │
              ├── field_model
              ├── field_unit
              └── field_price
```

示例：

``` ts
Map<string, Set<string>>

field_product_name -> linkage_product
field_status       -> linkage_product
```

当 `field_product_name`
改变，只执行依赖它的规则，而不是扫描所有联动规则。

------------------------------------------------------------------------

## 5.8 循环依赖检测

必须阻止：

``` text
A -> B
B -> A
```

以及：

``` text
A -> B -> C -> A
```

保存规则时构建有向图并执行 DFS / 拓扑检测。

发现环路：

``` text
无法保存数据联动：
字段「A」与「B」形成循环联动，请调整联动关系。
```

前端做即时检测，后端发布时必须再次检测。

------------------------------------------------------------------------

## 5.9 Runtime 触发

``` ts
onFieldValueChange(fieldId, value)
  -> dependencyGraph.getRules(fieldId)
  -> scheduler.schedule(rule)
  -> resolveDependencies(rule)
  -> linkageApi.execute(...)
  -> requestGuard.validateResponse()
  -> mappingExecutor.apply(...)
```

------------------------------------------------------------------------

## 5.10 防抖与竞态

例如用户连续输入：

``` text
A
AB
ABC
```

产生三个请求：

``` text
request#1 A
request#2 AB
request#3 ABC
```

如果 #1 最后返回，不能覆盖 ABC 的结果。

建议：

``` ts
{
  ruleId: 'linkage_01',
  requestVersion: 17
}
```

Runtime 只接受当前最新 version。

同时使用 `AbortController` 尽量取消旧请求。

默认：

``` text
debounceMs = 250
```

## 6.4 API：执行联动

推荐：

``` http
POST /api/v1/forms/{formId}/linkages/{ruleId}/execute
```

请求不要把完整可信规则从浏览器重新传给后端。

``` json
{
  "schemaVersion": 12,
  "values": {
    "field_product_name": "A100",
    "field_status": "enabled"
  },
  "requestVersion": 17
}
```

后端根据：

``` text
formId + schemaVersion + ruleId
```

读取已经发布的可信规则。

响应：

``` json
{
  "code": 0,
  "data": {
    "ruleId": "linkage_product",
    "requestVersion": 17,
    "matched": true,
    "values": {
      "field_model": "M-100",
      "field_unit": "台",
      "field_price": "1299.00"
    }
  }
}
```

这样可以防止浏览器篡改：

``` text
sourceId
sourceFieldId
targetFieldId
operator
```

绕过权限查询其它数据。

## 6.5 后端执行流程

``` text
ExecuteLinkage
     │
     ├─ 1. Auth / Tenant Context
     ├─ 2. Load Published Form Schema
     ├─ 3. Find Linkage Rule
     ├─ 4. Validate Rule
     ├─ 5. Resolve Runtime Values
     ├─ 6. Build Query AST
     ├─ 7. Inject Tenant Scope
     ├─ 8. Inject Permission Scope
     ├─ 9. Resolve Physical Table/Column
     ├─10. Compile parameterized SQL
     ├─11. Execute via pgx
     ├─12. Map logical values
     └─13. Return target field values
```

## 6.6 Query AST

数据联动层生成逻辑 AST：

``` go
type Query struct {
    Source     Source
    Projection []FieldRef
    Filter     FilterNode
    OrderBy    []OrderBy
    Limit      int
}
```

例如：

``` text
产品名称 = 当前表单.产品名称
AND
状态 = "enabled"
```

转为：

``` text
AND
├─ EQ(product_name, "A100")
└─ EQ(status, "enabled")
```

再由 Query Engine 编译。

------------------------------------------------------------------------

## 6.7 SQL 示例

逻辑规则：

``` text
source = 产品管理
产品名称 = "A100"
状态 = "enabled"

return 型号规格、单位、产品定价
```

最终 SQL 应类似：

``` sql
SELECT
    f_model,
    f_unit,
    f_price
FROM biz_t_xxxxx
WHERE tenant_id = $1
  AND deleted_at IS NULL
  AND f_product_name = $2
  AND f_status = $3
  AND <permission predicate>
ORDER BY updated_at DESC, id DESC
LIMIT 2;
```

注意使用 `LIMIT 2` 而不是直接
`LIMIT 1`，这样可以判断本应唯一的数据是否出现多结果。

所有用户值必须使用 pgx 参数绑定，禁止字符串拼 SQL。

## 7. 数据库建模

## 7.1 设计原则

Evolyn 的表单定义/发布 Schema 如果已经采用 JSONB 保存完整表单
Schema，则**数据联动定义的事实源应继续位于版本化 Form Schema
中**，不要同时维护一份完整规则关系表造成双写一致性问题。

数据库额外关系表主要解决：

-   快速依赖查询；
-   发布时索引；
-   运维审计；
-   运行错误分析；
-   后续跨表依赖影响分析。

因此推荐：

``` text
Form Schema JSONB = Source of Truth
linkage_dependency = 派生索引
linkage_execution_log = 可选运行日志
```

------------------------------------------------------------------------

## 7.3 表：form_linkage_dependency

用途：发布 Schema 后生成的数据联动依赖索引。

## 7.4 表：form_linkage_execution_log

不建议记录每一次成功联动，否则高频输入会造成日志爆炸。

V1 建议仅记录：

-   error；
-   timeout；
-   permission_denied；
-   invalid_rule；
-   multi_result_conflict；
-   slow_query。

``` sql
CREATE TABLE form_linkage_execution_log (
    id                  BIGSERIAL PRIMARY KEY,

    tenant_id           VARCHAR(64) NOT NULL,
    app_id              VARCHAR(64) NOT NULL,
    form_id             VARCHAR(64) NOT NULL,
    form_version_id     VARCHAR(64) NOT NULL,
    linkage_id          VARCHAR(64) NOT NULL,

    user_id             VARCHAR(64),

    source_type         VARCHAR(32) NOT NULL,
    source_id           VARCHAR(64) NOT NULL,

    status              VARCHAR(32) NOT NULL,
    error_code          VARCHAR(64),
    error_message       TEXT,

    duration_ms         INTEGER NOT NULL DEFAULT 0,
    result_count        INTEGER NOT NULL DEFAULT 0,

    request_id          VARCHAR(64),

    created_at          TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

索引：

``` sql
CREATE INDEX idx_linkage_log_rule_time
ON form_linkage_execution_log (
    tenant_id,
    linkage_id,
    created_at DESC
);

CREATE INDEX idx_linkage_log_status_time
ON form_linkage_execution_log (
    tenant_id,
    status,
    created_at DESC
);
```

建议日志配置 TTL，例如只保留 30
天，或进入统一审计/可观测体系后删除该专表。

## 7.5 是否建立 form_linkage_rule 表

**V1 不推荐把完整 Rule 再存一份 `form_linkage_rule`。**

原因：

``` text
form_schema_version.schema_json
          +
form_linkage_rule.rule_json
```

会产生两个事实源。

如果未来 Evolyn 的 Form Schema 存储模型改为完全关系化，再迁移为：

``` text
form_linkage_rule
form_linkage_condition
form_linkage_mapping
```

当前阶段没有必要过早拆分。

``` text
     ▼
Draft Form Schema
     │
     ▼
Publish
     │
     ├─ Schema validation
     ├─ Field existence validation
     ├─ Source existence validation
     ├─ Type compatibility validation
     ├─ Operator validation
     ├─ Permission/reference validation
     ├─ Circular dependency detection
     │
     ▼
Freeze Form Version
     │
     ▼
Generate linkage dependency index
     │
     ▼
Published
```

运行时永远针对发布版本执行，不直接信任 Designer Draft。

## 9. 权限与安全

联动查询必须满足：

``` text
最终数据范围
=
Tenant Scope
∩ Form Read Permission
∩ Data Permission
∩ Field Permission
∩ Linkage Filter
```

不能因为目标字段允许显示，就默认用户拥有源字段读取权限。

建议策略：

-   源表无读取权限：联动返回 permission denied；
-   源字段无读取权限：该字段不得在设计器中成为 Mapping Source；
-   运行时权限发生变化：后端重新校验；
-   所有逻辑 fieldId 必须经 Physical Table Engine 映射；
-   禁止前端提交物理 tableName/columnName；
-   禁止动态原始 SQL；
-   禁止未经白名单注册的 operator。

## 11. 数据一致性

数据联动只负责"填写当前表单值"。

提交表单时不能认为此前联动查询结果仍然可信。

例如：

``` text
10:00 联动价格 = 100
10:05 产品价格改成 120
10:10 用户提交订单
```

平台必须明确字段语义：

### Snapshot 模式

联动值就是用户提交时的表单快照，提交时不重新查询。

适合：

``` text
历史价格
客户名称
地址描述
```

### Strong Reference 模式（后续）

提交时根据 source record ID 重新校验。

因此后续建议联动结果支持携带：

``` json
{
  "sourceRecordId": "record_xxx"
}
```

为引用字段、数据追溯和提交校验预留。

## 12. 性能设计

前端：

-   默认 debounce 250ms；
-   同一 rule 旧请求取消；
-   相同依赖值短时间缓存；
-   Dependency Graph 精准触发；
-   hidden/disabled rule 不执行。

后端：

-   Projection 只查询 Mapping 需要字段；
-   默认 Limit；
-   使用 pgx 参数化；
-   Query Engine 支持执行超时；
-   记录 slow query；
-   条件字段应由 Physical Table Engine 的索引能力支持。

建议慢联动阈值：

``` text
500ms warning
2000ms timeout/降级（最终以平台统一配置为准）
```

## 16. V1 完成标准

V1 可以定义为以下场景完整跑通：

``` text
产品管理
├ 产品名称
├ 产品编号
├ 产品分类
├ 型号规格
├ 单位
└ 产品定价

订单明细
├ 产品名称
├ 型号规格
├ 单位
└ 单价
```

配置：

``` text
数据源 = 产品管理

WHERE
产品管理.产品名称
=
订单明细.产品名称

MAPPING
产品管理.型号规格 -> 订单明细.型号规格
产品管理.单位     -> 订单明细.单位
产品管理.产品定价 -> 订单明细.单价
```

达到：

1.  Designer 可配置；
2.  Schema 可保存和发布；
3.  Runtime 可监听；
4.  Backend 可查询；
5.  Permission 生效；
6.  Tenant 隔离生效；
7.  Mapping 正确；
8.  竞态正确；
9.  无结果策略正确；
10. 循环依赖不能发布；
11. PostgreSQL 查询参数化；
12. 前端完全不知道物理表名和物理字段名。

满足以上条件，Evolyn 的数据联动 V1 才算形成完整的平台级闭环。

## 17. 最终技术决策

**决策 1：数据联动不是一个新的数据库查询体系。**

它是 Form Runtime 对 Query Engine / Data Engine 的业务编排。

**决策 2：数据联动不是普通 defaultValue。**

字段属性中的"默认值"只是 Designer 的产品入口，真实定义是版本化
`DataLinkageDefinition`。

**决策 3：Schema 是规则事实源。**

V1 不重复创建完整规则关系表；关系表只做依赖索引与运行观测。

**决策 4：前端不拥有可信 Query。**

浏览器只提交当前运行时字段值；后端从发布 Schema 获取
source/operator/mapping。

**决策 5：Field Engine 决定类型能力。**

Designer 不维护另一套字段类型和 operator 判断。

**决策 6：权限在 Query Engine 注入。**

任何联动都不能绕开 Tenant、Form Permission、Data Permission 和 Field
Permission。

**决策 7：从 V1 就处理 Dependency Graph、竞态和循环依赖。**

这三项不是优化项，而是响应式低代码 Runtime 正确性的基础。
