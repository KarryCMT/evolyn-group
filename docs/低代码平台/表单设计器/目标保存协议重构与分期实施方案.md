# 表单设计器目标保存协议重构与分期实施方案

## 1. 决策与目标

### 1.1 已确认决策

表单设计器保存给后端的唯一事实结构固定为用户确认的两层字段协议：

```json
{
  "content": {
    "type": "form",
    "items": [
      {
        "widget": {
          "type": "text",
          "widgetName": "_widget_xxx",
          "enable": true,
          "visible": true,
          "allowBlank": true
        },
        "description": "",
        "label": "单行文本",
        "labelHidden": false,
        "lineWidth": 12
      }
    ]
  }
}
```

其中：

- `content.type` 固定为 `form`；
- `content.items` 是字段及布局项的唯一有序列表；
- 每项公共展示属性位于 `item`；控件能力和专属配置位于 `item.widget`；
- `widget.type` 决定控件语义，`widget.widgetName` 是记录值、规则、关联和接口错误回填使用的稳定字段键；
- 设计器、后端草稿、发布版本和最终渲染器均读写这一结构，禁止在中间持久化另一份等价 Schema；
- 对已定义字段，保存、加载、编辑、发布必须无损保留其 JSON 字段、层级和空值语义。未知字段不可静默删除，应拒绝保存并返回精确路径错误，或在版本升级策略明确后保留。

本方案将该协议称为“目标保存协议”，不在代码、接口、示例或产品文案中使用第三方产品名称。

### 1.2 目标边界

本专项覆盖：字段定义、设计器、发布、最终填写、记录提交、草稿、权限校验和运行性能。

本专项不包含：流程图定义、任意脚本执行、将第三方服务的 API 或产品名称暴露到灵衍云接口。

## 2. 当前差距

当前 `packages/form` 的持久化模型是 `FormDocument { version, kind, title, fields, settings }`，字段为 `FormField { id, key, type, label, required, config }`。它不能直接读取目标保存协议的 `content.items` 根结构。

已存在的字段类型枚举在概念上基本覆盖目标样本中的 27 种不同 `widget.type`，但这不是协议兼容：

- 现有设计态转换器只转换文本、数字、日期、下拉、成员、部门、子表单 7 类画布控件；
- 现有最终渲染器只注册 9 类基础字段：文本、多行文本、数字、日期时间、单选、复选、下拉、多选下拉、分割线；
- 成员、部门、附件、地址、定位、子表单、关联、计算、签名、富文本等缺少完整的组件、服务端契约或运行行为；
- `enable`、`visible`、`allowBlank`、`labelHidden`、`lineWidth` 和绝大多数控件专属属性尚未以目标协议原样贯通设计器、发布和运行时；
- 后端尚未落地表单资产、表单版本和记录提交域，现有应用菜单仅预留表单资产入口。

因此，本方案是协议替换与表单资产建设，不能按“改字段名”处理。

## 3. 总体实施原则

1. **协议优先。** 每个阶段新增或修改的能力必须直接读写 `content.items[].widget`，禁止再以 `FormDocument` 作为后端事实来源。
2. **先纵向闭环，再横向扩展。** 每一阶段至少包含设计、保存、发布、读取、填写/执行和测试中的完整最小闭环；不能只堆前端控件。
3. **字段类型可分批交付，协议不可分叉。** 未在当前阶段完成运行能力的字段必须被服务端发布白名单拦截，不得发布后在用户侧静默显示“暂不支持”。
4. **配置按控件严格校验。** `widget.type` 是判别字段；各控件的专属属性必须有前端与后端一致的校验器。`null`、空数组、缺省值和布尔值必须逐项定义，不用 truthy/falsy 代替。
5. **结构与执行分离。** `visible`、`enable` 等静态属性先按保存值执行；依赖其他字段的动态规则以声明式 JSON 另行定义，不允许 Schema 执行任意 JavaScript。
6. **发布不可变。** 草稿可修改；每次发布生成不可覆盖的版本快照。记录提交必须带发布版本和修订口令，后端依据该快照校验。
7. **服务端最终裁决。** 浏览器校验只改善交互；权限、字段必填、类型、范围、关联数据可见性、附件归属和计算结果均由后端复核。

## 4. 目标协议的分层与通用映射

### 4.1 每个字段项的公共属性

| 目标字段 | 语义 | 第一落地阶段 |
| --- | --- | --- |
| `item.widget` | 判别控件类型及其专属配置 | P1 |
| `item.label` | 字段显示名称 | P1 |
| `item.description` | 字段说明 | P1 |
| `item.labelHidden` | 是否隐藏标签 | P2 |
| `item.lineWidth` | 桌面栅格宽度 | P2 |
| `widget.widgetName` | 稳定字段键，需全表单唯一 | P1 |
| `widget.enable` | 是否可填写 | P2 |
| `widget.visible` | 是否可见 | P2 |
| `widget.allowBlank` | 是否允许空值 | P1 |

### 4.2 控件分组

| 分组 | `widget.type` | 主要专属配置 |
| --- | --- | --- |
| 基础输入与选项 | `text`、`textarea`、`number`、`datetime`、`radiogroup`、`checkboxgroup`、`combo`、`combocheck`、`separator` | 长度、格式、精度、范围、选项、布局、分割线样式 |
| 组织与文件 | `user`、`usergroup`、`dept`、`deptgroup`、`image`、`upload`、`address`、`location`、`signature`、`phone` | 组织范围、文件数、地址层级、定位半径、签名、号码区域/验证 |
| 业务与关联 | `subform`、`linkquery`、`linkfield`、`lookup`、`aggregation`、`sn` | 子字段、关联目标、过滤/排序、映射、聚合与流水号规则 |
| 富交互 | `richtext`、`button` | 内容、操作与样式 |

## 5. 分期实施

### P0：协议冻结与资产域设计

**目标：** 在写重构代码前，把“结构完全一致”的可验证边界固定下来。

**本阶段工作：**

- 建立每种 `widget.type` 的字段字典：完整属性、类型、是否必填、默认值、`null` 语义、值协议、前端展示、后端校验、权限要求和测试用例；
- 将样本中的每个属性登记为“首期执行”“保存但延后执行”或“不纳入目标协议”，后两类必须由产品确认，不能开发时自行丢弃；
- 设计表单资产、草稿、不可变发布版本、记录、附件引用、关联数据与审计的后端数据模型及 API 契约；
- 确定后端域归属、权限资源、配额、乐观锁字段、版本策略和菜单资产关联方式；
- 审计现有 `packages/form`、预览页面以及所有可能持久化 `FormDocument` 的调用点，形成迁移清单；
- 产出端到端测试矩阵与性能基线。

**交付物：** 协议字典、后端 API 草案、数据迁移清单、字段验收矩阵与 ADR（如涉及既有架构结论变更）。

**进入 P1 的条件：** 27 种字段的属性归属已逐项确认；后端草稿/发布/提交 API 的字段名与错误码已评审；不存在“先存起来以后再说”的未定义属性。

### P1：协议核心与校验器替换

**目标：** 让前端和后端能以目标保存协议创建、校验、加载和无损保存空表单及字段定义。

**本阶段工作：**

- 在 `packages/form` 新建目标协议的 TypeScript 判别联合类型、JSON 校验器、深拷贝器和版本迁移器；
- 将设计器状态与持久化接口从 `FormDocument` 切换为 `content.items`；移除“画布模型转换为另一份发布 Schema”的持久化路径；
- 实现公共字段的唯一性校验：`widgetName` 非空、全表单唯一，子表单字段在其作用域内唯一；
- 实现按 `widget.type` 分派的严格配置校验，并返回 JSON Path 级错误；
- 后端落地表单资产草稿与版本表、服务层事务边界、租户/应用归属校验、审计及乐观锁；
- 增加草稿保存和读取接口，仅允许通过校验的数据写入；
- 为旧 `FormDocument` 制定一次性迁移脚本或明确开发环境无存量数据的切换方案。迁移仅用于已有灵衍云数据，绝不把旧协议继续作为双写事实来源。

**验收：** 目标协议样本可原样加载、编辑一个公共属性后保存，未编辑属性不丢失；非法类型、重复键、错误枚举、非 JSON 值和越权应用均被拒绝。

**进入 P2 的条件：** 前后端对同一 JSON 的校验结果一致；草稿保存/读取不再依赖 `FormDocument`；迁移策略经过演练。

### P2：基础字段设计器与首个发布闭环

**目标：** 完成最常用字段的可设计、可发布、可填写和可提交闭环。

**本阶段工作：**

- 完成 `text`、`textarea`、`number`、`datetime`、`radiogroup`、`checkboxgroup`、`combo`、`combocheck`、`separator` 的素材面板、拖放、复制、删除与属性面板；
- 逐项实现 `allowBlank`、`enable`、`visible`、`labelHidden`、`lineWidth`、说明、选项、数字范围/精度、日期格式和分割线样式；
- 最终渲染器改为直接以 `widget.type` 注册组件；提交值以 `widgetName` 为键；
- 后端实现发布、运行时 bootstrap、提交、字段错误回填和发布版本校验；
- 为基础字段建立浏览器/后端一致的值编解码和校验；
- 完成桌面和移动端基础布局、无障碍标签、错误定位和回归测试。

**验收：** 基础字段从设计到发布再到提交均只使用目标保存协议；`allowBlank`、禁用、隐藏、选项、范围与版本冲突在前后端均有可验证行为。

**进入 P3 的条件：** 发布快照不可被草稿覆盖；历史发布版本仍可正确填写；基础字段不存在运行时“暂不支持”。

### P3：组织、文件与位置字段闭环

**目标：** 将依赖租户数据、对象存储或设备能力的字段纳入正式运行时。

**本阶段工作：**

- 完成 `user`、`usergroup`、`dept`、`deptgroup` 的分页检索、范围限制、成员/部门失效处理和提交值协议；
- 完成 `image`、`upload` 的直传/受控上传、文件数量限制、类型与大小校验、文件归属、预览和提交前上传完成检查；
- 完成 `address`、`location`、`signature`、`phone` 的专属 UI、移动端交互、隐私授权、数据格式及服务端复核；
- 为这些字段接入 Adapter 与后端端点，确保租户隔离和记录读取授权；
- 按模块动态加载重型组件，避免把地图、签名或上传库带入基础字段首屏包。

**验收：** 所有组织、文件和位置字段均可从设计、发布、填写到记录回显；越权成员、跨租户部门、未完成上传、无权限附件和不合法位置数据被服务端拒绝。

**进入 P4 的条件：** 重型字段没有静态进入基础运行时包；文件与组织数据的权限回收、记录历史回显和错误处理已覆盖。

### P4：子表单、关联、计算与流水号

**目标：** 完成业务数据建模能力，建立结构化记录与关联数据的安全边界。

**本阶段工作：**

- 完成 `subform` 的嵌套 `items` 协议、行 ID、增删改、行级校验、桌面表格化编辑和移动端逐行编辑；
- 实现 `linkquery`、`linkfield`、`lookup` 的关联目标、查询条件、过滤、排序、字段映射和权限过滤；
- 实现 `aggregation` 的受控公式/聚合模型、依赖图、精度与显示模式，关键结果由服务端重新计算；
- 实现 `sn` 的流水号生成规则、并发唯一性和版本归属；
- 后端建立记录值 JSON/索引策略、关联引用完整性、删除/归档限制与跨租户防护；
- 对长子表单和大关联集合实施分页、虚拟列表和取消请求。

**验收：** 子表单与关联字段能在新建、编辑、历史记录回显和权限变化后保持正确；计算与流水号无法由客户端伪造；关联读取不会泄露无权限记录。

**进入 P5 的条件：** 关联、计算、流水号均具备发布校验、运行时校验、提交校验和回归用例；长表单性能达到既定基线。

### P5：富交互、规则与执行收口

**目标：** 完成剩余交互字段以及协议中静态/动态行为的一致执行。

**本阶段工作：**

- 完成 `richtext` 的安全内容模型、编辑/展示隔离、XSS 防护和移动端呈现；
- 完成 `button` 的声明式 `actions` 执行模型、权限校验、幂等与可观测性；
- 将字段联动、动态可见/可用/必填、默认值、受控计算和异步校验定义为声明式规则，建立依赖图与循环检测；
- 为规则带来的字段状态变化补齐服务端最终校验，防止绕过浏览器；
- 完成草稿恢复、版本冲突提示、离线/弱网失败恢复和完整错误定位。

**验收：** 全部 27 种字段都能按协议设计、保存、发布、渲染和提交；规则不执行任意脚本；按钮操作、富文本与动态规则均通过安全审计。

**进入 P6 的条件：** 字段验收矩阵全绿；不存在仅“可保存不可运行”的已发布字段；所有动态行为均有后端复核。

### P6：发布准备、迁移收口与可观测性

**目标：** 将专项从功能完成提升到可运营、可升级、可回滚的产品能力。

**本阶段工作：**

- 完成生产数据迁移、回滚预案和旧预览链接兼容策略；
- 建立协议版本迁移机制，新增字段属性只能通过新版本与迁移器演进；
- 压测长表单、长子表单、附件、关联查询、弱网和中端移动设备；
- 接入匿名性能指标与失败码监控，严禁采集字段原始值、附件内容或组织数据；
- 完成无障碍审计、权限渗透测试、跨租户测试、发布演练与运维文档。

**验收：** 生产发布演练可通过；任意发布版本可复现其字段定义和提交校验；监控、审计、回滚和问题定位路径完整。

## 6. 阶段交接纪律

- 一个阶段未达到验收条件，不得将后续控件标记为“已支持”。
- P1 之后的每次协议修改必须同时改前端类型、前端校验、后端校验、发布校验、运行时、接口契约和测试；缺一项不得合并。
- 新控件先完成协议字典，再开发 UI；禁止由组件实现反推后端字段结构。
- 发布服务必须使用能力白名单：当前未落地的控件不能发布，避免用户提交时才发现不可用。
- 设计器草稿与已发布版本必须分表或分版本存储；禁止更新草稿时覆盖已填写记录关联的版本。

## 7. 建议的首个执行切片

下一个开发阶段应从 **P0** 开始，而不是直接改 `packages/form`。P0 完成后，以 **P1 + P2 的基础字段纵向切片** 作为首个可交付增量：

1. 确认完整字段字典和后端资产契约；
2. 用目标保存协议替换现有持久化模型；
3. 打通草稿、发布、运行时 bootstrap、提交；
4. 仅开放 9 个基础字段发布；
5. 其余字段在设计器中不可发布，待后续阶段完成后按白名单逐步开放。

这样既遵守“保存结构完全一致”的要求，也避免在后端、权限、附件和关联能力尚未准备好时发布不可执行的表单。
