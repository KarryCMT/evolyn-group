# 提交时校验与二次确认前后端设计方案

> 状态：待实施。本文以协议 v7 为目标，建立在 v6 的字段显隐、字段权限和不可见字段值决议能力之上。本文只描述普通表单的填写提交；流程表单的发起/审批校验仍由流程引擎的节点规则负责，不能复用本能力绕过节点权限。

## 1. 背景、目标与结论

表单已有字段级必填、类型、范围、选项和动态可见性校验，但缺少两种表单级提交体验：

1. 由多个字段共同决定的业务校验。例如“联系电话长度为 11”“结束日期不早于开始日期”“采购提前期不少于 3 天”。
2. 在真正创建记录前，请填写人复核关键数据并明确确认。

参考交互显示，表单属性中的“表单提交时”包含“二次确认”和可新增、排序的数据校验项；每项有条件公式、可插入字段的提示语、实时校验开关，以及“阻止提交 / 允许忽略并继续提交”两种失败动作。字段变量在公式中以 `$_widget_xxx#` 表示，在提示文案中以 `${_widget_xxx}` 表示。

本方案保留用户给出的 `content.validators` 和 `content.preSubmitConfirm` 外部结构，但不把公式当作可执行脚本：公式在草稿保存和发布时必须经受控解析器编译，提交时由服务端重新执行。二次确认是防误操作的客户端交互，不是安全授权或服务端审批机制。

## 2. 范围与非目标

### 2.1 本期范围

- 普通表单创建记录时的表单级校验、实时提示、阻断与可忽略告警。
- 基于字段实际值渲染的告警、二次确认标题和正文。
- 设计器配置、草稿保存、发布快照编译、桌面和移动填写运行时、服务端终审、错误码、审计与测试。
- 对已发布基础字段（`text`、`textarea`、`number`、`datetime`、单/多选、下拉、成员字段）逐步开放可引用能力。

### 2.2 非目标

- 不执行任意 JavaScript、SQL、正则源码、网络请求或跨表查询；这些能力不得通过公式字符串隐式引入。
- 不修改记录提交 API 的字段信封，也不把“已点击确认”作为可伪造的请求参数。
- 不支持子表单逐行/聚合校验、关联字段、文件字段、流程节点校验、批量导入和后台批量修改；后续能力必须另行扩展表达式类型系统和执行上下文。
- 不把二次确认应用于保存草稿、重置、按钮自定义动作或流程审批。普通表单编辑记录若后续开放，需以相同方案单独定义 `update` 语义。

## 3. v7 保存协议

### 3.1 `content` 新增字段

v7 的 `content` 合法键在 v6 基础上新增 `validators` 与 `preSubmitConfirm`，两键均为必填。空数组与关闭对象均须原样保存，不能以缺键表示关闭。

```json
{
  "content": {
    "type": "form",
    "layout": "normal",
    "items": [],
    "layout_fields": [],
    "field_layout": [],
    "fieldShowRules": [],
    "submitRule": 2,
    "widget_submit_rules": {},
    "validators": [
      {
        "formula": "LEN($_widget_phone#) == 11",
        "remind": "联系电话 ${_widget_phone} 必须为 11 位数字",
        "remark": "联系电话长度校验",
        "realtime": true,
        "failAction": 0
      }
    ],
    "preSubmitConfirm": {
      "enable": false,
      "title": "确认继续提交吗？${_widget_name}",
      "content": "请确认 ${_widget_name} 的填写内容。"
    }
  }
}
```

用户提供的 `CONCATENATE($_widget_...#)` 样例可作为公式编辑器中的字段引用样式示例，但其结果是文本，不能作为校验条件直接发布；校验器要求公式最终结果为布尔值，例如 `CONCATENATE(...) != \"\"`。

| 字段 | 类型及约束 | 语义 |
| --- | --- | --- |
| `validators` | 数组，0–50 项，顺序有意义 | 表单提交校验规则。执行、列表展示与实时提示均保持数组顺序。 |
| `validators[].formula` | 非空字符串，1–4,000 字符 | 返回 `boolean` 的受控公式源码。 |
| `validators[].remind` | 模板字符串，1–500 字符 | 条件不成立时的面向填写人的提示；支持字段占位符。 |
| `validators[].remark` | 字符串，0–200 字符 | 仅供设计者识别规则的备注；不下发填写端、不参与执行。 |
| `validators[].realtime` | boolean | `true` 时，在依赖字段有效修改后作客户端预校验。 |
| `validators[].failAction` | 整数枚举 `0` / `1` | `0`：阻止提交；`1`：允许填写人忽略告警后继续。 |
| `preSubmitConfirm` | 对象 | 表单提交前的确认设置；即使 `enable=false`，`title` 和 `content` 也必须是合法模板，避免日后打开时暴露坏配置。 |
| `preSubmitConfirm.enable` | boolean | 是否在所有阻断校验通过、可忽略告警获确认后显示二次确认框。 |
| `preSubmitConfirm.title` | 模板字符串，1–100 字符 | 二次确认对话框标题。 |
| `preSubmitConfirm.content` | 模板字符串，1–1,000 字符 | 二次确认对话框正文。 |

`failAction` 固定使用用户给出的数值协议，禁止接受字符串数字：`0` 为阻止提交，`1` 为允许忽略。若日后需要更多动作，应新增枚举值和协议版本，不得重解释既有 `0/1`。

### 3.2 字段引用与模板语法

`widget.widgetName` 是本系统的稳定字段键，因此不得把显示名、数据库 ID 或可变 label 写进公式。v7 采用以下两套有意区分的语法：

| 使用位置 | 形式 | 示例 | 含义 |
| --- | --- | --- | --- |
| `formula` | `$` + `widgetName` + `#` | `$_widget_phone#` | 有类型的字段值引用，参与表达式计算。 |
| `remind`、确认标题、确认正文 | `${` + `widgetName` + `}` | `${_widget_phone}` | 格式化后的展示值插值。 |

解析器不能把手工输入的字段显示名称替换成变量。设计器必须通过变量选择器插入原子 token；粘贴公式后，解析器只接受上述语法和当前发布快照中存在的顶层字段键。字段改名由既有设计器重命名事务同步更新三处引用；删除、改为未发布控件或改为不兼容类型时，阻断保存并报告精确 JSON Path。

模板不是公式：不支持函数、嵌套表达式或转义执行。引用字段未填写时格式化为空串；多选值按选项显示名用 `、` 连接，日期按控件格式显示，成员使用当前可见显示名。字段无查看权限时不得出现在可用变量列表中，运行时也不得从其原值插值。

### 3.3 旧版本迁移和新建默认值

- `FORM_PROTOCOL_VERSION` 升为 `7`；读取 v1–v6 文档时先执行既有迁移，再补 `validators: []` 和关闭的 `preSubmitConfirm`。
- 新建空表单固定写入：

```json
"validators": [],
"preSubmitConfirm": {
  "enable": false,
  "title": "确认继续提交吗？",
  "content": "请确认填写内容无误后继续提交。"
}
```

- v7 文档缺少任一新键、包含未知键、数组项不是对象或枚举/类型错误时，草稿保存返回 `FORM_SCHEMA_INVALID` 和 JSON Path；不做读取侧静默修正。
- 历史发布版本继续按其 `protocol_version` 解释。v1–v6 没有表单级校验与二次确认；发布新 v7 版本不重写历史记录或历史版本。

## 4. 受控公式引擎

### 4.1 编译与安全边界

公式引擎位于 `internal/platform/form` 的纯计算子包，并在 `packages/form/src/schema` 提供同一语法、fixture 和类型矩阵的 Web 实现。两端不得各自用 `eval`、动态函数或宽松字符串替换实现。建议的流水线为：

```text
公式源码 → 词法/语法解析 → 类型检查和字段依赖收集 → 不可变编译产物
                                                ↓
用户提交值 → v6 可见性与值决议 → 公式求值 → 校验结果 / 展示模板
```

草稿保存验证语法、字段存在性、控件可引用性和返回布尔类型；发布再次编译并将不可变编译产物与表单版本一起保存。建议新增迁移 `000065_form_submit_validators`，在 `tn_form_versions` 增加 `compiled_submit_rules JSONB NOT NULL DEFAULT '{}'::jsonb`。该列只保存 AST、依赖字段、静态类型与模板 token 索引，不保存填写人数据；草稿仍只保存人类可编辑的源码。版本加载/提交只读取对应版本的编译产物，绝不使用当前草稿重新解释历史提交。

v7 初始函数集仅开放确定性函数：`AND`、`OR`、`NOT`、`IF`、`ISBLANK`、`LEN`、`CONCATENATE`、`LOWER`、`UPPER`、`TRIM`、`ABS`、`ROUND`、`DATE`、`DATEDIF`，以及 `+ - * /` 与 `== != > >= < <=`。函数参数数量、输入类型、空值传播、日期时区和数值精度必须由共享 fixture 固化。除零、无效日期、溢出和类型不匹配是发布期错误；运行期不会因正常用户输入产生解释器崩溃。

首期只允许已发布且有确定性值编解码的顶层字段作为引用源。数组字段必须经明确的数组函数处理，不能依赖隐式字符串化；子表单、关联、附件、富文本和未开放字段在草稿、发布均拒绝引用。`formula` 的根节点必须为 `boolean`，不能以“非空即真”兼容文本或数字。

### 4.2 权限、显隐与依赖约束

公式求值使用服务端在 v6 值决议后得到的规范值和有效可见性（静态可见 ∧ 字段权限 ∧ 显隐规则），而不信任浏览器传来的展示结果。条件源有效不可见时其值为 `null`，模板也不读取它。

一个可新增权限组若允许成员新增记录，则该组的 `addFields` 中必须同时包含该表单每一条校验规则的全部依赖字段，且可见、可编辑。权限组保存/发布时须做这一静态检查；否则成员会遇到“无法查看也无法修改却被规则阻止”的死锁。对于没有任何权限组的基线表单，所有已发布字段视为可用。确认模板引用字段要求至少具备 `view` 权限；不满足的变量在配置器中报错而不是在运行时脱敏替换。

字段显隐规则可以使依赖字段在某次填写中不可见。公式作者必须显式使用 `ISBLANK`、`IF` 等处理空值；禁止由运行时偷偷使用隐藏字段的旧值。实时校验仅在本次表单会话中所有依赖字段有效可见时展示；提交终审仍按相同的 `null` 语义判断。

## 5. 设计器功能

### 5.1 表单属性入口

在“表单属性 → 表单提交时”新增：

- “二次确认”开关。关闭时折叠标题/正文编辑，开启后展开；标题和正文右侧均提供字段变量插入按钮。
- “校验数据”行与新增按钮。存在规则时显示数量与摘要；点击进入规则抽屉，支持新增、编辑、复制、删除及拖拽排序。

规则编辑对话框包含四个区块：

1. **校验条件**：公式编辑器、字段列表、函数列表、函数说明和语法/类型即时诊断。字段 token 渲染为不可破坏的标签，支持复制公式但不接受未知裸字段名。
2. **不满足条件时的提示文字**：必填模板输入，变量插入选择器与按当前预览值渲染的即时预览。
3. **字段修改时实时校验**：开关；说明“仅在依赖字段有效可见且其值变化后显示字段附近提示”。
4. **不满足校验条件后**：单选“阻止提交”与“允许忽略并继续提交”，分别写为 `0` 和 `1`。

规则列表按数组顺序展示：摘要（公式格式化文本）、失败动作、实时状态、备注和依赖字段数量。拖拽只改变 `validators` 顺序；保存前移除临时 UI ID，不能把 UI 状态污染协议。删除规则必须二次确认，关闭对话框时按草稿编辑器既有未保存变更策略处理。

### 5.2 设计时校验与发布阻断

前端和后端要以相同 JSON Path 返回以下问题：

- `content.validators[i].formula` 为空、语法不合法、引用不存在/不可发布字段、根类型非 `boolean`、函数或参数不在白名单。
- `content.validators[i].remind` 为空、模板 token 非法/不存在/无权限或长度超限。
- `content.validators[i].failAction`、`realtime`、`remark` 类型或枚举错误；规则数超过上限。
- `content.preSubmitConfirm.*` 的形状、长度、模板 token 错误。
- 任何可新增权限组没有覆盖规则依赖字段，或确认模板引用字段对该组不可查看。

草稿阶段可在编辑器内显示问题并拒绝保存；发布阶段必须再次执行结构、权限和编译检查。发布接口沿用 `FORM_SCHEMA_INVALID` 的 `data.issues` 结构，能力尚未开放的字段引用以 `FORM_PUBLISH_UNSUPPORTED_FIELD` 返回。公式运行时不存在“配置已经发布但填写时才报不支持”的降级路径。

## 6. 填写端交互与执行顺序

### 6.1 实时校验

运行时在字段修改后通过编译产物的反向依赖索引，仅重算依赖该字段且 `realtime=true` 的规则；使用 250 ms 防抖，同一批变更合并一次求值。失败提示显示在该规则依赖字段中第一个有效可见字段的下方，并通过 `aria-describedby` 关联；当该字段不可见时显示在表单级错误摘要。提示仅用于辅助，不弹确认框、不改变 `failAction`，也不把会话置为已提交。

字段再次变更、显隐状态变化、权限 bootstrap 更新或规则转为通过时，立即清除该规则产生的旧提示。运行时不得向服务端发出每次输入的校验请求；首期公式全部本地确定性执行，服务端只在真正提交时终审。

### 6.2 点击提交的状态机

提交按钮必须按以下顺序执行，避免二次确认在必填/业务错误之前出现：

```text
点击提交
  → 基础字段校验和 v6 有效可见性重算
  → 本地执行全部 validators
  → 有 failAction=0 失败？显示错误、定位首个依赖字段，结束
  → 有 failAction=1 失败？汇总告警，选择“返回修改”或“忽略并继续”
  → preSubmitConfirm.enable？显示动态标题/正文，选择“取消”或“确认提交”
  → 生成一次 dataOpId，发送 POST /form-records
  → 服务端终审并创建记录 / 返回错误
```

多个阻断失败一次性展示全部规则摘要，焦点定位至第一条规则的第一个可编辑依赖字段。多个可忽略失败合并为一个告警框，逐条展示已渲染 `remind`；选择“忽略并继续”只对本次点击有效，字段再次变化后必须重新确认。告警确认与二次确认不合并：前者确认“知晓校验未通过”，后者确认“本次提交内容无误”，文案职责清晰。

二次确认点击“取消”、关闭弹窗、网络失败、版本冲突或服务端拒绝时，保留所有已填值和会话中的实时错误；不会创建记录。双击保护沿用运行时 `activeOperation`，一旦发起 HTTP 请求立即禁用提交按钮；重试必须为同一网络重放复用 `dataOpId`，用户再次主动提交则创建新 ID。

### 6.3 服务端终审

`POST /api/v1/form-records` 的请求结构保持不变。`SubmitRecord` 在既有 `validateSubmitValues` 返回规范值后、写入 `tn_form_records` 前追加 `ValidateSubmitValidators(version, content, compiled, cleaned, member)`：

1. 从不可变版本加载 `content` 和 `compiled_submit_rules`，复核编译产物与源码摘要匹配；缺失/不匹配视为服务配置错误并拒绝写入。
2. 以服务端规范值、当前成员和有效可见性求值所有规则，不读取客户端已渲染的 `remind` 或“忽略”决定。
3. `failAction=0` 失败时返回 `FORM_RECORD_VALIDATION_FAILED`，`data.validatorErrors` 按规则数组下标升序返回 `{ index, remind, fields }`；不创建记录。
4. `failAction=1` 失败允许创建记录。服务端不能信任“用户已经看过告警”，因此该模式的业务含义必须仅是可接受的软告警，不能承担合规、额度、库存等硬约束。
5. 与记录创建、幂等检查在同一事务边界内执行。相同 `dataOpId` 的重放优先返回既有成功记录，不重新执行规则或产生重复审计。

前端收到 `FORM_RECORD_VALIDATION_FAILED` 时，清空旧服务器规则错误，按 `fields` 将提醒附着至可编辑字段并在表单摘要显示完整列表；此错误不同于已有 `FORM_RECORD_INVALID` 的字段类型/必填错误，二者可同时由同一次服务端终审聚合返回。推荐最终错误载荷：

```json
{
  "errCode": "FORM_RECORD_VALIDATION_FAILED",
  "data": {
    "validatorErrors": [
      {
        "index": 0,
        "remind": "联系电话 123 不是 11 位数字",
        "fields": ["_widget_phone"]
      }
    ]
  }
}
```

不要记录完整公式输入值、模板渲染后的敏感内容或二次确认正文到审计日志。提交审计仅追加 `validatorWarningIgnoredCount`（软告警被确认的数量）和发布版本号；阻断失败记录匿名化计数指标，不写业务字段原值。

| 层 | 改动 | 责任 |

| 协议类型 | `packages/form/src/schema/types.ts`、`dictionary.ts` | 升为 v7，声明规则、确认对象、上限、函数/字段类型矩阵。 |
| 协议校验与迁移 | `validate.ts`、`migrate.ts`、对应 fixture | 严格键白名单、JSON Path、v1–v6 → v7 补默认值、前后端对拍。 |
| 公式/模板纯逻辑 | 新增 schema 级 parser/compiler/evaluator/template 模块 | 无 UI、无 HTTP；浏览器与 Go 共享 golden fixtures，禁止执行字符串。 |
| 设计器 | `FormSchemaPropertyPanel` 与新的提交规则/确认配置组件 | 配置、排序、token 插入、发布错误定位和预览。 |
| Web/移动运行时 | `createFormRuntime`、桌面/移动 surface | 反向依赖实时校验、提交状态机、告警框与二次确认；移动端复用相同文本与按钮语义。 |
| 后端模型与迁移 | `internal/platform/form/model`、迁移 `000065` | 版本编译产物，不把 AST 写入记录值或草稿外部协议。 |
| 后端服务 | `service/schema.go`、`publish.go`、新 validator service | 草稿/发布编译、权限组依赖检查、`SubmitRecord` 的最终裁决。 |
| API/错误码 | controller、`httpx`、Web `errorCodes.ts` | 新增稳定码 `FORM_RECORD_VALIDATION_FAILED`；Swagger、前端错误处理同步。 |
| 文档与验收 | 字段字典、迁移清单、API 契约 | 将 v7 两个键和新错误码写入既有唯一事实文档。 |

表达式解析和执行必须独立于 Gin、GORM、HTTP、Vue 与 Element Plus；后端服务只注入字段值/成员上下文和已编译版本，便于单测、模糊测试和未来工作流复用。

## 8. 验收与测试矩阵

### 8.1 协议和编译

- v1–v6 读取后稳定补齐两个默认字段，再保存为 v7；v7 缺键与未知键均失败。
- 公式/模板字段引用、函数签名、空值、日期、数值精度、格式化输出在 TypeScript 与 Go fixture 中逐例相同。
- 文本返回值、未知变量、手写显示名、未开放字段、除零和无效函数均在草稿或发布期失败；`CONCATENATE` 只有与比较表达式组合后可作验证器。
- 规则顺序、复制、删除、拖拽与字段改名后源码/编译依赖/模板 token 一致；删除被引用字段被阻断。

### 8.2 交互

- `realtime=true` 的规则仅在依赖字段变更后更新，250 ms 合并防抖有效；`false` 的规则只在点击提交时展示。
- 阻断规则阻止二次确认和请求；软告警可返回修改或仅本次忽略；多规则顺序与提示正确。
- 二次确认关闭、取消、确认、模板字段为空、多选/日期格式化、键盘焦点和屏幕阅读器语义均正确；桌面和移动输出一致。
- 字段变化后，已忽略告警失效；网络重放不重复创建记录；服务端拒绝后输入保留并正确定位。

### 8.3 安全和服务端

- 篡改浏览器为“所有规则通过”、伪造 `visible`、跳过确认弹窗、改写模板文本均不能绕过 `failAction=0` 服务端终审。
- 软告警不能被用于硬性权限/合规约束；对这类规则设计器必须要求 `failAction=0`。
- 任一新增权限组缺少依赖字段可见可编辑权限时，组保存/发布失败；无查看权限字段无法作为确认模板变量。
- 跨租户、过期版本、字段类型/必填错误与业务校验失败沿用现有边界；服务端不会记录字段原值到审计或指标。

## 9. 实施顺序

1. 先冻结 v7 字典、公式语法/类型矩阵和 TS/Go golden fixtures；完成迁移与严格校验器。
2. 完成 Go 编译器、版本编译产物、发布门禁和 `SubmitRecord` 阻断终审，再接入错误码与 API 测试。
3. 完成设计器规则列表、公式/模板编辑器和预览。
4. 完成 Web 与移动运行时的实时校验、软告警和二次确认；以真实发布版本进行端到端回归。
5. 最后接入权限组依赖检查、审计/指标、性能和安全测试；通过后才将 v7 标记为可发布。

本顺序的关键约束是：任何阶段都不能让浏览器侧交互成为唯一校验。阻断规则必须先具备发布期编译与服务端终审，才能在设计器中开放配置。
