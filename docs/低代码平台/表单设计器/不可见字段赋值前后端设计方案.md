# 不可见字段赋值前后端设计方案

> 状态：已实施（P0 协议冻结 / P1 服务端安全内核 / P2 前端配置与运行时已落地；P3 派生计算执行器交付前 `recompute` 保持不可配置）。依赖《字段显隐规则设计方案》（v5）以表单保存协议 v6 实施。本文只定义字段在**本次提交**中因不可见而产生的值处理，不把它扩展为字段权限、字段显隐、公式语言或数据联动本身。

## 1. 背景、结论与边界

不可见字段可能来自静态 `widget.visible=false`、表单级字段显隐规则，或流程/表单权限组投影。它们虽然不应在填写界面呈现，却不能一概从记录中删除：评分、汇总等派生字段需要继续计算；多节点流程中，后续处理人看不到的前序信息需要保留；条件切换后不再适用的数据则需要清空。

参考的[不可见字段赋值说明](https://hc.jiandaoyun.com/doc/9041)定义了“始终重新计算、保持原值、空值”三种策略，并允许以字段级规则覆盖表单默认策略；其[特殊字段赋值规则示例](https://hc.jiandaoyun.com/doc/13003)也说明了“默认清空、对分值/总分单独重算”的组合需求。灵衍云采用相同的三种业务语义，但以发布快照、服务端终审和字段权限为边界，避免浏览器篡改隐藏数据或借由计算结果泄露无权字段。

### 1.1 结论

- 将配置置于 `content.submitRule` 与 `content.widget_submit_rules`，作为表单级唯一事实源；不向 `widget` 写入等价策略，避免字段复制、删除和规则覆盖时发生分叉。
- `submitRule` 是表单默认策略，`widget_submit_rules` 是以稳定 `widgetName` 为键的字段级例外映射；映射值优先于默认策略。未列入映射的**可处理字段**采用默认策略。
- 先由字段显隐规则得到动态可见性，再与静态可见、字段权限求交集，最后对不可见字段应用本策略。字段权限决定“用户是否可读写”，而不是“是否允许保留/计算”。
- 客户端只负责展示预期结果和构造提交信封；服务端以不可变发布快照、既有记录值及可信上下文最终计算、清空或保留值。任何客户端提交的隐藏字段 `data` 都不能成为 `preserve` 或 `recompute` 的数据来源。
- `recompute` 只允许已接入**服务端确定性计算执行器**的派生字段。当前 v4 的公开运行字段仅支持静态 `defaultValue`，尚无公式/联动执行器，因此首期配置器必须将 `recompute` 置为不可选，直至该执行器和相同的 Web 执行器一并交付；不能把“重新计算”降级为相信前端旧值。

### 1.2 范围

首期覆盖：标准表单的新建提交、记录编辑（编辑 API 开放时）、流程发起、流程人工任务提交和重提交；桌面与移动端共用相同提交语义。策略面向顶层有值字段，整个子表单在其运行时能力开放后可作为一个字段参与。

首期不覆盖：子表单逐行策略、布局字段、文件的物理删除、异步外部数据拉取、循环公式、跨表回写、历史记录迁移。历史记录始终按绑定的发布快照解释；发布新策略不重写旧 `tn_form_records.values`。

## 2. 现状分析与设计前提

当前代码库处于协议 v4：`FormContent` 只含 `type/layout/items/layout_fields/field_layout`，后端 `model.CurrentProtocolVersion` 也为 4。`tn_forms.draft_content` 和 `tn_form_versions.content` 已分别保存草稿与不可变快照，`tn_form_records.values` 是服务端清洗后的记录值，因此本能力不需要新增业务表或冗余策略列。

现有运行时提交字段信封为 `{ data?, visible }`。`createFormRuntime` 会跳过静态隐藏字段的数据；后端 `ValidateSubmittedRecordValues` 与权限管线目前要求信封 `visible` 严格等于发布快照的静态 `widget.visible`，且隐藏字段不得带 `data`。这足以抵御直接伪造，但无法表达：动态显隐后清空、从旧记录保留值，或服务端重新计算。因此必须替换为本方案的“可见性求值 → 策略解析 → 值决议 → 类型终审”管线，不能在 Controller 层补丁式处理。

《字段显隐规则设计方案》将字段显隐升级为 v5，并定义了 `content.fieldShowRules`、依赖图和服务端求值器。不可见字段赋值必须建立在该能力之上，因而本能力是 v6；如果 v5 尚未发布，v6 迁移须一次性补齐 `fieldShowRules: []`、`submitRule: 2` 与 `widget_submit_rules: {}`。v4 数据升级后保持原有行为：所有静态隐藏字段仍为空值。

## 3. 协议设计（v6）

### 3.1 根结构与示例

`content` 在 v6 的合法键为 `type`、`layout`、`items`、`layout_fields`、`field_layout`、`fieldShowRules`、`submitRule`、`widget_submit_rules`。未知键继续拒绝。字段名和枚举值沿用参考实现的实际载荷，避免设计器展示、存储协议与运行逻辑出现翻译层。

```json
{
  "content": {
    "type": "form",
    "layout": "normal",
    "items": [],
    "layout_fields": [],
    "field_layout": [],
    "fieldShowRules": [],
    "submitRule": 2,
    "widget_submit_rules": {
      "_widget_product_code": 1,
      "_widget_product_image": 1,
      "_widget_service_score": 3,
      "_widget_total_score": 3
    }
  }
}
```

| 路径 | 类型 / 约束 | 语义 |
| --- | --- | --- |
| `submitRule` | 必填整数枚举 `1` / `2` / `3` | 所有未设特殊规则的不可见字段的默认策略。`1`=保持原值，`2`=空值，`3`=始终重新计算；新建表单固定默认 `2`。 |
| `widget_submit_rules` | 必填对象，键数 0–500 | 特殊字段赋值规则；键是顶层 `widgetName`，值是 `1` / `2` / `3`，优先于 `submitRule`。空对象必须保留。 |

映射使一个字段天然只能拥有一个特殊策略，避免分组数组重复引用的冲突。`widget_submit_rules[field]` 与 `submitRule` 相同属于冗余配置，校验器拒绝保存，设计器切换默认策略时自动删除相同项。接口读取时不做“静默修正”，保持未知键与非法枚举严格失败的既有协议原则。

### 3.2 可配置性与校验

保存草稿和发布均执行结构校验，发布额外验证运行能力：

- 引用必须是顶层、具有值语义的 `widgetName`；禁止 `separator`、`richtext`、`button`、`sn`、`linkquery` 等当前没有普通用户提交值的字段，禁止子表单列和布局节点。
- `widget_submit_rules` 的每个键必须是顶层、具有值语义的 `widgetName`；同一个 JSON 对象键重复由 JSON 解析器拒绝。值只允许 `1` / `2` / `3`，不得接受字符串数字或未知枚举。
- 值为 `3` 的字段必须在字段字典登记 `derived=true`、存在执行器、其依赖图无环，且所有依赖均可在本次执行上下文取得；否则在草稿保存即以 `content.widget_submit_rules.<widgetName>` 报错，发布再次兜底。
- 当 `submitRule=3` 时，每一个未被 `widget_submit_rules` 覆盖为 `1` 或 `2` 的可处理字段都必须是可重算字段；否则拒绝保存。这样不会让普通手填字段因“默认重算”悄然丢值。
- `preserve` 对新建记录无旧值，只会得到该字段的类型空值；设计器显示“仅编辑/流程后续提交时保留”的提示。若业务要在新建时写入默认值，应使用默认值或派生计算，而不是 `preserve`。
- 静态 `visible=false` 且 `allowBlank=false` 的字段继续按字段字典拒绝；赋值策略不能绕过必填约束。可见字段的必填校验在策略之后执行。
- 字段删除、变更为不支持类型、改为子表单列或删除派生配置时，设计器提示依赖并阻止保存；服务端仍以 `FORM_SCHEMA_INVALID` 兜底。

### 3.3 策略解析

对可处理字段 `F`：若 `widget_submit_rules[F]` 存在，取其整数值；否则取 `submitRule`。普通可见字段不执行策略。由策略配置处理的“不可见”指的是字段内容对本次操作者不可见，不包括布局节点。

```text
strategy(F) = widget_submit_rules[F] ?? submitRule
```

策略没有优先级叠加，也不受 `fieldShowRules` 的数组顺序影响。特殊字段覆盖永远优先于默认策略，与参考交互一致。

## 4. 统一语义与值决议

### 4.1 三种策略

| 策略 | 新建提交 | 编辑 / 流程后续提交 | 可信数据来源 |
| --- | --- | --- | --- |
| `clear` | 写类型空值 | 覆盖为类型空值 | 字段字典的 `emptyWidgetValue` 镜像 |
| `preserve` | 写类型空值 | 保留受理前记录的该字段值 | 事务内锁定的 `tn_form_records.values` / 流程表单快照 |
| `recompute` | 计算后写入 | 计算后覆盖旧值 | 发布快照、已获准的输入值、系统/流程上下文和计算执行器 |

空值必须按字段值协议归一化，而非删除 map 键：单值字段为 `null`，多选/成员多选/已开放子表单为 `[]`，没有值语义的字段不进入 `values`。保留空键可使记录详情、导出与后续版本校验区分“该字段在快照中存在但本次为空”和“未知字段”。

`preserve` 的基线是本次操作开始前的持久化值，不是客户端 `initialValues`、本地缓存或用户提交的隐藏 `data`。流程场景以工作流同事务传入的表单记录快照为基线；如果该事务没有可锁定的基线，服务端拒绝请求而非猜测保留值。

`recompute` 是服务器写入权限，不是绕过权限让用户填写。执行器只能读取以下值：本次对操作者可读且参与本次提交的字段、同一记录的受限内部值（仅当该派生字段已声明该依赖）、以及经白名单注入的当前成员、提交时间、流程实例等上下文。不得把“用户无权查看的字段”直接暴露到 Web 计算器、错误消息、日志或派生字段详情中。

### 4.2 有效可见性

字段 `F` 的有效可见性为：

```text
effectiveVisible(F) = schemaVisible(F)
                  ∧ permissionVisible(F, operation)
                  ∧ showRuleVisible(F, submittedValues, trustedContext)
```

其中 `permissionVisible` 来自 `addFields/editFields/viewFields` 投影；`showRuleVisible` 来自 v5 的规则编译结果。字段权限是硬上限：即使显隐规则满足也不能显示。反之，即使用户无权限查看字段，其不可见策略仍由服务器执行；这保证流程后续节点不会因字段裁剪而意外清掉前序值。

当显隐规则的条件源无权限或自身不可见，规则求值沿用 v5 的安全语义：该条件不满足，不能读取其值推导下游展示。策略决议则在服务端的受控内部值视图上进行，不向客户端返回决议过程。

### 4.3 服务端事务内顺序

```text
锁定记录基线（编辑/流程）
  → 解析发布快照与字段权限
  → 校验提交键、可见字段信封与操作权限
  → 合并“允许用户写入”的原始值
  → 编译/求值显隐规则，得到 effectiveVisible
  → 对不可见字段按 clear / preserve / recompute 决议
  → 按依赖拓扑执行派生计算
  → 对最终值执行类型、必填、范围、选项与权限终审
  → 在同一事务写记录/流程表单值和审计事件
```

提交信封的 `visible` 必须等于服务端算出的 `effectiveVisible`。有效不可见字段：

- `clear` / `preserve`：客户端必须省略 `data`；带 `data` 返回 `FORM_RECORD_INVALID`。
- `recompute`：客户端同样必须省略 `data`；服务器返回的字段错误也不得包含计算后的敏感值。
- 可见但不可编辑字段：沿用现有权限管线，只允许服务端从基线合并，客户端带 `data` 返回字段级错误。

这样既保留现有 `{data?, visible}` API 形状，也把 `visible` 的含义从“静态快照布尔值”升级为“服务端可复算的本次有效可见性”。API 契约、Swagger 注释、Web 类型与测试必须同步调整。

## 5. 前端设计

### 5.1 表单设计器

在右侧“表单属性”中，紧邻“字段显隐规则”增加“不可见字段赋值”区块：

- 首行采用“选择框 + 齿轮按钮”的紧凑布局。选择框绑定 `submitRule`，按固定顺序提供“保持原值（1）/ 空值（2）/ 始终重新计算（3）”；新建表单默认选中“空值”。选择后立即更新下方说明：保持原值提示仅编辑/后续流程节点有效，空值提示会清除原有值，始终重新计算提示与可见字段执行同一计算链路。
- 齿轮是独立、带名称“配置特殊字段赋值规则”的按钮；点击打开配置对话框，不改变默认策略。无权限编辑表单时，选择框与齿轮均禁用，但仍展示当前规则和说明。
- 当 `widget_submit_rules` 为空，选择框下仅展示默认策略说明；存在至少一个特殊规则时，在其下展示浅色摘要卡。卡片标题为“已设置特殊字段赋值规则”，右侧提供“查看详情 / 收起详情”按钮和方向箭头，初始收起，避免表单属性面板被长字段列表占满。
- 展开摘要卡后，按“保持原值 / 空值 / 始终重新计算”固定顺序展示非空分组。每组第一行显示策略名称，下一行只显示字段**标签**（例如“单行文本、数字”），不暴露 `widgetName`；字段按 `field_layout` 排序，超出两行时以“等 N 个字段”收起并支持展开全部。截图所示的“保持原值—单行文本、多行文本、数字、复选框组”“空值—日期时间、单选按钮组……”即为该摘要形态。
- 齿轮按钮打开“特殊字段赋值规则”对话框，按三段显示“保持原值 / 空值 / 始终重新计算”，每段可搜索并多选字段，以标签展示已选项和移除按钮。对话框的分组只是编辑视图，保存时归一化为 `widget_submit_rules: Record<widgetName, 1 | 2 | 3>`。
- 同一字段一旦被分配，另外两段置灰并展示当前所在策略；将字段选入另一段表示移动，不允许重复。值与 `submitRule` 相同的特殊规则不展示为可保存项：选择默认策略后自动移除对应冗余映射，并在对话框底部提示“与默认规则相同的字段无需单独配置”。
- `preserve` 段提示“新建时无原值，将按空值写入”；`recompute` 段仅列出当前已登记的可重算字段，未接入执行器时整段禁用并说明原因。
- 对话框点击“确定”只更新设计器内存态并立即刷新摘要卡、画布徽标和预览；点击“取消”、关闭按钮或 Esc 均丢弃本次弹窗内修改。最终由表单工作区既有“保存”动作携带完整 Schema 与 `draftRevision` 持久化，不在切换下拉框或关闭对话框时单独请求接口。
- 选择框、齿轮、详情开关和字段移除均可键盘操作，`aria-expanded` 反映摘要开合；字段搜索空结果和不可选重算字段需提供文本原因，不能只用颜色表达状态。普通填写预览不暴露策略细节。

字段显隐规则和赋值规则应在同一个属性页分别配置：前者回答“何时看得见”，后者回答“看不见时怎样写值”。两者不可互相隐式修改，避免设计者误认为删规则会清除数据。

### 5.2 运行时

`@evolyn.do/form` 增加无 UI 副作用的 `schema/invisible-value-policy` 模块，负责协议解析、字段可处理性和客户端预演；不可在组件内分散写策略判断。`createFormRuntime` 在 v5 可见性重算后同步字段状态：

- 字段变为不可见时清除错误、移走焦点，并保留会话内 `values` 作为再次显示时的体验缓存；不在前端直接把它清成正式记录值。
- `buildSubmitPayload()` 为所有非布局字段写入服务端预演的 `visible`；不可见字段一律不带 `data`。前端可为 `clear` 将本地显示缓存重置为类型空值，但这不是权威写入。
- 编辑和流程任务 bootstrap 必须分别携带记录基线、操作类型和字段权限；浏览器从不读取无 `view` 权限的原始值。`preserve` 仅显示为“将保留原值”的状态，不向用户回传实际内容。
- 桌面、移动、预览和流程任务都复用同一规则模块；设计预览允许管理员开启“策略调试”，只显示字段键、可见性和策略名，不显示无权依赖值。

## 6. 后端设计

### 6.1 模块与职责

在 `apps/evolyn-core/internal/platform/form/service/` 内新建纯领域服务（不得依赖 Gin/GORM）：

- `invisible_value_policy.go`：解析/校验 v6 配置、策略解析、可处理字段白名单和类型空值。
- `visibility.go`：复用/承接 v5 显隐规则编译器，输出字段有效可见性；接受最小权限矩阵与受控值视图。
- `value_resolution.go`：按事务上下文合并可写输入、基线值、策略和派生执行结果；只输出最终 `map[string]any`。
- `derived_executor.go`：派生字段执行端口。公式、联动、查询等实现通过此窄端口注册；未注册字段不可配置 `recompute`。

`schema.go` 继续作为协议严格校验入口，增加 v6 根键和策略校验。`value.go` 只保留控件值归一化与最终值校验；删除其“静态 visible 等值”假设。`permission_pipeline.go` 改为先输出可写字段和基线合并结果，再交给值决议器，不能在权限层直接清空不可见字段。

### 6.2 API 与持久化

草稿保存、发布和读取接口不新增字段：完整 `content` 自动携带 `submitRule` 与 `widget_submit_rules`，版本号从 6 起随既有 `protocolVersion` 传递。新表单的 `emptyFormDocument` 必须包含：

```json
{
  "fieldShowRules": [],
  "submitRule": 2,
  "widget_submit_rules": {}
}
```

`POST /form-records` 维持 `values[widgetName] = {data?, visible}`。服务端以 v6 快照重算 `visible`，写入的 `tn_form_records.values` 是策略决议后的完整字段值，而不是客户端原载荷。编辑记录接口应在请求中带记录 ID 与并发口令，在同一数据库事务中 `FOR UPDATE` 读取旧值；流程任务提交通过既有 WorkflowRecordStore 在同一工作流事务传入原记录基线。两种路径均调用同一个 `ResolveSubmittedValues`，不得各自实现策略。

无需数据库迁移：策略随 JSONB 草稿与发布快照保存，记录表结构也已可存终审后的 JSONB。需要更新 Go 默认值注释与后端模型 `CurrentProtocolVersion` 为 6；数据库列的 `default:4` 只影响 ORM 声明、仍应同步为 6，存量行由读取迁移升级而非 SQL 回填。

### 6.3 安全、审计与错误

- 将 `publishedVersion + schemaRevision + recordRevision` 作为编辑提交的并发事实；策略必须按目标版本执行，绝不能用当前草稿解释历史提交。
- 对无字段读取权限的数据，拒绝将其复制到响应、计算错误、审计 `summary` 或 tracing 属性。审计只记录 `invisible_policy_applied`、策略枚举、字段数与版本，不记录字段值。
- `recompute` 的执行记录写入已有审计/产品日志事件，含字段键和执行器版本；计算失败事务回滚，向字段返回不含输入值的 `FORM_RECORD_INVALID` 错误。
- Schema 配置错误继续使用 `FORM_SCHEMA_INVALID`，不支持的重算字段发布使用 `FORM_PUBLISH_UNSUPPORTED_FIELD`，提交信封、权限或值决议不一致使用 `FORM_RECORD_INVALID`（`fieldErrors[widgetName]`）。不新增模糊的通用错误码。

## 7. 关键场景

### 7.1 条件切换清空旧值

“任务状态=未开始”时显示“预计处理时间”；改为“进行中”后该字段隐藏，默认策略为 `clear`。后端先用新任务状态求得字段隐藏，再将其值写为 `null`，统计不会残留旧预计时间。用户伪造该字段 `data` 会被拒绝。

### 7.2 流程节点保留前序字段

发起人填写“产品编号、图片、定价”，审批人无字段可见权限。三字段覆写为 `preserve`。审批人提交时，服务端从锁定的原记录值合并三字段，审批人的请求没有也不能包含这些 `data`；无论审批人的浏览器如何构造载荷，都不能清除或改写前序内容。

### 7.3 隐藏评分实时重算

“服务评价 / 产品评价”由显隐规则切换题目；两个分值和总分对填写人不可见，默认策略为 `clear`，三个派生字段覆写为 `recompute`。服务器在可见题目值通过校验后，按派生依赖拓扑计算分值与总分，再写入记录。题目切换时不相关分值可由公式归零，避免保留上一轮评分。

## 8. 迁移、分期与验收

### 8.1 版本迁移

| 来源 | 读取迁移结果 |
| --- | --- |
| v4 | 补 `fieldShowRules: []`、`submitRule: 2` 和 `widget_submit_rules: {}`，升级为 v6。 |
| v5 | 保留显隐规则，补 `submitRule: 2` 与空规则对象，升级为 v6。 |
| v6 | 严格校验并原样使用。 |

迁移器只在读取/编辑草稿时生成当前版本文档；下一次乐观锁保存才落库为 v6。发布快照不可改写，旧版本仍按旧协议和旧静态可见语义提交；不要批量更新 JSONB 或历史记录。

### 8.2 实施阶段

1. **P0：协议冻结**。评审 v5/v6 组合、更新字段字典、前后端类型、迁移器和 JSON fixture；先不暴露 UI。
2. **P1：服务端安全内核**。完成策略校验、空值、可见性与值决议器，重构提交终审，覆盖新建/编辑/流程端口的单元与集成测试。
3. **P2：前端配置与运行时**。交付表单属性入口、特殊规则对话框、桌面/移动运行时的可见性信封和预演。
4. **P3：派生计算**。先交付确定性公式/联动执行器及前后端共用 fixture，再解除 `recompute` 的配置限制；任何外部/异步计算另行评审。
5. **P4：全链路回归**。接入流程任务、历史详情、导出/打印裁剪、审计和性能基准后再开放发布白名单。

### 8.3 验收矩阵

- 三种默认策略与字段覆盖组合均验证新建、编辑、流程任务；覆盖策略优先于默认策略。
- `clear` 的单值、多值、成员多选、未来子表单空值形态前后端完全一致。
- `preserve` 不信任客户端隐藏 `data`，编辑时只保留数据库锁定基线，新建时为空。
- `recompute` 必须完全由服务端执行；未注册、依赖缺失、循环依赖和执行异常均无法发布或提交。
- 静态隐藏、条件隐藏、字段权限隐藏及三者交集均按有效可见性决议；无权限用户不能从网络载荷、错误或调试信息获得字段值。
- 发布快照变更后，旧记录详情和历史版本提交仍按旧快照语义；v4/v5 草稿升级到 v6 不丢字段与布局。
- 伪造 `visible`、携带隐藏 `data`、省略可见必填字段、并发编辑基线过期均得到稳定错误码和字段定位。
- 500 顶层字段、200 条显隐规则、全量策略覆盖下，单字段变更只遍历受影响的显隐/派生依赖，不全表扫描；提交终审的耗时与可观察指标达成基线后方可开放。
