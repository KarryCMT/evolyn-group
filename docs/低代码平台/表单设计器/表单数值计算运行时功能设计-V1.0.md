# 表单数值计算运行时功能设计-V1.0

> 项目：Evolyn Group（灵衍云企业级低代码平台）
> 仓库：`https://github.com/KarryCMT/evolyn-group`
> 基线分支：`1.0.0`
> 文档目标：基于当前 Evolyn 前后端架构，为低代码平台设计统一、可扩展、可审计的高精度数值计算运行时 NumericRuntime，覆盖普通数值、金额、税额、百分比、公式、聚合查询、表单字段、API 传输及 PostgreSQL 持久化。

---

## 1. 背景与问题

JavaScript `number` 基于 IEEE-754 双精度浮点数，无法稳定表示大量十进制值。例如：

```ts
0.1 + 0.2 !== 0.3;
```

对于普通 UI 展示问题通常不大，但 Evolyn 是企业级低代码平台，后续需要承载：

- 数值字段
- 金额字段
- 税率与税额
- 单价 × 数量
- 含税价 / 未税价
- 折扣
- 百分比
- 表单公式
- 子表汇总
- `SUM / AVG / MIN / MAX`
- 仪表盘聚合
- Query Engine 数值过滤
- PostgreSQL `NUMERIC`
- ERP、采购、销售、财务类业务数据

这些场景不能允许前端、Go、PostgreSQL 三端使用不同的数值语义。

因此，Evolyn 需要一套平台级数值规范，而不是在业务页面中零散调用 `decimal.js`。

## 3. 当前各 Engine 与 NumericRuntime 的关系

### 3.1 Formula Engine

当前：

```text
@evolyn.do/formula
```

职责明确为：

```text
公式 DSL
函数目录
AST
Parser
静态诊断
```

当前并不真正执行公式。

现有 Formula 函数已经包含大量数值类能力：

```text
ABS
AVERAGE
CEILING
COUNT
FLOOR
INT
LARGE
LOG
MAX
MIN
MOD
POWER
PRODUCT
ROUND
SMALL
SQRT
SUM
SUMIF
SUMIFS
SUMPRODUCT
```

以及：

```text
VALUE
RMBCAP
DATEDIF
DAYS
TIME
TIMESTAMP
DISTANCE
```

这些函数中的“数值运算部分”不应该各自使用 JS `number` 实现。

正确关系应为：

```text
Formula Engine
      │
      ▼
Formula Runtime
      │
      ▼
NumericRuntime
```

Formula Engine 本身继续只负责 DSL 定义、解析和诊断。

---

### 3.2 Data Engine

当前 Data Engine 定义：

```ts
export type DataRecord = Record<string, unknown>;
```

以及：

```text
DataQuery
DataPage
DataSource
DataMutation
```

说明 Data Engine 当前是数据访问协议层，而不是字段具体类型层。

NumericRuntime 不应被 Data Engine 反向依赖来改变 `DataRecord` 的通用设计。

但是当 Data Engine 执行：

```text
本地汇总
计算字段
导入预处理
数据转换
```

可以调用 NumericRuntime。

---

### 3.3 Field Engine

Field Engine 当前只定义：

```text
FieldDefinition
FieldRegistry
```

并通过：

```ts
valueKind;
```

表达字段的值类别。

因此未来字段层可以增加：

```text
number
decimal
money
percent
taxRate
taxAmount
```

但：

> Field Engine 只描述字段能力，不实现运算。

运算仍归 NumericRuntime。

---

### 3.4 Schema Engine

当前 Schema Engine 定义：

```ts
type JsonValue =
  | string
  | number
  | boolean
  | null
  | JsonValue[]
  | { [key: string]: JsonValue };
```

这一点非常重要。

NumericRuntime 的 Runtime Value 不应该直接进入 Schema。

例如：

```ts
new Decimal('12.30');
```

不是平台 Schema 中稳定的 JSON 基础值。

因此需要明确：

```text
Schema / Form Data：
Decimal 类型使用 string 持久化

Runtime：
使用 NumericValue / Decimal
```

---

### 3.5 Query Engine

当前 Query Engine 明确要求 DSL：

```text
可序列化
不绑定 Vue
不绑定 HTTP
不绑定 SQL
```

当前：

```ts
type QueryScalar = string | number | boolean | null;
```

数值条件未来必须支持 decimal-string。

例如：

```json
{
  "field": "amount",
  "operator": "gte",
  "value": "1000.01"
}
```

而不是强制：

```json
"value": 1000.01
```

Query Engine 不负责真正的小数比较，服务端 Query Compiler 根据字段 metadata 把字符串参数绑定到 PostgreSQL NUMERIC。

---

### 3.6 Physical Engine

当前 Physical Engine 只描述：

```text
持久化意图
```

DDL 编译、锁、执行由 Go 后端负责。

因此 Numeric 字段 Physical Model 应描述：

```text
precision
scale
```

例如：

```ts
{
  type: 'decimal',
  precision: 20,
  scale: 6
}
```

服务端 Physical Engine 编译：

```sql
NUMERIC(20, 6)
```

## 4. NumericRuntime 的正确定位

NumericRuntime 不应该是：

```text
金额工具类
税额工具类
公式工具函数集合
decimal.js 的薄封装
```

它应该是：

> Evolyn 平台统一的十进制数值语义与运算运行时。

它负责：

```text
输入解析
十进制表示
高精度运算
比较
聚合
舍入
精度控制
异常
类型转换
序列化
```

它不负责：

```text
税务业务规则
货币币种规则
字段 UI
PostgreSQL SQL 编译
公式 AST 解析
业务权限
表单联动
```

# 7. 核心数据模型

## 7.1 NumericInput

```ts
export type NumericInput = string | number | Numeric | null | undefined;
```

注意：

`number` 仅用于兼容。

平台规范应优先：

```ts
'123.45';
```

而不是：

```ts
123.45;
```

原因是 `number` 在进入 NumericRuntime 前就可能已经发生精度损失。

---

## 7.2 Numeric Value

不建议向上层直接暴露 Decimal。

推荐：

```ts
export interface NumericValue {
  readonly kind: 'numeric';
}
```

真实 Decimal 由内部保存。

示例：

```ts
export class Numeric {
  readonly kind = 'numeric' as const;

  #value: Decimal;

  constructor(value: Decimal) {
    this.#value = value;
  }

  add(value: NumericInput): Numeric;
  subtract(value: NumericInput): Numeric;
  multiply(value: NumericInput): Numeric;
  divide(value: NumericInput): Numeric;

  compare(value: NumericInput): number;

  round(scale: number, mode?: RoundingMode): Numeric;

  serialize(): string;
  toFixed(scale: number): string;
}
```

# 8. NumericRuntime API

推荐公共 API：

```ts
export interface NumericRuntime {
  of(value: NumericInput): Numeric;

  parse(value: NumericInput): Numeric;

  add(a: NumericInput, b: NumericInput): Numeric;
  subtract(a: NumericInput, b: NumericInput): Numeric;
  multiply(a: NumericInput, b: NumericInput): Numeric;
  divide(a: NumericInput, b: NumericInput): Numeric;
  mod(a: NumericInput, b: NumericInput): Numeric;
  pow(a: NumericInput, b: NumericInput): Numeric;

  abs(value: NumericInput): Numeric;
  negate(value: NumericInput): Numeric;
  sqrt(value: NumericInput): Numeric;

  round(value: NumericInput, scale?: number, mode?: RoundingMode): Numeric;

  ceil(value: NumericInput, scale?: number): Numeric;

  floor(value: NumericInput, scale?: number): Numeric;

  compare(a: NumericInput, b: NumericInput): number;

  eq(a: NumericInput, b: NumericInput): boolean;
  gt(a: NumericInput, b: NumericInput): boolean;
  gte(a: NumericInput, b: NumericInput): boolean;
  lt(a: NumericInput, b: NumericInput): boolean;
```

# 9. 推荐链式 API

例如：

```ts
const taxAmount = numeric.of('1000.00').multiply('0.13').round(2).toFixed(2);
```

返回：

```text
130.00
```

复杂公式：

```ts
const total = numeric.of(unitPrice).multiply(quantity).multiply('1');
```

运行时始终保持 Decimal。

最后才：

```ts
total.serialize();
```

# 10. 精度策略

必须区分三个概念：

```text
运算精度 Precision
业务 Scale
展示 Scale
```

例如：

```text
100 / 3
```

运行阶段可能为：

```text
33.333333333333333333...
```

金额最终落库：

```text
33.33
```

不能在每一步计算都：

```text
toFixed(2)
```

否则会放大误差。

# 11. RoundingMode

定义平台自己的舍入枚举：

```ts
export enum RoundingMode {
  UP = 'UP',
  DOWN = 'DOWN',
  CEIL = 'CEIL',
  FLOOR = 'FLOOR',
  HALF_UP = 'HALF_UP',
  HALF_DOWN = 'HALF_DOWN',
  HALF_EVEN = 'HALF_EVEN',
}
```

Numeric Adapter 内部再映射：

```text
HALF_UP → Decimal.ROUND_HALF_UP
HALF_EVEN → Decimal.ROUND_HALF_EVEN
...
```

不允许业务层引用：

```ts
Decimal.ROUND_HALF_UP;
```

# 12. Empty Value 设计

低代码表单一定会出现：

```text
''
null
undefined
```

不能把处理逻辑散落在业务代码。

建议：

```ts
export enum EmptyValuePolicy {
  ZERO = 'ZERO',
  NULL = 'NULL',
  ERROR = 'ERROR',
}
```

解释：

### ZERO

```text
null → 0
"" → 0
```

适合部分公式兼容模式。

### NULL

```text
null → null
"" → null
```

推荐平台默认。

### ERROR

严格计算场景直接报错。

# 13. NumericError

统一错误：

```ts
export type NumericErrorCode =
  | 'INVALID_NUMBER'
  | 'DIVISION_BY_ZERO'
  | 'NON_FINITE_NUMBER'
  | 'PRECISION_EXCEEDED'
  | 'SCALE_EXCEEDED'
  | 'INVALID_ARGUMENT';
```

示例：

```ts
throw new NumericError('DIVISION_BY_ZERO', 'division by zero');
```

Formula Runtime 可以映射：

```text
DIVISION_BY_ZERO → #DIV/0!
INVALID_NUMBER → #VALUE!
```

业务页面则可以映射成：

```text
数值格式不正确
```

# 14. 禁止 NaN / Infinity

NumericRuntime 中必须禁止：

```text
NaN
Infinity
-Infinity
```

这些值：

- 不能作为数据库有效业务数值
- 不应该出现在表单 Schema
- 不应该进入 API
- 不应该参与税额计算


```text

```

```text

```

---

# 19. Formula 数值执行示例

公式：

```text
$quantity# * $unitPrice# * $taxRate#
```

Parser 生成：

```text
Binary(*)
├── Binary(*)
│   ├── Field(quantity)
│   └── Field(unitPrice)
└── Field(taxRate)
```

Evaluator：

```ts
case '*':
  return numeric.multiply(
    evaluate(node.left),
    evaluate(node.right),
  )
```

绝对禁止：

```ts
Number(left) * Number(right);
```

---

# 20. Formula 数字 Literal

当前 Formula Lexer 能识别：

```text
123
123.45
.5
```

Parser 不应该在词法阶段直接：

```ts
Number(token.value);
```

建议 AST Literal 保存原始字符串：

```ts
{
  kind: 'literal',
  valueType: 'number',
  raw: '123.4500'
}
```

后续 Runtime：

```ts
numeric.of(node.raw);
```

这一项建议未来对现有 Formula AST 做兼容升级。

```text

```

```text

   ↓
NumericRuntime
```


---

## 23.1 未税金额计算税额

输入：

```json
{
  "amountWithoutTax": "1000.00",
  "taxRate": "0.13"
}
```

计算：

```text
税额 = 未税金额 × 税率
```

输出：

```json
{
  "amountWithoutTax": "1000.00",
  "taxAmount": "130.00",
  "amountWithTax": "1130.00"
}
```

---

## 23.2 含税价反算

输入：

```json
{
  "amountWithTax": "1130.00",
  "taxRate": "0.13"
}
```

计算：

```text
未税金额 = 含税金额 / (1 + 税率)

税额 = 含税金额 - 未税金额
```

---

## 23.3 行级税额与汇总税额

必须明确：

```text
逐行算税再汇总
```

和：

```text
汇总未税金额再算税
```

可能产生几分钱差异。

因此 TaxRuntime 未来需要：

```ts
type TaxAggregationMode = 'LINE' | 'TOTAL';
```

这属于 TaxRuntime，不属于 NumericRuntime。

```text
               │
               ▼
           权威结果
```


# 55. 性能

Decimal 运算一定比原生 number 慢。

但是：

> 不能为了性能把关键业务金额换回 float。

性能优化策略应该是：

```text
只对 Decimal 字段使用 NumericRuntime
整数 UI 参数继续 number
避免无意义反复 parse
一次计算链保持 Numeric
批量聚合避免重复创建对象
```

而不是降低精度。


```text

Decimal String

Numeric Runtime Value

        ↓

展示
```

```text

    ↓

    ↓

```

## 文档结论

NumericRuntime 对 Evolyn 来说不是一个“小工具库”，而应该被定义为与 Schema、Field、Formula、Query、Data 同级的低代码基础引擎。

它最终承担的是：

> Evolyn 全平台唯一可信的十进制数值语义。

这会成为后续金额、税额、公式字段、子表汇总、仪表盘聚合、ERP 业务、Query Engine 与 PostgreSQL NUMERIC 能够长期保持一致的基础。
