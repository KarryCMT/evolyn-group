# 管理后台-消息推送开发设计方案

## 1. 背景与目标

管理后台的「消息推送」是**租户级**的外部 Webhook 配置能力：租户管理员维护一套服务地址与共享 Secret，后续由平台将该租户内发生的业务消息异步推送给其指定服务。

一期目标是支撑管理后台的启停、配置编辑、Secret 生成、服务端连通性测试与保存闭环；不在一期实现业务事件分发、投递重试和发送记录页面。

## 2. 范围与边界

### 2.1 一期范围

- 每个租户维护一份消息推送配置。
- 管理员可启用或停用能力；停用不清除既有地址和 Secret。
- 管理员可设置服务地址、生成或替换 Secret，并验证服务端连通性。
- 已保存的 Secret 仅以密文落库，读取接口不返回明文。
- 写操作使用乐观锁，配置修改在提交后写入业务审计。

### 2.2 非本期范围

- 成员个人通知偏好、站内信、短信、邮件等通知渠道。
- 按应用、部门、成员配置不同 Webhook。
- 真实业务消息的异步投递、失败重试、死信处理与发送记录查询。
- 自定义事件订阅、消息模板与签名算法多版本协商。

### 2.3 领域边界

消息推送不是产品中心、账号安全或租户基础信息的附属字段。后端新建 `internal/platform/messagepush/` 域，域内保持 controller → service → repository → model 分层；由 `internal/platform/server/server.go` 装配。

接口位于租户域路由，必须经过 Authentication → Tenant → TenantStatus → Authorization 链路。租户 ID 仅从请求上下文取得，禁止信任客户端传入的租户 ID。

## 3. 前端状态与后端语义

| 前端状态 | 后端语义 | 说明 |
| --- | --- | --- |
| 顶部开关关闭 | `enabled=false` | 不投递消息，但保留服务地址和 Secret，便于后续恢复。 |
| 顶部开关开启、未完成配置 | `enabled=true`、`ready=false` | 允许管理员先开启再进入配置；投递服务不得发送消息。 |
| 地址与 Secret 已保存 | `enabled=true`、`ready=true` | 后续投递域可使用此配置。 |
| 配置弹窗中的输入 | 前端草稿 | 未保存内容不得影响正在运行的投递配置。 |
| 服务端连接测试结果 | 瞬时响应，可选更新最近测试摘要 | 测试当前草稿，不要求先保存。 |

`ready` 是服务端派生字段：`enabled=true`、服务地址有效且 Secret 已配置时才为 `true`，不得由前端直接提交。

> 已保存 Secret 不允许按参考界面以明文回显。读取后前端显示“已配置”或末四位掩码；只有新生成或新输入的 Secret 在当前编辑会话中短暂可见。

## 4. 数据模型

新增迁移 `000036_tenant_message_push.up.sql` 与对应 down 迁移，并同步 `scripts/db.sql` 快照。生产 Schema 只以迁移为准，开发/测试的 AutoMigrate 仅用于辅助。

### 4.1 `tenant_message_push_configs`

| 字段 | 类型 | 约束/说明 |
| --- | --- | --- |
| `id` | `BIGSERIAL` | 主键。 |
| `tenant_id` | `BIGINT` | 所属租户；非空。 |
| `enabled` | `BOOLEAN` | 租户是否启用消息推送，默认 `false`。 |
| `service_url` | `varchar(2048)` | 推送服务地址；未配置时允许为空。 |
| `secret_ciphertext` | `TEXT` | Secret 的 AES-256-GCM 密文；绝不保存明文。 |
| `secret_key_version` | `INTEGER` | 加密主密钥版本；与密文成对存在。 |
| `revision` | `BIGINT` | 乐观锁版本，默认 `1`。 |
| `last_test_status` | `varchar(16)` | 可选：`never`、`success`、`failed`。 |
| `last_test_http_status` | `INTEGER` | 最近一次测试的 HTTP 状态码，可空。 |
| `last_tested_at` | `timestamp with time zone` | 最近一次测试完成时间，可空。 |
| `created_at`、`updated_at`、`deleted_at` | `timestamp with time zone` | 与 `TenantBaseModel` 一致。 |

约束与索引：

- `tenant_id` 上建立有效记录部分唯一索引：`WHERE deleted_at IS NULL`，保证每个租户只有一份有效配置。
- `revision > 0`；`last_test_status` 通过 CHECK 限定为 `never/success/failed`。
- `secret_ciphertext` 与 `secret_key_version` 必须同时为空或同时非空。
- 每个新增表、字段、约束和索引均按仓库约定写入中文 SQL 注释。

一期不单独建立测试记录表：测试弹窗只消费本次响应，主表仅保留最近测试摘要。后续投递中心落地时，再新增独立的 `message_push_deliveries` 与 `message_push_attempts`，避免将运行日志混入配置表。

## 5. Secret 加密与密钥轮换

不得复用账号 MFA 的 TOTP 包作为配置凭据实现。应在 `internal/infrastructure/secretbox/` 提供通用但受限的凭据加密能力：AES-256-GCM、密钥版本、加解密失败显式报错。

- 消息推送使用独立主密钥集合，由未提交的部署配置或密钥管理系统注入。
- 新写入使用 `currentKeyVersion`；解密按行内 `secret_key_version` 选择历史密钥。
- 使用与租户绑定的 AAD，例如 `tenant-message-push:{tenantId}`，阻止密文被跨租户替换后解密。
- 生产环境缺失当前主密钥必须 fail-fast；不得生成临时密钥后继续运行。
- 密钥轮换时先增加新版本、切换 current 版本、后台重加密历史数据，确认完成后才移除旧版本。

Secret 生成使用 `crypto/rand` 生成至少 32 字节随机值，再编码为 URL-safe 字符串。生成接口的响应只返回给当前会话；HTTP 日志、应用日志、审计日志、错误信息都不得包含该值。

## 6. API 契约

所有接口统一使用 `{ code, msg, data }` 响应包络，并使用 `httpx.BizError` 定义稳定错误码。

| 方法与路径 | 权限 | 用途 |
| --- | --- | --- |
| `GET /api/v1/message-push/config` | `message-push:view` | 读取当前租户配置与脱敏状态。 |
| `PUT /api/v1/message-push/config` | `message-push:update` | 保存地址和可选 Secret，需携带 revision。 |
| `PUT /api/v1/message-push/config/enabled` | `message-push:update` | 顶部开关即时启停，需携带 revision。 |
| `POST /api/v1/message-push/secrets:generate` | `message-push:update` | 生成一次性 Secret，不持久化。 |
| `POST /api/v1/message-push/connection-tests` | `message-push:update` | 测试当前草稿服务地址与 Secret，不保存配置。 |

### 6.1 读取响应

```json
{
  "enabled": true,
  "serviceUrl": "https://notify.example.com/webhook",
  "secretConfigured": true,
  "secretHint": "••••A9f2",
  "ready": true,
  "revision": 7,
  "lastTest": {
    "status": "failed",
    "httpStatus": 404,
    "testedAt": "2026-08-27 16:56:44",
    "errorCode": "MESSAGE_PUSH_REMOTE_NOT_FOUND"
  }
}
```

### 6.2 保存请求

```json
{
  "serviceUrl": "https://notify.example.com/webhook",
  "secret": "仅在新建或替换时提交",
  "revision": 7
}
```

`secret` 缺省时表示保留既有 Secret；空字符串不得解释为清空。若未来需要清空凭据，应增加具有明确语义与二次确认的独立操作。并发提交旧 revision 时返回 `MESSAGE_PUSH_CONFIG_CONFLICT`（HTTP 409），前端重新拉取最新配置。

### 6.3 连通性测试

测试请求接收当前草稿的 `serviceUrl` 和可选 `secret`。未提交新 Secret 时，服务端只在内存中解密已保存凭据使用；不得将明文写回响应。

服务端向目标地址发送无业务数据的测试事件：

```http
POST {serviceUrl}
Content-Type: application/json
X-Lingyanyun-Event: message.push.connection_test
X-Lingyanyun-Timestamp: 2026-08-27T16:56:44+08:00
X-Lingyanyun-Signature: sha256=...
```

签名采用 `HMAC-SHA-256(secret, timestamp + "." + requestBody)`。测试响应向前端返回成功/失败、HTTP 状态码、时间与**已清洗**错误详情；原始响应体和下游敏感响应头不得出网。

建议错误码包括：

- `MESSAGE_PUSH_CONFIG_CONFLICT`：配置已被其他管理员更新。
- `MESSAGE_PUSH_CONFIG_INCOMPLETE`：尝试投入使用但地址或 Secret 未配置。
- `MESSAGE_PUSH_SERVICE_URL_INVALID`：地址格式或协议不合法。
- `MESSAGE_PUSH_CONNECTION_FAILED`：目标不可达、超时或 TLS 失败。
- `MESSAGE_PUSH_REMOTE_NOT_FOUND`：远端返回 404 等明确状态。
- `MESSAGE_PUSH_SECRET_UNAVAILABLE`：密钥版本缺失或密文无法解密。

## 7. 写入、事务与审计

- 启停与保存必须通过 `TxManager.WithinTransaction` 执行；仓储通过 `infrastructure.ResolveDB` 取得连接。
- 更新时先按当前租户加载并锁定配置，校验 revision，再以 `WHERE id = ? AND revision = ?` 原子更新并 `revision = revision + 1`；零行影响必须返回冲突，不能静默成功。
- 当前租户不存在配置行时，由服务层在同一事务内创建默认行；创建竞态以唯一索引兜底后重新读取。
- 审计在事务提交后 best-effort 记录：启用、停用、服务地址变更、Secret 轮换与测试结果摘要。审计内容仅记录状态和地址主机名，不能记录完整 Secret、签名或下游响应体。

迁移还需幂等补授基线租户管理员角色：`message-push:view` 与 `message-push:update`。权限资源不应授予应用管理员，也不通过管理组范围回退放行。

## 8. SSRF 与外部调用防护

服务地址由租户管理员填写，但仍属于不可信输入。测试和未来投递均必须经统一的出站 HTTP Client，并执行以下控制：

- 生产环境只允许 `https`；开发环境放宽 HTTP 必须显式配置。
- 解析前校验 URL，禁止用户信息段、非预期端口与空主机名。
- DNS 解析后拒绝 loopback、私网、链路本地、组播、保留地址和云元数据地址；连接建立时再次校验解析结果，降低 DNS rebinding 风险。
- 默认不跟随重定向；如后续确有需求，只允许有限次数并对每一跳重复校验。
- 限制连接、响应头和总请求超时，限制响应体读取大小；测试只需读取有限正文或状态码。
- 禁止把目标 URL、响应正文、请求签名或 Secret 原样写入普通日志。
- Kubernetes 网络策略应进一步限制 API/Worker 对非必要网段的出站访问。

## 9. 后续投递演进

真实业务消息不得在业务 HTTP 请求内同步调用外部服务。后续新增投递中心后，流程为：

```text
业务事务提交
  → 写入 message_push_outbox
  → Worker 读取租户 ready 配置
  → 解密 Secret、构造并签名消息
  → 调用统一出站 HTTP Client
  → 指数退避重试 / 记录投递结果 / 最终失败进入死信
```

`message_push_outbox` 与投递尝试记录必须保存配置 revision、事件 ID、幂等键、脱敏目标地址、尝试次数和状态，不保存 Secret 明文。接收端以事件 ID 或幂等键去重，确保至少一次投递语义可控。

## 10. 实施顺序与验收

1. 新建领域模型、Repository/Service/Controller 接口与迁移 000036，完成租户管理员权限补授。
2. 落地独立 `secretbox`、部署密钥配置校验与密钥轮换测试。
3. 实现配置读取、启停、保存、Secret 生成与 revision 冲突处理。
4. 实现 SSRF 受控的连通性测试与脱敏结果映射。
5. 接入前端消息推送页：顶部开关、全屏配置层、测试结果弹窗、未保存变更提示和深色模式。
6. 补齐 Service 单测与真实 PostgreSQL 集成测试：租户隔离、并发 revision、密文不出网、Secret 轮换、SSRF 拦截、审计脱敏。

验收时至少确认：任意租户无法读取或修改其他租户配置；读取与审计均无 Secret 明文；重复并发保存有且仅有一个成功；停用后不会投递；草稿测试不会覆盖已保存配置；私网和本机地址不能作为生产测试目标。
